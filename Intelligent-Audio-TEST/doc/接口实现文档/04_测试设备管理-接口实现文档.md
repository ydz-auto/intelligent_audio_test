# 测试设备管理接口实现文档

## 1. 模块概述

测试设备管理模块负责管理执行测试任务的终端设备（如手机、智能音箱、车载终端等）。它记录了设备的硬件信息、系统版本及应用版本，用于在测试报告中提供环境追溯。

## 4. 接口详细实现思路

### 4.1 获取测试设备列表 (GET /api/v1/test-devices)

**实现思路：**
1. **参数解析**：提取 `page`, `per_page`, `keyword`, `status`, `type`。
2. **构建查询**：针对 `devices` 表执行查询，过滤 `deleted=False` 的记录。
3. **过滤条件**：
   - `keyword`：在 `name`, `model`, `location` 字段进行模糊匹配 (OR条件)。
   - `status`：精确匹配设备状态 (online, offline, maintenance, testing)。
   - `type`：精确匹配设备类型。
4. **分页处理**：使用 SQLAlchemy 的 `paginate` 方法执行分页。
5. **响应格式化**：将模型对象序列化为字典，字段名转换为 camelCase。
6. **性能优化**：建议对 `status` 和 `type` 字段建立索引以加速过滤。

**代码流程：**
```
get_all() 
  → 解析请求参数
  → 构建基础查询 (deleted=False)
  → 应用过滤条件
  → 执行分页查询
  → 遍历结果，序列化每个设备
  → 转换字段名为 camelCase
  → 返回分页响应
```

### 4.2 获取批量设备状态 (GET /api/v1/test-devices/status)

**实现思路：**
1. **参数解析**：解析 `ids` 查询参数列表。
2. **构建查询**：
   - 如果传了 `ids`，则查询指定 ID 的设备。
   - 如果没传 `ids`，则返回所有在线设备。
3. **轻量响应**：只返回 `id`, `name`, `status`, `lastOnlineAt` 字段。
4. **用途**：用于 HTTP 轮询降级，当 WebSocket 不可用时的备用方案。

**代码流程：**
```
get_statuses()
  → 解析 ids 参数
  → 根据是否传参构建不同查询
  → 只返回必要字段
  → 返回状态列表
```

### 4.3 获取测试设备详情 (GET /api/v1/test-devices/:id)

**实现思路：**
1. **参数解析**：从 URL 路径获取 `device_id`。
2. **资源查找**：在 `devices` 表中根据 `id` 查询 `deleted=False` 的记录。
3. **错误处理**：若不存在，返回 404 错误。
4. **响应格式化**：序列化完整的设备信息，字段名转换为 camelCase。

**代码流程：**
```
get_one(device_id)
  → 根据 ID 查询设备
  → 设备不存在则返回 404
  → 序列化设备信息
  → 返回完整响应
```

### 4.4 新增测试设备 (POST /api/v1/test-devices)

**实现思路：**
1. **数据校验**：必填字段为 `name`, `model`, `type`, `system`, `systemVersion`, `appName`, `appVersion`。
2. **重复性检查**：检查 `name` 是否已存在（同一未删除设备）。
3. **数据入库**：创建新的 `Device` 记录，设置 `deleted=False`。
4. **状态初始化**：默认设为 `offline`。
5. **错误处理**：任何异常都回滚事务并返回错误信息。

**代码流程：**
```
create()
  → 解析 JSON 请求体
  → 校验必填字段
  → 检查名称重复性
  → 创建 Device 对象
  → 保存到数据库
  → 返回新设备 ID
```

### 4.5 更新测试设备 (PUT /api/v1/test-devices/:id)

**实现思路：**
1. **资源查找**：确认设备存在且未删除。
2. **重复性检查**：如果修改了 `name`，检查是否与其他设备重名。
3. **字段更新**：使用字段映射表更新对应属性。
4. **时间戳**：自动更新 `updated_at` 字段。
5. **错误处理**：任何异常都回滚事务。

**代码流程：**
```
update(device_id)
  → 根据 ID 查询设备
  → 设备不存在则返回 404
  → 检查名称冲突（如有修改）
  → 根据字段映射表更新属性
  → 更新 updated_at
  → 提交事务
```

### 4.6 删除测试设备 (DELETE /api/v1/test-devices/:id)

**实现思路：**
1. **资源查找**：确认设备存在且未删除。
2. **引用检查**：查询 `task_device_relations` 表（或 TaskDevice 模型），检查是否有关联任务。
3. **清理标签**：删除 `device_tags` 中该设备的关联记录。
4. **逻辑删除**：设置 `deleted=True`，而非物理删除。
5. **错误处理**：有关联任务时返回 400 错误。

**代码流程：**
```
delete(device_id)
  → 根据 ID 查询设备
  → 设备不存在则返回 404
  → 检查关联任务
  → 删除标签关联
  → 设置 deleted=True
  → 提交事务
```

### 4.7 扫描物理设备 (POST /api/v1/test-devices/scan)

**实现思路：**
1. **驱动工厂**：使用 `device_driver_factory` 获取各平台驱动。
2. **多平台扫描**：依次扫描 Android、iOS、HarmonyOS 设备。
3. **驱动调用**：
   - Android 驱动：使用 ADB 命令获取设备列表。
   - iOS 驱动：使用 libimobiledevice 或其他工具。
   - HarmonyOS 驱动：使用 hdc 命令或 ADB。
4. **Mock 数据**：开发模式下若无扫描结果，返回模拟数据方便前端调试。
5. **注册状态**：检查扫描到的设备是否已注册在数据库中。
6. **字段标准化**：统一各平台返回的字段名以兼容前端。

**代码流程：**
```
scan()
  → 获取各平台驱动
  → 扫描 Android 设备
  → 扫描 iOS 设备
  → 扫描 HarmonyOS 设备
  → 开发模式添加 Mock 数据
  → 检查注册状态
  → 标准化字段名
  → 返回扫描结果
```

### 4.8 测试设备 (POST /api/v1/test-devices/:id/test)

**实现思路：**
1. **资源查找**：确认设备存在且未删除。
2. **获取驱动**：根据设备系统类型获取对应的设备驱动。
3. **发送指令**：调用驱动的 `wake_up` 方法或直接发送唤醒指令。
   - Android：发送 `input keyevent KEYCODE_WAKEUP`。
   - iOS：发送 `wake screen`。
4. **日志记录**：通过 `LogController` 记录操作日志。
5. **状态更新**：将设备状态设为 `testing`。
6. **响应**：返回执行的唤醒指令供前端显示。

**代码流程：**
```
test(device_id)
  → 根据 ID 查询设备
  → 设备不存在则返回 404
  → 获取对应系统的驱动
  → 调用驱动唤醒设备
  → 记录操作日志
  → 更新设备状态为 testing
  → 返回唤醒指令
```

### 4.9 停止测试 (POST /api/v1/test-devices/:id/stop-test)

**实现思路：**
1. **资源查找**：确认设备存在且未删除。
2. **状态恢复**：将设备状态从 `testing` 恢复为 `online`。
3. **持久化**：提交数据库事务。

**代码流程：**
```
stop_test(device_id)
  → 根据 ID 查询设备
  → 设备不存在则返回 404
  → 设置状态为 online
  → 提交事务
```

### 4.10 批量健康检查 (POST /api/v1/test-devices/health-check)

**实现思路：**
1. **参数解析**：解析 `device_ids` 数组，不传则检查所有设备。
2. **异步执行**：启动后台线程执行检查，不阻塞主请求。
3. **检查逻辑**：
   - Android：执行 `adb -s <serial> get-state`。
   - 网络设备：执行 ping 或 TCP 连接测试。
4. **状态更新**：根据检查结果更新 `status` 和 `last_online_at`。
5. **实时推送**：通过 WebSocket 广播每个设备的检查结果。
6. **响应**：立即返回"任务已启动"，实际检查在后台异步进行。

**代码流程：**
```
health_check()
  → 解析请求参数
  → 查询目标设备列表
  → 启动后台线程
    → 遍历设备
    → 执行连接测试
    → 更新数据库状态
    → 通过 SocketIO 推送状态
  → 返回启动消息
```

### 4.11 获取驱动关键字 (GET /api/v1/test-devices/driver-keywords)

**实现思路：**
1. **驱动工厂查询**：从设备驱动工厂获取所有支持的驱动关键字。
2. **关键字过滤**：根据设备类型过滤相关关键字。
3. **响应返回**：返回关键字列表供前端显示。

**代码流程：**
```
get_driver_keywords()
  → 获取驱动工厂实例
  → 获取所有驱动关键字
  → 按设备类型过滤
  → 返回关键字列表
```

### 4.12 获取可用序列号 (GET /api/v1/test-devices/serials)

**实现思路：**
1. **扫描设备**：调用设备扫描获取当前连接的设备序列号。
2. **序列号过滤**：过滤掉已注册的设备序列号。
3. **响应返回**：返回可用序列号列表供前端选择。

**代码流程：**
```
get_available_serials()
  → 扫描可用设备
  → 获取所有设备序列号
  → 过滤已注册的序列号
  → 返回可用序列号列表
```

## 5. 设备状态流转

```
offline → online: 健康检查通过或设备连接
online → testing: 开始测试设备
testing → online: 测试完成
online → offline: 健康检查失败或设备断开
```

## 6. 错误码说明

| 错误码 | 错误信息 | 描述 |
|--------|----------|------|
| 404 | 未找到设备 | 设备不存在或已删除 |
| 400 | 设备名称 xxx 已存在 | 新增/更新时名称重复 |
| 400 | 该设备已关联测试任务，无法删除 | 删除时存在关联任务 |
| 500 | xxx | 服务器内部错误 |

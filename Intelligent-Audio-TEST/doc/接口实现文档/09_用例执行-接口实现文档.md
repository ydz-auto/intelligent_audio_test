# 09_用例执行-接口实现文档

## 1. 模块概述
用例执行模块是系统的核心引擎，负责协调测试用例、测试设备（或 API 端点）以及评估逻辑。它支持端到端（E2E）测试的串行执行与 API 测试的并行执行，提供实时的进度反馈与运行控制。该模块支持 API 多链接（endpoints）配置，可根据优先级和健康度智能选择最佳端点，并动态调整健康度评分。

### 1.1 核心流程与数据链路
系统遵循标准的 MVC + Service 架构，数据链路如下：
`Electron UI` -> `Flask Blueprint` -> `ExecutionEngine` -> `AudioEngine/EvaluationService` -> `PostgreSql/SocketIO`

**端到端执行序列 (Sequence):**
1. **指令下发**：用户点击“开始测试”，Renderer 通过 IPC 调用 Preload，Preload 发起 POST 请求至 Flask `/api/v1/tasks/{id}/start`。
2. **环境预检**：`ExecutionEngine` 验证任务合法性，初始化 `stop_event` 和 `pause_event`。
3. **主循环启动**：引擎开启后台线程 `_run_task`，开始遍历 `pending` 状态的用例。
4. **音频播放**：调用 `AudioEngine.play_audio`，传入计算好的 `gain`。
5. **结果采集**：模拟或真实调用移动端代理，获取识别结果。
6. **自动化评估**：`EvaluationService` 聚合维度 API 请求，计算得分。
7. **数据持久化**：结果写入 `test_results` 和 `test_result_dimensions` 表。
8. **实时推送**：通过 `socketio.emit` 向命名空间 `/ws/tasks` 推送 `task_progress`。

## 2. MVC 分层职责

### 2.1 视图层 (View - Electron Renderer)
- **组件**：`E2ETest.vue`, `APITest.vue`, `TestExecutionComponent.vue`。
- **职责**：
  - 展示任务基础信息（名称、创建者、预计耗时）。
  - 实时渲染总进度条、分类统计（已完成、进行中、待执行）。
  - 展示实时运行日志。
  - 捕获用户操作（暂停、停止、跳过、新增用例）。

### 2.2 控制层 (Controller - Electron Preload / Flask Blueprint)
- **Preload (IPC Bridge)**：
  - 暴露 `taskControl.start(taskId)`, `taskControl.pause(taskId)` 等方法。
  - 封装 WebSocket 监听，将 `task_status_update` 事件分发给 Vue 状态。
- **Flask Controller (Task API)**：
  - 接收前端指令，验证任务状态，下发任务到异步引擎。
  - 提供日志查询与结果拉取接口。

### 2.3 服务层 (Service - Execution Engine)
- **调度器 (Scheduler - ExecutionEngine)**：
  - **单例模式**：系统全局唯一的 `ExecutionEngine` 实例，负责任务队列管理。
  - **状态管理**：维护 `tasks_status` 字典，记录所有运行中任务的 `stop_event`、`pause_event` 和进度。
  - **线程安全**：使用 `threading.Lock` 保护全局状态，确保并发控制指令的原子性。
  - **API 端点管理**：
    - 在任务启动时获取所有在线的 API 端点（`APIEndpoint`）
    - 按优先级排序并缓存可用端点列表
    - 根据端点的 `max_process` 动态调整线程池大小
- **执行器 (Worker)**：
  - **API Worker**：并行模式。
    - **并行执行策略**：
      - 引入 **API 级执行队列**：为每个 API 实例维护一个 `queue.Queue`，取代旧有的 `Condition` 变量，彻底解决高并发下的串行化瓶颈。
      - **精确状态流转**：
        - `pending` -> `queued`：用例已提交到线程池，正在排队申请 API 执行权。
        - `queued` -> `running`：成功获取 API 执行权，开始网络请求。
      - **动态负载平衡**：最大线程数由所选端点的 `max_process` 动态决定。
    - **端点智能选择**：
      - 按优先级（`priority`）降序排序。
      - 同优先级下按健康度（`health_score`）降序排序。
    - **健康度动态更新**：
      - 调用成功：健康度 +5（最高100）。
      - 调用失败：健康度 -10（最低0）。
    - 自动聚合相同 URL 的请求，支持维度结果缓存。
  - **E2E Worker**：串行/同步模式。
    - **放音控制**：通过 `AudioEngine` 控制 `playback_devices`。
    - **录音与采集**：调用移动端代理接口获取 `asr_result` 和 `translation_result`。
- **音频引擎 (AudioEngine)**：
  - **驱动实现**：基于 `PyAudio` 封装，支持多声卡、多通道输出。
  - **播放器管理**：支持 `Dry` (单次播放) 和 `Noise` (循环背景音) 两类播放器实例。
  - **实时混音**：支持在同一输出设备上叠加多路音频信号。
- **评估引擎 (Evaluator)**：
  - **维度映射**：从 `test_case_dimensions` 加载关联指标。
  - **API 聚合优化**：自动合并具有相同 `api_url` 的评估请求，减少冗余网络开销。
  - **分值计算**：支持基于正则表达式或 JSONPath 提取 API 响应值，并根据预设规则（阈值、区间）进行打分。

### 2.4 模型层 (Model - SQLAlchemy)
- **核心实体**：`TestTask`, `TestResult`, `TestResultDimension`, `SPLMapping`, `CalibrationHistory`。
- **关联关系**：`TestTask` -> 1:N -> `TestResult` -> 1:N -> `TestResultDimension`。

### 2.5 播放设备控制实现 (Playback Control)
- **驱动抽象层**：
  - `AudioService` (单例) 统一管理 `PyAudio` 资源。
  - 根据硬件唯一标识 (`hw_id`) 自动映射系统设备索引。
- **声压级 (SPL) 转换逻辑**：
  - **距离优先**：每个 `SPLMapping` 记录对应特定距离（如 1m, 0.5m）下的 `Target SPL` 与 `Digital Gain`。
  - **线性外推**：
    - 若存在多个校准点（`CalibrationHistory`），优先使用线性插值计算目标增益。
    - 若仅有单点参考，基于 `6dB/距离翻倍` 规律或直接比例进行参考计算。
- **多通道并发同步**：
  - **Noise 播放器**：在任务开始时独立启动，与测试步进解耦。
  - **Dry 播放器**：受执行引擎主循环控制，确保“放音-录音-评估”链路同步。
- **异常保护机制**：
  - **预检**：启动前检查音频文件是否存在、采样率是否与硬件匹配。
  - **运行时**：若发生缓冲区溢出或设备掉线，Worker 捕获异常并记录 `ErrorCode.HARDWARE_ERROR`，同时释放所有已锁定设备。

## 3. 接口规范 (OpenAPI 3.0)

### 3.1 启动任务 (POST /api/v1/tasks/{id}/start)
**功能描述**：触发异步执行引擎。
**请求参数**：
- `id` (Path): 任务唯一标识。
**业务逻辑**：
1. **环境预检**：
   - E2E：检查关联设备是否 `online` 且未被锁定。
   - API：检查被测 API 的所有在线端点：
     - 获取所有 `status='online'` 的 `APIEndpoint`
     - 按优先级排序并缓存可用端点列表
     - 根据端点的 `max_process` 动态调整线程池大小
2. **状态锁定**：更新 `test_tasks.status = 'running'`。
3. **异步触发**：通过任务队列（如 Celery 或内部线程池）启动 Worker。

### 3.2 任务控制 (POST /api/v1/tasks/{id}/control)
**功能描述**：运行时人工干预。
**请求体 (JSON)**：
```json
{
  "action": "pause | resume | stop | skip | retry",
  "case_id": "string (optional)"
}
```
**实现机制**：
- **Pause/Resume**：使用线程事件信号（Event）阻塞/唤醒 Worker 循环。
- **Stop**：设置终止标志位，Worker 完成当前原子操作后清理资源并退出。
- **Skip**：标记当前正在执行的 `case_id` 为 `skipped`，强制跳过当前步骤进入下一用例。

### 3.3 动态用例调整 (PATCH /api/v1/tasks/{id}/cases)
**功能描述**：在任务执行过程中动态增删待执行用例。
**请求体 (JSON)**：
```json
{
  "action": "add | remove",
  "case_ids": ["string"] 
}
```
**业务逻辑**：
1. **中途新增 (add)**：
   - 允许向 `task_case_relations` 添加新的待执行用例，初始状态为 `pending`。
   - 异步引擎检测到表变更后，动态更新内存中的执行队列。
2. **中途移除 (remove)**：
   - 仅允许移除状态为 `pending` 的用例。
   - 引擎从执行队列中剔除对应 ID。
3. **进度重计**：调整后，后端需重新计算 `total_count` 并通过 WebSocket 推送最新的 `ITaskProgress`。

### 3.4 实时进度推送 (SocketIO)
**命名空间**：`/ws/tasks`
**事件名**：`task_progress`
**Payload (Shared Type: `ITaskProgress`)**：
```typescript
interface ITaskProgress {
  taskId: string;
  totalProgress: number; // 0-100
  status: 'running' | 'paused' | 'completed' | 'failed';
  completedCount: number;
  totalCount: number;
  currentCase?: {
    caseId: string;
    name: string;
    step: string; // e.g., "playing", "recording", "evaluating"
    startTime: number; // Unix ms
  };
  logs: Array<{
    level: 'info' | 'warn' | 'error';
    message: string;
    timestamp: number;
  }>;
}
```

### 3.4 任务创建负载 (POST /api/v1/tasks)
**功能描述**：从前端测试页面（E2E/API）发起任务申请。

### 3.5 执行引擎 API

#### 3.5.1 启动执行 (POST /api/v1/execution/:task_id/start)
**功能描述**：通过执行引擎启动任务执行。
**业务逻辑**：
1. **任务存在性检查**：使用 SQLAlchemy 的 `query.get()` 方法根据 ID 查找任务，若不存在返回 404 错误。
2. **待运行用例检查**：查询 `task_cases` 表中状态为 `pending` 的用例，若没有待运行用例则返回错误。
3. **异步执行**：获取 Flask 应用实例，调用 `execution_engine.start_task()` 方法启动异步执行。
4. **结果返回**：根据执行引擎的返回结果，返回成功或错误消息。

#### 3.5.2 控制执行 (POST /api/v1/execution/:task_id/control)
**功能描述**：控制执行引擎的运行状态。
**请求参数**：
- `action`：控制动作，包括 `pause`, `resume`, `stop`
**实现机制**：
1. **参数验证**：检查请求中是否包含 `action` 参数，若缺少则返回错误。
2. **异步控制**：获取 Flask 应用实例，调用 `execution_engine.control_task()` 方法控制执行引擎。
3. **结果返回**：根据执行引擎的返回结果，返回成功或错误消息。
4. **支持的动作**：
   - `pause`：暂停执行引擎
   - `resume`：恢复执行引擎
   - `stop`：停止执行引擎并清理资源

#### 3.5.3 调整执行用例 (PATCH /api/v1/execution/:task_id/cases)
**功能描述**：调整执行引擎中的用例列表。
**请求参数**：
- `action`：操作类型，包括 `add` 或 `remove`
- `caseIds/case_ids`：用例 ID 数组（支持驼峰式和下划线式参数格式）
**业务逻辑**：
1. **参数验证**：检查请求中是否包含 `action` 和 `caseIds/case_ids` 参数，若缺少则返回错误。
2. **根据动作执行不同逻辑**：
   - `add`：遍历 `caseIds` 列表，为每个用例创建 `TaskCase` 记录（状态为 `pending`），若已存在则跳过。
   - `remove`：遍历 `caseIds` 列表，删除状态为 `pending` 的 `TaskCase` 记录。
3. **事务处理**：使用 `db.session.add()` 添加记录，`db.session.commit()` 提交事务，发生错误时通过 `db.session.rollback()` 回滚。
4. **结果返回**：返回成功或错误消息。

### 3.6 全局错误码 (ErrorCode)
| 错误码 | 枚举值 | 描述 |
|--------|--------|------|
| 0 | `SUCCESS` | 操作成功 |
| 101 | `PARAM_ERROR` | 请求参数缺失或格式错误 |
| 201 | `DEVICE_LOCKED` | 设备已被其他任务占用 |
| 202 | `TASK_NOT_FOUND` | 任务 ID 不存在 |
| 203 | `STATE_TRANSITION_INVALID` | 任务状态转换非法（如已停止的任务无法暂停） |
| 301 | `DATABASE_ERROR` | 数据库读写异常 |
| 302 | `HARDWARE_ERROR` | 硬件设备（播放器/录音机）响应超时 |
| 401 | `API_ENDPOINT_ERROR` | API 端点不可用或已全部离线 |

## 4. 前后端适配层 (Preload Bridge)

### 4.1 TypeScript 接口定义 (`shared/types/task.ts`)
```typescript
// 统一接口契约，禁止 any 类型
export enum TaskAction {
  PAUSE = 'pause',
  RESUME = 'resume',
  STOP = 'stop',
  SKIP = 'skip',
  RETRY = 'retry'
}

export interface ITaskControlResponse {
  code: number;
  message: string;
  data?: any;
}

// Preload 暴露给 Renderer 的 API
export interface ITaskAPI {
  startTask: (taskId: string) => Promise<ITaskControlResponse>;
  controlTask: (taskId: string, action: TaskAction, caseId?: string) => Promise<ITaskControlResponse>;
  addTestCases: (taskId: string, caseIds: string[]) => Promise<ITaskControlResponse>;
  removeTestCase: (taskId: string, caseId: string) => Promise<ITaskControlResponse>;
  onProgress: (callback: (progress: ITaskProgress) => void) => void;
}
```

### 4.2 Preload 实现示例 (`preload/taskAdapter.ts`)
```typescript
contextBridge.exposeInMainWorld('taskAPI', {
  startTask: (taskId) => ipcRenderer.invoke('task:start', taskId),
  controlTask: (taskId, action, caseId) => ipcRenderer.invoke('task:control', { taskId, action, caseId }),
  addTestCases: (taskId, caseIds) => ipcRenderer.invoke('task:add-cases', { taskId, caseIds }),
  removeTestCase: (taskId, caseId) => ipcRenderer.invoke('task:remove-case', { taskId, caseId }),
  onProgress: (callback) => ipcRenderer.on('task:progress-update', (event, data) => callback(data))
});
```

## 5. 闭环验证逻辑

### 5.1 数据流一致性 (E2E 链路)
1. **读取配置**：Worker 从 `test_case_audios` 获取音频文件路径及 `playback_device_id`。
2. **多端放音**：控制 `playback_devices`（如 USB 播放卡、蓝牙音箱）执行放音。
3. **采集结果**：控制 `devices` (iOS/Android) 采集语音识别结果，存入 `test_results.asr_result` 和 `translation_result`。
4. **维度评估**：
   - Evaluator 查询 `test_case_dimensions` 确定评估项。
   - 调用 `dimensions.api_url` 指定的评估接口（传入 `asr_result` 等作为参数）。
   - 将返回的打分数据存入 `test_result_dimensions`。
5. **实时反馈**：WebSocket 将上述各步骤状态及最终结果实时推送到 `TestExecutionComponent.vue`。

### 5.2 数据流一致性 (API 链路)
1. **API 端点选择**：
   - 获取任务关联的 API 配置
   - 查询所有 `status='online'` 的 `APIEndpoint` 记录
   - 按优先级和健康度智能选择最佳端点
2. **音频准备**：
   - 从 `test_case_audios` 获取测试音频路径
   - 读取音频元数据（预设 ASR 文本、翻译文本等）
3. **API 调用**：
   - 使用 `APIDriver` 调用选定的 API 端点
   - 上传音频文件并获取识别/翻译结果
   - 动态更新端点健康度评分
4. **结果处理**：
   - 记录原始 API 响应
   - 计算评估维度得分
   - 存入 `test_results` 和 `test_result_dimensions` 表
5. **实时反馈**：WebSocket 将进度和结果实时推送到前端界面

### 5.2 冲突处理规范
- **设备争抢**：E2E 测试启动前必须通过原子操作锁定设备记录，防止多个任务同时操作同一硬件。
- **并发写冲突**：PostgreSql 开启 WAL 模式，Flask 使用单例数据库引擎，确保高频进度更新不锁库。

## 7. 性能指标 (SLA)
- **首渲染耗时**：从任务启动到收到第一条进度推送 < 500ms。
- **数据一致性**：UI 进度与后端数据库误差 < 1s。
- **API 并发上限**：单机支持至少 50 并发 API 测试。

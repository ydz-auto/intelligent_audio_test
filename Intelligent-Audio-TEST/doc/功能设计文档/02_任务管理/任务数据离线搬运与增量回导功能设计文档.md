# 任务数据离线搬运与增量回导功能设计文档

> 前置设计基线：《任务数据导入导出功能设计文档》（V9.7.10）已覆盖"任务整包导入导出"（16 表 + ZIP + 自动 ID 策略）。
> 本文在其之上新增三项能力：**用例一致性硬校验**、**增量回导（评估+报告合并回原任务）**、**报告独立导入（平台报告 / 独立文件报告 / Agent 分析总结报告三类）**。
> 背景约束：服务 A 与 B 网络环境不通，跨服务器数据只能以"导出 ZIP → 离线搬运 → 导入"的方式传递。
> 本版口径已按 INT-1758（D0 方案评审）A1~A12 裁定回写（2026-10-24，INT-1773），D1~D6 实施以本文为准，修订明细见 §10。

---

## 1. 背景与目标

### 1.1 背景

- A、B 两套服务部署在网络互不可达的环境，任务数据、评估结果、报告只能离线搬运。
- 场景：A 导出任务（含用例结果）→ 离线搬运到 B → B 导入并重新评估、生成新报告 → B 导出增量数据 → 离线搬回 A → A 合并导入。
- 现有 data-transfer 为"任务级整包"语义：导出 16 表整包，导入时 ID 冲突自动重映射为**新副本任务**，无法合并回原任务。

### 1.2 目标

1. 任务整包迁移时增加**用例一致性硬校验**（A 包引用用例必须已存在于 B，否则拒绝导入）。
2. 支持**增量回导**：从 B 只导出"新评估数据 + 新报告"，合并回 A 的**原任务**（而非副本）。
3. 支持**报告独立导入**，区分三类报告：
   - **平台报告**（结构化）：test_reports 7 表数据行，导入后落平台报告体系，替换旧报告。
   - **独立报告**（文件型）：MD / PPTX / HTML 等文件，挂到 Report Studio documents（`source_type=uploaded_file`），用户可选是否关联任务。
   - **Agent 分析总结报告**：Agent（DSH）阅读源报告后生成的总结文档，同样落 Report Studio documents（`source_type=agent_summary`）；源报告可以是平台报告，也可以是用户上传的报告文件。

### 1.3 非目标

- 不做跨库实时同步（网络不通，离线搬运为前提）。
- 不迁移用户/权限、设备/API/用例定义等基础配置（沿用现有 data-transfer 边界；用例一致性校验只是"要求目标库已有"，不代迁移）。
- 不做报告文件在线转换（MD→PPTX 等），仅按原格式存储与展示。
- 不迁移 Agent 的 DSH 会话与对话历史（会话属于 B 侧本地运行时，A 侧无法续接）。

## 2. 术语

| 术语 | 解释 |
|------|------|
| 源服务 A | 任务/用例结果的原始持有方，也是增量回导的最终落库方 |
| 目标服务 B | 导入 A 的任务包，执行重新评估与报告生成 |
| 用例一致性 | A 包内引用的 test_case_ids 集合 ⊆ B 已存在且可用的用例 id 集合 |
| 增量回导包 | 从 B 导出的"新评估数据 + 新报告"，不含任务/结果/文件本体 |
| source_map | B 侧持久化的"源 ID ↔ 本地 ID"映射（task_id / test_result_id / dimension_id / report_id 等） |
| 平台报告 | test_reports 及其 6 张子表的结构化数据（7 表） |
| 独立报告 | MD / PPTX / HTML 等文件形式的报告文档，挂 Report Studio documents（`source_type=uploaded_file`，无平台报告行） |
| Agent 分析总结报告 | Agent（DSH）阅读源报告后生成的 Markdown 总结文档，落 Report Studio documents（`source_type=agent_summary`） |
| 源报告 / 源文档 | Agent 总结所依据的报告：平台报告（走 `report_id`）或用户上传报告（走 `parent_doc_id`） |

## 3. 三条链路总览

```
链路 1 · 任务整包迁移（现有 + 硬校验）
  A 导出任务(ZIP) →【用例一致性硬校验】→ B 导入任务 → B 重评 + 生成报告

链路 2 · 增量回导（新增）
  B 子集导出(新评估 + 新报告 7 表 + source_map) → A 合并导入 → 匹配原任务 → 维度覆盖集合并 + 报告原地替换

链路 3 · 报告独立导入（新增）
  3a 平台报告：B 导出报告 7 表数据包 → A 导入 → 匹配原任务 → 原地替换旧报告
  3b 独立报告：外部 MD/PPTX/HTML 文件 → A 导入 → 挂 Report Studio documents（可选关联任务）
  3c Agent 分析总结：B 导出 Studio 文档 + 版本 + 图表规格 + 血缘 → A 导入 → 先落源报告（3a/3b）再挂总结文档
      依赖顺序：3a / 3b → 3c（源缺失时降级为孤儿文档，不阻塞）
```

## 4. 链路 1：任务整包迁移 + 用例一致性硬校验

### 4.1 现有能力（沿用）

- A 导出：`POST /api/v1/data-transfer/export`（16 表 ZIP，含任务/结果/维度/报告 7 表/文件；同步返回文件流）。
- B 导入：`POST /api/v1/data-transfer/import`（预检 + 自动 ID 策略 + 5 段提交 + 补偿回滚；**异步：202 + `batchId`，进度与终态见 §7.3**）。

### 4.2 新增：用例一致性硬校验

| 项 | 现有（warning） | 新增（硬校验） |
|----|----------------|----------------|
| 触发点 | [preview_import](file:///d:\00_code\V9.7.31\Intelligent-Audio-TEST\task_service\application\task\data_transfer_import_service.py#L77-L126) 的 `_build_warnings` | 预检 + 执行导入双阶段 |
| 缺失用例 | 仅 warning："目标库缺少 N 个测试用例…无法重新执行" | 预检提示清单、执行阶段拒绝导入 |
| 全局开关 | — | `DATA_TRANSFER_CASE_CONSISTENCY_REQUIRED`（默认 true） |
| 请求级开关 | — | `requireCaseConsistency`（可选，缺省取全局值） |
| 校验规则 | 引用集合差集 | `refs['test_case_ids'] - usable_case_ids` 非空且要求校验时拒绝 |

**开关粒度**：

- 全局 `DATA_TRANSFER_CASE_CONSISTENCY_REQUIRED`（默认 true）。
- 请求级 `requireCaseConsistency`（可选，缺省 = 全局值）：**只能把 true 放宽成 false**；全局为 false 时传 true 不生效（防止前端任意提权）。

**导入意图 `intent`**：请求体加 `intent`，取值 `migrate`（默认）或 `restore`。

- `migrate`（任务迁移，B 侧要重新执行）：按开关强校验。
- `restore`（历史结果查看 / 备份恢复）：**默认关闭硬校验**，预检回执 `data.intent='restore'`，`warnings` 写明"未校验用例一致性，导入后无法重新执行"。该 warning **只在确实未校验时**追加；`restore` 且显式传 `requireCaseConsistency=true` 时仍走全量校验，通过后不得再出现"未校验"文案。
- 请求字段拼写以 D0 原文 `requireCaseConsistency` 为准（multipart 表单字段），网关必须接受该拼写；`require_case_consistency` 如保留只能作只读别名，不得成为唯一入口（INT-1850 审计发现 V9.7.31 当前只认 snake_case，修复见 INT-1870）。

**两阶段错误结构**：

| 阶段 | 语义 |
|------|------|
| 预检 | **不阻断**，`success=true`，`data.intent` 回填报文意图，`data.caseConsistency = { required, complete, missingCaseIds[], invisibleCaseIds[], missingCount, truncated }`；前端据此禁用"开始导入"按钮并展示缺失清单 |
| 执行 | `required && missing` → **HTTP 422 / `code 422`**，`data.missingCaseIds`（最多 500 条，`invisibleCaseIds` 同为 500 条上限）+ `data.missingCount`（全量计数）+ `data.truncated`（是否已截断） |

> 实现演进裁定（INT-1850 一致性审计，2026-10-25）：`intent` 落在 `data.intent`（与本节「restore 预检回执 `data.intent='restore'`」一致），`caseConsistency` 内不再重复；`invisibleCaseIds` / `truncated` 为实测回执的补充字段。`data.warnings` 是**字符串数组**（人读文案），不含结构化判定字段，机读判定一律走 `caseConsistency`。

**校验口径（两处必须修正，否则判定失真）**：

1. `fetch_existing_case_ids` 必须过滤 `TestCase.deleted == False`——软删用例不能算"存在"。
2. 私有用例（`visibility='private'` 且导入方非 owner）不可用，归入缺失（或单列 `invisibleCaseIds`）。

**校验逻辑（伪代码）**：

```python
refs = collect_external_references(rows_by_table)      # 复用现有
required = request.requireCaseConsistency
if required is None:
    required = Config.DATA_TRANSFER_CASE_CONSISTENCY_REQUIRED
    if request.intent == 'restore':
        required = False                               # restore 默认不走硬校验
# restore + 显式 requireCaseConsistency=true → 仍按全局总闸校验（"默认"不覆盖显式要求）
availability = transfer_repository.fetch_case_availability(refs['test_case_ids'])  # 三分：available / missing（含软删）/ invisible（私有非 owner）
missing = sorted(availability['missing'] | availability['invisible'])              # 不可用即缺失
# 预检：success=true + data.intent + data.caseConsistency{required,complete,missingCaseIds,invisibleCaseIds,missingCount,truncated}
# 执行：required and missing → code 422 + data.missingCaseIds / data.missingCount / data.truncated
```

> 实现演进裁定（INT-1850 一致性审计，2026-10-25）：旧伪代码 `required = required and intent == 'migrate'` 会把「restore + 显式要求校验」也放过，与本节「`restore` **默认**关闭」及 `_resolve_policy` 的实现语义相反；实际实现为 `restore` 仅在请求未显式给开关时关闭。可用性判定方法名以 `fetch_case_availability`（`fetch_existing_case_ids` 收敛为其 `available` 子集）为准。

**配套前置**：A 侧先用现有 testcase export/import（`POST /testcases/export` / `POST /testcases/import`，权限 `testcase:import_export`）把用例迁移到 B，B 库用例齐备后再走任务导入。

**联动说明**：升级为硬校验后，纯"历史结果查看/备份恢复"场景（不重新执行）也会被卡住。因此全局开关默认 true，并提供两条兼容路径——请求级放宽（`requireCaseConsistency=false`）与 `intent=restore`；预检只提示不阻断，保证前端能拿到缺失清单而不是只看到失败。

## 5. 链路 2：增量回导（B → A 合并新评估 + 新报告）

### 5.1 场景

B 上任务已重评、新报告已生成（报告 7 表为 B 侧最新），需要把"新评估数据 + 新报告"离线搬回 A，**合并到 A 的原任务**（不是产生副本）。

**v1 业务前提（硬约束）**：B 侧对该任务**只允许重新评估（reevaluate）**，不允许重新执行（retry / reset 后重新 start / 任何新增结果行的操作）后再做增量回导。重新执行会新增、甚至先删 `test_results` 行（`reset_task_for_start` 会清空该任务全部结果），包内维度行引用的 A 原始 `test_result_id` 在 B 上会变成"不存在"或"同一用例两条"，增量包语义直接失效。该约束由导出侧硬闸 + A 侧反向校验兜底（见 §5.2 / §5.4）。

### 5.2 子集导出（B 侧）

**接口**：`POST /api/v1/data-transfer/export-incremental`（同步返回文件流；包体 >100MB 走 OSS 预签名直传与离线 sha256 校验见 §7.7）

```jsonc
// 请求
{ "taskIds": [25], "include": ["dimensions", "reports"] }  // reports 含 7 表
```

**导出侧硬闸（v1 必做）**：逐行把 `test_result_dimensions.test_result_id` 经 source_map 翻译回 A 原始 id。**任何一行在 source_map 中没有映射**（= B 侧重新执行新产生的结果）→ **拒绝整包导出**，返回 `HTTP 409 / code 409`、`data.unmappedResultIds[]`，文案："B 侧存在 A 未登记的结果行（重新执行产生），增量回导 v1 不支持，请改用整包导出或先在 B 侧回退"。同理，包内每个 `test_reports.task_id` 也必须能翻译，否则不产出包。

**导出包结构**（复用 data-transfer ZIP 规范，manifest 版本 `1.1`）：

```
incremental_<ts>.zip
├── manifest.json          # 1.1：version / exportedAt / serverInfo{source} /
│                          #       sourceTask{id,name,caseCount,caseSetHash} / entities[] / tasks[] / stats / options
├── db/
│   ├── test_result_dimensions.json   # 维度评分行（test_result_id 已翻译为 A 原始 id；dimension_id 保留 B 侧值）
│   └── 报告 7 表.json                 # test_reports + 6 子表（task_id 已翻译为 A 原始 task_id）
└── meta/
    └── dimensions.json    # B 侧维度定义快照（name / parent_dimension_id 链 / task_type_code），供 A 侧匹配
```

- `manifest.sourceTask.caseSetHash = sha256(','.join(sorted(test_case_ids)))`，A 侧据此做指纹校验（§5.4）。
- `tasks[]` 必填（manifest 结构校验要求它是 list），增量包写 `[{ id: <A 原始 id>, name, status, resultCount }]`。
- 整包导出（`/export`）继续产出 `1.0`；导入侧同时接受 `1.0` / `1.1`，不因版本号误拒历史包。

**关键：ID 翻译**——导出时把 B 库 id 通过 source_map 翻译回 **A 原始 id** 再写入包：

| 包内字段 | B 库值 | 包内写入值 |
|---------|--------|-----------|
| test_result_dimensions.test_result_id | 205（B id） | 101（A 原始 id） |
| test_reports.task_id | 25（B id） | 12（A 原始 task_id） |

**维度 id 不翻译、不直写**：现有维度导入仓储只重映射 `test_result_id`，**不重映射 `dimension_id`**；而 B 重评产出的行带的是 B 侧维度 id。因此：

1. 包内维度行保留 B 的 `dimension_id`，同时由 `meta/dimensions.json` 带出 B 侧维度定义；
2. A 合并时按 `(name, parent_dimension_id 链路, task_type_code)` 映射到 A 的 `dimensions.id` 后再写入；
3. **匹配不到的维度行跳过并计入导入回执 `warnings`，绝不把 B 的 `dimension_id` 直写进 A 库**。

### 5.3 source_map 持久化（B 侧新增）

**背景**：现有 `strip_conflicting_ids` 导入时丢弃冲突行的原始 id，B 无法反查"本地 id 对应 A 的哪个原始 id"。增量回导依赖此映射，必须持久化。

**存储**：新增表 `data_transfer_source_maps`（归属 task_service）：

| 列 | 说明 |
|----|------|
| id | 自增主键 |
| source_server | 源服务标识（manifest.serverInfo.source） |
| source_task_id | A 原始 task_id |
| entity_type | tasks / test_results / test_result_dimensions / test_reports |
| source_id | A 原始 id |
| local_id | B 本地 id |
| created_at / updated_at | 时间戳 |

**唯一键与索引**：

- 唯一约束：`UNIQUE(source_server, entity_type, local_id)`；
- 普通索引：`(source_server, entity_type, source_id)`、`(source_server, source_task_id)`。

其中 `(source_server, source_task_id)` 供增量回导按「源服务 + 源任务」一次取回该任务四类映射（`TransferRepository.fetch_source_maps` / `fetch_source_maps_grouped` 的查询路径）；`(source_server, entity_type, source_id)` 供按源 id 反查本地副本。

理由：同一 A 任务被 B 导入两次会产生两份本地副本，此时一个 `source_id` 对应多个 `local_id`；而导出方向永远从 B 的 `local_id` 反查 `source_id`，local 侧天然唯一。若把唯一键建在 `source_id` 上，第二次整包导入会直接失败。

**写入方**：本表归 task_service，**只有导入编排层写**（`data_transfer_import_service`）；evaluation_service / report_service 只返回各自的 `id_mapping`，不得直写（DDD 红线），也不各自维护一份。

**source_server 取值**：配置项 `DATA_TRANSFER_SERVER_ID`（§8）。导出写 `manifest.serverInfo.source = DATA_TRANSFER_SERVER_ID`，导入以它作为 `source_server`；为空时回落 `SERVICE_NAME-hostname` 并打 WARNING（`SERVICE_NAME` 只是角色名，A/B 相同，不能当服务标识；`socket.gethostname()` 换机器/容器即变）。

**登记时机**：B 导入任务整包（链路 1）时，**全部数据段成功后**由编排层在**一次事务**里对发生重映射的 4 类主键逐条 upsert；未冲突（`source_id == local_id`）不登记（等价映射）。**重复导入走 upsert**，重放幂等。批次补偿 / 批次回滚只回删**本批次新增**的映射行（被覆盖的旧行无快照，删掉等于丢历史映射）。

**登记失败补偿**：远端已提交但本地登记失败时**不回滚远端数据**，返回 partial 状态（`code 500` + `data.sourceMapPending=true` + `data.batchId`；网关对该 partial 回执把 `data` 原样带回，不塞进 `detail`），并把完整 mapping 快照同时写进 Redis 批次登记的 `source_map` 字段（与批次登记同一 7 天 TTL），使失败后可人工/脚本重放登记。

**生命周期**：**永久保留**，不做 TTL 清理，供后续任意时点增量回导使用。清理只发生在批次回滚 / 人工维护：任务「彻底删除」（`trash_repository.purge_tasks`）当前**不级联删除**本表映射行，孤儿映射不影响功能（本地行已不存在，导出侧不会读到），如需随硬删级联另开卡。

### 5.4 合并导入（A 侧）

**接口**：`POST /api/v1/data-transfer/import-incremental`（multipart ZIP，权限复用 `task:import`）

**匹配与校验**：

| 项 | 口径 |
|----|------|
| 定位原任务 | `manifest.sourceTask.id` → A 库 `test_tasks.id`；不存在 / 已软删按 404 处理 |
| 任务一致性 | `manifest.tasks[0].id`、`sourceTask.id`、包内报告行 `task_id` 必须一致，否则 400 拒绝 |
| 指纹 | `sourceTask.caseSetHash` 与 A 原任务 `task_case_relations` 实时计算值比对，不符 → 409 拒绝（`data.expected` / `data.actual`）；任务名只做二次提示、不阻断 |
| A 侧反向校验 | 包内每个 `test_result_id`、`test_reports.task_id` 必须存在于 A 库，**不存在 → 409 拒绝**（禁止把 B 的本地 id 当 A id 写入） |
| 用例硬校验 | 不触发（增量包不含 `task_case_relations`，见 §5.5） |

**过滤可见性**：复用 `filter_visible_task_ids` 口径；任务私有且导入方非 owner → 403。

**异步**：立即返回 **202 + `batchId`**，不再同步等待合并完成；进度与终态经 WS `/ws/transfer` 的 `transfer_progress` 事件下发，断线/缺口用 `GET /api/v1/data-transfer/batches/{batch_id}` 补齐（§7.3）。

**合并语义**：

| 数据 | 合并策略 |
|------|----------|
| test_result_dimensions | 按 **`(result_id, dimension_id)` 覆盖集**合并：先删 A 侧该结果在这些维度下的旧行（**含各 `round_number`**），再插包内行；包内未出现的维度保持不动。不做整行 upsert——纯 upsert 会把"B 少评了某轮"留成脏数据 |
| 报告 7 表 | **原地替换、保留 A 报告 id**：`UPDATE test_reports` 覆盖内容字段（name / description / analysis / status），**保留** `visibility` / `created_by_user_id` / `type` / `created_at`；随后 `DELETE` 6 张子表中该 `report_id` 的行，再 `INSERT` B 的子表行（子表 id 由 A 重新分配，`report_id` 固定为旧 id）。**先写后删、单事务**：全部成功才提交，失败整事务回滚，旧报告完好 |
| 任务 / 用例状态 | **不改**：增量包不含 `task_case_relations`，增量回导只覆盖评估与报告，不改任务 / 用例执行状态、不改计数 |

> 保留 `visibility` / `created_by_user_id` 是硬要求：B 的用户 id 在 A 不存在，直接写入会让报告 owner 校验失效，私有报告可能泄漏给 shared 读者。

**目标报告定位顺序**（B 的 `regenerate_report` 会删旧建新，source_map 里的报告映射可能陈旧，不能只靠它）：

1. B 报告 id 经 source_map 翻译到 A 报告 id → 用它；
2. 否则取 A 原任务下 `type='task' AND deleted=false` 的最新报告（与 `published_task_repository` 同口径）；
3. 都没有 → 新建报告（新 id，引用方本来就为空）。

**事务边界与回滚**：

- 维度合并与报告替换**分属两个服务事务**（evaluation / report），由编排层按现有分段补偿**逆序回滚**（report → evaluation）。
- 回滚依赖旧值快照（维度旧行 + 旧报告 7 表旧值），快照落各服务自有库表 `data_transfer_merge_snapshots`（evaluation / report 各一张，不跨服务写对方表、不塞 Redis），并与删除 / 覆盖**在同一事务内**写入；批次登记保留 7 天，补偿失败显式报错要求人工介入。
- 每次替换后跑引用方孤儿检查（SQL 见 §6.1），结果非 0 时写进导入回执 `warnings`。

**失败码**（必须同时出现在 `data.code` 与 HTTP 状态；前提是 §7 的 `int32 code` 透传已落地）：

| 场景 | HTTP / code | `data` |
|------|-------------|--------|
| manifest 版本 / 结构非法 | 400 | — |
| 增量包含多个任务 | 400 | `taskIds` |
| 包内 id 与源任务不一致 | 400 | 不一致的 id 列表 |
| A 库任务不存在 / 已软删 | 404 | `sourceTaskId` |
| 无权写入该任务（私有且非 owner） | 403 | — |
| 指纹不符 | 409 | `expected` / `actual` |
| 包内 result / report id 在 A 不存在 | 409 | `missingIds` |
| 导出侧存在未映射结果行 | 409 | `unmappedResultIds` |
| 补偿部分失败 | 500 | `batch_id` / `compensationErrors` |

**ID 冲突处理**：增量包内已是 A 原始 id，A 侧**不做重映射**（维度 id 除外，按 §5.2 的维度匹配规则翻译）。

### 5.5 权限与校验

- 权限：`task:export`（导出）/ `task:import`（导入），复用现有。
- 用例一致性：增量回导包只含评估+报告，不含 task_case_relations，不触发链路 1 的用例硬校验。

### 6.2 独立报告（文件型：MD / PPTX / HTML）

**落点**：Report Studio documents 体系（[report_studio.py](file:///d:\00_code\V9.7.31\Intelligent-Audio-TEST\report_service\domain\entities\report_studio.py#L14-L29)）——已有版本快照、chart_refs、样式偏好、导出作业能力，MD 渲染成熟。

**接口**：`POST /api/v1/report-studio/import`（multipart 文件 + 元数据；单文件 ≤ `REPORT_STUDIO_UPLOAD_MAX_MB`(50) 走同步上传，更大的文件先走 OSS 预签名直传再提交 `ossKey`，见 §7.7）

```jsonc

title: "XX 算法对比报告"
task_id: 12            // 可选：是否关联任务（用户自选）
format: "md" | "html" | "pptx"
```

**存储与校验**：

1. **OSS 类别复用现有 `reports`**，key 前缀 `studio_uploads/{uuid}.{ext}`（单桶模式下为 `{OSS_KEY_PREFIX}/reports/studio_uploads/...`）。**不得为此新造 OSS category**——多桶模式下未知 category 直接 `ValueError`。
2. **格式白名单** `md / html / pptx`，扩展名 + Content-Type 双校验，不匹配 415。
3. **大小上限**独立配置 `REPORT_STUDIO_UPLOAD_MAX_MB`（默认 50），超限 **413**；不复用 `DATA_TRANSFER_MAX_UPLOAD_MB`。

**导入行为**：

1. md → 直接存 `markdown_content`（不落文件列），参与编辑与版本链。
2. html / pptx → 存 OSS 文件，写 `source_file_path` / `source_format` / `source_file_size` 三列；**不做格式转换，预览 = 下载 / 沙箱展示**。
3. 创建 Report Studio document（`source_type='uploaded_file'`、`report_id` 为空 / `title` / `chart_refs` 空）。
4. `task_id` 可选：为空则不关联任务（独立文档库）；有值则写入关联，任务详情 / 报告列表可见。

**HTML 预览防 XSS（硬要求）**：上传文件**永不作为同源文档直接返回**。下载 / 预览接口统一带 `Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`、`Content-Security-Policy: sandbox; default-src 'none'; img-src data:; style-src 'unsafe-inline'`；前端用 `<iframe sandbox="allow-scripts">`，**不得**加 `allow-same-origin`。注意平台自身导出的 HTML 是转义过的受控输出，与上传 HTML 不是一回事，不能以此为由放开。

**权限**：`report:studio:create`（新建）+ `report:read`（读取），沿用现有权限点。

**与平台报告的关系**：独立报告不进 test_reports 7 表，不参与报告统计 / 对比矩阵；仅作为文档形态存在。

### 7.3 异步化与进度事件契约（P2）

**1）导入类一律 202，禁止同步等待。** 整包 / 增量 / 报告包导入都是分钟级（单包上限 2048MB，`config.py:130-131`），同步等待会让网关、反代、浏览器三方超时叠加。

```http
POST /api/v1/data-transfer/import
Content-Type: multipart/form-data
Idempotency-Key: 3f9a...            # 可选；建议前端生成，见 §7.6

HTTP/1.1 202 Accepted
Location: /api/v1/data-transfer/batches/9f2c4d1e
{
  "code": 0,
  "message": "已受理",
  "data": { "batchId": "9f2c4d1e", "status": "queued",
            "progressUrl": "/api/v1/data-transfer/batches/9f2c4d1e" }
}
```

**2）异步执行的归属：task_service 内置 job runner（定案，实施不得二选一）。**

现状是**网关同步调用**：请求线程阻塞在 `data_transfer_bp.py:41-48` → `data_transfer_service.py:122-146` → `data_transfer_proxies.py:56-65`（`_EXECUTE_TIMEOUT_SECONDS = 3600`，`:17`），期间 HTTP 连接、网关 worker 线程、task_service gRPC worker 线程三方同时被占。仓库里**不存在** job worker / 后台执行器（`grep -rn "job_worker\|BackgroundExecutor"` 0 命中），本节把它拆成两层：**提交**（gRPC，秒级）+ **执行**（task_service 进程内 runner）。

- **提交**：网关 `POST /data-transfer/import*` → 落盘或校验 `ossKey` → 调 task_service `ExecuteImport` / `ImportIncremental` / `ImportReportPackage`。这三个 RPC **语义改为「提交」**，固定顺序为：**① 幂等分流**（带 `Idempotency-Key` 时先按 §7.6 幂等表判「复用同一批次 / 开新批次 / 409 指纹冲突」，此步在入队前，冲突直接返回，不产生批次）→ **② 分配 `batch_id`** → **③ 写进度快照 `status=queued`（附 `ownerUserId`）+ 批次登记** → **④ 入队** → **⑤ 立即返回** `{success:true, data:{batch_id, status:"queued"}}`，deadline 30s。网关据此回 202（本节第 1 条）。
- **执行**：新增 `task_service/application/task/transfer_job_runner.py`（application 层，不碰 interfaces / infrastructure）：
  - 进程内 `ThreadPoolExecutor`，worker 数 `DATA_TRANSFER_JOB_WORKERS`（默认 2）；超出并发的批次保持 `queued`、按入队顺序起跑（**不新增排队/拒绝错误码**，积压只体现为 `queued`）。
  - job 复用现有编排 `DataTransferImportService.execute_import`（`data_transfer_import_service.py:170`）等；`batch_id` 由提交层分配后**作为入参传入**（今天在 `:172` 内部 `uuid.uuid4()` 生成，须改成入参，否则 202 无号可回）。
  - **身份透传**：提交线程 `capture_identity()`（`user_context.py:53-60`），worker 内 `run_with_identity(identity, job)`（`:62-79`）。contextvars 不跨线程——不透传则 job 内全部出站 gRPC 不带 `x-user-id`，下游按未认证身份过滤可见性（§7.5）。
  - job 总上限 3600s（`DATA_TRANSFER_JOB_TIMEOUT_SECONDS`）**由 runner 在段边界检查累计耗时**（协作式中断，不 kill 线程）；单段 RPC deadline 600s（§7.6）。
  - **心跳（必须，不依赖进度事件）**：批次**入队时**即由 runner 登记心跳，`queued` 与 `running` 两个状态都由独立心跳线程每 `DATA_TRANSFER_JOB_HEARTBEAT_SECONDS`（默认 30s）刷新快照 `updated_at`，随终态退出。两个理由：① 整段 RPC（最长 600s）期间没有阶段事件——现有编排 `extracting_files` 整段只发一次事件（`task_service/application/task/data_transfer_import_service.py:234`），下一事件在 `:241`，2048MB 包该段超过 120s 是常态；② 超出 `DATA_TRANSFER_JOB_WORKERS` 的批次在队列里等前序 3600s job，同样没有事件。**只用阶段/表边界事件刷新 `updated_at` 会让正常在跑的 job 被读侧误判 failed。**
- **批次状态存哪**：唯一权威 = Redis 进度快照 `data_transfer:batch:{batch_id}:progress`（本节第 6 条）；回滚主键另存批次登记 `data_transfer:batch:{batch_id}`（`data_transfer_batch.py:20-36`）。v1 **不落 DB 批次表**，也不做跨实例队列。
- **进程重启 / 崩溃：不自动续跑**（分段补偿只能逆序回滚，不能从断点续跑；续跑需要段级断点，v1 不做）。恢复靠**读侧 stale 检测 + 同键重投开新批次**：
  - `updated_at` 由 runner **心跳**刷新（上条），**不得**只由阶段事件刷新。
  - `GET /batches/{id}` 发现 `status ∈ {queued, running}` 且 `now - updated_at > DATA_TRANSFER_JOB_STALE_SECONDS`（默认 **900s**；必须 ≥ 段级 deadline 600s + 余量，禁止取小于单段上限的值）→ 返回 `status=failed`、`code=500`、`message="导入作业已中断（服务重启或进程退出），请用同一 Idempotency-Key 重新提交"`，并附 `data.stale=true` + `data.rawStatus`（快照里的真实状态，供排查）。
  - **stale 判定只影响读侧展示：不中断 job、不回写 Redis、不触发补偿**（不回写是为防多实例互踩）。它是「疑似中断」的展示判据，不是终止信号——job 可能仍在写库并最终成功。因此前端在 `stale=true` 时必须**显式让用户确认**再重投，且**不得自动把 stale 当失败触发回滚**（回滚只能走 §7.6 的显式端点）；确需清理半导入残段时，`queued`/`running` 且已过 stale 的批次按 §7.6 回滚表第二行带 `forceStale=true` 显式处理；即便新旧批次撞在一起，按 §7.6 **幂等末条**的 upsert / 原地替换语义最终收敛。
  - **恢复由提交层保证，不由读侧保证**：用户用同一 `Idempotency-Key` 重投 → 提交层发现命中的批次为 `failed` / `cancelled`，**或** 为 `queued` / `running` 且已过 stale 阈值 → **分配新 `batch_id`、覆盖 `data_transfer:idem:{key}` 映射、重新入队**，返 202 + 新 `batchId`；旧批次随 TTL 清理，不复活。注意 stale 子句**必须限定 `queued`/`running`**：已 `succeeded` 的批次 `updated_at` 同样会超过 900s，不限定就会把成功的批次重开，与「想再导一次已成功的批次 → 换键」相悖（§7.6 幂等表第一、二行）。即**幂等只在非终态去重**（完整规则见 §7.6）。读侧「判 failed」与提交层「同键开新批次」用的是同一个 stale 判据，不存在「判死却投不进去」的状态。
- **取消**：job 在段边界轮询 Redis 取消标志（§7.6）；`queued` 批次在起跑前发现标志直接转 `cancelled`，不执行任何段。
- **202 与 3600s 各约束谁**：202 约束「提交完成」（30s 内）；3600s 约束「job 执行」（runner 内）。两者不再共享同一个调用栈。

**3）进度事件统一信封**（唯一结构，REST 快照、WS、SSE 三处同构）：

```jsonc
{
  "event_type": "transfer_progress",
  "batch_id": "9f2c4d1e",
  "stage": "writing_task",          // 见下表
  "processed": 1200,                 // 已处理行数/条目数
  "total": 3400,                     // 总数；未统计完为 0
  "status": "running",               // queued | running | succeeded | failed | cancelled
  "code": 0,                         // 0=无错误；非 0 见 §7.4（仅 running 之外的终态有意义）
  "message": "正在写入 test_results",
  "ts": "2026-10-24T08:12:33.512Z",  // ISO8601 UTC
  "seq": 17,                         // 批次内单调递增，从 1 起
  "percentage": 42.5,                // 派生字段，仅为展示；判进度以 processed/total 为准
  "data": {}                         // 终态附加：summary / missingIds / compensationErrors 等
}
```

**信封是后端传输结构（snake_case），不是前端领域对象（架构红线，写死）**：React / 新 Vue 一律在各自 **infrastructure 适配层**（React `frontend-react/src/infrastructure/api/client.ts`；新 Vue `frontend/src/infrastructure/`，wiring/ux-vue）把信封转换为 camelCase 领域对象后再交给 UI，**组件不得直接消费原始事件**（不得出现 `evt.batch_id` / `evt.event_type` 这类读取）。前端 infrastructure 是唯一做 snake_case↔camelCase 转换的层（devloop §3.1），两前端各建一份同形转换，口径一致。

| queued | 已受理未开始 | — |
| parsing | 解析 ZIP / 校验 manifest | `parsing` |
| writing_task | 写 task_service 8 表 | `writing_db` |

**4）WS 通道（前端唯一订阅通道）**

- **命名空间 `/ws/transfer`（新开，不复用 `/ws/logs`）**。理由：`/ws/logs` 的 payload 是日志信封 `{task_id, log}`（`socketio_server.py:122-125`），与进度信封不可混用；且日志房间按 `task:{task_id}`（`:26-31`），而搬运批次是多任务的（整包可含多任务），房间键对不上。
- 房间 `batch:{batch_id}`；客户端 `emit('subscribe_batch', {batch_id})` / `emit('unsubscribe_batch', {})`；服务端校验通过才 `enter_room`（校验规则见 §7.5）。
- 事件名 `transfer_progress`，payload 即上面的统一信封（不套第二层）。
- 断线重连：socket.io 重连后房间关系丢失，必须重新 `subscribe_batch`；重连后**先 `GET /batches/{batch_id}` 取快照**，再按 `seq` 续接，缺口由快照补齐。
- 不随任务日志混流：搬运进度绝不发到 `/ws/logs`。

**5）SSE 通道**

- 事件名同名 `transfer_progress`，信封相同（`GET /api/v1/sse/events`，`app.py:181`）。
- **与前端既有订阅的关系：SSE 不是前端搬运进度通道。** SSE 是全局单流——订阅五通道全量、无按用户/批次过滤（`sse_bp.py:84-112`），且 EventSource 无法携带 `Authorization` 头（网关只认 Bearer，`middleware.py:192-203`），浏览器前端今天用不了。SSE 只作为运维/脚本的旁路观察（curl + Bearer）。
- 要让浏览器用 SSE，须先解决 token 与按用户过滤两件事，单独立卡，不在本需求范围。

**6）投递语义：至多一次（at-most-once）+ 快照补齐**

- 传输层是 Redis pub/sub：无持久化、无 ack、无重投（`redis_pubsub.py:85-107` 直接 `listen()` 后回调），网关订阅到即转发、**不缓存、不补发事件**。
- 因此**实时事件是「至多一次」**：可能丢（订阅断线/进程重启期间的事件永久丢失），但同一订阅连接上不会重复投递；**实现方不要做 ack / 等待重发 / 服务端重投——没有这个机制，也不在本卡新增**。
- 客户端契约：按 `seq` 检测缺口（`seq` 不连续 = 丢事件），一旦发现缺口或重连，立即 `GET /batches/{batch_id}` 拉快照并重置 `seq` 基线。快照与后续事件可能重叠（同一 `seq` 既在快照又在事件里），按 `(batch_id, seq)` 取最大者处理即可，重复处理必须幂等。
- 权威状态只有一个：Redis 批次快照 `data_transfer:batch:{batch_id}:progress`（TTL = `DATA_TRANSFER_PROGRESS_TTL_SECONDS`，默认 24h）。今天用的是全局单键 `data_transfer:import_progress`（`data_transfer.py:148`），并发两次导入会互相覆盖——按批次分键是硬要求。
- 若将来确需「至少一次」，须换成持久化队列（Redis Streams / MQ 消费组），v1 不做。

**7）禁止把行数据 / 文件内容塞进事件**

事件只带计数、表名、阶段名与错误摘要；单条 payload ≤ 8KB。行数据走 REST 查询，文件走存储通道。理由：事件总线无背压，大 payload 会拖垮所有订阅方（SSE 与 WS 共用同一 EventBus），且会绕过 REST 层的可见性过滤。

**8）事件类型迁移（不留双口径）**

- 新增 `EventType.TRANSFER_PROGRESS = 'transfer_progress'`，**取代** `IMPORT_PROGRESS = 'import_progress'`（`redis_pubsub.py:48`）；D1/D3 实施时旧常量删除，**不允许新旧双发**。
- 迁移影响面（实施卡必须一并改）：`redis_pubsub.EventType`、`import_progress_reporter.py`、`event_bus_forwarder._SOCKET_FORWARD_MAP`（`event_bus_forwarder.py:25-34`）、`sse_bp._map_event`（`sse_bp.py:60-67`）、`socket_payloads.ImportProgressPayload`（改为 `TransferProgressPayload`）、`tests/api/test_data_transfer.py:31`、`tests/integration/test_data_transfer_roundtrip.py:135`。
- 前端两个仓库同步改订阅名；React 与新 Vue 用同一信封、同一事件名，**且都经各自 infrastructure 转换层转成 camelCase 领域对象**（本节第 3 条），组件不得读原始 snake_case 字段。

### 7.4 错误码跨协议一致（P3）

**原则**

1. **业务失败一律走 `code` 字段，不在 gRPC 层抛业务异常**：服务端返回 `success=false + code + message + data(JSON)`；只有传输层故障（连不上、超时、JSON 解析失败）才抛出，网关统一记 500。
2. 网关按 `code` 映射 HTTP 状态，映射表**全量枚举**（下表）；未登记的 code 一律 500 并打 WARNING，不静默降级成 400。
3. 同一语义在四个通道用同一个 code：REST 放响应体 `code` + HTTP 状态；WS/SSE 放事件的 `code` 字段；MCP 不暴露（§7.9）。
4. code 取 HTTP 语义值（与 D0 A7 一致），**不复用** `ErrorCode` 业务码段（0/1xx/2xx/3xx，`error_codes.py:3-36`）——搬运链路的失败语义要能跨通道对齐，两套码混用会让前端无法判等。
5. **前置依赖**：`TaskConfigResponse` 加 `int32 code = 4` 并三处透传（proto / servicer / proxy），见 D0 A7；不做这一步，下表所有 code 都会退化成 500（今天 `data_transfer_service.py:136-138` 写死 `http_code=500`，`data_transfer_proxies.py:25-31` 丢 code）。

| code / HTTP | 场景 | `data` | 通道表现 |
|---|---|---|---|
| 400 | manifest 版本/结构非法；参数缺失；包内 id 与 `sourceTask.id` 不一致 | — / 不一致 id 列表 | 202 前同步回，或 job 终态 `status=failed` |
| 400 | **增量包 / 报告包含多个任务**（`manifest.tasks` 或包内报告行跨多个任务，D0 A7「增量包只支持单任务」） | `taskIds`（涉事的任务 id 列表） | 202 前同步回，或 job 终态 `status=failed` |
| 400 | **对已终态批次取消**：`POST /batches/{id}/cancel` 时批次已 `succeeded`/`failed`/`cancelled`（只能走 rollback） | `batchStatus` | 取消端点同步回 400（§7.6 取消） |
| 401 | 未认证：REST 无/过期 token；WS 握手 token 无效；SSE 无 Bearer | — | WS `connect_error` 不建连；SSE 连接即断 |
| 403 | 缺权限（`task:import`/`task:export`）；私有任务非 owner；订阅非本人批次 | — | WS `subscribe_rejected{code:403}` |
| 404 | A 库源任务不存在/已软删；`batch_id` 不存在 | `sourceTaskId` / `batchId` | `GET /batches/{id}` 直接 404 |
| 409 | 指纹不符；包内 result/report id 在 A 不存在（`missingIds`）；source_map 缺失；B 侧重跑产生未登记结果（`unmappedResultIds`，D0 A2） | `expected`/`actual`/`missingIds`/`unmappedResultIds` | job 终态 `status=failed` |
| 409 | **同一 `Idempotency-Key` 但包体指纹（`sha256`）不同** | `expectedSha256`/`actualSha256`/`existingBatchId` | **202 前同步回**（提交层在入队前比对 idem 映射，§7.6） |
| 409 | **批次在途不可回滚**：`POST /batches/{id}/rollback` 时状态为 `queued`/`running` 且未过 stale（含「已请求 cancel 但 job 未到段边界」）；已过 stale 但**未带 `forceStale=true`** 同回 409 | `batchStatus` / `hint:"forceStale"` | 回滚端点同步回 409（§7.6 回滚表） |
| 413 | 上传超 `DATA_TRANSFER_MAX_UPLOAD_MB`（2048）；报告文件超 `REPORT_STUDIO_UPLOAD_MAX_MB`（50）；合并快照超 `DATA_TRANSFER_MERGE_PACKAGE_MAX_ROWS`（D0 A8） | `limitBytes` / `limitRows` | 202 前同步回 |
| 422 | 用例硬校验缺失（仅链路 1，D0 A10） | `missingCaseIds[]`（≤500）+ `missingCount` | 预检回执 `success=true` 带 `caseConsistency`；执行阶段 `code 422` |
| 500 | 内部错误；补偿失败；未登记 code | `batchId` / `compensationErrors` | 终态事件 `status=failed` + 文案要求人工介入 |
| 504 | 网关 → 服务 gRPC deadline（导出/预检 120s、段级 600s、**同步回滚 1800s**；提交类 30s） | — | 同步端点直接 504；job 内按 500 终态。**回滚 504 特殊**：服务端可能仍在删，前端不得直接重发，先 `GET /batches/{id}` 复核再按回滚表处理（§7.6） |

> 202 不是错误码，是受理语义；`code` 恒为 0。

### 7.5 认证与隔离（P4）

**REST**：`Authorization: Bearer <JWT>`（`middleware.py:192-203`）。**全仓网关没有 cookie 通道**（`api_gateway` 内无 `set_cookie`/`request.cookies` 读写），文档与前端一律按 Bearer 实现，不要假设 cookie 会话。权限点见 §7.1。

**WS：今天不校验，本需求必须补上。**

- 现状：两个 `connect` 回调都忽略 `auth` 参数（`socketio_server.py:219-231`），`subscribe_task` 直接 `enter_room` 不做任何归属校验（`:56-58,239-243`）；默认命名空间的事件是全局广播（`:176-181`）。后果：任意客户端可订阅任意 `task:{id}` 房间、可收到所有用户的进度广播。
- 搬运链路契约（不满足不得上线前端接线卡）：
  1. 握手带 `auth: {token}`（socket.io 客户端 `io(url, {auth: {token}})`）；服务端 connect 时用 `TokenService.verify` 校验并绑定 `user_id` + 权限集，失败返回 `connect_error`，不建立连接。
  2. `subscribe_batch` 校验两件事：具备 `task:import`（或 `task:export`，按批次方向）权限，且批次 `ownerUserId` 等于当前 `user_id`（admin `*` 放行）；否则回 `subscribe_rejected {code: 403}` 且不入房间。
  3. 因此 `ownerUserId` 必须由提交层写入并全程可读：**进度快照**（§7.3-2，WS 校验读这里）+ **批次登记**（`TransferBatchRegistry.record` 的 payload 扩展，`data_transfer_batch.py:30-36`，供回滚审计）；这是 D1/D3 的必做项。
  4. `/ws/logs` 的既有跨用户订阅缺口**不在本需求范围**，另立缺陷卡；本需求只保证搬运事件不可被跨用户订阅。

**SSE**：`require_permission('sse:read')` + Bearer（`sse_bp.py:79-80`），但如前所述浏览器 EventSource 带不了头、且五通道全量广播无过滤 → 明确不作为前端通道（§7.3-5），本需求不改。

**gRPC：带用户态（拦截器自动附加），但权限点判定只在网关做一次。**

- **现状事实**：所有出站调用经 `ClientUserContextInterceptor`（`shared/infrastructure/grpc_interceptors.py:242-258`）自动附加 `x-user-id` / `x-user-is-admin`，因为 `_get_task_channel()` 就是 `grpc.intercept_channel(chan, *_CLIENT_INTERCEPTORS)`（`shared/clients/_grpc_channels.py:33-34,81-84`）；下游 `user_id / is_admin` **一律取自 `x-user-id` / `x-user-is-admin`**（`shared/infrastructure/visibility_filter.py:1-12`）。`get_data_transfer_service_stub` 里没有**显式**注入 metadata（`_grpc_stubs.py:128-131`）只是工厂写法，**推不出「不带用户态」**——不要再按服务账号口径实现。
- 因此：**权限点（`task:import` / `task:export` / `report:studio:*`）只在网关判一次**；服务侧用同一身份做**数据校验**（批次 `ownerUserId`、任务可见性 `filter_visible_task_ids`，即 D0 A7 的 403/404），不重复判权限。
- **异步 job 必须显式透传身份**：gRPC 入口的 `ServerUserContextInterceptor` 已把操作人写进 contextvar（`grpc_interceptors.py:260+`），提交线程 `capture_identity()`、worker 内 `run_with_identity()`（`user_context.py:53-79`，§7.3-2）——contextvars 不跨线程。
- **未透传 = 按未认证身份处理**：下游会把 job 当 guest，私有任务/结果被可见性过滤，批次表现为「源任务不存在 404」而不是 403。这是 D1/D3 的验收点（私有任务导入必须由 owner 发起且端到端可见）。
- 开发态例外：`AUTH_MODE=off` 时 `set_current_user_id` 为 None、不附加 metadata（`grpc_interceptors.py:250-258`），仅用于开发栈，不作为生产契约。

**两前端**：React 与新 Vue 用同一套 REST + WS 契约，**差异只在呈现**（进度条形态、阶段文案）。禁止任一前端直连 gRPC 或 Redis，也禁止用轮询 REST 代替事件（轮询只用于断线重连补齐）。

### 7.6 超时 / 幂等 / 取消 / 重试（P5）

**Deadline**

| 调用 | deadline | 依据 |
|---|---|---|
| 网关 → task `ExportTasks` / `PreviewImport` / `ExportIncremental` | 120s | `data_transfer_proxies.py:18` |
| 网关 → task **提交类** RPC（`ExecuteImport` / `ImportIncremental` / `ImportReportPackage`） | 30s | 只做批次登记 + 入队，秒级返回（§7.3-2）；`data_transfer_proxies.py:17` 的 3600s 常量随之删除 |
| task_service job runner 内的 job 总上限 | 3600s | `DATA_TRANSFER_JOB_TIMEOUT_SECONDS`，**runner 在段边界检查累计耗时**，不是 gRPC deadline |
| task → evaluation `MergeDimensions`、→ report `ReplaceReports` / `ImportReports` / Studio 文档 RPC | 600s | 本节新增（单服务事务段） |
| 网关 → task **`RollbackImport`（同步回滚）** | **1800s**（`DATA_TRANSFER_ROLLBACK_TIMEOUT_SECONDS`） | 本节新增，**不得沿用段级 600s**：回滚是一条链——task 本地段 → evaluation 段（600s）→ report 段（600s）→ 按登记 `files` 逐个 `delete_written_files`（数量随包规模线性增长），串起来的上限远大于 600s。取 2 × 段级 600s + 余量（默认 1800s），**不得低于 2 × `DATA_TRANSFER_SEGMENT_TIMEOUT_SECONDS`**。取 600s 会在段中途 504 而服务端仍在删，用户重试正好撞上半删段 |
| 前端 HTTP 请求（**导入提交类，202 前**） | 30s | 只约束「提交」这一段：202 后即结束，不随 job 延长（§7.3-2）。**同步端点不适用本行**——导出下载流、预检、回滚的 HTTP 超时必须 ≥ 对应 gRPC deadline + 余量（导出/预检 120s → 前端/反代 ≥ 180s；回滚 1800s → ≥ 1860s），否则前端先于服务端断开、用户在服务端仍写库时看到失败 |

**幂等**

- 客户端可带 `Idempotency-Key`（建议前端生成 uuid），网关原样透传给提交 RPC。**批次号由 task_service 提交层分配**（§7.3-2），网关不自己生成。
- **幂等只在非终态去重**（写死，实施不得自行取舍）：同键重投 → task_service 按 `data_transfer:idem:{key}` 查到既有批次，按命中的快照状态分流（下表）。**这是崩溃恢复的唯一出口**：读侧把中断批次显示成 `failed`（§7.3-2）但**不回写 Redis**，若同键重投仍返回旧 `batchId` 且不入队，用户将永远拿不到新 job。用户想再导一次已成功的批次 → 换键（换键一律新批次）。

| 命中批次的状态 | 提交层行为 | 响应 |
|---|---|---|
| `queued` / `running` 且未过 stale 阈值 | 不重复入队 | 202 + **同一** `batchId` |
| `succeeded` | 不重复入队（已完成，无需重做）。**已回滚的批次不适用本行**：回滚成功会把快照置 `cancelled` 并删除 idem 映射（见下「回滚成功后的状态」），同键重投落到第三行 | 202 + **同一** `batchId`，`status=succeeded` |
| `failed` / `cancelled`，或 `queued` / `running` 且 `now - updated_at` 已过 `DATA_TRANSFER_JOB_STALE_SECONDS` | **分配新 `batch_id`、覆盖 idem 映射、重新入队**；旧批次随 TTL 清理，不复活 | 202 + **新** `batchId` |

- **包体指纹 `sha256` 从哪来（写死，D3 不得二选一）**：
  - **≤ `DATA_TRANSFER_DIRECT_UPLOAD_THRESHOLD_MB`（默认 100，网关 multipart 落盘）**：网关在落盘后、调用提交 RPC **前**计算，随提交 RPC 下发；客户端不需要传。
  - **>100MB OSS 直传**：网关只收到 `ossKey`、不碰包体，因此提交请求**必须带 `packageSha256`**（客户端上传前算好，算法与 §7.7 离线搬运的 `X-Package-SHA256` 头一致）；缺该字段 = **400 参数缺失**，不进入幂等比对。网关以该值作幂等指纹，**不回源下载重算**（2GB 回源与异步化目标相悖）；包体内容与上报值的一致性由 job 在 `parsing` 阶段读包时复核，不符走 job 终态 409（`data.stage=parsing`）。
  - **同键不同指纹 → 提交层在入队前返回 `success=false code=409`**，网关在 202 **之前**同步回 HTTP 409（§7.4），不产生批次、不写 idem 映射。
- 未带键 → 每次提交都是新批次（会重复导入）——文档要求前端必须带键，`Idempotency-Key` 与批次的对应关系保留 `DATA_TRANSFER_PROGRESS_TTL_SECONDS`（24h）。
- 批次内部天然幂等：source_map 按 D0 A4 upsert、报告按 A5 原地替换、维度按 A2-5 覆盖集，同一包重复合并结果一致。

**取消**

- `POST /batches/{batch_id}/cancel`：网关写 Redis 取消标志 `data_transfer:batch:{batch_id}:cancel` 并返回 202（这是网关**唯一**的 Redis 写操作，其余批次读写一律走快照/登记语义）；**不做强杀**（不中断进行中的单事务）。
- **Redis 写入分层（写死，D1/D3 不得各写一份）**：网关只有上面这一处写取消标志；**`forceStale` 回滚路径的取消标志、回滚成功后的快照 `status=cancelled` + `data.rolledBack=true`、以及 `data_transfer:idem:{key}` 的删除，全部由 task_service 的 `rollback_import` 内部完成**，网关不写（回滚成功后网关只读回执、原样透传 HTTP 状态）。同一个 key 不存在两个写入层。
- task_service job runner 在**每个段边界**检查标志（`queued` 批次在起跑前检查），命中则停止后续段，按既有分段补偿逆序回滚已提交段（`data_transfer_import_service.py:282-291`）。
- 终态 `status=cancelled` + 事件；若回滚本身失败 → 事件 `status=failed` + `code 500` + `compensationErrors`（不掩盖成 cancelled），要求人工介入。
- 已完成的批次取消 → 400（只能走 rollback）。

**回滚（`POST /data-transfer/batches/{batch_id}/rollback`，映射现有 `RollbackImport` RPC，§7.1）与在途 job 互斥**

按批次当前状态写死，实施不得自行放宽：

| 批次状态 | 行为 |
|---|---|
| `queued` / `running` 且未过 stale 阈值 | **409**，`data.batchStatus` = 当前状态，`message` 提示先 `POST /batches/{id}/cancel` 并等终态。**禁止边跑边回滚**：回滚删的是已提交段，job 后续段仍会写库，结果是半回滚 + 数据不一致 |
| `queued` / `running` 且已过 `DATA_TRANSFER_JOB_STALE_SECONDS` | **允许，但必须显式带 `forceStale=true`**（不带仍回 409）。操作者据此声明「确认无在跑实例」；回执 `data.stale=true` + `data.rawStatus`。回滚前**由 task_service 的 `rollback_import` 先写取消标志**（同一 key `data_transfer:batch:{batch_id}:cancel`，不新增 key；**网关不写**，见上「Redis 写入分层」），给真在跑的实例一个段边界退出的机会，再按登记删除。stale 判据与提交层、读侧共用同一个值（§7.3-2）。**该路径把「存疑」当「已死」，风险由操作者显式承担**：若 job 实际仍在跑，后续段可能写回已删段。因此前端/CLI 只在 `GET /batches/{id}` 已显示 `stale=true` 时提示该参数，**不得默认带上** |
| `succeeded` | 允许，走 **`rollback_import`**（`data_transfer_import_service.py:319-349`），**不是** `_compensate`（见下条） |
| `failed` / `cancelled` | 允许但**幂等**：已删段在登记里已不存在，重复调用不再删任何行，回执带 `alreadyRolledBack: true` |

**回滚实现路径（写死，D1/D3 不得另起一条）**：一律调用现有 **`rollback_import(batch_id)`** —— 按批次登记 `data_transfer:batch:{batch_id}` 的各服务 field 取主键删除（顺序 task → evaluation → report，**不是逆序**），全部成功才 `transfer_batch_registry.delete(batch_id)`（`:347`）。

- **不得**用 `_compensate`（`:282-291`）实现事后回滚：它依赖 `execute_import` **内存里**的 `files_tracker` / `inserted_pks`（`:174` 初始化、`:259` 调用），事后回滚拿不到。
- **文件清理必须补上**：`_compensate` 会删已回写的结果/音频文件，而 `rollback_import` 今天不删 —— 登记 payload 只有 `{表名: [主键]}`（`shared/utils/data_transfer_batch.py:30-36`；`record` 调用点 `data_transfer_import_service.py:213`）。本需求把 task 段登记 payload 扩展为 `{tables: {表名: [主键]}, files: [[key, storedPath], ...]}`（与 §7.5 要求扩展 `ownerUserId` 同批改，`record` 增可选 `files` 参数；`evaluation_service` / `report_service` 的调用点不变）；`rollback_import` 在删完各服务段后按 `files` 调 `delete_written_files`（`task_service/infrastructure/transfer/file_transfer.py:160`），失败并入 `compensationErrors`（**不得静默**）。
- **回滚范围**：DB 段（task / evaluation / report）+ 已回写文件。**上传源包对象**（>100MB 直传落 OSS `temp`）不归回滚管，按批次 TTL / 单独清理（§7.7）。

**回滚成功后的状态与幂等映射（写死，不得留给实施者选择）**：以下三件事**全部由 task_service 的 `rollback_import` 在回滚成功分支内完成**，网关不写 Redis（回滚成功后网关只读回执、原样透传 HTTP 状态；见 §7.6「Redis 写入分层」）。

- 回滚成功后进度快照置 `status=cancelled` 并附 `data.rolledBack=true`（与「用户取消的批次」区分）。**不新增 `rolled_back` 状态** —— §7.3 的 `status` 枚举保持 `queued | running | succeeded | failed | cancelled` 不变；这是对 D0 的补充裁定。
- 同时**删除 `data_transfer:idem:{key}` 映射**：快照内存 `idemKey`（提交层写入），回滚成功时按它反查删除。此后同键重投按新批次处理，**不会被幂等表第二行吞成静默 no-op**。
- 双保险：即便 idem 映射删除失败，快照已是 `cancelled` → 同键重投落在幂等表第三行 → 同样开新批次。
- 回滚**失败**的批次保持原状态（如 `succeeded`）并回 500 + `compensationErrors`，**不置 `cancelled`** —— 否则用户会误以为数据已清干净。

- 回滚是同步端点，网关 → task `RollbackImport` 的 deadline 取 **`DATA_TRANSFER_ROLLBACK_TIMEOUT_SECONDS`（默认 1800s）**，**不是段级 600s**（理由见表）；回滚失败 → 500 + `compensationErrors`，要求人工介入（与终态 `failed` 同口径，不掩盖成成功）。回滚中途 504 时服务端可能仍在删：前端不得直接重发，先 `GET /batches/{id}` 复核，再按回滚表（幂等 / 在途 409）决定。
- 已请求 `cancel` 但 job 尚未到段边界、且未过 stale 的批次，状态仍是 `running` → 仍回 409，等终态后再回滚；已过 stale 的按上表第二行带 `forceStale=true` 回滚。

**重试**

- 导出/查询：可自由重试（只读）。
- 导入：重试**必须复用同一 `Idempotency-Key`**——提交层据此把「失败 / 中断的批次重投」判成新批次（§7.6 幂等表），不产生孤儿批次；换键等于声明「这是另一件导入」，按新批次处理（会重复导入，仅用于确实要再导一次的场景）。
- gRPC 层不自动重试写调用（`_grpc_call` 无重试逻辑，`_common.py:10-34`）。
- 补偿失败不进重试队列，必须人工处理（D0 A8 语义）。

**HTTP 超时与异步 job 的关系**

202 之后 HTTP 请求立即结束，反代/Nginx 的 30~60s 请求超时与 job 无关；job 由 task_service 内置 runner（§7.3-2）在独立线程池跑，进度与终态只走事件 + 快照。**谁先超时**：提交 RPC 30s → 前端 HTTP 30s（**仅导入提交类**，在提交之后立刻结束）→ job 3600s（runner 段边界检查）→ 单段 600s（gRPC deadline），四者互不共用调用栈。**新链路不再存在 3600s 同步等待**；3600s 只作为 job 自身的处理上限。同步端点（导出下载 / 预检 / 回滚）不适用 30s：前端与反代超时必须 ≥ 对应 deadline + 余量（回滚按 `DATA_TRANSFER_ROLLBACK_TIMEOUT_SECONDS` = 1800s，前端 ≥ 1860s）。

### 7.7 大文件通道与离线搬运（P6）

**通道选择**

| 包体 | 通道 | 端点 |
|---|---|---|
| ≤ `DATA_TRANSFER_DIRECT_UPLOAD_THRESHOLD_MB`（默认 100） | 网关 multipart 中转，落共享卷 | 各导入端点（现状） |
| > 100MB 且 ≤ 2048MB | OSS 预签名**分片直传**，网关只收 `ossKey` | `POST /data-transfer/uploads` 取签名 → 提交时传 `ossKey` |

- 分片能力已就绪，直接复用：`create_multipart_upload` / `get_part_upload_presigned_url` / `complete_multipart_upload`（`shared/clients/oss_client.py:430-471`，失败清理用 `abort_multipart_upload` `:473-482`）、单对象直传 `get_upload_presigned_url`（`:417-426`），`expires` 默认 3600s。
- 签名 endpoint 走 `OSS_PUBLIC_ENDPOINT`（初始化见 `oss_client.py:129-134`，`get_presigned_url` `:398-415`），与容器内读写 endpoint 解耦。
- 类别用现有 `temp`，key `data_transfer/{batch_id}/{filename}`；**不得新造 category**——多桶模式下未知 category 直接 `ValueError`（`shared/clients/oss_client.py:193-199`），单桶模式自动带 `OSS_KEY_PREFIX`。
- **失败清理**：网关临时文件删除沿用现状（`data_transfer_service.py:54-59,156-160`）；OSS 分片失败必须 `abort_multipart_upload` + 删对象；批次取消/失败的对象按批次 TTL 清理。
- 下载：导出包仍走网关 `FileResponse` 流式（不经 OSS 预签名），内网场景够用。

**离线 / 跨网（无外网）手工拷贝路径**

1. A 侧 `POST /data-transfer/export` 下载 `task_export_<ts>.zip`。**服务端不下发 `.sha256` 旁文件**——导出是单文件 `FileResponse` 流，浏览器/脚本只能拿到 zip 与响应头，校验值取响应头 **`X-Package-SHA256`**；
2. 在**拷贝机上**用该头值生成旁文件（左边两个空格是 `sha256sum` 的格式要求）：

   ```bash
   echo "<X-Package-SHA256 头值>  task_export_<ts>.zip" > task_export_<ts>.zip.sha256
   ```

3. U 盘/跳板机把 zip 与旁文件一起拷到 B 侧；
4. B 侧先本地校验 `sha256sum -c task_export_<ts>.zip.sha256`，再 `POST /data-transfer/import/preview`；
5. 预检回执回显 `data.package = {sha256, sizeBytes}`，与服务端实测不一致 → 400 拒绝；校验不过不得导入（防拷半包）。

`X-Package-SHA256` 响应头为新增产物（D1/D3 实现）；`.sha256` 旁文件由操作员在拷贝机上按头值生成，**服务端不提供下载，也不新增取回端点**。

**错误码透传（D1 前置阻塞项，A7）**：以上所有 `code` 目前都到不了 HTTP——`TaskConfigResponse` 只有 `success/message/data`，servicer `_resp` 丢 `code`，网关代理也丢，最后 `data_transfer_service.py` 把 `http_code` 写死 500（实测：manifest 版本不符返回 HTTP 500 / code 500）。必须与 D1 同批完成：

2. task_service servicer `_resp`、网关 gRPC proxy、`api_gateway/application/services/transfer/data_transfer_service.py` 三处透传；
3. 网关按 `code` 映射 HTTP 状态（400 / 403 / 404 / 409 / 413 / 422 / 500）。

否则本文 §4.2 / §5.4 的失败语义全是假的。

**MCP 登记（裁定 A9-2）**：新增的增量 / 报告导入端点**不进 MCP**——ZIP 与文件二进制上传无法用 MCP 工具表达，且合并导入不可逆；`api_gateway/application/services/mcp/tools_registry.py` 与 `skill_templates/SKILL.md` 均不登记（现有 4 个 data-transfer 端点的登记不变）。

- 现有 MCP 登记了 3 个同步搬运工具（`tools_registry.py:848-857`），`SKILL.md` §5.11 同源。
- **本次新增的全部端点一律不登记**：增量导出 / 增量导入、报告包导出 / 导入、独立报告导入、上传签名、批次状态 / 取消 / 回滚。理由：① ZIP 与文件二进制、预签名直传无法用「JSON body → REST」的工具模型表达；② 合并导入不可逆、冲突需人工判断；③ 202 + 事件的异步语义与 MCP 的一次请求一响应对不上。
- **只读的批次状态查询也不进 MCP**：外部 agent 持 Bearer 走 REST 即可（与 CLI/脚本同路径），进 MCP 只增加一个权限面审核点，不带来新能力。

- CLI / 脚本：与前端同一套 REST + Bearer，不直连 gRPC、不直读 Redis。

## 9. 边界与风险

| 场景 | 处理 |
|------|------|
| B 侧重评后报告未重新生成 | 需手动 `regenerate_report`（现有能力），链路 2/3 导出的都是已生成的最新报告。**B 侧只允许重新评估**（§5.1），重新执行会新增 / 替换 `test_results` 行 |
| B 侧重新执行后再导出增量 | 导出侧逐行校验 `test_result_id` 映射，未映射即 `409 + data.unmappedResultIds[]`，提示改用整包导出或先在 B 侧回退 |
| A、B 维度定义不一致 | 维度定义不迁移，仅快照参考；A 侧按 `(name, 父维度链, task_type_code)` 映射到 A 的 `dimensions.id`，匹配不到的维度行**跳过并计入 `warnings`**，绝不直写 B 的 `dimension_id`。同名不同义的错配无法自动识别（见 §10.2） |
| A、B 用例不一致（链路 1） | 硬校验拒绝（预检提示清单，执行 422 + `data.missingCaseIds`）；A 侧先用 testcase export/import 迁移用例 |

### 10.2 遗留风险（D3~D6 验收需覆盖）

1. **人工纪律兜底**：「B 只允许重新评估」靠导出侧拒绝 + 本节约束；若 B 绕过导出（例如直接整包导出），A 侧反向 id 校验只能兜住"id 不存在"，兜不住"B 用新结果覆盖了同名用例"。
2. **维度命名漂移**：按名称匹配可能错配同名不同义的维度，`warnings` 只能提示；后续建议给 `dimensions` 加稳定业务码（不在本需求范围）。
3. **报告替换并发**：替换期间若有用户正在编辑该报告的 studio 文档或导出作业，会读到"子表刚删完"的中间态；D4 必须复用任务级生成锁。
4. **跨服务部署顺序**：新 RPC 上线窗口内 task_service 调新 RPC 会 `UNIMPLEMENTED`，发布顺序必须是 report / evaluation → task_service → gateway。
5. **性能未实测**：报告 7 表快照 + 原地重建在超大报告上的耗时与事务体量未测，D4 验收需带一次真实库只读体量抽样。
6. **对比 / 基准报告的 `task_id` 非任务 id（D2 登记口径边界）**：主库 2026-10-25 实测 `test_reports` 中 `comparison` 22 条有 21 条 `task_id=0`、1 条 NULL；`secondary_comparison` 17 条有 15 条 `task_id=0`、2 条 NULL；`benchmark` 1 条为 0。`task` 类型 168 条全部正常。按 §5.3 以行内 `task_id` 作 `source_task_id` 登记时，`0` 会落成 `source_task_id=0` 的无效映射（无 WARNING，不静默丢弃但也不可用），NULL 则跳行并 WARNING。D3 按真实源任务取映射会漏掉这些报告，D3 / D6 验收须覆盖（源任务可回落到 `comparison_matrix` 等真实引用）。

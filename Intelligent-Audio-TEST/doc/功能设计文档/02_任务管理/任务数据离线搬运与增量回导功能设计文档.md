# 任务数据离线搬运与增量回导功能设计文档

> 前置设计基线：《任务数据导入导出功能设计文档》（V9.7.10）已覆盖"任务整包导入导出"（16 表 + ZIP + 自动 ID 策略）。
> 本文在其之上新增三项能力：**用例一致性硬校验**、**增量回导（评估+报告合并回原任务）**、**报告独立导入（平台报告 / 独立文件报告 / Agent 分析总结报告三类）**。
> 背景约束：服务 A 与 B 网络环境不通，跨服务器数据只能以"导出 ZIP → 离线搬运 → 导入"的方式传递。

---

## 1. 背景与目标

### 1.1 背景

- A、B 两套服务部署在网络互不可达的环境，任务数据、评估结果、报告只能离线搬运。
- 场景：A 导出任务（含用例结果）→ 离线搬运到 B → B 导入并重新评估、生成新报告 → B 导出增量数据 → 离线搬回 A → A 合并导入。
- 现有 data-transfer 为"任务级整包"语义：导出 16 表整包，导入时 ID 冲突自动重映射为**新副本任务**，无法合并回原任务。

### 1.2 目标

1. 任务整包迁移时增加**用例一致性硬校验**（A 包引用用例必须已存在于 B，否则拒绝导入）。
2. 支持**增量回导**：从 B 只导出"新评估数据 + 新报告"，合并回 A 的**原任务**（而非副本）。
3. 支持**报告独立导入**，区分三类报告：
   - **平台报告**（结构化）：test_reports 7 表数据行，导入后落平台报告体系，替换旧报告。
   - **独立报告**（文件型）：MD / PPT / HTML 等文件，挂到 Report Studio documents（`source_type=uploaded_file`），用户可选是否关联任务。
   - **Agent 分析总结报告**：Agent（DSH）阅读源报告后生成的总结文档，同样落 Report Studio documents（`source_type=agent_summary`）；源报告可以是平台报告，也可以是用户上传的报告文件。

### 1.3 非目标

- 不做跨库实时同步（网络不通，离线搬运为前提）。
- 不迁移用户/权限、设备/API/用例定义等基础配置（沿用现有 data-transfer 边界；用例一致性校验只是"要求目标库已有"，不代迁移）。
- 不做报告文件在线转换（MD→PPT 等），仅按原格式存储与展示。
- 不迁移 Agent 的 DSH 会话与对话历史（会话属于 B 侧本地运行时，A 侧无法续接）。

---

## 2. 术语

| 术语 | 解释 |
|------|------|
| 源服务 A | 任务/用例结果的原始持有方，也是增量回导的最终落库方 |
| 目标服务 B | 导入 A 的任务包，执行重新评估与报告生成 |
| 用例一致性 | A 包内引用的 test_case_ids 集合 ⊆ B 已存在用例 id 集合 |
| 增量回导包 | 从 B 导出的"新评估数据 + 新报告"，不含任务/结果/文件本体 |
| source_map | B 侧持久化的"源 ID → 本地 ID"映射（task_id / test_result_id 等） |
| 平台报告 | test_reports 及其 6 张子表的结构化数据（7 表） |
| 独立报告 | MD / PPT / HTML 等文件形式的报告文档，挂 Report Studio documents（`source_type=uploaded_file`，无平台报告行） |
| Agent 分析总结报告 | Agent（DSH）阅读源报告后生成的 Markdown 总结文档，落 Report Studio documents（`source_type=agent_summary`） |
| 源报告 / 源文档 | Agent 总结所依据的报告：平台报告（走 `report_id`）或用户上传报告（走 `parent_doc_id`） |

## 3. 三条链路总览

```
链路 1 · 任务整包迁移（现有 + 硬校验）
  A 导出任务(ZIP) →【用例一致性硬校验】→ B 导入任务 → B 重评 + 生成报告

链路 2 · 增量回导（新增）
  B 子集导出(新评估 + 新报告 7 表 + source_map) → A 合并导入 → 匹配原任务 → 最新覆盖

链路 3 · 报告独立导入（新增）
  3a 平台报告：B 导出报告 7 表数据包 → A 导入 → 匹配原任务 → 替换旧报告
  3b 独立报告：外部 MD/PPT/HTML 文件 → A 导入 → 挂 Report Studio documents（可选关联任务）
  3c Agent 分析总结：B 导出 Studio 文档 + 版本 + 图表规格 + 血缘 → A 导入 → 先落源报告（3a/3b）再挂总结文档
      依赖顺序：3a / 3b → 3c（源缺失时降级为孤儿文档，不阻塞）
```

## 4. 链路 1：任务整包迁移 + 用例一致性硬校验

### 4.1 现有能力（沿用）

- A 导出：`POST /api/v1/data-transfer/export`（16 表 ZIP，含任务/结果/维度/报告 7 表/文件）。
- B 导入：`POST /api/v1/data-transfer/import`（预检 + 自动 ID 策略 + 5 段提交 + 补偿回滚）。

### 4.2 新增：用例一致性硬校验

| 项 | 现有（warning） | 新增（硬校验） |
|----|----------------|----------------|
| 触发点 | [preview_import](file:///d:\00_code\V9.7.31\Intelligent-Audio-TEST\task_service\application\task\data_transfer_import_service.py#L77-L126) 的 `_build_warnings` | 预检 + 执行导入双阶段 |
| 缺失用例 | 仅 warning："目标库缺少 N 个测试用例…无法重新执行" | **拒绝导入**，返回缺失用例清单 |
| 配置开关 | — | `DATA_TRANSFER_CASE_CONSISTENCY_REQUIRED`（默认 true） |
| 校验规则 | 引用集合差集 | `refs['test_case_ids'] - existing_case_ids` 非空 → 400 拒绝 |

**校验逻辑（伪代码）**：

```python
refs = collect_external_references(rows_by_table)      # 复用现有
existing_case_ids = transfer_repository.fetch_existing_case_ids(refs['test_case_ids'])
missing = [cid for cid in refs['test_case_ids'] if str(cid) not in existing_case_ids]
if missing and Config.DATA_TRANSFER_CASE_CONSISTENCY_REQUIRED:
    raise ValueError(f'目标库缺少 {len(missing)} 个测试用例，拒绝导入: {missing[:10]}')
```

**配套前置**：A 侧先用现有 testcase export/import（`POST /testcases/export` / `POST /testcases/import`，权限 `testcase:import_export`）把用例迁移到 B，B 库用例齐备后再走任务导入。

**联动说明**：升级为硬校验后，纯"历史结果查看/备份恢复"场景（不重新执行）也会被卡住。因此开关默认 true、仅任务迁移场景强制；如需宽松可关闭。

## 5. 链路 2：增量回导（B → A 合并新评估 + 新报告）

### 5.1 场景

B 上任务已重评、新报告已生成（报告 7 表为 B 侧最新），需要把"新评估数据 + 新报告"离线搬回 A，**合并到 A 的原任务**（不是产生副本）。

### 5.2 子集导出（B 侧）

**接口**：`POST /api/v1/data-transfer/export-incremental`

```jsonc
// 请求
{ "taskIds": [25], "include": ["dimensions", "reports"] }  // reports 含 7 表
```

**导出包结构**（复用 data-transfer ZIP 规范）：

```
incremental_<ts>.zip
├── manifest.json          # version: "1.1" + 源服务 B + source_task_id(原始 A task_id)
├── db/
│   ├── test_result_dimensions.json   # 最新覆盖后的维度评分（引用 A 原始 test_result_id）
│   └── 报告 7 表.json                 # test_reports + 6 子表（引用 A 原始 task_id）
└── meta/
    └── dimensions.json    # B 侧维度定义快照（参考）
```

**关键：ID 翻译**——导出时把 B 库 id 通过 source_map 翻译回 **A 原始 id** 再写入包：

| 包内字段 | B 库值 | 包内写入值 |
|---------|--------|-----------|
| test_result_dimensions.test_result_id | 205（B id） | 101（A 原始 id） |
| test_reports.task_id | 25（B id） | 12（A 原始 task_id） |

### 5.3 source_map 持久化（B 侧新增）

**背景**：现有 `strip_conflicting_ids` 导入时丢弃冲突行的原始 id，B 无法反查"本地 id 对应 A 的哪个原始 id"。增量回导依赖此映射，必须持久化。

**存储**：新增表 `data_transfer_source_maps`（归属 task_service）：

| 列 | 说明 |
|----|------|
| id | 自增主键 |
| source_server | 源服务标识（manifest.serverInfo.source） |
| source_task_id | A 原始 task_id |
| entity_type | tasks / test_results / test_result_dimensions / test_reports |
| source_id | A 原始 id |
| local_id | B 本地 id |
| created_at / updated_at | 时间戳 |

**登记时机**：B 导入任务整包（链路 1）时，对发生重映射的 4 类主键逐条登记；未冲突（source_id == local_id）可不登记（等价映射）。

**生命周期**：跨批次长期保留（不做 7 天 TTL 清理），供后续任意时点增量回导使用。

### 5.4 合并导入（A 侧）

**接口**：`POST /api/v1/data-transfer/import-incremental`（multipart ZIP，权限复用 `task:import`）

**合并语义**：

| 数据 | 合并策略 |
|------|----------|
| test_result_dimensions | 按 A 原始 test_result_id 匹配 → **最新覆盖 UPDATE** |
| 报告 7 表 | 匹配原任务 → **先删旧报告（级联 6 子表）再写入新报告**（regenerate 语义） |

**匹配键**：manifest 中 `source_task_id` → A 库 `test_tasks.id` 定位原任务。

**ID 冲突处理**：增量包内已是 A 原始 id，A 侧**不做重映射**（包内 id 与 A 库一致），纯 UPDATE / 删除重建。

**回滚**：沿用分段补偿体系（[data_transfer_batch.py](file:///d:\00_code\V9.7.31\Intelligent-Audio-TEST\shared\utils\data_transfer_batch.py)）。回滚策略与整包导入不同——先记录被覆盖行的**旧值快照**（维度评分旧行 + 旧报告），失败时按快照恢复。批次登记保留 7 天，补偿失败显式报错要求人工介入。

### 5.5 权限与校验

- 权限：`task:export`（导出）/ `task:import`（导入），复用现有。
- 用例一致性：增量回导包只含评估+报告，不含 task_case_relations，不触发链路 1 的用例硬校验。

## 6. 链路 3：报告导入（3a 平台报告 / 3b 独立报告 / 3c Agent 总结）

### 6.1 平台报告（结构化，7 表数据包）

**接口**：`POST /api/v1/data-transfer/report/import`（multipart ZIP）

- 包内：`db/test_reports.json` + 6 张子表 JSON + manifest（含 source_task_id）。
- 合并语义：按 `source_task_id` 匹配 A 原任务 → 先删旧报告（级联子表）再写入新报告（regenerate 语义，同 5.4）。
- 不携带维度评分（评估数据已由链路 2 处理，或无需同步）。
- 回滚：同 5.4（旧报告快照恢复）。

**导出接口**：`POST /api/v1/data-transfer/report/export`（按 taskId / reportIds 导出报告 7 表数据包）。

### 6.2 独立报告（文件型：MD / PPT / HTML）

**落点**：Report Studio documents 体系（[report_studio.py](file:///d:\00_code\V9.7.31\Intelligent-Audio-TEST\report_service\domain\entities\report_studio.py#L14-L29)）——已有版本快照、chart_refs、样式偏好、导出作业能力，MD 渲染成熟。

**接口**：`POST /api/v1/report-studio/import`（multipart 文件 + 元数据）

```jsonc
// multipart/form-data
file: report.md / report.pptx / report.html
title: "XX 算法对比报告"
task_id: 12            // 可选：是否关联任务（用户自选）
format: "md" | "ppt" | "html"
```

**导入行为**：

1. 文件落 OSS（storage 抽象，category 如 `report_docs`）。
2. 创建 Report Studio document（`source_type='uploaded_file'`、`report_id` 为空 / `title` / `chart_refs` 空 / `markdown_content` 按文件格式：
   - md → 直接存 markdown_content；
   - html / ppt → 存文件路径引用 + 元数据，展示走文件预览）。
3. `task_id` 可选：为空则不关联任务（独立文档库）；有值则写入关联，任务详情/报告列表可见。

**权限**：`report:studio:create`（新建）+ `report:read`（读取），沿用现有权限点。

**与平台报告的关系**：独立报告不进 test_reports 7 表，不参与报告统计/对比矩阵；仅作为文档形态存在。

### 6.3 Agent 分析总结报告（数据级，复用 Report Studio documents）

**场景**：报告可以由 Agent（DSH）阅读源报告后生成总结/分析文档。源报告有两类：

- **平台报告**：Agent 基于 test_reports 数据生成总结；
- **用户上传的报告**：Agent 阅读 3b 导入的 MD/PPT/HTML 文档后生成分析总结。

**落点**：**复用** `report_studio_documents` 体系（[report_studio_models.py](file:///d:\00_code\V9.7.31\Intelligent-Audio-TEST\report_service\infrastructure\persistence\models\report_studio_models.py#L22-L40)）——版本快照、chart_specs、导出作业能力直接复用，**不新建表**。

**数据包**（与 3a / 3b 同一个 ZIP，`manifest.entities` 声明所含实体）：

```
db/
├── test_reports.json + 6 子表.json              # 3a（源为平台报告时）
├── report_studio_documents.json                 # 3b 上传文档 + 3c Agent 总结
├── report_studio_document_versions.json         # 版本快照
└── report_studio_chart_specs.json               # 图表规格
```

**血缘字段与 ID 翻译**：

| 文档类型 | source_type | 血缘字段 | 翻译方式 |
|---|---|---|---|
| 平台报告文档 | `platform_report` | `report_id` | 走 3a 报告 source_map |
| 用户上传文档 | `uploaded_file` | `report_id` 为空 | 无需翻译 |
| Agent 总结（源=平台报告） | `agent_summary` | `report_id` | 走 3a 报告 source_map |
| Agent 总结（源=上传文档） | `agent_summary` | `parent_doc_id` | 走文档 source_map（doc_id） |

**关键规则**：

1. **`agent_session_id` 不迁移**：DSH 会话属于 B 侧本地运行时，A 上无法续接对话 → 导入时置空，文档降级为普通可编辑文档（Markdown 正文、版本链、图表规格保留）。
2. **拓扑序导入**：同一包内先落源报告（3a）与上传文档（3b），再落 Agent 总结（3c）。
3. **源缺失降级**：源文档未随包搬运时，`parent_doc_id` 置空并在导入回执 `warnings` 中列出（孤儿文档），**不阻塞导入**。
4. **版本策略**：默认**全带**（document + 全部 versions + chart_specs），保证 A 侧版本链可回滚；需要小包时用导出参数 `docVersionScope=latest` 只带当前版本，历史版本留在 B。
5. **图表降级**：源为上传文档时 `report_studio_chart_specs.report_id` 置空，A 侧打开文档时图表提示「需重新绑定报告」，不静默报错、不丢文档正文。

**权限**：导出 `task:export`；导入 `task:import`（与报告数据包一致，不额外开放 `report:studio:*` 给搬运链路）。

### 6.4 数据模型变更（复用，不新建表）

| 表 | 变更 | 说明 |
|---|---|---|
| `report_studio_documents` | `ADD source_type VARCHAR(20) NOT NULL DEFAULT 'platform_report'` | 取值 `platform_report` / `uploaded_file` / `agent_summary` |
| `report_studio_documents` | `report_id` 改为**可空** | 上传文档、以及「源为上传文档的 Agent 总结」没有平台报告行 |
| `report_studio_documents` | `ADD parent_doc_id VARCHAR(36) NULL` + 索引 `idx_rs_doc_parent` | Agent 总结 → 源文档（仅源为上传文档时使用） |
| `report_studio_chart_specs` | `report_id` 改为**可空** | 同上，图表等待重新绑定 |

**迁移脚本**：`scripts/migrations/202610/alter_report_studio_sources.py`

- 存量行 `source_type` 落默认值 `platform_report`——现有文档全部挂在平台报告上，语义等价，无需回填。
- `report_id` 放开非空只放宽约束，不改数据；现有“按 report_id 取文档”的查询语义不变。
- 新增索引：`idx_rs_doc_source_type`、`idx_rs_doc_parent`。

**兼容性**：`report_id IS NULL` 的行不得进入依赖平台报告的既有查询（报告详情页文档列表等），需在这些查询上补 `source_type='platform_report'` 过滤；这是本次改动唯一的存量代码触碰点。

## 9. 边界与风险

| 场景 | 处理 |
|------|------|
| B 侧重评后报告未重新生成 | 需手动 `regenerate_report`（现有能力），链路 2/3 导出的都是已生成的最新报告 |
| A、B 维度定义不一致 | 维度定义不迁移，仅快照参考；B 重评缺维度自动跳过（现有 UC-04 语义）；A 展示以 A 侧维度为准 |
| A、B 用例不一致（链路 1） | 硬校验拒绝；A 侧先用 testcase export/import 迁移用例 |
| 增量导入中途失败 | 旧值快照恢复（维度旧行 + 旧报告），批次登记 7 天，补偿失败人工介入 |
| source_map 缺失 | B 从未整包导入过 A 的数据 → 无法翻译回源 id → 增量导出报错提示先走链路 1 |

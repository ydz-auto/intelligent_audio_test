# 任务数据导入导出功能设计文档

## 1. 用户场景与流程

### 1.1 目标用户

- 测试工程师
- 系统管理员
- 质量管理人员

### 1.2 适用场景

| 场景 | 说明 |
|------|------|
| 多服务器迁移 | 系统在多台服务器部署，需将A服务器的任务数据迁移到B服务器 |
| 数据备份归档 | 将已完成任务的数据打包导出，作为离线备份 |
| 跨环境复现 | 在测试环境复现生产环境的任务执行结果，用于问题排查 |
| 数据同步 | 新部署的服务器需要导入历史任务数据 |
| 导入后重新评估 | 导入任务后基于已有执行结果重新评估（更换评估维度或评估API） |
| 导入后重新执行 | 导入任务后基于已有配置重新执行测试（更换被测设备或API） |

### 1.3 Use-Case

#### UC-01: 导出任务数据

```
角色: 测试工程师
前置条件: 用户已登录系统，任务列表页存在已完成的任务

主流程:
1. 用户在任务列表页选中一个或多个任务
2. 用户点击"导出"按钮
3. 系统弹出导出选项弹窗，展示:
   - 选中任务的基本信息（任务名称、类型、状态、结果数）
   - 导出选项:
     a. 是否包含参考参数文件（默认勾选）
     b. 是否包含音频文件（默认不勾选，提示体积较大）
4. 用户确认导出选项后点击"开始导出"
5. 系统在后台执行导出:
   a. 查询 DB 中与选中任务关联的所有数据（15张表）
   b. 收集磁盘上的结果文件、参考参数文件（如勾选）
   c. 打包为 ZIP 文件
6. 浏览器开始下载 ZIP 文件: task_export_<timestamp>.zip

后置条件: 用户获得包含完整任务数据的 ZIP 文件
```

#### UC-02: 导入任务数据

```
角色: 测试工程师
前置条件: 用户已登录系统，拥有待导入的 ZIP 文件

主流程:
1. 用户在任务列表页点击"导入任务"按钮
2. 系统弹出导入弹窗
3. 用户选择 ZIP 文件并上传
4. 系统执行预检:
   a. 解析 ZIP 中的 manifest.json
   b. 展示预检结果:
      - 源服务器信息、导出时间
      - 将导入的任务列表（名称、类型、状态、结果数）
      - 将导入的数据统计（结果数、维度评分数、报告数）
      - 文件统计（文件数、总大小）
      - ID 冲突检测结果（系统自动判断是否需要重映射）
5. 用户确认后点击"开始导入"
6. 系统自动判断 ID 策略:
   - 如果原 task_id 在目标 DB 中不存在 → 保持原 ID
   - 如果原 task_id 已存在 → 自动重映射为新的自增 ID
   无需用户选择，全自动处理
7. 系统在后台执行导入:
   a. 解析所有 DB 数据 JSON
   b. 按 ID 映射处理外键引用
   c. 按依赖顺序写入 DB（15张表）
   d. 解压磁盘文件到 STATIC_BASE_PATH 对应目录
   e. 更新文件路径字段
8. 导入过程中展示进度条（百分比 + 当前步骤）
9. 导入完成后展示结果统计，自动刷新任务列表
10. 导入的任务状态为"completed"，用户可:
    - 查看任务详情和报告
    - 对任务执行"重新评估"操作
    - 对任务执行"重新执行"操作

后置条件: 目标服务器新增导入的任务，可正常查看详情、报告，并支持重新评估和重新执行
```

#### UC-03: 导入失败回滚

```
角色: 测试工程师
前置条件: 导入过程中发生错误

主流程:
1. 系统在导入某一步骤时检测到错误
2. 系统自动回滚 DB 事务，撤销所有已写入的数据
3. 系统清理已解压的磁盘文件
4. 系统向用户展示错误信息:
   - 失败步骤
   - 错误原因
   - 已回滚的说明
5. 用户可修正后重新尝试导入

后置条件: 目标服务器数据状态恢复到导入前
```

#### UC-04: 导入后重新评估

```
角色: 测试工程师
前置条件: 任务已通过导入功能导入到目标服务器，状态为"completed"

主流程:
1. 用户在任务列表页选中导入的任务
2. 用户点击"重新评估"按钮（复用现有重新评估功能）
3. 系统基于导入的执行结果（TestResult）和参考参数，调用目标服务器的评估维度和评估API
4. 评估完成后更新 TestResultDimension 表
5. 用户可查看更新后的评估报告

说明:
- 导入的 TestResult.result_data（含算法执行结果）和 result_data_path（大字段文件）已正确迁移
- 评估时读取的是目标服务器的 Dimension 定义和评估API配置
- 如果目标服务器缺少某些评估维度，对应维度评分会被跳过
```

#### UC-05: 导入后重新执行

```
角色: 测试工程师
前置条件: 任务已通过导入功能导入到目标服务器，状态为"completed"

主流程:
1. 用户在任务列表页选中导入的任务
2. 用户点击"重新执行"按钮（复用现有任务执行功能）
3. 系统基于导入的任务配置（Task.config、Task.algorithm_params）和关联的用例、设备、API
4. 在目标服务器上重新执行测试
5. 执行完成后生成新的 TestResult 和 TestResultDimension
6. 用户可查看新的执行结果和报告

说明:
- 导入的任务配置完整保留，可直接用于重新执行
- 重新执行时使用目标服务器上的设备（需确保设备序列号匹配）和API配置
- 新结果会追加到同一任务下，旧结果保留
```

## 2. 功能概述

### 2.1 功能描述

任务数据导入导出功能允许用户将平台上的任务数据（包括 DB 记录和磁盘上的结果文件）打包导出为 ZIP 文件，并在另一台服务器上导入恢复。该功能面向多服务器部署场景，支持跨服务器手动迁移完整任务数据。

### 2.2 功能边界

| 范围 | 说明 |
|------|------|
| 包含 | 任务主表、任务关联表、测试结果、维度评分、报告全系列、结果数据文件、参考参数文件 |
| 不包含 | 音频文件（可选导出）、eval_server 的 eval_tasks 表、设备/API/用例/维度定义等基础配置数据、系统日志 |
| 不包含 | 用户与权限数据（安全考虑） |

### 2.3 术语定义

| 术语 | 解释 |
|------|------|
| 导出包 | 包含 DB 数据 JSON + 磁盘文件的 ZIP 压缩包 |
| manifest.json | 导出包内的清单文件，记录版本、任务列表、统计信息 |
| ID 自动判断 | 导入时系统自动检测原 ID 是否冲突：不冲突则保持原 ID，冲突则重映射为新自增 ID，无需用户选择 |
| ID 重映射 | 导入时为数据分配新 ID，维护 old_id→new_id 映射表，避免跨服务器 ID 冲突 |
| 预检 | 导入前解析 ZIP 并展示将导入的数据量和冲突检测结果 |

## 3. 需求分析

### 3.1 功能需求

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| REQ-001 | 支持选择一个或多个任务导出为 ZIP 文件 | 高 |
| REQ-002 | 导出包包含任务关联的全部 DB 数据（15张表） | 高 |
| REQ-003 | 导出包包含磁盘上的结果数据文件（result_data.json） | 高 |
| REQ-004 | 导出包可选包含参考参数文件 | 中 |
| REQ-005 | 导出包可选包含音频文件 | 低 |
| REQ-006 | 导出包包含 manifest.json 清单文件 | 高 |
| REQ-007 | 导入前支持预检，展示数据量和冲突检测 | 高 |
| REQ-008 | 导入时自动判断 ID 冲突并处理（无需用户选择策略） | 高 |
| REQ-009 | 导入过程异步执行，展示进度 | 高 |
| REQ-010 | 导入失败时事务回滚，撤销已写入数据 | 高 |
| REQ-011 | 导入完成后自动更新磁盘文件路径 | 高 |
| REQ-012 | 导入的任务状态为 completed，支持重新评估 | 高 |
| REQ-013 | 导入的任务支持重新执行测试 | 高 |

### 3.2 非功能需求

| 需求编号 | 需求描述 |
|---------|---------|
| NFR-001 | 导出大任务（100+ 结果）时不超过 30 秒 |
| NFR-002 | ZIP 文件流式生成，避免内存溢出 |
| NFR-003 | 导入过程单事务包裹，保证数据一致性 |
| NFR-004 | 导出包使用 JSON 格式存储 DB 数据，跨数据库版本兼容 |
| NFR-005 | 文件路径使用相对路径，适配不同服务器的绝对路径 |

### 4.5 导出流程

```
1. 接收 task_ids + 选项
2. 查询 DB：
   a. Task 主表 → WHERE id IN task_ids AND deleted = false
   b. 关联表 → WHERE task_id IN task_ids
   c. TestResult → WHERE task_id IN task_ids
   d. TestResultDimension → WHERE test_result_id IN (上一步结果ID集合)
   e. Report 系列 → WHERE task_id IN task_ids
3. 序列化每张表为 JSON 数组 → 写入 ZIP 的 db/ 目录
4. 收集磁盘文件：
   a. 遍历 TestResult.result_data_path → 拼接 STATIC_BASE_PATH → 写入 ZIP 的 files/case_results/（相对路径）
   b. （如勾选）遍历 TestCase.config.rounds[].referenceParamsPath → 写入 ZIP 的 files/ref_params/
5. 查询 Dimension 表 → 写入 meta/dimensions.json（快照）
6. 生成 manifest.json → 写入 ZIP
7. 返回 ZIP 文件流
```

### 4.6 导入流程

```
1. 预检阶段:
   a. 解析 ZIP → 读取 manifest.json
   b. 读取各 db/*.json 文件
   c. 检测 ID 冲突: 查询目标 DB 中是否已存在相同 task_id
   d. 返回预检结果（含冲突信息，供用户参考）

2. 执行导入:
   a. 解析所有 db/*.json 到内存
   b. 自动判断 ID 策略:
      - 查询目标 DB 中是否已存在相同 task_id
      - 不存在 → 保持原 ID 直接插入
      - 已存在 → 该任务自动重映射: 先不设置 id，让 DB 自增分配新 ID
      - 记录 old_id→new_id 映射表（仅对冲突的记录）
   c. 按依赖顺序逐表写入 DB:
      Task → TaskCase/Device/API/Tag/Merge → TestResult → TestResultDimension → Report系列
   d. 外键引用转换（通过映射表，无冲突的保持原值）:
      - TaskCase.task_id → id_mappings["tasks"].get(old_task_id, old_task_id)
      - TestResult.task_id → id_mappings["tasks"].get(old_task_id, old_task_id)
      - TestResultDimension.test_result_id → id_mappings["test_results"].get(old_id, old_id)
      - Report.task_id → id_mappings["tasks"].get(old_task_id, old_task_id)
      - Report子表.report_id → id_mappings["test_reports"].get(old_id, old_id)
      - TaskMergeRelation.merged_task_id / source_task_id → id_mappings["tasks"].get(old_id, old_id)
   e. 解压磁盘文件到 STATIC_BASE_PATH 对应目录
      - 无 ID 冲突 → 直接解压到原始相对路径
      - 有 ID 冲突 → 解压到新 task_id 对应的路径
   f. 更新文件路径字段:
      - 有冲突的 TestResult.result_data_path → 根据新 task_id 重新生成相对路径
   g. 通过 SocketIO 推送进度
3. 返回导入统计（含重映射记录）
```

### 4.7 ID 自动判断策略

导入时无需用户选择策略，系统自动逐条检测：

```python
# 伪代码
existing_task_ids = set(query_existing_task_ids())
id_mappings = {"tasks": {}, "test_results": {}, "test_result_dimensions": {}, "test_reports": {}}

for task_row in db_data["task"]:
    old_id = task_row["id"]
    if old_id in existing_task_ids:
        # 冲突: 移除 id 字段，让 DB 自增分配新 ID
        task_row.pop("id")
        db.session.add(Task(**task_row))
        db.session.flush()  # 获取新 id
        new_id = task_obj.id
        id_mappings["tasks"][old_id] = new_id
    else:
        # 无冲突: 保持原 ID 插入
        db.session.add(Task(**task_row))
        id_mappings["tasks"][old_id] = old_id  # 映射到自身
```

## 6. 边界处理

| 场景 | 处理方式 |
|------|---------|
| 音频文件 | 默认不导出（体积大），勾选时导出 |
| eval_server 数据 | 不在导出范围内（评估结果已通过 TestResultDimension 存入主库） |
| 维度定义 | 导出时附带快照（meta/dimensions.json），导入时仅作参考展示，不自动写入 |
| ID 冲突 | 系统自动判断：原 ID 不冲突则保持，冲突则自动重映射为新自增 ID，无需用户选择 |
| 导入后重新评估 | 导入的任务状态为 completed，直接复用现有重新评估功能，读取目标服务器的维度定义和评估 API |
| 导入后重新执行 | 导入的任务配置完整，直接复用现有执行功能，使用目标服务器的设备和 API |
| 导入失败 | 事务回滚 DB，清理已解压文件 |
| 磁盘文件路径 | 导出存相对路径，导入时拼接目标 `STATIC_BASE_PATH`；ID 重映射时自动更新路径中的 task_id |
| 大任务导出 | ZIP 写入临时文件后返回，避免内存溢出 |
| 临时文件清理 | 导出临时 ZIP 文件定期清理（超过 1 小时） |

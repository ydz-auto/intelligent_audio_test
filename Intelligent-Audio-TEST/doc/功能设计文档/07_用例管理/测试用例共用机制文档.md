# 测试用例共用机制文档

## 1. 概述

测试用例采用 **纯数据无类型架构**：用例是纯数据载体（`config` 结构性配置 + `algorithm_params` 算法参数 + `reference_params` 参考参数），不包含任何执行方式信息，也不区分测试类型。执行方式由任务创建时选择的被测设备类型决定（物理设备 / HTTP API / WebSocket API）。这种设计使同一份用例数据可以被不同执行链路消费，配合复制机制实现快速派生与复用。

## 2. 核心设计理念

### 2.1 纯数据无类型架构

- **用例不区分类型**：用例没有 `test_type` 字段，不区分 api 用例与 e2e 用例。用例只有一份结构，同一份用例可被物理设备、HTTP API、WebSocket API 三种执行链路消费。
- **用例是纯数据**：`config`、`algorithm_params`、`reference_params` 只描述"测什么"（音频序列、算法参数、评估维度），不描述"怎么执行"。执行方式由任务创建时选择的被测设备类型决定（见 4.2 节）。
- **执行路由按设备类型**：被测设备 `device_type` 决定执行方式——`physical`→E2EExecutor、`http_api`→APISessionExecutor、`websocket_api`→RealtimeSessionExecutor。一个任务内可混跑不同类型设备。
- **分组管理**：测试用例必须选择所属分组，分组来源于 `TestCaseGroup` 模型，支持在分组选择时动态新增。
- **标签管理**：用例可挂多个标签，支持按标签筛选、批量增删标签与重命名标签。

### 2.2 用例结构与轮次配置

用例结构性配置集中在 `config`（JSON 列）中，按**轮次（rounds）**组织：

- **rounds**：多轮配置列表，每轮包含：
  - `round_number`：轮次序号（1 起始）
  - `audios`：本轮音频配置（`audio_id`、`audio_name`、`spl`、`playback_device_id`、`play_order`），其中 `playback_device_id` 仅 E2E 执行使用，API 类执行忽略
  - `background_noise`：轮次级背景噪声（`audio_id`、`spl`、`device_ids`、`loop`）
  - `evaluation`：单轮评估配置（`enabled`、`dimensions[]`）
  - `is_interruption` / `stop_intent`：打断标记轮 / 停止指令标记
  - `interferers`：干扰人列表（`audio_id`、`spl`、`startDelay`、`loop`）
- **dimensions**：顶层整体评估维度（数组，跨轮次聚合）
- **background_noise**：用例级全局背景噪声（跨所有轮次）
- **多干声音频**：同轮多个音频按 `play_order` 控制播放顺序；执行时音频 ASR 文本按播放顺序拼接后用于指标计算
- **背景噪声**：与干声同时播放，可在独立的噪声播放设备上播放（E2E 执行）

### 2.3 评估维度体系

评估维度按作用范围分为两层，**互不合并**（详见《多轮评估维度隔离与报告聚合设计文档》）：

| 层级 | 存储位置 | 触发条件 |
|------|---------|---------|
| 单轮评估维度 | `config.rounds[n].evaluation.dimensions` | 该轮 `enabled != False` 且 `dimensions` 非空 |
| 整体评估维度 | `config.dimensions`（数组） | 顶层数组非空 |

维度条目为 `{ id, name, weight, threshold }` 结构，通过"批量设置评价维度"功能可按轮次范围（所有轮次 / 指定轮次 / 逐轮设置）批量写入，`-1` 代表"最后一轮"。

## 3. 数据库模型设计

### 3.1 核心模型结构

```
+----------------------+
|      TestCase        |
+----------------------+
| id                   |
| name                 |
| description          |
| config (JSON)        | <-- 结构性配置：rounds / dimensions / background_noise 等
| algorithm_params(JSON)| <-- 算法参数 [{round_number, params:[{field_code, field_value}]}]
| reference_params(JSON)| <-- 参考参数路径 [{round_number, reference_params_path}]，内容存文件
| group_id (FK)        | <-- 所属分组（TestCaseGroup）
| algorithm_type       | <-- 算法类型（translation / asr / speaker_recognition / tts 等）
| created_at           |
| updated_at           |
| deleted              | <-- 逻辑删除
+----------------------+

+----------------------+
|   TestCaseGroup      |
+----------------------+
| id                   |
| name (unique)        |
| description          |
| algorithm_type       | <-- 关联算法类型
| created_at           |
| updated_at           |
+----------------------+
```

> 注意：TestCase 没有 `test_type` 列。用例不区分类型，执行方式由被测设备类型决定。

### 3.2 config 字段 JSON 结构示例

```json
{
  "rounds": [
    {
      "round_number": 1,
      "audios": [
        { "audio_id": 101, "audio_name": "唤醒词.wav", "spl": 70.0,
          "playback_device_id": "dev-5", "play_order": 1 }
      ],
      "background_noise": { "audio_id": 10, "spl": 65.0, "device_ids": ["dev-9"], "loop": true },
      "evaluation": { "enabled": true, "dimensions": [ { "id": 2, "name": "唤醒率", "weight": 50, "threshold": 60 } ] },
      "interferers": []
    }
  ],
  "dimensions": [ { "id": 3, "name": "响应延迟", "weight": 40, "threshold": 60 } ],
  "background_noise": { "audio_id": 10, "spl": 65.0 },
  "algorithm_type": "asr"
}
```

> 算法参数与参考参数不存放在 `config` 中，分别存于 `algorithm_params`、`reference_params` 独立列（按轮次分组）。

### 3.3 关键配置关系

1. **测试用例与音频配置**：
   - 音频按轮组织在 `config.rounds[n].audios` 数组中
   - E2E 执行时每个音频需指定 `playback_device_id`（必填）、可配置 `spl` 与 `play_order`
   - API 类执行忽略 `playback_device_id`，`spl` 仍然生效（经 SPL 映射换算混音增益）

2. **测试用例与评估维度关联**：
   - 单轮评估维度写入 `config.rounds[n].evaluation.dimensions`，仅对该轮结果生效
   - 整体评估维度写入顶层 `config.dimensions`（数组，非按类型区分的子对象），跨轮次聚合
   - 两层维度通过"批量设置评价维度"功能批量配置（见《批量设置评价维度功能设计文档》）

3. **测试用例与背景噪音关联**：
   - 用例级：`config.background_noise`，跨所有轮次生效
   - 轮次级：`config.rounds[n].background_noise`，仅该轮生效

4. **测试用例与分组、标签关联**：
   - 通过 `group_id` 外键关联 `TestCaseGroup` 分组
   - 通过标签多对多关系分类，支持按标签筛选与批量操作

## 4. 测试用例共用流程

### 4.1 测试用例创建

1. **基本信息填写**：
   - 填写测试用例名称、描述
   - **分组选择**：从下拉列表中选择所属分组，分组数据来源于 `TestCaseGroup` 模型；支持直接输入新分组名称动态创建
   - 配置通用属性，如用例级背景噪声

2. **轮次与音频配置**（分步编辑模态窗）：
   - 按轮次组织音频：每轮添加音频并配置 `audio_id`、`spl`、`play_order`
   - 音频可指定 `playback_device_id`（E2E 执行时使用，API 类执行时忽略）
   - 配置轮次级/用例级背景噪声与干扰人

3. **评估维度配置**：
   - 单轮维度：在各轮"单轮评估"编辑器中选择维度并设置权重、阈值
   - 整体维度：在"整体评估"编辑器中配置 `config.dimensions`

4. **算法参数与参考参数**：
   - 算法参数按轮配置字段值（`field_code` / `field_value`），写入 `algorithm_params`
   - 参考参数按轮配置文件路径，写入 `reference_params`（内容存文件，通过 ref-params 接口读写）

### 4.2 测试用例执行

1. **任务创建**：
   - 创建测试任务，选择要执行的测试用例与被测设备
   - 为每个 TaskCase 关联一个被测设备，被测设备类型决定执行方式

2. **执行路由（按被测设备类型，而非用例类型）**：

   | 被测设备类型 | 执行器 | 音频处理 | 调用模式 |
   |---|---|---|---|
   | 物理设备（`physical`） | E2EExecutor | 物理播放 + PCM 抓取 | — |
   | HTTP API（`http_api`） | APISessionExecutor | 混音 → 整文件 / chunk | 非实时 / 流式 |
   | WebSocket API（`websocket_api`） | RealtimeSessionExecutor | 混音 → chunk → WS 全双工 | 流式 |

   - 用例中设备相关字段（`playback_device_id`、`device_ids`）在非 E2E 执行时被忽略，因此**同一份用例结构可被三种执行链路消费**
   - 一个任务内不同 TaskCase 可关联不同类型设备，混跑 E2E + API + Realtime
   - SPL 映射来源：物理设备取 `device.spl_mapping_id`，API 类取 `api.rms_spl_mapping_id`

3. **评估数据提交**：
   - E2EExecutor 按轮构建评估数据：轮次启用判定为 `enabled != False` 且单轮 `dimensions` 非空
   - 评估服务按轮次隔离读取维度（单轮维度取 `rounds[n].evaluation.dimensions`，整体维度取顶层 `config.dimensions`），不跨层合并

### 4.3 测试用例复用

1. **复制复用**：
   - 单条复制：`POST /api/v1/testcases/{id}/copy`，复制完整的 `config`、`algorithm_params`、`reference_params` 与标签
   - 批量复制到分组：batch 动作 `copy_to_group`（指定 `target_group_id`）
   - 按分组批量复制：batch 动作 `copy_by_group`（整组用例复制）
   - 按标签批量复制：batch 动作 `copy_by_tag`（可复制到新分组）
   - 典型用法：创建用例后复制一条，调整音频设备字段即可在不同执行环境下复用

2. **跨执行方式复用**：
   - 用例数据不绑定执行方式，设备相关字段在 API 类执行时被忽略
   - 同一份用例可在物理设备、HTTP API、WebSocket API 三种执行链路下复用
   - 移动 / 复制到其他分组（`move_to_group` / `copy_to_group`）即可在不同环境配置下复用

3. **配置调整**：
   - 通过编辑模态窗调整轮次音频、评估维度、算法参数与参考参数
   - 通过批量操作统一调整：批量设置评价维度、批量更新算法参数、批量更新播放设备、批量设置声压级、批量设置背景噪声、批量移动分组、批量增删标签、自动命名等

## 5. 接口支持

### 5.1 测试用例管理接口

蓝图前缀为 `/api/v1/testcases`，主要路由：

| 方法与路径 | 说明 |
|-----------|------|
| `GET /api/v1/testcases` | 用例列表，支持按标签、分组、关键词过滤与分页 |
| `GET /api/v1/testcases/{id}` | 用例详情，含完整 config 配置 |
| `POST /api/v1/testcases` | 新增用例 |
| `PUT /api/v1/testcases/{id}` | 更新用例 |
| `DELETE /api/v1/testcases/{id}` | 删除用例（逻辑删除） |
| `POST /api/v1/testcases/{id}/copy` | 复制用例 |
| `POST /api/v1/testcases/{id}/preview` / `stop_preview` | 音频预览 / 停止预览 |
| `GET|PUT /api/v1/testcases/{id}/rounds/{round_number}/ref-params` | 按轮读写参考参数文件 |
| `GET /api/v1/testcases/stats` / `GET /api/v1/testcases/tags` | 统计 / 标签列表 |
| `POST /api/v1/testcases/ids` | 按筛选条件查询用例 ID 集合 |
| `POST /api/v1/testcases/export` / `import` / `import/preview` | 导出 / 导入 / 导入预览 |
| `GET /api/v1/testcases/template/download` | 下载导入模板 |
| `GET /api/v1/testcases/refresh_task/{task_id}` | 异步刷新任务进度查询 |

### 5.2 批量操作接口

统一批量端点：`POST /api/v1/testcases/batch`，请求体 `{ action, ids, ...params }`。常用 action：

- 评估维度：`update_dimensions`（详见《批量设置评价维度功能设计文档》）
- 复制与移动：`copy_to_group`、`move_to_group`、`copy_by_group`、`copy_by_tag`
- 参数类：`update_algorithm_params`、`update_playback_devices`、`update_spl`、`update_noise`
- 标签类：`add_tags`、`remove_tags`、`rename_tag`、`auto_generate_name`
- 其他：`delete`、`restore`、`refresh_reference`

## 6. 优势与收益

### 6.1 提高测试用例复用率

- 用例是纯数据，同一份轮次/音频/维度配置可被物理设备、HTTP API、WebSocket API 三种执行链路消费
- 通过复制机制（单条 / 按分组 / 按标签 / 按目标分组）快速派生新用例，减少重复创建
- 便于保持不同执行方式下测试配置的一致性

### 6.2 降低维护成本

- 用例不区分类型，无需维护类型标识，列表过滤与统计直接基于分组与标签
- 统一的管理界面与批量操作，便于集中维护
- 分组 + 标签双维度分类，快速定位用例

### 6.3 增强测试覆盖度

- 同一轮次结构下可灵活组合打断标记轮、停止指令轮、干扰人与背景噪声，覆盖更多测试场景
- 单轮维度与整体维度分层配置，评估粒度灵活
- 便于对比同一用例在不同执行方式下的结果差异

## 7. 应用场景

### 7.1 同一用例在不同执行方式下的测试

1. 创建用例，配置轮次音频（可指定播放设备，E2E 执行时使用）与评估维度
2. 创建任务时为该用例关联物理设备 → E2E 执行
3. 创建任务时为该用例关联 HTTP API → APISessionExecutor 执行
4. 创建任务时为该用例关联 WebSocket API → RealtimeSessionExecutor 执行
5. 三次执行共用同一份用例数据，结果可对比

### 7.2 同一用例在不同设备上的 E2E 测试

1. 创建用例，配置基本的轮次音频
2. 复制用例并批量更新播放设备（`update_playback_devices`），适配不同被测设备
3. 分别创建测试任务执行
4. 系统按各自设备的 SPL 映射换算播放增益

### 7.3 测试用例的跨团队复用

1. 创建用例后通过标签分类、按分组归档
2. 通过 `copy_by_group` / `copy_by_tag` 将整组或同标签用例复制到新分组供其他团队使用
3. 各团队按需调整评估维度（批量设置评价维度）与算法参数（批量更新算法参数）
4. 保持核心话术与音频序列一致，仅调整环境相关配置

### 7.4 一个任务混跑不同设备类型

1. 创建任务，关联多条用例
2. 为不同 TaskCase 选择不同类型的被测设备：
   - TaskCase #1: 用例A × 物理设备（小翼音箱）→ E2EExecutor
   - TaskCase #2: 用例A × WebSocket API（ChatGPT RT）→ RealtimeSessionExecutor
   - TaskCase #3: 用例B × HTTP API（通义千问）→ APISessionExecutor
3. 启动任务 → 系统按每个 TaskCase 的设备类型路由到对应 executor

## 8. 最佳实践

### 8.1 测试用例设计建议

1. **用例是纯数据**：`config` / `algorithm_params` / `reference_params` 只放"测什么"；播放设备等环境字段按需配置，API 类执行自动忽略
2. **核心数据与执行环境分离**：用例不绑定执行方式，执行路由由被测设备类型决定
3. **合理使用分组与标签**：分组承载环境/业务维度，标签承载特征维度，两者配合筛选
4. **评估维度分层配置**：轮次级关注该轮特有指标（如唤醒率），整体级关注跨轮聚合指标（如响应延迟）；无需评估的轮次直接清空维度即可关闭该轮评估

### 8.2 测试执行建议

1. **按需选择被测设备**：物理设备走 E2E 执行，HTTP API 走 APISessionExecutor，WebSocket API 走 RealtimeSessionExecutor
2. **执行环境合理配置**：E2E 任务确认播放设备与 SPL 映射；API 任务确认被测 API 配置与流式/非实时模式
3. **结果的对比分析**：利用报告的整体/各轮取值优先级（整体结果优先，无整体则各轮算术平均）做跨轮次分析
4. **定期维护**：用批量操作统一清理过期标签、调整分组归属，用导入预览验证批量导入数据

## 9. 总结

测试用例共用机制以 **纯数据无类型架构** 为基础，以 **纯数据用例模型** 为核心：

1. **用例不区分类型**：用例没有 `test_type` 字段，不区分 api 用例与 e2e 用例，用例只有一份结构
2. **按轮组织的用例结构**：音频、噪声、干扰人、单轮评估维度全部按轮次组织，整体评估维度独立于顶层，两层维度互不合并
3. **执行方式与用例解耦**：执行路由由被测设备类型决定（物理设备 / HTTP API / WebSocket API 三执行器），设备相关字段在非 E2E 执行时被忽略，用例数据得以跨执行链路复用
4. **完善的复制与批量机制**：单条复制、按分组/标签批量复制、批量移动与批量参数更新，支撑快速派生与集中维护

这种设计提高了测试用例的复用性和维护效率，降低了测试成本，同时增强了测试覆盖度。通过合理的用例设计与复制策略，可以充分发挥用例共用机制的优势。

# 测试结果人工复核功能设计文档

> 版本：V9.7.31 v1.0（2026-10-14）｜负责人口头需求落文档初始稿（原话见 §1.2，待拍板项文中标注）

## 1. 文档说明

### 1.1 目标

任务执行完毕后，允许人工复核并修改测试结果（改判/备注等）；当任务后续被重新执行或重新评估时，明确提醒用户：**人工复核填写的结果会被覆盖**。

### 1.2 需求来源

负责人口头需求（2026-10-14）原话：

> 任务执行完毕后，允许人工复核 修改测试结果啥的，如果重新执行 或者重新评估任务 要提醒用户 人工 复核 填写的结果 会被覆盖

同日追加（范围与边界）：

> 人工复核 可以 设置用例的评估状态 还有 执行 状态啥的 相当于 也是一种cherry pick

> 这俩cherry pick 不是一个功能 别混了

**边界澄清（负责人 2026-10-14）**：人工复核与「结果挑选合并（Cherry-Pick 购物车，见 02_任务管理/任务结果CherryPick挑选合并功能设计文档.md）」是**两个独立功能，不得混合**——复核界面的用例选取可参考挑选交互（正选/反选、单个/分组/按维度），但功能边界、入口、数据流各自独立。

## 2. 复核范围与入口

- **触发时机**：任务到达终态（completed/failed/stopped/skipped，对齐 `TaskStatus.is_terminal` 含 skipped）后即可复核；执行中/评估中不允许（复核以稳定结果为对象）。
- **入口**：任务执行详情模态窗的结果列表（单条结果「人工复核」操作）+ 结果详情页。
- **复核动作（默认范围）**：
  1. **设置用例执行状态**：人工改判用例执行结果状态（如 failed ↔ passed；可设置枚举规格阶段对齐 status_fields_relationship.md §8.2）；
  2. **设置用例评估状态**：人工设置用例评估状态（枚举规格阶段对齐 §8.3）——负责人 2026-10-14 口径「可以设置用例的评估状态 还有 执行状态啥的」，双状态两维都可人工设置；
  3. 复核备注/结论：填写复核意见。
  4. 待拍板：评估维度**分数**是否允许人工修改（默认**不允许**——状态可设、分数不改）。
- 每条结果可多次复核，复核记录**留痕不覆盖**（历史复核记录可查）。

## 3. 复核标记与展示

- 结果增加复核字段（命名规格阶段定，snake_case 仅库与 DTO 转换层）：人工复核标记（bool）/ 复核人 / 复核时间 / 复核动作 / 复核备注 / 原值留痕。
- 复核过的结果在任务详情与报告页打「**人工复核**」标记（展示谁/何时/改了什么）。
- 统计口径：任务统计与报告统计按**复核后判定**计算。
- 报告口径：复核后不自动修改已生成报告（对齐报告冻结精神），提示用户重新生成报告（待拍板，§6）。

## 4. 覆盖提醒（本功能核心口径）

- **触发点**：对存在人工复核结果的任务发起**重新执行**或**重新评估**（含整任务/选择性，含重新评估三份文档的全部入口）时，弹确认提醒：

  > 该任务存在 N 条人工复核结果，重新执行/重新评估后人工复核填写的结果将被覆盖，是否继续？

- **覆盖语义**：
  - 重新执行 → 新 TestResult 生成后任务结果以新执行为准；人工复核留痕随旧结果去留（对齐任务重新执行功能设计文档 §5 约束 #2「旧结果去留」待拍板——若旧结果保留可查，则复核留痕随旧结果保留）；
  - 重新评估 → 评估数据重算，人工复核的评估侧修改被覆盖。
- 选择性重执行**未选中**的用例：其人工复核结果不受影响（对齐 INT-302 口径）。
- 提醒为**硬确认**（必须点击确认才发起），不做静默覆盖。

## 5. 权限与审计

- 复核操作记录操作人/操作时间/原值/新值，审计事件预留 `MANUAL_REVIEW_SUBMITTED`。
- 权限编码预留 `task.result.review`。

## 6. 待拍板（负责人）——已裁定（2026-10-15，INT-400 #6 并入规格）

> 本节原为待拍板项；负责人 2026-10-15 已裁定（INT-400 #6），裁定结果如下并已落规格：

1. **执行/评估状态可人工设置的枚举范围**：已裁定。执行状态可改判全集 `completed/failed/stopped/skipped`（禁 pending/queued/running）；评估状态按双状态口径 `completed/failed`（对齐 status_fields_relationship.md §8.2/§8.3）。
2. **评估维度分数是否允许人工修改**：默认**不允许**（状态可设、分数不改）。
3. **复核备注是否必填**：**必填**（比默认选填严）。
4. **复核后已生成报告的处理**：**不自动重算**，详情页提示重新生成（对齐报告冻结精神）。
5. **新增批量复核**（负责人追加）：结果列表多选批量复核，逐条留痕（进 S4 前端范围 + S3 批量接口）。

## 7. 验收标准

1. 终态任务的单条结果可人工复核（设置执行状态/评估状态 + 备注）并留痕（谁/何时/原值/新值），支持多次复核且历史记录可查。
2. 任务详情与报告页正确展示「人工复核」标记；任务统计与报告统计按复核后判定计算。
3. 存在复核结果的任务发起重新执行/重新评估时，出现覆盖提醒，确认后才发起；不做静默覆盖。
4. 无复核结果的任务重执行/重评估无此提醒。
5. 选择性重执行未选中用例的人工复核结果不受影响。

## 8. AI 复核（实现演进裁定 2026-10-19，INT-800 / INT-821~824）

> 本节为 AI 复核机制的功能设计口径，与 §2~§7 人工复核同属复核域。设计基线见 UX 规范
> `19_人工审核与AI复核交互设计.md` §2.1/§5.2/§5.3/§8-2（原「待后端立项清单 #2」）；
> INT-800 可行性评审定稿契约并实施（INT-821 ai_reviews 数据模型 / INT-822 task_service
> 命令侧 / INT-823 evaluation_service LLM 复检 gRPC / INT-824 api_gateway 契约层+RBAC），
> 一致性审计（INT-855）确认实现与契约一致，回写本节（实现演进裁定）。

### 8.1 定位与边界

- 定位：对疑似问题结果（低分、评估失败、断言不符、LLM 评语存疑）由大模型独立复检，
  产出 AI 判定（verdict/confidence/reasoning）供人确认。**不直接修改统计**；仅人工
  「采纳」才落入人工复核语义（改判评估状态 + 留痕 + 统计重算）。
- 与人工复核边界：AI 复核 = **建议层**，人工复核 = **权威层**。AI 结论独立建表
  `ai_reviews`，**不与人工复核留痕 `test_result_reviews` 同表**（AI 结论是机器判定，
  无 old→new 改判语义；同表会破坏人工复核审计留痕的不可变性，且既有读路径
  review-history/review-count/reviewed_result_ids 全表查询会被 AI 行污染——双口径回归）。
- 与 LLM Judge 维度边界：LLM Judge 是评估维度（执行时判分产分数）；AI 复核是事后复检，
  复用 LLM Judge 的模型/Prompt 配置与 voice_llm 评语作为输入上下文。
- 架构红线：**单次 LLM 复检**，非 E 域 Agent 编排（不引入 LangGraph 多步编排）。

### 8.3 端点契约（挂 `/api/v1/tasks/results` 前缀，统一信封 {success,message,data}）

1. `POST /tasks/results/ai-review` —— 发起
   - 入参 `{result_ids:[int]≥1, dimension_ids?:[int], force?:boolean}`
   - 权限 `task.result.ai_review`（新码）
   - 行为：每对 (result_id, dimension_id) 落一条记录（dimension_ids 缺省 = 结果现有
     已完成评估的 LLM 判分维度，经 evaluation_service 维度评估结果 ∩ LLM 判分维度集
     过滤）；幂等：非 force 且该对已有 running/completed → 复用最近一条
     （`reused=true`，不重复发起）；否则 status=running 异步执行（后台线程经
     evaluation_service `AiReviewCheck` gRPC 调 LLM，回写 verdict/confidence/reasoning
     并置 status=completed；失败置 status=failed 不落判定，重试=force 再发）
   - 出参 `{items:[AiReviewRecordDto], reused?:boolean, skipped?:[{result_id,message}]}`
2. `GET /tasks/results/{task_id}/ai-review-history` —— 历史
   - Query 可选 `?result_id=&dimension_id=&status=`
   - 权限 `task:read`
   - 出参 `{items:[AiReviewRecordDto]}`，时间倒序
3. `POST /tasks/results/ai-review/{id}/adopt` —— 采纳（原子落人工复核语义）
   - 入参 `{execution_status?:str, evaluation_status?:str, comment:str 必填}`
   - 权限 `task.result.review`（采纳衔接权威改判，对齐 §6 人工复核权限）
   - 行为：校验记录 status=completed 且未处置（adopted/rejected 均 0）→ 置
     adopted/adopted_by/adopted_at → **复用 `review_repository.apply_review`**
     （单事务：TestResult + TaskCase + 留痕行）落 `test_result_reviews` + 统计重算
     （recalc_task_stats）+ 评估侧 TRD 联动——与 `POST /tasks/results/review` 同一
     改判契约与准入（终态任务 / 执行 completed/failed/stopped/skipped、评估
     completed/failed / comment≥1 / 至少设置一项）
   - 出参 `{item: 更新后 AiReviewRecordDto, applied:[{field_name,old_value,new_value}]}`
4. `POST /tasks/results/ai-review/{id}/reject` —— 驳回
   - 入参 `{}`；权限 `task.result.ai_review`
   - 行为：置 rejected/rejected_by/rejected_at，**原判定不变**
   - 出参 更新后 AiReviewRecordDto（已驳回幂等返回现状）

### 8.5 交互口径（对齐 UX 规范 §2.1 状态机）

- 状态机：**待发起 → 执行中**（异步，可取消）→ **已完成**（复核通过/复核不通过/存疑 +
  置信度 + 理由）→ 人工处置：**采纳**（打开人工复核弹窗预填 AI 判定的评估状态 + 备注
  =AI 理由 → 人工确认提交 → 落 test_result_reviews + 统计重算）/ **驳回**（AI 记录标记
  已驳回，原判定不变）/ **忽略**（AI 记录保留待查，不置标记）。
- 幂等：同一结果同一维度重复发起 → 复用最近一次 AI 结论（前端提示「该结果已有
  AI 复核结论（{时间}），可查看/重新复核」）；`force=true` 新建记录重新执行。
- 超时/失败：进度失败 → Alert + 重试；不落任何判定（status=failed）。
- 回归红线：AI 记录不污染人工复核计数/历史/标记（review-count / review-history /
  reviewed_result_ids 结果不变）。

### 8.6 验收要点（实施单测已覆盖，INT-821~824；全流程实测需配置 LLM 判分维度环境）

- 真实数据实测（连常驻后端 :5000）：发起 → 异步执行 → 结论卡（verdict/confidence/
  reasoning）→ 采纳（预填评估状态 + 备注=AI 理由 → 落 test_result_reviews + 统计重算）→
  驳回（原判定不变 + rejected 标记）全流程。
- 幂等：同结果同维度重复发起返回最近结论 + reused 提示；force 重新复核新建记录。
- 权限：tester 全流程；无 task.result.review 角色采纳按钮隐藏 + API 403。
- 回归：人工复核计数/历史/标记不受 AI 记录影响。

# 09 原始报文外置对象存储（uri-only）

> 口径来源：INT-1807（C1：列 + 回填 + 门禁）、INT-1809（C2：读写路径切换）、INT-1805（D1：禁止本地降级）。
> 对象口径的唯一实现是 `shared/infrastructure/raw_payload_store.py`——回填脚本、在线写路径、读路径三处共用，改口径先改卡。

## 1. 为什么要外置

`test_result_dimensions.api_raw_response` / `api_request_body` 是 JSON 列，同一份厂商报文按「维度 × 轮」重复落库：主库实测 51,857 行，去重后只有 **6,492 个响应 + 6,164 个请求体**，TOAST 约占 695MB。外置后行上只留指针，报文按内容寻址在对象存储里去重一次；M1 再 DROP 两列回收空间。

## 2. 对象口径

| 项 | 取值 |
|---|---|
| key | `raw/resp/{sha[:2]}/{sha}.json.gz`、`raw/req/{sha[:2]}/{sha}.json.gz` |
| category | `case_result`（多桶模式落 case-result 桶；单桶模式自动加 `{OSS_KEY_PREFIX}/case_result/` 前缀） |
| 规范化字节 | `json.dumps(v, sort_keys=True, separators=(',', ':'), ensure_ascii=False).encode('utf-8')` |
| sha256 | 对**规范化后未压缩字节**计算，即 key 里的 `{sha}` |
| 压缩 | gzip（`mtime=0`，压缩确定），`content_type=application/json+gzip`，`bytes` 记压缩后大小 |
| 写入 | 一律 `storage.save_bytes(..., allow_fallback=False)`：OSS 不可用即抛 `StorageUnavailableError`，**不落本地盘、不写 `local://`** |
| 读取 | 一律 `storage.load_bytes(..., allow_fallback=False)`；解压后**校验 sha256**，不符抛 `RawPayloadCorruptError` |

响应体与请求体是独立取值空间（6,492 / 6,164），不打包成一份对象，否则跨值去重失效。`None` 视同「无报文」：不建对象、不写指针（C1 回填同口径；JSON `null` 同理）。

行上五列（两组各五）：`{api_raw_response|api_request_body}_uri / _sha256 / _bytes / _content_type / _created_at`，全部可空、无默认值、无索引。

## 3. 写路径（组级一次上传 + uri-only 落库）

写点：`evaluation_service/infrastructure/persistence/_result_group_mixin.py:process_group_dimension_results`
与 `_result_dimension_mixin.py`（`update_dimension_result` / `_overwrite_round_results` / `update_all_dimensions_in_group_failed`）。

```
组入口（进 DB 会话前）
  ├─ 按值去重：resp_data、api_request_body、per_round[] 逐个 → sha256 + gzip + 上传
  │    （同值只上传一次：组内按 (kind, sha) 缓存；轮值每行可能不同，按值去重）
  ├─ 任一次上传失败 → 整组不落库，异常上抛 → endpoint_worker → mark_case_failed_if_active
  └─ 全部成功 → 进会话逐行写指针（JSON 两列一律写 **SQL NULL**）
```

硬约束：

1. **上传必须在组级**。一组 6~7 行的 resp/req 通常完全相同，逐行上传会把每天约 8 千次写放大成 5 万次 OSS 操作（6.44 倍失败面）。
2. **先对象后库**。对象写失败 → 不写 uri，按失败语义结束（用例 failed、无指针、无 `local://`）；对象成功而库写失败 → 只留孤儿对象，无害。
3. **不引入 outbox / 重试队列**：权威在对象、库只存指针，失败方向天然安全；第二套重试状态机会留下双口径。
4. **失败行**（`update_all_dimensions_in_group_failed`）带报文时同样外置；存储不可用 → 指针全 NULL，失败状态照常落库。
5. 重评前 `reset_score_to_pending` 一并清空指针列，避免「评分是新的、报文是旧的」。
6. **置空必须是 SQL NULL，不是 JSON 字面量 `null`**。`Column(JSON)` 默认 `none_as_null=False`，Python `None` 会落成 JSON `null`——此时 `api_raw_response IS NOT NULL` 为真，C1 切换门禁
   （`api_raw_response IS NOT NULL AND api_raw_response_uri IS NULL`）会把「本来没有报文」的行误判成悬空指针，每次重评 / 存储不可用失败都会把门禁顶上去。
   故 PO 上两列声明为 `Column(JSON(none_as_null=True))`（纯客户端类型标志、无 DDL），一次覆盖 ORM 写入与 Core update（`reset_score_to_pending`）。
   判空证据必须用 SQL 判据（`IS NULL` / `json_typeof(...) IS NULL`）：ORM 读回时 JSON `null` 与 SQL NULL 都是 Python `None`，区分不出来。

## 4. 读路径

| 读点 | 改法 |
|---|---|
| 报告快照构建 `_result_group_mixin._build_and_store_algorithm_results` → `_load_dim_result_rows` | **吃内存**：本组刚写入的 payload 按行上 `sha256` 命中缓存，0 次 OSS；别的组写下的行按 sha 读对象，**每个唯一 sha 只读一次**（另有进程内 64MB 缓存）。行形状改为 `{dimension_id, round_number, api_raw_response}`，快照字段不变 |
| `GetDimensionResultsByResultIds(include_body=True)`（INT-1752 / LLM 复检 INT-823 / 报告加权策略） | 按指针读对象（`evaluation_dimension_repository.get_dimension_results_with_names_by_result_ids`），载荷形状不变（解析后的 dict）。对象缺失 / sha256 不符 / 存储不可用 → **显式抛错**，绝不返回空上下文（空 prompt 判分等于编结论）。LLM 复用同一入口所以自动收口 |
| 默认 `include_body=False` | 不读对象、不 SELECT 两个 JSON 大字段（只取指针列） |

没有「读不到 uri 就回退 JSON 列」的分支：门禁（C1）保证 100% 回填，兼容层只会把双口径拖到 M1 之后。

## 5. 生命周期与上线

1. **C1**：加列 + 人工限流回填（`backfill_raw_payload_pointers_int1807.py --apply`）+ 门禁 `--gate`；
2. 切换前门禁必须 `resp_missing = req_missing = 0`，并跑一次增量补漏：
   `WHERE api_raw_response IS NOT NULL AND api_raw_response_uri IS NULL`（阶段 1 回填后仍可能有新写入）；
3. **C2 与 A1 必须同批上线**：只上 C2 = 库里有 uri 而导出包里没对象（离线搬运到对端即悬空指针）；只上 A1 = 包里有对象而库里没 uri；
4. **M1**：DROP 两列 + VACUUM FULL 回收 TOAST 空间（`reset_score_to_pending` 等写点已经不再碰这两列）。

对象是派生物：回滚只需回退镜像（指针列无人读时数据库结构可原样保留）。

## 6. 与导出 / 归档的关系

导出包需要携带对象本体（A1 / INT-1811）：按 `uri` 清单取对象即可，包内按 `raw/{resp|req}/{sha[:2]}/{sha}.json.gz` 原样落盘；导入侧按 key 回填对象后重建指针。不做预签名 URL——不给前端开原始报文直读入口（越权面 + 绕开 `OSS_PUBLIC_ENDPOINT` 主机名坑）；将来若需「原始报文回显」，走网关鉴权代理。

## 7. 验收口径（本卡实测）

- 单轮 / 多轮 / 失败三条链路：行内五列非空、JSON 两列 **SQL NULL**（`IS NULL` 为真、`json_typeof` 为 NULL；置空走 `none_as_null=True`，ORM 与 Core update 同口径）；
- 组级去重：6 维度 × 3 轮 = 24 行只上传 5 个对象（resp / req / 3 个不同轮值）；
- 内容等价：对象解压后与评估 payload deep-equal，sha256 校验通过；
- 失败方向：注入 OSS 不可用 → 整组不落库、无指针、无 `local://`；
- 读路径：对象缺失 / 篡改 → 显式报错并写明原因；同 sha 只下一次 OSS；
- 隔离库 + 真实 OSS：6 整体行 + 12 逐轮行 / 4 个对象 / include_body 18 行 deep-equal。

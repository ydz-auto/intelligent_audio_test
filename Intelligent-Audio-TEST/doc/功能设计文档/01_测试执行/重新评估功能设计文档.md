# 重新评估功能设计文档

> 版本：v3.0（V9.7.31 适配版）| 更新日期：2026-09-10 | 变更说明：废弃 test_type，支持 E2E/API/Realtime 三种执行模式的重新评估；同步 V9.7.10 v3.0 语义，按 V9.7.31 微服务架构（DDD+CQRS+事件驱动）落位

## 1. 概述

### 1.1 功能目标
- 支持任务重新评估，包括重新提取设备输出和重新执行评估
- 实现重新评估任务的队列管理机制
- 支持与普通测试执行并行执行，但同一时间只能有一个重新评估任务在运行

### 1.2 设计原则
- 重新评估与普通测试执行使用不同的任务状态
- 重新评估队列独立管理，但与普通测试共享评估服务队列
- 线程安全的状态管理

【适配说明】V9.7.31 微服务落位原则：
- 重评估命令入口为 application command（CQRS）：`ReevaluateTaskCommand` 于 task_service:5001，执行器 `ReevaluationExecutor` 于 evaluation_service:5004
- 跨服务调用一律 gRPC（evaluation_service 经 ACL 仓储调 task_service:5001，不直连其数据库）
- 任务/用例状态一律使用 `shared/utils/status_constants.py` 常量，事件一律使用 `shared/utils/redis_pubsub.py` 的 `EventChannel`/`EventType` 枚举，禁止硬编码状态字符串

## 2. 状态设计

### 2.1 Task.status 状态流转

状态常量定义于 `shared/utils/status_constants.py` 的 `TaskStatus`（含 `REEVALUATE_QUEUED`/`REEVALUATING`），禁止裸字符串。

#### 普通测试
```
pending → queued → running → evaluating → completed/failed/stopped
```

#### 重新评估
```
completed/failed → reevaluate_queued → reevaluating → completed/failed
```

### 2.2 TaskCase.evaluation_status 状态流转

状态常量定义于 `shared/utils/status_constants.py` 的 `ExecutionStatus` / `EvaluationStatus`；活跃评估状态集合 `ACTIVE_EVALUATION_STATUSES` 用于中断状态判定。

#### 普通测试
```
execution_status: pending → queued → running → completed/failed
evaluation_status: queued → pending → running → calculating → completed/failed
```

#### 重新评估
```
重新评估前: completed/failed
     ↓ (提交重新评估)
queued
     ↓ (开始处理)
pending
     ↓ (评估服务处理中)
running
     ↓ (计算指标中)
calculating
     ↓ (所有维度评估完成)
completed/failed
```

## 3. 架构设计

### 3.1 组件关系

【适配说明】V9.7.31 为微服务架构，重评估链路横跨 api_gateway / task_service / evaluation_service 三个服务：

```
┌─────────────────────────────────────────────────────────────────┐
│                api_gateway:5000                                  │
│      POST /tasks/{task_id}/reevaluate（路由代理，camelCase）       │
└─────────────────────────┬───────────────────────────────────────┘
                          │ gRPC（跨服务一律 gRPC）
                          ▼
┌─────────────────────────────────────────────────────────────────┐
│                task_service:5001                                 │
│  ReevaluateRequest → ReevaluateTaskCommand（application command） │
│  → task_command_handler.handle_reevaluate_task()                 │
│  → evaluation_acl_repository.submit_reevaluate()  (gRPC)          │
└─────────────────────────┬───────────────────────────────────────┘
                          │ gRPC：EvaluationService.Reevaluate
                          ▼
┌─────────────────────────────────────────────────────────────────┐
│                evaluation_service:5004                           │
│                ReevaluationExecutor（interfaces/grpc/             │
│                evaluation_servicer.py 接收后委托）                 │
│  ┌─────────────────────┐  ┌──────────────────────────────────┐ │
│  │ reevaluation_queue   │  │  is_reevaluating = False          │ │
│  │ [task1, task2]      │  │  _check_queue()                   │ │
│  └─────────────────────┘  │  _run_reevaluation()              │ │
│                           │  _on_complete()                   │ │
│                           └──────────────────────────────────┘ │
│  application/handlers/reevaluation_executor.py（编排）            │
│  domain/services/reevaluation_service.py（纯业务规则，下沉）       │
└─────────────────────────┬───────────────────────────────────────┘
                          │ task_acl_repository（gRPC → task_service）
                          ▼
┌─────────────────────────────────────────────────────────────────┐
│                task_service:5001（共享评估队列侧的数据与状态）      │
│  Task / TaskCase / TestResult 读写经 ACL（Task 状态、TaskCase      │
│  evaluation_status 由 evaluation_service 经 gRPC 回写）            │
└─────────────────────────────────────────────────────────────────┘
```

- Task / TaskCase / TestResult / TestCase 的读写一律经 `evaluation_service/infrastructure/acl/task_acl_repository.py`（gRPC），仅 `TestResultDimension` 为本服务自有 PO 可直连 DB
- 业务规则（all/failed 过滤、反序列化、多轮/单轮分发、API 聚合）下沉到 `evaluation_service/domain/services/reevaluation_service.py`，Application 层只做编排（预加载数据 + 调用 Domain Service）

### 3.2 并行关系

| 普通测试 | 重新评估 | 评估队列 |
|---------|---------|---------|
| running (可多个) | reevaluating (最多1个) | 共享 |
| evaluating | reevaluate_queued | 共享 |

### 3.3 API/Realtime 重新评估说明（新增）

不同被测设备类型（device_type）的重新评估，algorithm_result 的来源不同：

| device_type | algorithm_result 来源 | 说明 |
|-------------|----------------------|------|
| physical (E2E) | device_driver 输出 | 从设备存档重新提取（reextract），经 convert_device_output 转换 |
| http_api (API) | adapter.send() 响应 | 由 HttpAPIAdapter / HttpStreamAdapter 返回，无需重新提取 |
| websocket_api (Realtime) | adapter.output | 由 RealtimeAPIAdapter 保存，包含 audio PCM、text、event_log、latency_ms |

**device_type 语义**（取代 task.type/test_type 作为执行语义）：
- device_type 取值 `physical` / `http_api` / `websocket_api`，枚举落位 `shared/models/common_enums.py`（新增 `DeviceType` 枚举），TaskType 不引入 `'realtime_api'`
- `task_case_relations` 已有 `device_id` 列，本轮新增 `device_type` 列（新增），重评估时按用例级 device_type 路由结果来源，不再依赖 task.type/test_type

**reextract_device_output 适用范围**：仅适用于物理设备（device_type='physical'）的 E2E 测试。HTTP API 和 WebSocket API 测试没有设备存档，无法重新提取。对于 API/Realtime 测试，重新评估时直接使用 adapter 保存的结果（algorithm_result / adapter.output）。

【适配说明】result_type 双通道映射：评估结果关联 result_type 区分 frame / summary 双通道——frame 通道为执行期逐帧结果，不落库；summary 通道为汇总结果，落库（test_results.result_data / result_data_path，经 `shared/utils/result_data_store.py` 的 `load_full_result_data` 恢复）并触发评估。重评估仅消费 summary 通道已落库的数据。

### 3.4 事件与前端通知（新增）

- 每个用例评估完成后，evaluation_service 经 Redis EventBus 发布领域事件：`EventBus().publish(EventChannel.CASE_EVENTS, EventType.CASE_EVALUATION_COMPLETED, {...})`（`shared/utils/redis_pubsub.py`）
- api_gateway:5000 订阅 Redis 事件频道，经 Socket.IO（`api_gateway/websocket/socketio_server.py`）转发前端，按 task_id 房间隔离推送
- 事件驱动替代 gRPC 同步回传：Redis 不可用时只打日志不阻塞评估主流程（EventBus 内建降级）

## 4. ReevaluationExecutor 设计

### 4.1 类定义

落位：`evaluation_service/application/handlers/reevaluation_executor.py`（【适配说明】P1.7 后 ReevaluationExecutor 从 task_service 迁移至 evaluation_service；业务规则下沉 Domain 层）。

```python
# evaluation_service/application/handlers/reevaluation_executor.py
class ReevaluationExecutor:
    """重新评估执行器 - 管理重新评估任务的队列

    所有 Task/TaskCase/TestResult/TestCase 的访问经 task_acl_repository (gRPC)。
    仅 TestResultDimension 为本服务自有 PO，可直连 DB。
    """

    _instance = None
    _lock = threading.Lock()   # 双检锁（对比旧版单例：get_instance 线程安全）

    def __init__(self):
        self.reevaluation_queue = []       # 重新评估队列
        self.reevaluation_lock = threading.Lock()  # 线程锁
        self.is_reevaluating = False       # 是否有任务正在重新评估
        self.running_task_id = None        # 当前执行的任务ID

    @classmethod
    def get_instance(cls):
        if cls._instance is None:
            with cls._lock:
                if cls._instance is None:
                    cls._instance = cls()
        return cls._instance
```

重新评估类型判别符（非任务/用例状态，配置化常量，拒绝魔法字符串）：

```python
REEVALUATE_TYPE_ALL = 'all'
REEVALUATE_TYPE_FAILED = 'failed'
```

业务规则下沉（P0-2 DDD）：`evaluation_service/domain/services/reevaluation_service.py` 的 `ReevaluationService` 提供：
- `collect_cases_all` / `collect_cases_failed`：all/failed 过滤与 case_info 构建（纯逻辑）
- `deserialize_algorithm_result`：算法结果反序列化（双重序列化兼容）
- `is_multi_round`：多轮/单轮分发决策
- `compute_api_aggregated`：API 多轮聚合计算

### 4.2 核心方法

#### submit()
```python
def submit(self, task_id, reextract_device_output=True, reevaluate_type='all'):
    """提交重新评估任务

    Args:
        task_id: 任务ID
        reextract_device_output: 是否重新提取设备输出
        reevaluate_type: 重新评估类型（REEVALUATE_TYPE_ALL / REEVALUATE_TYPE_FAILED）

    Returns:
        (success, message)
    """
    with self.reevaluation_lock:
        # 检查是否已在队列或正在执行
        if task_id == self.running_task_id:
            return False, "任务正在重新评估中"

        if any(item['task_id'] == task_id for item in self.reevaluation_queue):
            return False, "任务已在重新评估队列中"

        # 加入队列
        self.reevaluation_queue.append({
            'task_id': task_id,
            'reextract_device_output': reextract_device_output,
            'reevaluate_type': reevaluate_type
        })

        # 通过 gRPC（task_acl_repository）更新 Task 状态为排队（枚举常量，非硬编码）
        task_acl_repository.update_task_status(task_id, TaskStatus.REEVALUATE_QUEUED)

    log_and_emit('INFO', 'reevaluator',
                 f"重新评估任务已提交: task_id={task_id}, type={reevaluate_type}",
                 task_id=task_id)

    # 触发检查队列
    self._check_queue()

    return True, "重新评估任务已提交"
```

#### _check_queue()
```python
def _check_queue(self):
    """检查重新评估队列，启动下一个任务"""
    with self.reevaluation_lock:
        # 如果有任务在执行或队列为空，不处理
        if self.is_reevaluating or not self.reevaluation_queue:
            return

        # 取出下一个任务
        task_info = self.reevaluation_queue.pop(0)
        self.is_reevaluating = True
        self.running_task_id = task_info['task_id']
        task_id = task_info['task_id']
        reextract_device_output = task_info['reextract_device_output']
        reevaluate_type = task_info['reevaluate_type']

    # 通过 gRPC 更新任务状态为正在重新评估
    task_acl_repository.update_task_status(task_id, TaskStatus.REEVALUATING)

    # evaluation_service 本地线程池执行重新评估（daemon 线程，随服务退出）
    threading.Thread(
        target=self._run_reevaluation,
        args=(task_id, reextract_device_output, reevaluate_type),
        daemon=True,
    ).start()
```

#### _run_reevaluation()
```python
def _run_reevaluation(self, task_id, reextract_device_output, reevaluate_type):
    """执行重新评估"""
    success = False

    try:
        # 1. 重新提取设备输出（如果需要）
        # 注意: reextract_device_output 仅适用于 device_type='physical' (E2E)
        #       device_type='http_api'/'websocket_api' 的测试结果由 adapter 直接保存，无设备存档
        if reextract_device_output:
            test_results = self._reextract_device_output(task_id, reevaluate_type)
        else:
            # 通过 gRPC 读 TestResult
            test_results = task_acl_repository.get_test_results_by_task_and_case(task_id=task_id)

        # 2. 收集需要重新评估的用例（委托 Domain Service，纯业务逻辑）
        # result_type 取值: E2E 为 'real-time'/'non-real-time'，API/Realtime 为 'api'/'realtime'
        # result_type 映射 frame/summary 双通道：frame 不落库，summary 落库触发评估（见 3.3）
        if reevaluate_type == REEVALUATE_TYPE_ALL:
            cases_to_reevaluate = self._collect_reevaluation_cases_all(
                task_id, test_results, reextract_device_output
            )
        elif reevaluate_type == REEVALUATE_TYPE_FAILED:
            cases_to_reevaluate = self._collect_reevaluation_cases_failed(
                task_id, test_results, reextract_device_output
            )
        else:
            cases_to_reevaluate = []

        if not cases_to_reevaluate:
            log_and_emit('WARNING', 'reevaluator',
                         f"没有需要重新评估的用例: task_id={task_id}",
                         task_id=task_id)
            success = True
            return

        # 将不满足重新评估条件的用例的评估状态标记为已完成，避免状态不一致
        # （仅当 evaluation_status 处于 ACTIVE_EVALUATION_STATUSES 时兜底置 completed）
        ...

        # 3. 提交用例进行重新评估
        #    多轮（algorithm_result 含 rounds）→ _reevaluate_multi_round
        #    单轮 → _reevaluate_single；经 evaluation_service.evaluate_case 入共享评估队列
        self._submit_cases_for_reevaluation(task_id, cases_to_reevaluate)

        success = True
        log_and_emit('INFO', 'reevaluator',
                     f"重新评估任务已提交: {len(cases_to_reevaluate)} 个用例",
                     task_id=task_id)

    except Exception as e:
        import traceback
        log_and_emit('ERROR', 'reevaluator',
                     f"重新评估失败: {str(e)}, traceback: {traceback.format_exc()}",
                     task_id=task_id)

    finally:
        # 通知完成
        self._on_complete(task_id, success)
```

【适配说明】收集用例的编排模式（Application 层）：
1. 预加载数据（Infrastructure 访问）：`load_full_result_data(result.result_data, result.result_data_path)` 恢复 summary 通道 full_data；`task_acl_repository.get_task_case_by_ids()` 读取 TaskCase
2. 调用 Domain Service 纯逻辑判断：`reevaluation_service.collect_cases_all(...)` / `collect_cases_failed(...)`
3. raw_results 字段重映射（`_remap_fields_from_raw`）后，经 `task_acl_repository.update_test_result_algorithm_result()` 写回（JSON 字段直接存 dict，避免双重序列化）

#### _on_complete()
```python
def _on_complete(self, task_id, success):
    """重新评估完成回调"""
    with self.reevaluation_lock:
        self.is_reevaluating = False
        self.running_task_id = None

    # 通过 gRPC 更新任务状态（枚举常量）
    new_status = TaskStatus.COMPLETED if success else TaskStatus.FAILED
    task_acl_repository.update_task_status(task_id, new_status)

    log_and_emit('INFO', 'reevaluator',
                f"重新评估完成: task_id={task_id}, success={success}",
                task_id=task_id)

    # 继续检查队列，启动下一个
    self._check_queue()
```

## 6. 线程安全

### 6.1 锁保护机制

```python
# 使用 reevaluation_lock 保护临界区
with self.reevaluation_lock:
    # 访问/修改 is_reevaluating
    # 访问/修改 running_task_id
    # 访问/修改 reevaluation_queue
```

### 6.2 避免死锁

- `submit()` 在锁外启动线程（状态更新经 gRPC 在临界区内完成，网络调用不持锁阻塞队列检查）
- `_run_reevaluation()` 在 finally 中调用 `_on_complete()`
- 【适配说明】V9.7.31 中无 Flask app_context 依赖：evaluation_service 为独立进程（:5004），重评估运行于 daemon 线程，跨服务数据访问全部经无状态 ACL 仓储（gRPC），数据库会话由各服务自身会话管理隔离

## 9. 注意事项（新增）

1. **线程安全**: 评估服务使用全局单例（双检锁），多线程调用时需注意跨服务 gRPC 会话隔离；重评估执行线程为 daemon 线程
2. **Realtime 测试结果来源**: 对于 Realtime 测试（device_type='websocket_api'），adapter.output 除了包含 algorithm_result 外，还包含 frame_results 和 event_log，重新评估时应一并保留
3. **reextract 适用范围**: 重新提取设备输出仅适用于物理设备（E2E，device_type='physical'），API/Realtime 测试结果由 adapter 保存，无需重新提取
4. **异常状态兜底**: 重评估收集后，将不满足条件但 evaluation_status 处于 `ACTIVE_EVALUATION_STATUSES` 的用例兜底置 completed，避免状态不一致
5. **事件通知**: 每个用例评估完成发布 `CASE_EVALUATION_COMPLETED`（EventBus → Redis），api_gateway:5000 经 Socket.IO 转发前端（task_id 房间隔离）；Redis 不可用时事件降级为日志，不阻塞评估
6. **分布式可靠性**: 执行器所在服务重启时，`reevaluate_queued`/`reevaluating` 属 `INTERRUPTED_TASK_STATUSES`，由 Task.worker_instance_id 归属标记 + RedisServiceRegistry（`shared/utils/service_registry.py`）的孤儿任务收养逻辑接管，避免中间态悬挂

| 项 | 内容 |

## 1. 功能概述

### 1.1 功能描述
任务重新评估功能允许用户在测试任务结束后，对任务内已完成评估的用例结果进行重新评估。用户可以选择重新评估全部用例，或仅重新评估之前评估失败的用例；对 physical（E2E）任务还可选择**重新提取设备输出**（`reextract_device_output`，**新增**参数，从存档日志重提取设备原始输出后重新评估）。http_api/websocket_api 任务的算法结果由执行侧 adapter 直接保存，仅支持重新评估，不支持重新提取。

### 1.2 适用场景
- 评估维度配置发生变化，需要重新评估历史任务结果
- 评估API服务更新，需要用新版本API重新评估
- 特定用例评估失败，修复后需要重新评估
- 用户对评估结果有疑问，需要重新运行评估

### 1.3 目标用户
- 测试工程师
- 质量管理人员
- 算法研究人员

## 2. 需求分析

### 2.1 功能需求

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| REQ-001 | 支持对已完成任务重新评估全部用例 | 高 |
| REQ-002 | 支持仅重新评估失败的用例 | 高 |
| REQ-003 | 重新评估应在后台异步执行，不阻塞用户界面 | 高 |
| REQ-004 | 重新评估时应保留原有的算法执行结果和参考参数（physical 任务可选重新提取覆盖） | 高 |
| REQ-005 | 重新评估后应更新评估状态和结果 | 中 |
| REQ-006 | 只能在任务终态（COMPLETED/FAILED/STOPPED/PAUSED/SKIPPED，取 `TaskStatus` 枚举）时才能重新评估 | 中 |
| REQ-007 | （**新增**）physical 任务支持 `reextract_device_output` 重新提取设备输出后评估；http_api/websocket_api 不支持该选项 | 中 |
| REQ-008 | （**新增**）用例评估完成后发布 `CASE_EVALUATION_COMPLETED` 事件，前端经 Socket.IO 实时刷新任务状态 | 中 |

### 2.2 用户交互流程

```
用户操作流程:
1. 用户在任务列表页面找到处于终态的任务（completed/failed/stopped/paused/skipped）
2. 点击任务操作按钮
3. 选择"重新评估"选项
4. 在弹窗（ReevaluateSelectModal）中选择评估类型:
   - 全部用例: 重新评估任务内所有执行成功的用例
   - 仅失败用例: 仅重新评估之前评估结果为 failed 的用例
   - 复选项"重新提取设备输出（从存档日志）": （**新增**）仅 physical 任务展示，
     勾选后评估前先从存档日志重提取设备原始输出
5. 确认后，系统经网关提交重评估命令（CQRS），立即返回
6. 用户收到成功提示，评估任务在 evaluation_service 后台执行，
   评估进度经 Socket.IO（task_id 房间）实时回推
```

## 3. 技术设计

### 3.1 数据模型

#### 3.1.1 相关数据表

| 表名 | 作用 |
|-----|------|
| test_tasks | 任务表，存储任务基本信息（status 取 `TaskStatus` 枚举） |
| test_results | 测试结果表，存储每个用例的执行结果和算法结果 |
| test_result_dimensions | 评估维度结果表，存储每个维度的评估结果 |
| task_case_relations | 任务-用例关联表，存储用例在任务中的评估状态；已有 device_id 列，device_type 列（**新增**） |

【适配说明：表分属微服务持久层——test_tasks / task_case_relations 归 task_service（`task_service/infrastructure/persistence/models/task_models.py`），test_results / test_result_dimensions 归 evaluation_service（`evaluation_service/infrastructure/persistence/models/evaluation_models.py`）；跨服务只经 gRPC 与 EventBus 访问，不跨库直连。】

#### 3.1.2 关键字段（枚举化）

**TaskStatus（shared/models/common_enums.py + shared/utils/status_constants.py，现有枚举）:**
- 重评估准入（终态）: `COMPLETED / FAILED / STOPPED / PAUSED / SKIPPED`
- 重评估过程态（现有）: `REEVALUATE_QUEUED / REEVALUATING`

**TestResult 表:**
- `execution_status`: 执行过程状态（取 `ExecutionStatus` 枚举: pending/running/completed/stopped/failed）
- `algorithm_result`: 算法执行结果 (JSON)
- `result_data`: 原始测试结果数据 (JSON)，包含 `adjusted_reference_params`

**TestResultDimension 表:**
- `status`: 评估结果状态 (passed/failed)
- `evaluation_status`: 评估过程状态（取 `EvaluationStatus` 枚举: pending/queued/running/evaluating/completed/failed/skipped，`shared/utils/status_constants.py`）

**task_case_relations 表:**
- `device_type`（**新增**列）: physical/http_api/websocket_api，取 `DeviceType` 枚举（**新增**于 `shared/models/common_enums.py`）；`device_id` 为已有列，不动

【适配说明：V9.7.10 中状态值以字符串字面量散落各处；V9.7.31 全部收敛到 shared 层枚举（`common_enums.py` + `status_constants.py`），业务代码一律 import 枚举引用，禁止魔法字符串/魔法数字；前端 `domain/enums.ts` 为后端枚举的逐字镜像。】

### 3.2 API 设计

#### 3.2.1 重新评估接口

**请求**（snake_case 为网关契约，前端转换收敛在 Infrastructure 层）:
```
POST /api/evaluation/task/reevaluate        # api_gateway routes/evaluation_bp.py，权限键 evaluation:execute
Content-Type: application/json

{
  "task_id": 123,                            // 任务ID
  "reevaluate_type": "all",                  // 评估类型: "all"(全部) 或 "failed"(仅失败)
  "reextract_device_output": false           // （**新增**）重新提取设备输出，仅 physical 任务生效
}
```

**响应:**
```json
{
  "success": true,
  "data": {
    "total_cases": 10,
    "queued_cases": 10,
    "reextracted_cases": 10,
    "message": "成功提交 10 个用例到评估队列"
  },
  "message": "成功提交 10 个用例到评估队列"
}
```

Schema 落位：`api_gateway/schemas/evaluation.py` 的 `TaskReevaluateInput`（task_id / reevaluate_type='all' / reextract_device_output=False）与 `TaskReevaluateResult`（total_cases / queued_cases / reextracted_cases / message），现有实现。前端侧 `TaskReevaluateResult` Domain 模型（`domain/model/dimension.ts`）经 `evaluationAdapter.toTaskReevaluateResult` 做 snake_case ↔ camelCase 映射。

#### 3.2.2 错误响应

```json
{
  "success": false,
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "未找到任务"
  }
}
```

其余错误：任务未终态（"只有已完成/失败/停止/暂停/跳过状态的任务才能重新评估"）、无测试结果、无需要重新评估的用例。

【适配说明：准入门槛由 V9.7.10 的 completed/failed 两态扩展为 `TaskStatus` 五个终态（COMPLETED/FAILED/STOPPED/PAUSED/SKIPPED）；校验收敛在 api_gateway `EvaluationCommandService.reevaluate_task_results()`（CQRS Command），evaluation_service 不重复校验。】

### 3.3 核心逻辑

#### 3.3.1 重新评估类型判断

落位：`evaluation_service/domain/services/reevaluation_service.py`（领域服务，现有）。

**全部用例 (reevaluateType = "all")：** `collect_cases_all()`
- 遍历任务的所有 TestResult
- 筛选条件: `execution_status = 'completed'` 且 `algorithm_result` 不为空
- 对每个用例重新提交评估

**仅失败用例 (reevaluateType = "failed")：** `collect_cases_failed()`
- 查询所有 `TestResultDimension.status = 'failed'` 的记录
- 通过关联获取对应的 TestResult
- 筛选条件: 对应的 TestResult `execution_status = 'completed'` 且 `algorithm_result` 不为空
- 使用 Set 去重，避免同一结果有多个失败维度时被重复添加

【适配说明：V9.7.10 在 Controller 内联完成筛选取数；V9.7.31 按 CQRS 读写分离收敛为领域服务方法，api_gateway 命令侧只做准入校验与转发，不触碰查询细节。】

#### 3.3.2 算法结果与参考参数获取

**算法结果 (algorithm_result):**
算法结果存储在 `test_results.algorithm_result` 字段中，包含经过字段映射转换后的数据（如 `rttm_res`、`stm_res`、`asr_result` 等）。

重要提示：
- `algorithm_result` 是测试执行后经过字段映射转换的**映射后数据**
- `result_data.raw_results` 只包含设备返回的原始数据（如 `fix_rttm_content`、`fix_stm_content`），**不能直接用于重新评估**
- physical 任务若勾选 `reextract_device_output`，则先从存档日志重提取设备输出并覆盖 `result_data`，再走上述映射数据路径

重新评估时必须从 `result.algorithm_result` 读取数据，否则评估 payload 会缺少必需的映射字段。

**参考参数 (adjusted_reference_params):**
参考参数存储在 `test_results.result_data.adjusted_reference_params` 中，格式如下:

```json
{
  "adjusted_reference_params": [
    {
      "code": "asr_rerference_text",
      "type": "text",
      "api": "...",
      "e2e": "与观，点陪你打开文艺电影的盲...",
      "annotation_code": "asr",
      "annotation_format": "text"
    },
    {
      "code": "rttm_ref",
      "type": "rttm",
      "api": {...},
      "e2e": {...},
      "annotation_code": "diarization",
      "annotation_format": "rttm"
    }
  ]
}
```

在重新评估时，需要根据 `device_type`（**适配**：原"测试类型 api/e2e"）选择对应通道的参数值：`physical` 取 e2e 通道值，`http_api` / `websocket_api` 取 api 通道值。

#### 3.3.3 重新提取设备输出（reextract_device_output，**新增**）

- **仅 physical（E2E）支持**：`ReevaluationExecutor._run_reevaluation` 经 `device_result_acl_repository.reextract_result` 从存档日志重提取设备原始输出，重提取成功后覆盖结果数据再进入评估（`reextracted_cases` 计数返回）。
- **http_api / websocket_api 不支持**：两类通道的算法结果由执行侧 adapter（HttpAPIAdapter / RealtimeAPIAdapter）在执行时直接保存，无存档重提取语义；请求携带该参数时仅执行重新评估（前端仅对 physical 任务展示该复选项）。

#### 3.3.4 异步处理（CQRS + 单例执行器）

V9.7.10 的线程池模型替换为 **CQRS 命令 + 微服务异步执行**：

1. api_gateway 收到命令并完成准入校验后，经 `infrastructure/acl/reevaluation_acl_repository.py`（Port 见 `domain/repositories/acl/`）→ `infrastructure/grpc_proxies/evaluation_proxies.py` 调用 gRPC `Reevaluate`，立即返回 HTTP 响应
2. evaluation_service `ReevaluationExecutor`（`application/handlers/reevaluation_executor.py`，单例）：`submit(task_id, reextract_device_output, reevaluate_type)` → 任务置 `REEVALUATE_QUEUED` → `_check_queue`（Redis 队列检查，防重复提交）→ 置 `REEVALUATING` → `_run_reevaluation`
3. 每个用例内:
   - 清除旧的 test_result_dimensions 记录
   - 更新 task_case_relations.evaluation_status = QUEUED（取 `EvaluationStatus` 枚举）
   - 从 `result.algorithm_result` 获取映射后的算法结果
   - 从 `result.result_data.adjusted_reference_params` 按 `device_type` 通道获取参考参数
   - 组装评估参数并经 gRPC `EvaluateCase` 提交评估
4. 多轮/单轮分派：`_reevaluate_multi_round`（按 device_type 判定多轮语义）/ `_reevaluate_single`
5. 评估收尾 `post_evaluation.py` 发布 `CASE_EVALUATION_COMPLETED`（`EventChannel.CASE_EVENTS`）

**执行器基座与可靠性（现有设施）:**
- 执行器统一继承 `BaseExecutor` 五 mixin（`shared/infrastructure/base_executor/_base.py`：ControlMixin / LoggingMixin / ParamsMixin / ResultsMixin / DbMixin），重评估执行链复用其日志、参数、结果落库能力
- 孤儿任务收养：服务重启导致中断的 `REEVALUATING` 任务，由 task_service 调度器 `_adopt_orphan_tasks`（`core/execution_engine/mixins/scheduler.py`）基于 `worker_instance_id` + `RedisServiceRegistry`（`shared/utils/service_registry.py`）识别并收养重跑

【适配说明：V9.7.10 "主线程收集 + 每用例一线程"的进程内并发，替换为 api_gateway 命令转发（无业务逻辑）+ evaluation_service 单例执行器 + Redis 队列的状态机模型；批量规模阈值走配置项，不硬编码。】

### 3.4 评估参数构建

评估参数组装语义（V9.7.31 以 device_type 为通道语义，既有 test_type 键保留兼容既有评估分派）:

```python
full_case_params = {
    'algorithm_type': algorithm_type,
    'algorithm_params': test_case.config.get('algorithm_params', {}),
    'reference_params': reference_params  # 从 result_data 按 device_type 通道获取
}

eval_params = CaseParameterExtractor.get_evaluation_params(
    case_config=full_case_params,
    algorithm_result=algorithm_result,
    device_type=device_type        # （**适配**）原 test_type；DeviceType: physical/http_api/websocket_api
)
eval_params['algorithm_type'] = algorithm_type
eval_params['device_type'] = device_type   # 经 gRPC EvaluateCaseRequest 扩展字段传递（见《06_评估与前端.md》3.1）
```

【适配说明：V9.7.10 按 test_type（api/e2e）选择参考参数并写入 eval_params；V9.7.31 通道语义统一为 device_type（physical/http_api/websocket_api），经 gRPC `EvaluateCaseRequest` 扩展字段传递；eval_params 既有 `test_type` 键（'e2e'/'api'）保留兼容，路由/分派一律以 device_type 为准，TaskType 不引入 'realtime_api'。】

## 4. 前端设计（DDD 四层）

前端按用户 DDD 四层规则落位：Presentation（views/components）只 import camelCase Domain 与 composables（Ports）；Application（composables/store）编排用例；Domain（domain/model + enums.ts）零依赖；Infrastructure（api/adapters/dto/http/socket）是唯一知道 snake_case 的层。

### 4.1 任务列表操作按钮

| 按钮 | 显示条件 | 图标 | 类型 |
|-----|---------|------|------|
| 重新评估 | `FINISHED_STATUSES.includes(task.status)`（终态枚举合集，`domain/enums.ts`） | fa-sync-alt | info |

落位：`views/Tasks/Tasks.vue`（操作按钮定义）+ `components/task/TaskCard.vue`（`REEVALUATE_QUEUED` 状态图标 fa-hourglass-half，现有）。

【适配说明：显示条件由 V9.7.10 的 `status === 'completed' || status === 'failed'` 字面量判断，改为取 `FINISHED_STATUSES` 枚举集合（COMPLETED/FAILED/STOPPED/PAUSED/SKIPPED/MERGED），与后端准入门槛对齐，禁止魔法字符串。】

### 4.2 用户交互

1. 用户点击"重新评估"按钮
2. 弹出 `ReevaluateSelectModal`（`components/common/modal/ReevaluateSelectModal.vue`，现有）:
   - 单选评估类型: 仅重新评估失败用例 / 重新评估全部用例

### 4.3 API 调用（DDD 四层链，全部现有实现）

| 层 | 文件 | 职责 |
|---|------|------|
| Presentation | `views/Tasks/Tasks.vue` + `views/Tasks/tasks.ts` | 按钮触发，只见 Domain 类型与 composable，无 snake_case |

## 8. 注意事项

1. **状态机与并发**: `ReevaluationExecutor` 为单例，重评估经 `REEVALUATE_QUEUED → REEVALUATING` 状态机 + Redis 队列检查（_check_queue）防重复提交；准入状态校验收敛在 api_gateway 命令服务（CQRS），禁止散落校验
2. **孤儿任务**: 服务重启中断的 REEVALUATING 任务由 task_service `_adopt_orphan_tasks` 基于 `worker_instance_id` + `RedisServiceRegistry` 收养，避免任务永久悬挂
3. **算法结果来源**: 重新评估必须从 `result.algorithm_result` 获取映射后的算法结果，不能从 `result_data.raw_results` 直接获取，否则评估 payload 会缺少 `rttm_res`、`stm_res` 等必需字段；physical 任务勾选重提取时以重提取后的数据为准
4. **参考参数**: 重新评估依赖 result_data 中的 adjusted_reference_params，需确保历史数据包含该字段；参数通道按 `device_type` 选择（physical → e2e 通道，http_api/websocket_api → api 通道）
5. **重提取限定**: `reextract_device_output` 仅对 physical（E2E）生效；http_api/websocket_api 的结果由 adapter 执行时保存，前端仅对 physical 任务展示该选项
6. **枚举化**: 所有状态值取 `shared/models/common_enums.py` + `shared/utils/status_constants.py`（前端 `domain/enums.ts` 镜像），禁止魔法字符串/魔法数字；`DeviceType`（**新增**）取代 task.type/test_type 作为通道语义
7. **配置化**: 重评估队列与批量规模阈值走配置项，禁止硬编码魔法数字
8. **事件负载**: `CASE_EVALUATION_COMPLETED` 事件 payload 只携带 task_id/result_id/test_case_id 指针，帧结果等大字段不进事件总线
9. **评估状态**: 重新评估会清除旧的 test_result_dimensions 记录，请提前做好数据备份

# 任务重新评估功能设计文档

## 1. 功能概述

### 1.1 功能描述
任务重新评估功能允许用户在测试任务结束后，对任务内已完成评估的用例结果进行重新评估。用户可以选择重新评估全部用例，或仅重新评估之前评估失败的用例。

### 1.2 适用场景
- 评估维度配置发生变化，需要重新评估历史任务结果
- 评估API服务更新，需要用新版本API重新评估
- 特定用例评估失败，修复后需要重新评估
- 用户对评估结果有疑问，需要重新运行评估

### 1.3 目标用户
- 测试工程师
- 质量管理人员
- 算法研究人员

## 2. 需求分析

### 2.1 功能需求

| 需求编号 | 需求描述 | 优先级 |
|---------|---------|--------|
| REQ-001 | 支持对已完成任务重新评估全部用例 | 高 |
| REQ-002 | 支持仅重新评估失败的用例 | 高 |
| REQ-003 | 重新评估应在后台异步执行，不阻塞用户界面 | 高 |
| 重新评估时应保留原有的算法执行结果和参考参数 | 高 |
| REQ-005 | 重新评估后应更新评估状态和结果 | 中 |
| REQ-006 | 只能在任务状态为 completed 或 failed 时才能重新评估 | 中 |

### 2.2 用户交互流程

```
用户操作流程:
1. 用户在任务列表页面找到已完成/失败的任务
2. 点击任务操作按钮
3. 选择"重新评估"选项
4. 在弹窗中选择评估类型:
   - 全部用例: 重新评估任务内所有执行成功的用例
   - 仅失败用例: 仅重新评估之前评估结果为 failed 的用例
5. 确认后，系统异步提交评估任务
6. 用户收到成功提示，评估任务在后台执行
```

## 3. 技术设计

### 3.1 数据模型

#### 3.1.1 相关数据表

| 表名 | 作用 |
|-----|------|
| test_tasks | 任务表，存储任务基本信息 |
| test_results | 测试结果表，存储每个用例的执行结果和算法结果 |
| test_result_dimensions | 评估维度结果表，存储每个维度的评估结果 |
| task_case_relations | 任务-用例关联表，存储用例在任务中的评估状态 |

#### 3.1.2 关键字段

**TestResult 表:**
- `execution_status`: 执行过程状态 (pending/running/completed/stopped/failed)
- `algorithm_result`: 算法执行结果 (JSON)
- `result_data`: 原始测试结果数据 (JSON)，包含 `adjusted_reference_params`

**TestResultDimension 表:**
- `status`: 评估结果状态 (passed/failed)
- `evaluation_status`: 评估过程状态 (pending/running/completed/stopped)

### 3.2 API 设计

#### 3.2.1 重新评估接口

**请求:**
```
POST /api/v1/evaluation/task/reevaluate
Content-Type: application/json

{
  "taskId": 123,           // 任务ID
  "reevaluateType": "all"  // 评估类型: "all"(全部) 或 "failed"(仅失败)
}
```

**响应:**
```json
{
  "success": true,
  "data": {
    "totalCases": 10,
    "queuedCases": 10,
    "message": "成功提交 10 个用例到评估队列"
  },
  "message": "成功提交 10 个用例到评估队列"
}
```

#### 3.2.2 错误响应

```json
{
  "success": false,
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "未找到任务"
  }
}
```

### 3.3 核心逻辑

#### 3.3.1 重新评估类型判断

**全部用例 (reevaluateType = "all"):**
- 遍历任务的所有 TestResult
- 筛选条件: `execution_status = 'completed'` 且 `algorithm_result` 不为空
- 对每个用例重新调用评估服务

**仅失败用例 (reevaluateType = "failed"):**
- 查询所有 `TestResultDimension.status = 'failed'` 的记录
- 通过 JOIN 获取关联的 TestResult
- 筛选条件: 对应的 TestResult `execution_status = 'completed'` 且 `algorithm_result` 不为空
- 使用 Set 去重，避免同一结果有多个失败维度时被重复添加

#### 3.3.2 算法结果与参考参数获取

**算法结果 (algorithm_result):**
算法结果存储在 `TestResult.algorithm_result` 字段中，包含经过字段映射转换后的数据（如 `rttm_res`、`stm_res`、`asr_result` 等）。

重要提示：
- `algorithm_result` 是 E2E 测试执行后经过 `convert_device_output` 转换的**映射后数据**
- `result_data.raw_results` 只包含设备返回的原始数据（如 `fix_rttm_content`、`fix_stm_content`），**不能用于重新评估**

重新评估时必须从 `result.algorithm_result` 读取数据，否则评估 payload 会缺少必需的映射字段。

**参考参数 (adjusted_reference_params):**
参考参数存储在 `TestResult.result_data.adjusted_reference_params` 中，格式如下:

```json
{
  "adjusted_reference_params": [
    {
      "code": "asr_rerference_text",
      "type": "text",
      "api": "...",
      "e2e": "与观，点陪你打开文艺电影的盲...",
      "annotation_code": "asr",
      "annotation_format": "text"
    },
    {
      "code": "rttm_ref",
      "type": "rttm",
      "api": {...},
      "e2e": {...},
      "annotation_code": "diarization",
      "annotation_format": "rttm"
    }
  ]
}
```

在重新评估时，需要根据测试类型 (api/e2e) 选择对应的参数值。

#### 3.3.3 异步处理

由于评估任务可能较多，采用线程池异步处理:

1. 主线程收集需要重新评估的用例列表
2. 为每个用例启动一个后台线程
3. 主线程立即返回 HTTP 响应，不等待评估完成
4. 每个线程内:
   - 清除旧的 TestResultDimension 记录
   - 更新 TaskCase.evaluation_status = 'queued'
   - 从 `result.algorithm_result` 获取映射后的算法结果
   - 从 `result.result_data.adjusted_reference_params` 获取参考参数
   - 使用 CaseParameterExtractor 构建评估参数
   - 调用 EvaluationService.evaluate_case()

### 3.4 评估参数构建

使用 `CaseParameterExtractor.get_evaluation_params()` 统一构建:

```python
full_case_params = {
    'algorithm_type': algorithm_type,
    'algorithm_params': test_case.config.get('algorithm_params', {}),
    'reference_params': reference_params  # 从 result_data 获取
}

eval_params = CaseParameterExtractor.get_evaluation_params(
    case_config=full_case_params,
    algorithm_result=algorithm_result,
    test_type=test_type
)
eval_params['algorithm_type'] = algorithm_type
eval_params['test_type'] = test_type
```

## 4. 前端设计

### 4.1 任务列表操作按钮

在任务列表的操作按钮区域添加"重新评估"按钮:

| 按钮 | 显示条件 | 图标 | 类型 |
|-----|---------|------|------|
| 重新评估 | status === 'completed' \|\| status === 'failed' | fa-sync-alt | info |

### 4.2 用户交互

1. 用户点击"重新评估"按钮
2. 浏览器弹出确认对话框，显示两个选项:
   - 确定 = 重新评估全部用例
   - 取消 = 重新评估失败用例
3. 用户选择后点击确认
4. 系统调用 API 提交评估任务
5. 显示成功/失败提示

### 4.3 API 调用

```typescript
// frontend/src/utils/api.ts
async reevaluate(id: string | number, reevaluateType: string = 'all') {
  return request('POST', `/evaluation/task/reevaluate`, {
    taskId: id,
    reevaluateType
  });
}
```

## 8. 注意事项

1. **线程安全**: 评估服务使用全局单例，多线程调用时需要注意数据库会话隔离
2. **算法结果来源**: 重新评估必须从 `result.algorithm_result` 获取映射后的算法结果，不能从 `result_data.raw_results` 获取，否则评估 payload 会缺少 `rttm_res`、`stm_res` 等必需字段
3. **参考参数**: 重新评估依赖 result_data 中的 adjusted_reference_params，需确保历史数据包含该字段
4. **评估状态**: 重新评估会清除旧的 TestResultDimension 记录，请提前做好数据备份
5. **性能考虑**: 大批量评估任务建议分批提交，避免瞬时线程过多

# 任务重新执行功能设计文档

> 版本：V9.7.31 v1.0（2026-10-14）｜负责人口头需求落文档初始稿（待拍板项文中标注）
>
> 与《重新评估功能设计文档》《任务重新评估功能设计文档》《任务重新评估与重新提取功能设计文档》并列：**重新执行 = 执行域动作**（重跑测试链路），**重新评估 = 评估域动作**（不重跑执行，仅重算/重提取评估）。

## 1. 概述

### 1.1 功能目标

- 支持已结束任务基于原配置重新发起执行（整任务重执行）
- 支持选择性重执行：按用例粒度选择部分用例重执行（INT-302 口径）
- 重执行复用既有任务执行链路，不新建执行通道

### 1.2 术语

| 术语 | 含义 |
| --- | --- |
| 整任务重执行 | 对任务全部用例按原配置重新执行 |
| 选择性重执行 | 仅选中用例重新执行（INT-302） |
| 重新评估 | 不重跑执行，仅重新评估（另有三份文档承载） |

## 2. 入口与触发

| 入口 | 场景 | 依据 |
| --- | --- | --- |
| 任务卡片「重新执行」按钮 | 任务列表页对已结束任务发起 | 与重新评估入口对称（任务卡片+详情双入口） |
| 执行详情「重新执行」按钮 | 任务执行详情模态窗内发起 | 同上 |
| E2E 结果页「重新测试」 | 重新执行相同配置的测试 | 端到端测试功能设计文档 §5.3.1 |
| 导入任务后重新执行 | 导入的任务在目标服务器重跑 | 任务数据导入导出功能设计文档 UC-05 |

## 3. 执行语义

```text
已结束任务（completed/failed/stopped）
  -> 用户点击重新执行（整任务或选择用例）
  -> 基于 Task.config + Task.algorithm_params + 关联用例/被测设备/API 原样重跑
  -> device_type 路由复用主链路（physical → e2e_test_service / http_api·websocket_api → api_test_service）
  -> 执行完成后生成新的 TestResult 和 TestResultDimension
  -> 报告按新执行结果生成
```

- 复用现有 queued/running/completed 执行链路与 Redis 队列调度，不旁路（UC-05 口径「复用现有任务执行功能」）
- 版本任务（正式任务）的重执行不适用本流程：走《任务发布功能设计文档》§4.2——读发布快照新建日常任务执行，每次执行都是新日常任务并记录来源版本

## 4. 状态语义（与双状态的关系）

- 重执行触发后，任务执行状态重置并重新进入执行生命周期（pending/queued/running/…，映射见 `02_任务管理/status_fields_relationship.md` §8.2）
- 评估状态在执行完成后重新流转（§8.3），执行状态与评估状态**两维独立**展示（双徽章口径，INT-301）
- 选择性重执行时，未选中的用例及其结果状态不受影响（INT-302）

## 5. 约束与待拍板项

| # | 事项 | 基准 | 状态 |
| --- | --- | --- | --- |
| 1 | 可重执行状态集合 | completed/failed/stopped（对齐任务发布规则 §5.1 终态集合）；queued/running/paused 不允许 | **已拍板（负责人 2026-10-15）**：三态准入确认，pending 不允许、需先停止。前端重执行按钮现含 PENDING（`Tasks.vue:608`），与拍板不符，缺陷对齐卡另行开出 |
| 2 | 旧执行结果去留 | 新结果生成新 TestResult（UC-05 既定）；旧结果是否保留可查（归档/覆盖） | **已拍板（负责人 2026-10-15）**：直接覆盖，不归档。开发注意：报告引用链与 excluded 审计口径对齐 INT-305 软删留痕先例，重执行实现必须保证覆盖后报告聚合正确 |
| 3 | 重执行中的停止 | 复用任务停止链路（INT-308：全链路 stop_event 传播） | 既定，随 INT-308 验收 |
| 4 | 选择性重执行入口选择器 | 按用例勾选重执行、按维度选择重评估 | INT-302 交付口径 |
| 5 | 人工复核结果覆盖提醒 | 存在人工复核结果的任务发起重执行/重评估前，硬确认提醒「人工复核填写的结果将被覆盖」（[测试结果人工复核功能设计文档](测试结果人工复核功能设计文档.md) §4，负责人口头需求 2026-10-14） | 已落文档，随复核功能交付 |

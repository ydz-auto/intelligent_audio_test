GPT 管线接入设计与测试文档

版本：v1.2 日期：2026-11-26 状态：待评审 范围：管线只执行，平台负责评估与报告
一句话：HTTP 接口支持两种下发用例的方式——按轮下发（平台逐轮驱动，默认）和按用例下发（整条用例一次下发）。建任务时像普通 API 一样勾选目标，再选一下用哪种下发方式，平台按该选择挑执行器。
管线只做执行：收用例 → 跑 → 回原始结果与两条 wav 地址；不评估、不算分、不写平台库。评估、落库、报告全部在平台侧，且复用现有链路。

1管线要做什么（对外契约）

管线对外只暴露 4 个 HTTP 接口 + 1 个回调用例，其余什么都不用管：

接口方法说明
/executionsPOST下发一条用例的一次执行（整例，含全部轮次）；立即返回受理 {success, execution_id}，异步执行；同一 tc_rel_id + 尝试序号 重复下发返回原实例
/executions/{execution_id}/stopPOST停止该执行实例，幂等
/executions/{execution_id}/statusGET状态 / 进度 / 结果（平台回调失败时的轮询通道）
/healthGET健康检查
回调 callback_urlPOST执行完成后由管线调用平台回调地址，回原始结果（见 §2.2）
  • 鉴权：平台 → 管线用 Authorization: Bearer <token>；管线 → 平台用下发时给的一次性 callback_token。
  • 不评估：管线不调用任何评估接口、不计算分数、不回传 round_evaluation / aggregated；即使回了，平台也会丢弃。
  • 不读平台库：用例、轮次、算法与参考参数、混音音频全部由平台在下发 payload 里给全，管线不做参数展开、不查用例定义。
  • 不落库：管线不需要写平台任何表，只回结果。

2数据格式

2.1 平台 → 管线：下发 payload

POST /executions
Authorization: Bearer <token>

{
  "task_id": 123, "tc_rel_id": 88, "test_case_id": "201",
  "algorithm_type": "voice_llm",
  "rounds": [
    {"round_number": 1, "query": "你好",
     "audio_b64": "<平台混音后的音频，可选>", "audio_id": 303,
     "is_interruption": false, "interruption_delay_ms": 1000}
  ],
  "session_mode": "full", "session_timeout": 60,
  "algorithm_params": {}, "reference_params": {},
  "callback_url": "http://<api_test_service>/internal/gpt-pipeline/callback",
  "callback_token": "<一次性 token>"
}

不含任何评估维度 / 权重 / 评分字段——评估参数留在平台侧。

2.2 管线 → 平台：回调体

POST {callback_url}
X-Callback-Token: <下发时的一次性 token>

{
  "task_id": 123, "tc_rel_id": 88, "test_case_id": "201",
  "execution_status": "completed",       // completed / failed / stopped
  "response_time": 6600,                 // ms
  "algorithm_result": { "...见 2.3..." },
  "user_wav": "用户语音 wav 地址", "ai_wav": "AI 回复 wav 地址",
  "event_log": [],                       // 归一化事件时间线（打断/时序）
  "frame_results": [],                   // 逐 chunk 帧结果（可选）
  "first_frame_ms": 300,
  "error_message": null
}
音频传地址，不传文件体。平台评估侧原生支持 本地路径 / oss:// / http(s)://，自行解析为字节后送评估计算器。 管线二选一：① 回调带 http(s) 可下载 URL（最简）；② 平台下发时附 OSS 预签名上传 URL，管线直传后带 oss:// 路径回调。 两条地址平台原样并入 algorithm_result.user_wav / ai_wav 与 EvaluateCase.user_wav / ai_wav，不做文件搬运。

2.3 algorithm_result 格式（平台评估侧按此消费）

{
  "session_id": "a1b2c3d4-...", "round_count": 4,
  "total_latency": 6.6, "context_mode": "full", "error": null,
  "rounds": [
    {"roundNumber": 1,
     "input": {"text": "你好，我想了解一下天气", "audio_id": 303},
     "output": "今天北京天气晴朗……",
     "output_audio_path": null,
     "latency": 1.23,
     "response_metrics": {"first_token_latency": 0.3, "tokens_per_second": 25}}
  ]
}
round_evaluation 与 aggregated 由平台评估服务算完回填，管线不要填。 格式事实源：doc/voice_llm/98_API用例端到端示例.md。

2.4 状态取值（小写，按此回传）

字段合法值
execution_status（回调）completed / failed / stopped
/executions/{id}/status 返回running / completed / failed / stopped

3平台怎么接

HTTP 接口支持两种下发方式，由用户在界面上选（建任务时随 API 目标一起勾选）：

下发方式谁编排多轮执行器
按轮下发（默认）平台：逐轮调一次接口，轮次间上下文由平台维护现有 APISessionExecutor，不改
按用例下发对方：整条用例一次下发，多轮上下文在其内部完成新增 PipelineSessionExecutor
用户视角：照常选 API 目标，多选一个「下发方式」。
· API 目标仍是一条普通 API 记录（protocol=http、streaming=false），建任务时和普通 API 一样勾选；
· 该目标旁边提供「按轮 / 按用例」下拉，默认按轮（不选 = 现行为，零回归）；
· 选择随用例路由行落库（case_devices[].dispatch_mode），执行时由平台按该值选执行器。
  • 不新增设备类型：路由行 device_type 仍是 http_api，与普通 HTTP API 完全一致；参数作用域、统计、报告、评估口径都按 API 道处理。
  • 执行入口不变：仍走现有 StartAPITest / StopAPITest / GetAPITestStatus；不新增服务、不新增 proto、不新增端口。
  • 下发方式只影响执行器选择：按轮 → 现有链路原样；按用例 → 新增执行器。两者复用同一套落库 / 评估 / 进度代码。
  • 落库与评估复用现有实现：结果变换后交给 api_result_processor（SubmitResult / 状态回写 / 进度）与 evaluation_submitter（提交评估），失败收敛复用 _fail_tc_rel。

4时序

task_service │ ① StartAPITest(task_id, device_type=http_api, device_id=apis.id, case_ids) ← 现有契约 │ （路由行带用户选的下发方式 dispatch_mode = per_round / per_case） ▼ api_test_service（按下发方式选执行器） │ ② per_round → APISessionExecutor（按轮，现行为不变） │ ② per_case → PipelineSessionExecutor（按用例） │ ③ 组装 payload：用例 / rounds / 算法与参考参数 / 平台混音音频 │ ④ POST {pipeline}/executions ← 整用例 + Bearer token ▼ GPT 管线（只执行） │ ⑤ POST {callback_url} ← 原始结果 + user_wav / ai_wav │ （回调不可达：平台轮询 GET {pipeline}/executions/{id}/status） ▼ api_test_service 复用现有链路： SubmitResult → UpdateTaskCaseStatus(tc_rel_id) → NotifyProgress / NotifyCaseCompleted → EvaluateCase ▼ evaluation_service 评分后自动回写 task_service（现有链路，零改动）

6可靠性兜底

场景兜底
管线不可达 / 下发失败走现有失败收敛 _fail_tc_rel：用例置 failed + error_message，评估状态同步收口（否则主循环死等不收敛）
回调丢失平台按配置间隔轮询 /executions/{id}/status，拿到终态后走同一回写序列
重复回调按 execution_id + 尝试序号 幂等；重复请求返回首次受理结果，不重复落库、不重复入评估
平台重启执行实例表落库，重启后恢复轮询与停止映射；未知 execution_id 拒绝
停止任务StopAPITest → 逐实例调管线 /stop → 联动取消评估 → 未回结果的路由行置 stopped
管线报失败回 execution_status=failed + error_message；平台仍落库留痕，不提交评估
大结果轻量入 result_data，大字段走 result_data_path 外置（现有机制）；音频不入库
同一用例多路由行透传 tc_rel_id，按路由行精确回写，兄弟行互不覆盖（INT-604）

8验收与里程碑

8.1 验收

  • P0 用例全部通过；P1 全通过或有书面豁免。
  • 管线只执行：下发 payload、回调体、管线日志均不出现评估调用或评分字段；评估分只由平台产出。
  • 真管线至少 1 条多轮用例端到端跑通：建任务 → 管线执行 → 评估 → 报告可见。
  • 按轮路径回归零失败；停止 / 失败 / 回调丢失三条兜底有实测记录。
  • §1、§2 契约与管线侧逐字段核对一致后冻结。

8.2 里程碑

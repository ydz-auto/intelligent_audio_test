GPT 管线执行器接入设计与测试文档

版本：v0.3（评审稿） 日期：2026-11-26 状态：待评审 适用：Intelligent-Audio-TEST 执行域
一句话结论：新增一个薄桥接执行器 gpt_executor_bridge，对平台装成标准执行器（gRPC），对外部 GPT 管线只说 HTTP。 下发粒度 = 用例（路由行 tc_rel_id），不是整任务；管线执行完回调两条 wav 音频地址（user_wav / ai_wav，与现行口径一致，不传文件体），平台评估。 GPT 管线只开放 3 个 HTTP 接口（启动 / 停止 / 状态）+ 调 1 个回调；平台执行链只加一条路由分支。 评估结果回写由 evaluation_service 现有链路自动完成，管线与桥接都不搬运评估分。

1背景与目标

外部 GPT 执行管线（如 GPTLive，参考项目事件 WORK-20261123-003）要作为执行器接入平台：平台把用例信息下发给管线，管线执行完成后向评估系统发起评估，评估完成后结果回到平台。

  • 角色澄清：GPT 管线不是被测 API（DUT），而是与 e2e_test_service / api_test_service 平级的执行器。
  • 关键口径：按平台现有架构，「评估完成后传回平台」由 evaluation_service 评分后自动回写 task_service，不需要管线搬运评估结果。管线职责止于「接任务 → 执行 → 回写原始结果 → 提交评估」。
  • 非目标：不改现有执行器（e2e / api）行为；不改评估计算器；不做管线内部实现约束。

3方案选型

维度方案 A：管线直接实现执行器 gRPC 契约方案 B：薄桥接执行器（推荐）
管线侧负担重：实现入站 gRPC + 全部出站 ACL（SubmitResult / EvaluateCase / 参数展开 / 音频解析）轻：3 个 HTTP 接口 + 1 个回调
网络要求管线须可达内部 gRPC 网段（同机 / 反向隧道）双向 HTTPS 即可；回调不可达时桥接轮询兜底
平台改动几乎为零（注册为执行器实例）新桥接服务 + 一条路由分支（5 处，见 §6）
适用场景管线能像执行机一样部署进内网外部 / 跨团队 / 跨网络管线（当前场景）

拍板建议：方案 B。理由：外部管线零 gRPC 负担；桥接复用现有 ACL 仓储代码，平台执行链改动最小且纯新增、不动旧路径。

4总体架构与时序

task_service 执行引擎 │ ① gRPC StartGPTTask(task_id, tc_rel_id, case_ids) ← 新增路由分支 ▼ gpt_executor_bridge（平台侧新服务，薄，无业务逻辑） │ ② 拉全量用例：GetTaskCaseByIds / GetTestCaseDetail / │ ExtractCaseAllParams / audio_service 音频字节 │ ③ HTTP POST {pipeline}/executions ← push 单用例 payload + Bearer token ▼ GPT 管线（外部，只暴露 3 个 HTTP 接口） │ ④ 执行完回调 POST {bridge}/callback/results │ （回调不可达时：桥接轮询 GET {pipeline}/executions/{execution_id}/status 拉结果） ▼ gpt_executor_bridge 转内部 gRPC（固定动作序列）： SubmitResult → UpdateTaskCaseStatus(tc_rel_id) → NotifyProgress / NotifyCaseCompleted → EvaluateCase ▼ evaluation_service 评分后自动回写 task_service（现有链路，零改动）
职责边界：桥接只做「协议转换 + 数据组装 + 兜底」，不做执行编排、不做评估计算。 评估分（round_evaluation / aggregated）由评估服务回填，管线与桥接禁止填写。

5接口契约与数据格式

5.1 桥接入站 gRPC（平台执行引擎调用）新增

// shared/proto/gpt_executor_bridge.proto（草案，消息形状对齐 e2e_test_service.proto）
service GPTExecutorService {
  rpc StartGPTTask(StartGPTTaskRequest) returns (StartGPTTaskResponse);
  rpc StopGPTTask(StopGPTTaskRequest) returns (StopGPTTaskResponse);
  rpc GetGPTTaskStatus(GetGPTTaskStatusRequest) returns (GetGPTTaskStatusResponse);
}
message StartGPTTaskRequest {
  string task_id = 1;
  string tc_rel_id = 2;          // 路由行 ID，必须全程透传
  repeated int32 case_ids = 3;   // 逐用例精确分发（对齐 INT-71）
  string pipeline_config = 4;    // JSON：管线 endpoint / token 引用（预留）
}
// 响应统一 {success, message, data(JSON)}；Stop/Status 入参仅 task_id

桥接地址走 shared/config/service_ports.py 注册（e2e 同款固定地址模式，不引入实例注册表）。

5.2 桥接 → 管线：HTTP 下发（管线要开放的接口）管线侧实现

下发粒度：一条用例路由行（tc_rel_id）一次下发，与 StartAPITest 逐用例精确分发（INT-71）同口径；不存在「整任务打包下发」。停止 / 状态查询按执行实例（execution_id）；任务级停止由桥接逐实例下发。

接口方法说明
/executionsPOST下发一条用例的一次执行，push 单用例 payload；立即返回受理 {success, execution_id}（异步执行）；tc_rel_id 为幂等键，重复下发返回原实例
/executions/{execution_id}/stopPOST停止该执行实例；幂等
/executions/{execution_id}/statusGET状态 / 进度 / 结果（轮询兜底通道）
/healthGET健康检查（建议）
命名口径（v0.3 拍板）：资源叫 /executions（执行实例），不叫 /tasks 也不叫 /testcases。 平台语义里 task = 一批用例，按用例下发叫 tasks 会混淆；/testcases 是用例定义 CRUD（静态配置），管线收到的是「一次执行」而非用例定义管理。 execution 与网关 /api/v1/execution（执行编排）词汇一致。payload 内保留 task_id / tc_rel_id / test_case_id 做关联。

鉴权：Authorization: Bearer <token>（复用 apis 表密钥链）。下发 payload：

{
  "task_id": 123, "tc_rel_id": 88, "test_case_id": "201",
  "algorithm_type": "voice_llm",
  "case_config": {
    "rounds": [
      {"round_number": 1, "query": "你好", "audio_id": 303,
       "audio_bytes_b64": "<可选，桥接解析音频字节>",
       "is_interruption": false, "interruption_delay_ms": 1000}
    ],
    "session_mode": "full", "session_timeout": 60
  },
  "algorithm_params": {}, "reference_params": {},
  "evaluation": {"dimensions": [{"id": 1, "code": "wer", "weight": 50}]},
  "callback_url": "http://<bridge>/callback/results",
  "callback_token": "<一次性 token>"
}

字段来源全部为现有 ACL：GetTaskCaseByIds / GetTestCaseDetail（用例与 rounds）、ExtractCaseAllParams（算法/参考/评估参数）、audio_service（音频字节）。无新数据源。

5.3 管线 → 桥接：结果回调（桥接暴露）新增

POST /callback/results，头带 X-Callback-Token（下发时的一次性 token）：

{
  "task_id": 123, "tc_rel_id": 88, "test_case_id": "201",
  "execution_status": "completed",        // completed / failed / stopped
  "response_time": 6600,                  // ms
  "algorithm_result": { "...见 5.5..." : "" },
  "user_wav": "音频地址（用户语音 wav）", "ai_wav": "音频地址（AI 回复 wav）",
  "event_log": [],                        // 归一化事件时间线（打断/时序分析）
  "frame_results": [],                    // 逐 chunk 帧结果（可选）
  "first_frame_ms": 300,
  "error_message": null
}

桥接收到后固定动作：SubmitResult（拿 result_id）→ UpdateTaskCaseStatus（带 tc_rel_id）→ NotifyProgress / NotifyCaseCompleted → EvaluateCase。回调须幂等（按 task_id + tc_rel_id 去重）。

音频口径（与现状一致，已验证）：传地址，不传文件体。 现行执行器把 wav 落存储（shared/infrastructure/storage，OSS 优先、不可用降级本地磁盘）， 返回带 scheme 的存储路径字符串写入 algorithm_result.ai_wav 随结果落库 （api_test_service/core/realtime_session_executor.py · api_session_executor.py）； 评估侧原生支持 本地路径 / oss:// / http(s):// 三种地址，自行解析为字节后 multipart 发给评估计算器 （evaluation_service/infrastructure/evaluation_api/api_request_handler.py · payload_builder.py）。
外部管线二选一：① 回调直接带 http(s) 可下载 URL（最简，平台侧可达即可）； ② 桥接下发时附平台 OSS 预签名上传 URL，管线直传 wav 后回调带 oss:// 路径（复用 audio_upload_presign 同款机制）。 桥接把两条地址原样并入 algorithm_result.user_wav / ai_wav 与 EvaluateCase.user_wav / ai_wav，不做文件搬运。

7可靠性与兜底矩阵

异常场景兜底策略责任方
管线不可达 / 下发失败分发失败收敛：TaskCase 置 failed + error_message，刷新任务统计与进度（照抄 _execute_api_case 异常路径）桥接 + 执行引擎
回调超时 / 管线回调不可达桥接轮询 GET /executions/{execution_id}/status（间隔可配），拿到终态后走同一回写序列桥接
重复回调按 task_id + tc_rel_id 幂等去重，重复请求返回首次受理结果桥接
回调鉴权失败401 拒绝；token 一次性、随下发派发桥接
停止任务StopGPTTask → 桥接逐实例调管线 /executions/{id}/stop；联动 CancelEvaluation(reason=task_stopped)；未回结果的路由行置 stopped桥接
大结果（音频/帧日志）轻量列 + result_data_path 外置文件（split_result_data 现有机制）；音频不入库桥接
多路由兄弟行全链路透传 tc_rel_id，UpdateTaskCaseStatus 按路由行精确命中（INT-604）桥接
管线执行失败回调 execution_status=failed + error_message；仍 SubmitResult 留痕，不提交评估管线 + 桥接
评估服务不可达结果已落库；评估入队失败重试/告警，用例 evaluation_status 停留 queued，可走任务重新评估补救桥接

## 1. 为什么要外置

`report_cases` 是报告级用例行：一份报告 100~800 例，每例把用例配置**整份**再落一次库，同一份配置在几十份报告里重复。主库实测（容器 `intelligent-audio-test-postgres-1`，库 `intelligent_audio_test`，2026-10-26 06:45–07:15 UTC，只读 psql）：

| 项 | 实测 |
|---|---|
| 行数 / 总大小 / heap | 33,925 行 / 258MB / 64MB |
| 整行快照 distinct（12 个内容列） | 10,843（≈68% 冗余） |
| 9 字段 payload distinct | **10,843——与 12 字段完全相同** |
| 不同 `test_case_id` | 796 |
| 不同 `algorithm_results` | 7,359（全表 450.7MB 文本 → 去重 109.4MB） |
| 报告数 / 每报告用例数 | 204 份；均值 166、p50 138、p95 436、max 793 |

结论：去重的粒度是「用例配置 payload」，不是「报告」。把 payload 内容寻址化（sha256 一个值一份），行上只留指针，**引用集合以 `report_cases` 为准**——对象被多份报告共享，所以不能按报告删。

冻结语义是这张卡的硬约束：`name / description / category / tags / metrics / results / audios / reference_params / algorithm_results` 是**生成报告那一刻的用例配置快照**。去冗余**不得**改成「拿 `test_case_id` 回查 `test_cases` 实时值」——用例后来被编辑或软删，历史报告必须保持原样。

## 2. 快照边界（九字段进快照，五列留行上）

| 归属 | 字段 | 理由 |
|---|---|---|
| 进快照 payload | `name` `description` `category` `tags` `metrics` `results` `audios` `reference_params` `algorithm_results` | 9 字段 distinct 与 12 字段完全相同，去重无损；`metrics` / `results` / `algorithm_results` 占 94% 体积 |
| 留表列 | `id` `report_id` `test_case_id` `algorithm_type` `logs` | 前两个是键；`test_case_id` 是行键（写路径 `_report_children_write_mixin.add_case` / 解引用出口 `ResolvedReportCase` 都用；发布任务冻结已改经 `GetReportCasesRawPayload` 返回，不再直查本列——INT-1996）；`algorithm_type` 有 SQL 谓词（`report_service/infrastructure/persistence/_report_query_mixin.py:503-510`）；`logs` 全表 73KB、**仅 4 个不同值** |
| 指针列（新增） | `snapshot_uri` `snapshot_sha256` `snapshot_bytes` `snapshot_created_at` | 见 §3 |

**明确不存在的概念**：分数 / 轮次 / 执行结果**不是列**——它们分别在 `metrics` / `algorithm_results` / `results` 三个 jsonb 里，随 payload 进快照。任何「差异列留在行上」的写法都是错的。

**payload 必须从 ORM 原始列值构造，不能经响应装配层**：`report_service/application/services/report_aggregation/cases_mixin.py:29` 的 `rs.get('metrics') or {}` 与 `report_service/application/services/report_compare_helpers.py:437`（`:671` 同形，块 `:663-675`）的 `case_record.metrics or {}` 会把 `[]` 折成 `{}`。库里的数据形态：`metrics` `[]` 2,095 行 / `{}` 8 行；`results` `[]` 2,033 行；`algorithm_results` `[]` 1,988 行；`reference_params` `{}` 79 行。两处 `or {...}` 会把 `metrics` / `algorithm_results` 的 `[]` 改写成 `{}`，**折了就破坏逐字节冻结**。取值一律走 ORM 行属性原值，不做任何 falsy 归一。

## 3. 表结构与规范化口径

### 3.1 `report_cases` 新增 4 列（R1）

`snapshot_uri varchar(128)` / `snapshot_sha256 char(64)` / `snapshot_bytes bigint` / `snapshot_created_at timestamptz`
——全部可空、无默认值、无索引（与档3 指针列同风格；R1 期间旧内容列还在，不需要索引）。

- `snapshot_uri` 取值 `db://report_case_snapshots/{sha256}`：沿用本仓 `local://` / `oss://` 的 scheme 标记风格，把**载体**显式记在行上，将来要迁对象存储时键不变。
- `snapshot_sha256` 是解引用时的一等键（回填判据、门禁、sweep 全用它）。
- `snapshot_bytes` / 快照表 `payload_bytes` 记 **gzip 压缩后大小**（与档3 `_bytes` 同口径）。
- `snapshot_created_at` 语义是「该快照对应内容的生成时间」，回填口径见 §6。

### 3.2 新表 `report_case_snapshots`

| 列 | 类型 | 说明 |
|---|---|---|
| `sha256` | `char(64) PRIMARY KEY` | 内容寻址主键，天然幂等 |
| `payload_gz` | `bytea NOT NULL`，`SET STORAGE EXTERNAL` | gzip 后的九字段规范化字节；关掉 TOAST 二次压缩（已经是压缩体） |
| `payload_bytes` | `int` | 压缩后字节数 |
| `created_at` | `timestamptz` | 快照行写入时间（**不是**冻结时间；冻结时间看 `report_cases.snapshot_created_at`） |

**不建 `deleted` 列、不建 `report_id`**——纯内容寻址，引用集合以 `report_cases` 为准，登记多个报告反而制造第二份引用真相。回收走 §7 的 anti-join sweep。

### 3.3 规范化口径（复用，不重写）

100% 复用 `shared/utils/raw_payload.py` 的四个纯函数：

| 口径 | 函数 | 取值 |
|---|---|---|
| 规范化字节 | `canonical_bytes`（`:78`） | `json.dumps(sort_keys=True, separators=(',', ':'), ensure_ascii=False)` + utf-8 |
| sha256 | `sha256_of_bytes`（`:84`） | 对**未压缩**字节计算 |
| 压缩 | `compress`（`:103`） | gzip level 9、`mtime=0`（压缩确定） |
| 解压 | `decompress`（`:108`） | 仅 `gzip.decompress`；sha256 由调用方按 §5 校验，函数本身不校验 |

**不使用 `object_key` / `parse_object_key`**：`shared/utils/raw_payload.py:93-100` / `:112-125` 的 kind 白名单只认 `resp` / `req`，表载体没有 key 形态，档3 模块一行不改。存储层也不复用 `shared/infrastructure/raw_payload_store.py`（绑死 `api_raw_response` / `api_request_body` 两套列），另建 `report_service/infrastructure/persistence/report_case_snapshot_store.py`，但**照抄其读侧纪律**（§5）。

**与档3 的差异**：指针 4 列 vs 档3 的 5 列——少的 `content_type` 在表载体下无意义（表里恒为 `application/json+gzip` 语义，写不出别的值）；档3 的 `uri` 指向对象存储位置，档4 的 `uri` 只记载体 scheme + 主键。

## 4. 写路径

三个写入口统一走「算 sha → 快照表 `INSERT … ON CONFLICT (sha256) DO NOTHING` → 行上写指针」：

- `report_service/application/services/report_data_builder_persist_mixin.py:95`（生成报告 `add_case`）
- `report_service/application/services/report_compare_generator_persist_mixin.py:72`（对比报告：源用例搬运）
- `report_service/application/services/report_compare_generator_persist_mixin.py:159`（对比报告：重算用例）

约束：

1. **payload 从 ORM/入参原始值构造**（§2），不经过 `build_case_dict_from_entity` 这类响应装配层。
2. 一律 `ON CONFLICT (sha256) DO NOTHING`：同值并发插入天然收敛，不需要分布式锁。
3. **R1 期间同时写原 12 个内容列**（供回滚，§6 开关切回列读时要能读）。
4. 先写快照行、再写用例行：快照成功而用例行失败 → 只留孤儿快照（sweep 收，无害）；反序则会出现「行上有指针、表里没内容」的悬空指针。
5. `snapshot_created_at` 写**该行内容的生成时间**；在线路径取当前写入时刻（等价于此后的 `report_cases.created_at`），回填路径取源行 `created_at`（§6）。

## 5. 读路径（解引用出口）

两个读入口统一解引用：先取 `report_cases` 行，再**一次** `JOIN report_case_snapshots` 批量取 `payload_gz`，解压 + 校验 sha256，返回**属性名不变**的行对象（`name` / `description` / `category` / `tags` / `metrics` / `results` / `audios` / `reference_params` / `algorithm_results` + 行上五列），上层一行不用改：

- `report_service/infrastructure/persistence/_report_children_load_mixin.py:110-118`（`load_cases`，报告详情主路径）
- `report_service/infrastructure/persistence/_report_query_mixin.py:402-414`（`get_cases_by_report_id`，对比 / 挑选合并 / 导出复用）

上层不受影响：`_case_po_to_entity`、对比链路 `report_service/application/services/report_compare_helpers.py:429-441` / `:663-675` 全部照旧按属性名读。

**确定性序（INT-2041，实现演进裁定）**：`load_cases` / `get_cases_by_report_id` 显式
`ORDER BY report_cases.id`——回填 UPDATE 会整体改变堆物理序，不写 ORDER BY 时详情 / 导出 /
对比的用例顺序会跟着漂。用例顺序 = id 序（≈插入序），是确定化而非回归。

**键序还原（INT-2041，实现演进裁定）**：快照 payload 按 `canonical_bytes`（`sort_keys=True`
字典序）冻结，而 R1 的 column 读源给的是 PG jsonb 键序（先比键字节长度、再字节 memcmp）。
两者只在「同样遍历字典」的消费方（如按 `output.items()` 展开 `@round:N` 条目）会看到
不同条目顺序。解引用出口 `fetch_batch` 返回前用 `normalize_jsonb_order` 递归还原 jsonb
键序——只动键序、值一个不动，写侧（sha / 快照表 / 指针 / 回填）一字不改。M1 删列后恒走
快照源，该还原保证与历史 column 源逐字节等价。

**读侧纪律（硬约束）**：解压后校验 sha256，不符抛显式错误（如 `ReportCaseSnapshotCorruptError`，message 写明 `report_id` / `sha256`），**不**静默回退到内容列——R1 期间列还在，更要守住这一条，否则兼容层会一直活到 M1 之后。同样禁止「读不到就返回空 `cases`」。行上没有指针（`snapshot_sha256 IS NULL`）或指针悬空（快照行不存在）也由 `resolve_rows` 抛 `ReportCaseSnapshotMissingError`，门禁未归零时切读源即在此显式报错。

**缓存结论：不引入 Redis、不新增进程内 LRU**。`report_service` 现为单副本（`docker ps` 单容器），换表后 793 例报告一次 JOIN 已在百毫秒级，Redis 净收益只在多副本时出现。将来扩副本再按「报告级」而非「按 sha」加缓存——报告用例内容不可变，`report_id → cases` 的失效面天然干净。

## 6. 生命周期与容量（R1 → M1）

### 6.1 R1（本阶段）

建表 + 4 列 + 双写 + 读切换 + 回填。

- **回填判据** `WHERE snapshot_sha256 IS NULL`，**不需要 checkpoint 表**；幂等靠内容寻址 + `ON CONFLICT DO NOTHING`，可中断续跑。
- **进度** = `count(*) FILTER (WHERE snapshot_sha256 IS NOT NULL)` / 总数。
- **门禁** = `count(*) FILTER (WHERE snapshot_sha256 IS NULL OR 快照行不存在)` 必须为 **0**。
- **限流模板**：`scripts/migrations/202610/backfill_raw_payload_pointers_int1807.py`（`main()` `:391-426`，CLI `:395-410`）的 `--gate` / `--apply` / `--batch-groups` / `--sleep`（另有 `--limit-groups` / `--max-consecutive-failures`），批量 200 组 + 批间 sleep。
- **`snapshot_created_at` 回填必须填 `report_cases.created_at`，不能填 `now()`**——否则 33,925 行历史报告的快照时间全变成回填时刻，「生成时间」语义作废。
- **R1 不承诺任何空间回收**：双写 + 回填期间表只会更大，体积指标不属 R1 验收。
- **回滚**：开关 `REPORT_CASE_SNAPSHOT_SOURCE=column|snapshot` 切读源；回滚 = 翻开关 + 回退镜像，代价近零（列与双写都在）。**（M1 已删内容列后本条作废：`column` 读源不复存在，`read_source()` 恒返回 `snapshot`；M1 的回滚 = 按备份恢复。）**
- 新表与 4 列必须登记 `tests/data/schema_baseline.json`（新表一项 + `report_cases` 列表加 4 个列名）与 `scripts/migrations/`，否则 `test_int1565_schema_migration_guard` 会红。

### 6.2 M1（独立窗口）

- `DROP` **9 个 payload 列**：`name` / `description` / `category` / `tags` / `metrics` / `results` / `audios` / `reference_params` / `algorithm_results`；`DROP idx_report_cases_category`（索引列 `category` 同时被删）；`VACUUM FULL report_cases`。
  `id` / `report_id` / `test_case_id` / `algorithm_type` / `logs` 五列**保留**（§2：前两个是键，后三个有 SQL 投影 / SQL 谓词 / 体积可忽略），因此 `idx_report_cases_report_id` / `idx_report_cases_test_case_id` 不动。
  **口径说明**：父卡把这一步写作「DROP 12 个内容列」，这里的 12 指 §1 实测去重时统计的 12 个内容列（含上述保留的 `test_case_id` / `algorithm_type` / `logs`）；`DROP` 的实际范围以 §2 的快照边界为准 = 9 列，否则会删掉 `test_case_id` / `algorithm_type` 的投影与谓词，与 §2、§7 的 M1 前置「发布任务冻结链路改走解引用」（§7 第二条）自相矛盾。
  **PG 16 只 DROP 不 VACUUM FULL 不释放任何磁盘**（同档3 结论）。
- M1 是 DDL 卡：不随同批刷 docker 栈，`VACUUM FULL` 长时间持锁，须选低峰独立窗口。
  **已落地（2026-10-27，INT-1995 + INT-2070 独立窗口部署）**；删列后的复查命令 =
  `python scripts/migrations/202610/drop_report_cases_payload_columns_int1995.py --gate`
  （只读，照常打印门禁 N/A 与指针分布）。

### 6.3 容量

- 对象/快照体量 ≈ **33MB**（198MB 规范化字节 × canonical 0.943 × gzip 0.176）；行侧 33,925 × ~250B + 索引 ≈ 13MB → M1 后 **258MB → ≈46MB（−82%）**。
- 增长 ≈ 300 快照/天 ≈ **0.75MB/天 ≈ 270MB/年**（`report_cases` 当前 ≈950 行/天、≈5.2 份报告/天）。
- 不建 refcount 列的代价就是这 270MB/年，可接受。

- `ReportServiceCleaner.hard_delete_expired` **不得**删除 `report_case_snapshots` 行（`report_service/infrastructure/persistence/soft_delete_cleaner.py:40` 只 `DELETE report_cases`）：快照被多份报告共享，按报告删会打断别的报告的解引用。
- 孤儿由独立低频 sweep（建议月度 / 手动）收，**必须在 `hard_delete_expired` 之后跑**
  （脚本：`scripts/migrations/202610/sweep_report_case_snapshots_int1995.py`，默认只打印孤儿统计，`--apply` 执行）：

  ```sql
  DELETE FROM report_case_snapshots
   WHERE sha256 NOT IN (
     SELECT snapshot_sha256 FROM report_cases WHERE snapshot_sha256 IS NOT NULL
   );
  ```

  子查询**必须显式滤 NULL**——PG 的 `NOT IN` 遇 NULL 返回空集，一条都删不掉。
- **不建 refcount 列**：软删 / 搬运 / 替换 / 导入四条链路都会让计数漂移，权威引用集合永远可从 `report_cases` 重算；anti-join 是亚秒级。
- 备份恢复：快照与用例行在同一库同一份备份里，成对恢复不存在跨介质坑（这也是选表载体而非对象存储的理由之一）。

## 8. 冻结语义与验收口径

1. **冻结（正向）**：生成报告 R → 抓 `GET /reports/{R}/cases` 与 gRPC `GetReportCases` 基线 → 编辑 `test_cases`（`name` / `metrics`）+ 软删该用例 → 再抓两路，`canonical_bytes` **逐字节相同**，且 `report_cases.snapshot_sha256` 不变。
2. **冻结（负向，最硬）**：把 test_case 侧 gRPC 客户端 / 仓储方法 monkeypatch 成 `raise AssertionError`，再调报告详情 → **不得触发**。这条才真正证明「不回查」。
3. **四类读路径等价**：详情 / 导出 / 对比 / 挑选合并，抽样 ≥ 20 份跨用例报告（**必须含那份 793 例的**），对切换前后同一响应 JSON 做 `canonical_bytes` 比对；导出与对比各自覆盖 gRPC 与 HTTP 两路。**比对必须落在 `json.loads` 之后**——库里实际列类型是 **jsonb**（ORM 写的是 `Column(JSON)`，`report_service/infrastructure/persistence/models/report_models.py:144-149`），`::text` 渲染带 `", "` 且键序是 jsonb 短键优先序，语义相等但字节不等。
4. **失败语义**：删掉一行 `report_case_snapshots`（或改一字节让 sha 不符）→ 详情接口**显式报错**（明确 message），禁止返回空 `cases`、禁止回退内容列。
5. **回填**：可中断续跑 / 重复执行幂等；进度可核对；门禁 = 0；`snapshot_created_at` 等于源行 `created_at`。
6. **去重率**：33,925 行回填后快照行数 = **10,843**，偏差 0；同一 payload 的 N 份报告只产生 1 个快照行。
7. **回滚**：`REPORT_CASE_SNAPSHOT_SOURCE=column` 切回列读后，四类读路径结果与切换前 deep-equal。
8. **对外契约不变**：报告详情 / 导出 / 对比的 HTTP + gRPC 载荷形状与今天完全一致（`build_case_item` 展开逻辑不动）。
9. **两阶段指标**：R1 验收**不查表体积**（双写期间更大）；体积指标归 M1（≈46MB）。

## 9. 不做的

- 不把快照拆成「公共部分共享 + 差异覆盖」（运行时拼装 = 新的维护负担，且破坏逐字节冻结）。
- 不引入 Redis 或新的进程内缓存层（见 §5 结论）。
- 不改档3 的 `shared/utils/raw_payload.py` / `shared/infrastructure/raw_payload_store.py`，也不为档4 扩 `object_key` 的 kind 白名单。
- 不做「回查 `test_cases` 实时值」的任何降级——冻结语义优先于体积。
- 不在 R1 做 M1 的 `DROP` / `VACUUM FULL`（另一张卡、独立窗口）。

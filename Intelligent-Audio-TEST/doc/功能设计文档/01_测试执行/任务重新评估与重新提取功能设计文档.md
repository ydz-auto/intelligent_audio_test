# 任务重新评估与重新提取功能设计文档

> 版本：v3.0（V9.7.31 适配版，2026-09-10，同步 V9.7.10 v3.0 语义）
> 变更说明：重新提取仅限物理设备（device_type='physical'），API（http_api / websocket_api）仅支持重新评估。
> V9.7.31 落位：重新评估/重新提取命令为 application command（CQRS），分属 task_service:5001 / evaluation_service:5004；跨服务一律 gRPC；事件经 Redis EventBus（`shared/utils/redis_pubsub.py` 的 EventChannel/EventType）。

## 一、功能概述

本功能用于对已完成的任务进行重新评估或重新提取设备输出，支持两种场景：
1. **重新评估**：对已评估过的用例重新计算评估结果
2. **重新提取**：从设备存档日志中重新提取设备输出，替换原有的测试结果记录

【适配说明】V9.7.31 微服务架构下，执行语义由 `device_type`（physical / http_api / websocket_api，`shared/models/common_enums.py` 的 DeviceType（新增），不引入 'realtime_api' TaskType）决定，取代单体版 task.type/test_type 口径。重新提取仅对 `device_type='physical'`（E2E 链路，e2e_test_service 执行）有意义；http_api / websocket_api 用例的设备输出由 adapter 直接保存（adapter.output），无设备存档。

## 二、API 接口

### 2.1 重新评估 API

**接口**: `POST /api/v1/evaluation/task/reevaluate`（api_gateway:5000，`api_gateway/routes/evaluation_bp.py`，权限 `evaluation:execute`）

**Request Body**:
```json
{
    "task_id": 243,
    "reevaluate_type": "all",
    "reextract_device_output": true
}
```

**参数说明**:

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| task_id | int | 必填 | 任务ID |
| reevaluate_type | string | "all" | 重新评估类型: "all"(全部) / "failed"(仅失败) |
| reextract_device_output | bool | false | 是否同时重新提取设备输出（仅 physical 任务生效） |

**Response**:
```json
{
    "success": true,
    "data": {
        "task_id": 243,
        "total_cases": 10,
        "queued_cases": 8,
        "reextracted_cases": 5,
        "message": "成功提交 8 个用例到评估队列，其中 5 个用例已重新提取设备输出"
    }
}
```

【适配说明】api_gateway 侧（`api_gateway/application/services/evaluation/evaluation_command_service.py::EvaluationCommandService.reevaluate_task_results()`）只做参数校验（TaskReevaluateInput）与任务终态校验（TaskStatus.COMPLETED/FAILED/STOPPED/PAUSED/SKIPPED，枚举见 `shared/models/common_enums.py`），随后经 ACL gRPC 代理（`api_gateway/infrastructure/grpc_proxies/evaluation_proxies.py::_ReevaluationExecutorProxy`）以 `evaluation_service_pb2.ReevaluateRequest` 调用 evaluation_service:5004。网关不直接查询 TestResult，实际提交用例数由评估服务异步统计。

---

### 2.2 重新提取 API (独立接口)

**接口**: `POST /api/v1/tasks/{task_id}/reextract`（api_gateway:5000，`api_gateway/routes/task_bp.py`，权限 `task:reextract`）

**Request Body**:
```json
{
    "task_id": 243,
    "executionStatus": "completed",
    "evaluationStatus": null
}
```

**参数说明**:

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| task_id | int | 必填 | 任务ID |
| executionStatus | string | "completed" | 用例执行状态筛选（枚举 `shared/utils/status_constants.py` 的 ExecutionStatus） |
| evaluationStatus | string | null | 评估状态筛选 (可选，EvaluationStatus 枚举) |

**Response**:
```json
{
    "success": true,
    "data": {
        "task_id": 243,
        "reextracted_count": 5,
        "reextracted_cases": [
            {
                "test_case_id": "uuid-1",
                "result_types": ["real-time", "non-real-time"],
                "old_result_ids": [100, 101],
                "new_result_ids": [110, 111, 112]
            }
        ],
        "message": "成功重新提取 5 个用例"
    }
}
```

【适配说明】调用链：api_gateway → task_service:5001（gRPC）→ `task_service/application/commands/task_commands.py::RextractTaskCommand`（application command，CQRS）→ `task_service/application/handlers/command_handlers.py::TaskCommandHandler.handle_reextract_task()` → task_lifecycle_service.reextract → 经 ACL（`task_service/infrastructure/acl/evaluation_acl_repository.py::reextract_result()`）gRPC 委托 device_service 执行。

## 三、流程设计

### 3.1 驱动获取流程

【适配说明】驱动获取收敛在 device_service 内部，跨服务只经 gRPC 暴露：`device_service/interfaces/grpc/device_runtime_servicers.py::DeviceServiceServicer`（action='extract_results_from_archive'）→ `device_service/infrastructure/drivers/device_driver.py::device_driver_factory`。评估/任务服务不直接 import 驱动。

```
┌─────────────────────────────────────────────────────────────┐
│  Step 1: 获取设备信息                                        │
│  - 从 TestResult 获取 device_id                              │
│  - 经 task_data_acl_repository（gRPC）获取 Device 记录        │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 2: 通过 device_driver_factory 获取驱动                  │
│                                                           │
│  调用: device_driver_factory.get_driver(                     │
│            system=device.system,       # 如 "HarmonyOS"     │
│            keywords=device.keywords    # 如 "harden,huiji"   │
│        )                                                   │
│                                                           │
│  获取逻辑:                                                 │
│    1. 先在 _specialized_drivers 中根据 keywords 匹配        │
│    2. 匹配成功则返回专用驱动                                 │
│    3. 否则返回基础驱动 (Android/HarmonyOS)                   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 3: 调用驱动的 extract_results_from_archive()           │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 驱动的注册与匹配

**专用驱动注册**（`device_service/infrastructure/drivers/device_driver.py`）:

| 驱动类 | 关键字 | 系统 |
|--------|--------|------|
| `PlaudDriver` | plaud, ai录音, ai record | Android |
| `XiaoyiFace2FaceDriver` | face2face, 面对面, face | HarmonyOS |
| `XiaoyiSimultaneousInterpretationDriver` | simultaneous, 同传, interpretation | HarmonyOS |
| `HarmonyHardenXiaoyiHuiJiDriver` | harden, huiji, 慧记 | HarmonyOS |

**匹配逻辑**:
1. `keywords` 与注册的关键字进行匹配（支持逗号分隔的多个关键字）
2. 同时检查 `system` 是否匹配
3. 匹配成功返回对应驱动实例

### 3.3 重新提取核心流程

> **注意**：重新提取仅适用于物理设备（device_type='physical'）。HTTP API 和 WebSocket API 测试结果由 adapter 直接保存（adapter.output），没有设备存档可重新提取。

**入口**: `device_service/application/device_result_reextractor_service.py::DeviceResultReextractor.reextract_for_task()`（由 evaluation_service:5004 或 task_service:5001 经 gRPC 发起）

【适配说明】重新提取涉及音频素材（刺激音频/参考音频）的链路走 audio_service（gRPC:50052）；对齐所需算法字段配置经 `device_service/infrastructure/acl/algorithm_query_acl_repository.py` 获取。

```
┌─────────────────────────────────────────────────────────────┐
│  Step 1: 查找需要重新提取的用例                               │
│  - task_case_relations.device_type == 'physical'（（新增）列）│
│  - TaskCase.execution_status = 参数值 (默认: 'completed')    │
│  - TaskCase.evaluation_status = 参数值 (可选)                │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 2: 对每个 test_case_id 处理:                          │
│                                                           │
│    2.1 获取该用例所有的旧 TestResult 记录                    │
│                                                           │
│    2.2 从旧记录中提取 adjusted_reference_params             │
│        (所有记录的 adjusted_reference_params 相同)            │
│                                                           │
│    2.3 获取驱动并调用 extract_results_from_archive()        │
│        - 经 gRPC DeviceServiceServicer                     │
│          (action='extract_results_from_archive')           │
│          由 device_driver_factory.get_driver() 获取         │
│        - 从存档提取设备输出                                  │
│        - 返回: [{result_type: "real-time", ...},           │
│              {result_type: "non-real-time", ...}]           │
│                                                           │
│    2.4 为每个提取结果:                                      │
│        - 调用 _convert_device_output_to_algorithm_result() │
│          (经 algorithm_query_acl_repository) 转换为算法结果  │
│        - 创建新的 TestResult 记录                           │
│        - result_data 包含:                                 │
│          * adjusted_reference_params (原始值)                │
│          * result_type (real-time / non-real-time)         │
│          * 提取的设备输出                                   │
│                                                           │
│    2.5 删除所有旧的 TestResult                             │
│        - 删除关联的所有 TestResultDimension (不管状态)       │
│                                                           │
│    2.6 重置 TaskCase.evaluation_status = 'pending'         │
└─────────────────────────────────────────────────────────────┘
```

### 3.4 重新评估流程

**入口**: `api_gateway/application/services/evaluation/evaluation_command_service.py::EvaluationCommandService.reevaluate_task_results()`

【适配说明】V9.7.10 单体的 `EvaluationController.reevaluate_task_results()` 进程内调用，在 V9.7.31 拆分为三段跨服务链路：api_gateway:5000（校验）→ gRPC Reevaluate → evaluation_service:5004（`evaluation_service/application/handlers/reevaluation_executor.py::ReevaluationExecutor`，Redis 队列编排，Task 状态经 gRPC 置为 `reevaluate_queued`，见 `shared/utils/status_constants.py`）→ 重新提取段经 `evaluation_service/infrastructure/acl/device_result_acl_repository.py` gRPC 委托 device_service。

```
┌─────────────────────────────────────────────────────────────┐
│  Step 1: 参数校验（api_gateway）                             │
│  - task_id 存在                                             │
│  - 任务状态为 completed/failed/stopped/paused/skipped      │
└─────────────────────────────────────────────────────────────┘
                              │  gRPC Reevaluate
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 2: 如果 reextract_device_output=true                 │
│          （仅 physical）经 ACL gRPC 调用重新提取流程          │
│                                                           │
│  reevaluate_type='all':                                    │
│    - 调用 reextract_for_task(evaluation_status=None)       │
│                                                           │
│  reevaluate_type='failed':                                 │
│    - 调用 reextract_for_task(evaluation_status='failed')   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 3: 根据 reevaluate_type 查找需要重新评估的用例         │
│                                                           │
│  reevaluate_type='all':                                    │
│    - 遍历所有 execution_status=='completed' 的 TestResult   │
│    - 必须有 algorithm_result                                │
│                                                           │
│  reevaluate_type='failed':                                 │
│    - 查找 TestResultDimension.status == 'failed'           │
│    - TaskCase.execution_status == 'completed'               │
│    - result.algorithm_result 存在                           │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 4: 构建 case_info 并提交到评估队列                     │
│                                                           │
│  case_info 结构:                                           │
│  {                                                         │
│      'test_case_id': 'uuid',                               │
│      'result_id': 123,                                     │
│      'algorithm_result': {...},                             │
│      'reference_params': [...],                            │
│      'device_id': 1,                                       │
│      'task_id': 243,                                       │
│      'reextracted': True/False,                            │
│      'result_type': 'real-time' / 'non-real-time'          │
│  }                                                         │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 5: 异步执行评估                                       │
│  - 评估完成后更新 TestResultDimension 状态                   │
│  - 评估完成后更新 TaskCase.evaluation_status                 │
│  - 发布 CASE_EVALUATION_COMPLETED（（新增））                 │
│    shared/utils/redis_pubsub.py                             │
│    EventChannel.CASE_EVENTS / EventType.CASE_EVALUATION_    │
│    COMPLETED → api_gateway:5000 Socket.IO（（新增））         │
│    按 task_id 房间隔离推送 → 前端更新                         │
└─────────────────────────────────────────────────────────────┘
```

【适配说明：result_type 双通道（（新增））】评估结果关联 result_type 映射：frame（帧结果，逐帧经 Socket.IO 帧流推送，不落库）与 summary（最终结果，落库触发评估）双通道。重新评估提交的 case_info 携带 result_type，evaluation_service 按该映射决定帧流通道与落库通道。

### 3.5 设备输出文件拼接逻辑

【适配说明】以下拼接逻辑位于 device_service 的设备驱动实现内（如 `HarmonyHardenXiaoyiHuiJiDriver`），随重新提取链路经 gRPC 触发，逻辑与单体版一致。

#### 3.5.1 ASR 文件拼接

```
┌─────────────────────────────────────────────────────────────────┐
│  Step 1: 解析所有 ASR 文件                                       │
│  - 每个文件解析为 stm_lines, rttm_lines                           │
│  - 记录 first_ts, last_ts                                        │
│  - asr_parsed = [{stm_lines, rttm_lines, first_ts, last_ts}, ...] │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  Step 2: 按 first_ts 排序                                        │
│  - asr_parsed.sort(key=lambda x: x['first_ts'])                │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  Step 3: 拼接到 recording_stm_lines, recording_rttm_lines        │
│  for asr in asr_parsed:                                          │
│      recording_stm_lines.extend(asr['stm_lines'])                 │
│      recording_rttm_lines.extend(asr['rttm_lines'])               │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.5.2 Fix 文件插入逻辑

| 情况 | 条件 | 处理方式 |
|------|------|----------|
| fix 时间早于 ASR | `fix_last_ts < asr[i]['first_ts']` | 插入到 ASR 之前 |
| fix 时间晚于 ASR | `asr[i]['last_ts'] < fix_first_ts` | 插入到 ASR 之后 |
| 时间重叠 | 其他情况 | **删除整个重叠的 ASR 片段，用 Fix 内容替换** |

**重叠处理详细逻辑**:

```
for i, asr in enumerate(asr_parsed):
    if fix_last_ts < asr['first_ts']:
        # Fix 完全在 ASR 之前，插入位置为 i (ASR 之前)
        insert_idx = i
        insert_before = True
        break
    elif asr['last_ts'] < fix_first_ts:
        # Fix 完全在 ASR 之后，插入位置为 i + 1 (ASR 之后)
        insert_idx = i + 1
    else:
        # 时间重叠，标记删除该 ASR 片段
        asr_to_remove.add(i)
```

**最终拼接逻辑**:

```
if insert_idx is not None:
    # 非完全重叠场景：按插入位置拼接
    # - insert_before=True: Fix 优先添加，再添加所有未删除的 ASR
    # - insert_before=False: 遍历 ASR，在插入点位置添加 Fix
else:
    # 完全重叠场景：删除所有重叠 ASR，末尾添加 Fix
```

**示例1 (无重叠)**:
```
ASR文件: [ASR0: 0.84s~1.95s], [ASR1: 2.68s~6.83s], [ASR2: 7.4s~9.35s]
Fix文件: 0.5s~2.0s

结果: fix(0.5s~2.0s) + ASR0 + ASR1 + ASR2
```

**示例2 (有重叠)**:
```
ASR文件: [ASR0: 0.84s~1.95s], [ASR1: 2.68s~6.83s], [ASR2: 7.4s~9.35s]
Fix文件: 2.0s~4.0s

分析:
- ASR0 (0.84s~1.95s) 与 Fix 无重叠 → 保留
- ASR1 (2.68s~6.83s) 与 Fix 重叠 → 删除
- ASR2 (7.4s~9.35s) 与 Fix 无重叠 → 保留

结果: ASR0 + fix(2.0s~4.0s) + ASR2
```

#### 3.5.3 存储文件清单

| 文件路径 | 内容 | 说明 |
|----------|------|------|
| `recording.stm` | ASR 内容 | 仅 ASR 拼接，不包含 fix |
| `recording.rttm` | RTTM 内容 | 仅 ASR 拼接，不包含 fix |
| `recording_asr.txt` | 原始 ASR 内容 | 原始 ASR 文件拼接 |
| `fix.stm` | ASR + fix 内容 | 如果 fix 被插入到 ASR 时间段 |
| `fix.rttm` | RTTM + fix 内容 | 如果 fix 被插入到 ASR 时间段 |
| `fix_asr.txt` | fix 原始内容 | 独立保存 |

**注意**: `recording_asr.txt` 只包含原始 ASR 内容，不包含 fix。即使 fix 被拼接到 recording 中，fix 的原始内容也不会被添加到 `recording_asr.txt`。

## 四、场景组合

### 4.1 重新提取场景

> 【适配说明】以下场景仅对 `device_type='physical'` 任务开放；http_api / websocket_api 任务调用重新提取接口时直接返回"无需重新提取"。

| 场景 | executionStatus | evaluationStatus | 说明 |
|------|-----------------|------------------|------|
| 场景1 | completed | null | 重新提取所有执行成功的用例 |
| 场景2 | completed | failed | 重新提取评估失败的用例 |
| 场景3 | completed | passed | 重新提取评估成功的用例 |

### 4.2 重新评估场景

| 场景 | reevaluate_type | reextract_device_output | 重新提取 | 重新评估 | 适用 device_type |
|------|-----------------|------------------------|---------|---------|------------------|
| 场景1 | all | true | ✅ 删除旧记录，创建新记录，评估所有 | ✅ | physical |
| 场景2 | all | false | ❌ 保留旧记录不变 | ✅ 评估所有 | physical / http_api / websocket_api |
| 场景3 | failed | true | ✅ 删除旧记录，创建新记录，评估失败 | ✅ 只评估失败 | physical |
| 场景4 | failed | false | ❌ 保留旧记录不变 | ✅ 只评估失败 | physical / http_api / websocket_api |

### 4.3 重新评估行为说明

**场景1 (reevaluate_type='all', reextract_device_output=true)**:
- 删除旧的 `TestResult` 和所有关联的 `TestResultDimension` 记录
- 从存档重新提取设备输出，创建新的 `TestResult` 记录
- 重新评估所有维度

**场景2 (reevaluate_type='all', reextract_device_output=false)**:
- 保留旧的 `TestResult` 记录不变
- 重新评估所有有 `algorithm_result` 的 `TestResult`

**场景3 (reevaluate_type='failed', reextract_device_output=true)**:
- 从存档重新提取评估失败的用例
- 删除旧记录，创建新的 `TestResult` 记录
- 只评估 `TestResultDimension.status == 'failed'` 的维度

**场景4 (reevaluate_type='failed', reextract_device_output=false)**:
- 保留旧的 `TestResult` 记录不变
- 只评估 `TestResultDimension.status == 'failed'` 的维度

## 五、数据结构

### 5.1 重新提取前后 TestResult 变化

**旧的 TestResult** (被删除):
```
TestResult {
    id: 100,
    task_id: 243,
    test_case_id: "case-uuid",
    device_id: 1,
    algorithm_type: "asr",
    execution_status: "completed",
    algorithm_result: {旧的算法结果},
    result_data: {
        "adjusted_reference_params": [...],
        "result_type": "real-time",
        "raw_results": {...},
        ...
    }
}
```

**新的 TestResult** (被创建):
```
TestResult {
    id: 110 (新ID),
    task_id: 243,
    test_case_id: "case-uuid",
    device_id: 1,
    algorithm_type: "asr",
    execution_status: "completed",
    algorithm_result: {从存档重新提取并转换的算法结果},
    result_data: {
        "adjusted_reference_params": [...],  // 保留原始值
        "result_type": "real-time",          // 或 "non-real-time"
        "recording_stm_content": "...",       // 新的设备输出
        "recording_rttm_content": "...",
        "recording_asr_content": "...",
        "fix_stm_content": "...",
```

## 七、边界条件

### 7.1 重新提取边界条件

1. **device_type 过滤（（新增））**
   - 仅 `task_case_relations.device_type == 'physical'` 的用例进入重新提取；http_api / websocket_api 直接跳过（task_case_relations 已有 device_id 列，device_type 为（新增）列）

2. **execution_status 不匹配**
   - 只有 `TaskCase.execution_status == 参数值` 的用例才会被处理

3. **evaluation_status 筛选**
   - 如果指定了 `evaluation_status`，则同时按执行状态和评估状态筛选

4. **设备输出提取失败**
   - device_service 侧跳过该用例，不创建新记录
   - 记录警告日志，经 gRPC 响应回传评估/任务服务

5. **无 adjusted_reference_params**
   - 继续处理，但不保留该字段

6. **TestResultDimension 清理**
   - 删除 TestResult 时，**删除所有关联的 TestResultDimension 记录**（不管评估状态如何）
   - 目的是让所有用例都能从头开始重新评估

7. **TaskCase.evaluation_status 重置**
   - 重新提取后，将 `TaskCase.evaluation_status` 重置为 `'pending'`

### 7.2 重新评估边界条件

1. **无 algorithm_result**
   - 跳过该用例，不加入评估队列

2. **execution_status != 'completed'**
   - 跳过该用例，不加入评估队列

3. **非物理任务携带 reextract_device_output=true（（新增））**
   - reextract 仅对 physical 生效；http_api / websocket_api 任务忽略该标记，仅走重新评估分支

## 十、驱动能力前置过滤

> **注意**：此过滤仅适用于物理设备（device_type='physical'）。API（http_api / websocket_api）测试由 api_test_service:5003 的 adapter 体系执行，不走 device_driver，因此不存在存档提取环节。

### 10.1 不支持重新提取的驱动

并非所有设备驱动都实现了 `extract_results_from_archive()` 方法（驱动位于 device_service）。当前支持情况：

| 驱动 | 支持重新提取 |
|------|:---:|
| `PlaudDriver` | ✅ |
| `HarmonyHardenXiaoyiHuiJiDriver` | ✅ |
| `AndroidDriver` | ❌ |
| `HarmonyDriver` | ❌ |
| `XiaoyiFace2FaceDriver` | ❌ |
| `XiaoyiSimultaneousInterpretationDriver` | ❌ |

### 10.2 前置过滤流程

在 `reextract_for_task()` 中，用例循环**之前**会前置过滤设备（`device_service/application/device_result_reextractor_service.py::_filter_reextractable_devices()`）：

```
┌─────────────────────────────────────────────────────────────┐
│  Step 0: 前置过滤设备                                        │
│                                                           │
│  for device in task_devices:                               │
│      driver = device_driver_factory.get_driver(...)        │
│      if hasattr(driver, 'extract_results_from_archive'):   │
│          加入 reextractable_device_map                     │
│      else:                                                 │
│          记录日志并跳过                                     │
│                                                           │
│  if reextractable_device_map 为空:                         │
│      返回 "所有设备均不支持重新提取"                         │
└─────────────────────────────────────────────────────────────┘
```

效果：不支持重新提取的设备不会进入用例循环，避免无意义的数据库查询和参数构建。

## 十一、adjusted_reference_params 全覆盖保证

### 11.1 设计原则

所有结果统一包含 `adjusted_reference_params` 字段，语义为"最终用于评估的参考参数"：

| 场景 | adjusted_reference_params 的值 |
|------|------|
| 需要对齐的算法（慧记、Plaud 等） | 对齐后的参考参数 |
| 不需要对齐的算法（纯文本 ASR、翻译等） | 原始参考参数 |
| reference_params 为空 | `[]` |
| 采集异常 | reference_params 或 `[]` |

### 11.2 对齐跳过机制

采集/对齐判定与执行器基座对齐：V9.7.31 中执行链路统一继承 `shared/infrastructure/base_executor/_base.py::BaseExecutor`（五 mixin：ControlMixin + LoggingMixin + ParamsMixin + ResultsMixin + DbMixin），采集结果经 ResultsMixin/DbMixin 落库；重新提取侧在 device_service 内复算对齐：

1. **参考参数侧**：遍历 `reference_params`，检查是否有 `type` 为 `rttm` 或 `stm` 的条目
2. **设备输出侧**：经 `algorithm_query_acl_repository`（gRPC）查询数据库配置，检查算法是否有 `stm`/`rttm` 类型的输出字段

两者都有时间线数据时才需要对齐。不需要对齐时，`_calculate_effective_offset_for_single_result` 返回 `method='skipped'`，`adjusted_params` 为原始 `reference_params`。

### 11.3 覆盖路径

| 代码路径 | 保证方式 |
|----------|----------|
| `collect_raw_results` list 分支 | `alignment_result.get('adjusted_params') or reference_params or []` |
| `collect_raw_results` dict 分支 | 同上 |
| `collect_raw_results` 异常分支 | `setdefault('adjusted_reference_params', reference_params or [])` |
| `_calculate_effective_offset_for_single_result` reference_params 为空 | 返回 `reference_params or []` |
| `_calculate_effective_offset_for_single_result` 不需要对齐 | 返回原始 `reference_params` |
| `device_result_reextractor` 对齐成功 | 使用计算结果 |
| `device_result_reextractor` 对齐失败 | 使用旧的 adjusted 或原始参数 |
| `device_result_reextractor` 全部为空 | 使用 `original_reference_params or []` |

下游所有消费 `adjusted_reference_params` 的代码（`_process_results`、e2e 执行链路、评估参数构建中 `source == 'adjusted_reference'` 的映射）都不需要改。

## 十二、注意事项

1. **事务处理**: 重新提取在新旧记录替换时使用事务，确保数据一致性（事务边界在 device_service 内，跨服务不共享事务）
2. **数据完整性**: 删除旧 TestResult 时会删除所有关联的 TestResultDimension，确保从头开始重新评估
3. **并发安全**: 【适配说明】physical 用例执行以 Redis 分布式锁互斥（`shared/utils/distributed_coordinator.py::DistributedLock`）；重新提取和重新评估不建议同时对同一任务操作。重新评估链路带 `worker_instance_id`，服务重启后未完成的评估任务可由 `shared/utils/service_registry.py::RedisServiceRegistry` 孤儿任务收养机制接管，避免任务悬挂
4. **评估状态重置**: 重新提取后，TaskCase.evaluation_status 会被重置为 'pending'，需要重新评估才能变成最终状态
5. **重新提取适用范围**: 重新提取设备输出仅适用于物理设备（device_type='physical'，E2E）。http_api / websocket_api 测试结果由 adapter 保存（adapter.output），无需重新提取
6. **枚举与配置化（（新增））**: reevaluate_type / execution_status / evaluation_status / device_type 等状态与类型枚举统一落 `shared/models/common_enums.py` 与 `shared/utils/status_constants.py`（TaskType 不引入 'realtime_api'），端口、队列名、超时等配置化，拒绝魔法数字/魔法字符串
7. **事件驱动解耦（（新增））**: 评估完成仅以 `CASE_EVALUATION_COMPLETED` 事件（Redis EventBus，EventChannel.CASE_EVENTS）通知；前端经 api_gateway:5000 Socket.IO（task_id 房间隔离）接收，评估服务与前端零直连
8. **音频素材链路（（新增））**: 重新提取涉及音频素材（刺激音频/参考音频读取）时经 audio_service（gRPC:50052）获取，不在评估/任务服务内直接读音频文件

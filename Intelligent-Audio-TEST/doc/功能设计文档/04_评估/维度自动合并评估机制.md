# 维度自动合并评估机制

> 评估系统功能设计文档（补充篇）：同一分类下、评估服务与请求模板一致的维度，评估时自动合并为一次请求、共用一次判定结果。

## 1. 背景与问题

拒识族（`reject_judge`）有 3 个主维度 + 9 个子维度：

- 拒识成功数量（主，占比类）
- 拒识询问数量（主，占比类）
- 拒识失败数量（主，占比类）
- 静默时/回复时拒识恢复、回应、无关、静默等 9 个子维度

三个主维度均为占比类指标（`statistic_method = weighted_sum_ratio`），分母相同（拒识总轮次 `n_reject_rounds`），分子分别是 `n_rate_success / n_rate_inquiry / n_rate_failure`。每一轮判定结果只能是「成功 / 询问 / 失败」之一，因此理论上三率之和恒为 100%。

**问题**：此前三个主维度各自独立提交一次 eval_server 请求、各调一次 LLM 裁判，同一批音频每次判定的结果不完全一致，导致三个分子对不上同一分母，三率之和出现缺口。实测报告 424：成功 49.74% + 失败 46.67% + 询问 0% = 96.41%，缺 3.59%（7/195 轮「凭空消失」）。

## 2. 合并机制

### 2.1 合并条件

`evaluation_service._dispatch_evaluation_tasks` 在完成原有 parent 分组后，做**组间自动合并**。多个 parent 分组并入一组、只发一次请求，需同时满足：

| 条件 | 说明 |
|---|---|
| endpoint 一致 | 调用同一个 eval_server 服务 |
| category_id 一致 | 维度同属一个分类（族） |
| task_type_code 一致 | 组内所有维度的 `(task_type_code, body_template)` 组合完全一致（同一计算器、请求体相同） |
| body_template 一致 | 组内所有维度请求模板相同 |

任一条件不满足则保持原 parent 分组，不合并。

### 2.2 代码位置

- 后端：[backend/services/evaluation/evaluation_service.py](Intelligent-Audio-TEST/backend/services/evaluation/evaluation_service.py)
  - `_load_dimension_data`：维度数据补充 `category_id` 字段
  - `_dispatch_evaluation_tasks`：分组完成后组间自动合并（`endpoint + frozenset((task_type, body_template)) + frozenset(category_id)` 作为合并键）
- 拒识维度配置（无 group_key）：[backend/scripts/migrations/202609/seed_reject_judge.py](Intelligent-Audio-TEST/backend/scripts/migrations/202609/seed_reject_judge.py)
- 测试：[backend/tests/test_auto_merge_groups.py](Intelligent-Audio-TEST/backend/tests/test_auto_merge_groups.py)

### 2.3 为什么不能按 task_type_code 直接分组

分组键默认是 `(endpoint_url, parent_dimension_id)`，`task_type_code` 不参与分组：

- 一次请求只能带一个 `body_template`，同 task_type 的不同维度 body 可能不同
- 一个响应要能覆盖组内所有维度的 field_path，只有确认兼容的维度才能共享一次请求
- 「逐轮话轮评估」（`turn_eval`，category=1，无 group_key）主/子维度 task_type 不同（`turn_eval` vs `turn_evaluation`），依赖 parent 分组 + `sub_tasks` 一次请求批量计算——若按 task_type 分组会被误拆，因此必须保留 parent 分组、只做组间合并

## 3. 一次请求如何解析每个维度

eval_server 一次请求返回的 `result` 已包含全部字段（聚合时 12 个 `n_` 字段 + `n_reject_rounds` 分母都已计算）：

- eval_server 聚合：[eval_server/app/services/calculators/xiaoyi_metrics/env_judge/strategy.py](eval_server/app/services/calculators/xiaoyi_metrics/env_judge/strategy.py) `RejectionJudgeCalculator._calculate_per_round`
- 平台端回调：[backend/services/evaluation/evaluation_result_processor.py](Intelligent-Audio-TEST/backend/services/evaluation/evaluation_result_processor.py) `process_group_dimension_results` **遍历 group_items 内每个维度**，按各自维度的 `field_path` 从同一份 `resp_data` 提取并写各自的 TRD：

| 维度 | field_path | 取值 |
|---|---|---|
| 拒识成功数量 | `n_rate_success` | 成功轮次 |
| 拒识询问数量 | `n_rate_inquiry` | 询问轮次 |
| 拒识失败数量 | `n_rate_failure` | 失败轮次 |
| 静默时拒识恢复行为数量 | `n_success_silent_recover` | 子维度数量 |
| 回复时拒识恢复行为数量 | `n_success_reply_recover` | 子维度数量 |
| 静默时拒识询问行为数量 | `n_inquiry_silent` | 子维度数量 |
| 回复时拒识询问行为数量 | `n_inquiry_reply` | 子维度数量 |
| 静默时拒识回应行为数量 | `n_failure_silent_respond` | 子维度数量 |
| 回复时拒识回应行为数量 | `n_failure_reply_respond` | 子维度数量 |
| 静默时拒识无关行为数量 | `n_failure_silent_irrelevant` | 子维度数量 |
| 回复时拒识无关行为数量 | `n_failure_reply_irrelevant` | 子维度数量 |
| 回复时拒识静默行为数量 | `n_failure_reply_silent` | 子维度数量 |

此即「主维度 + 子维度同组」的既有工作方式（此前拒识 121 组内 3 个维度即一次请求），合并只是把 3 个组合并成 1 个组（组内 12 个维度），遍历提取逻辑不变。

## 4. 效果

- 拒识族 12 个维度合并为一组，只发一次请求、只做一次 LLM 判定
- 三个主维度从同一份 result 提取分子 → 成功 + 询问 + 失败 = 拒识总轮次，**三率之和恒为 100%**，不再出现缺口
- 子维度（9 个）同样从同一份 result 提取，分母为主维度总数，内部占比自洽

## 5. 兼容性

| 族 | 分类 | group_key | 合并方式 |
|---|---|---|---|
| 拒识族 reject_judge | 拒识(cat=3) | 无（已移除） | 自动合并一组 |
| 打断族 interruption_metrics | 打断(cat=2) | `interruption_v2` | 显式 group_key（不受影响） |
| 环境理解 env_judge | 环境理解(cat=4) | `env_judge_v2` | 显式 group_key（不受影响） |
| 逐轮话轮评估 turn_eval | 话轮(cat=1) | 无 | 主/子 task_type 不同 → 不合并，保持 parent 分组 + sub_tasks |

- 显式 `group_key` 优先：配了 group_key 的维度按 `(endpoint, group_key)` 分组，自动合并仅对无 group_key 的分组生效
- 合并要求组内所有维度 `(task_type_code, body_template)` 完全一致，因此含多 task_type（靠 sub_tasks）或 body 不一致的族不会被误拆/误并

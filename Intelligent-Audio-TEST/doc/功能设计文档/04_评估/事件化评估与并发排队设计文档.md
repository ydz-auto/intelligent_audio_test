# 事件化评估与并发排队设计文档

## 1. 背景与问题

### 1.1 评估结果交付依赖同步轮询

原有评估流程：主服务提交异步任务后，worker 线程阻塞轮询 `get_status`，直到任务完成或 **600 秒超时**。

### 1.2 暴露出的三个核心问题

| 问题 | 现象 | 根因 |
|---|---|---|
| **600s 硬超时误判失败** | 慢维度（reject_judge 等 LLM 判官类，单任务 8~10 分钟）在 600s 内没算完 → 用例被判评估失败 | 后端 `wait_for_task_completion` 轮询上限 600s，与 LLM 判官实际耗时不匹配 |
| **并发满直接 400 拒绝** | eval_server 本地路径并发满（`LOCAL_MAX_CONCURRENCY=60`）时返回 400 `code=3001`，后端旧代码直接把维度判失败 | eval_server 本地路径"满了就拒绝"、不排队；后端无排队重试 |
| **排队配置未接线** | `concurrency_config.json` 的 `evaluation_service.max_queue_size/max_wait_time/default_max_concurrent` 存在，但 `acquire_endpoint_slot/release_endpoint_slot` 零调用，是"死配置" | 主服务信号量限流从未接入实际提交流程 |

### 1.3 附加问题

- 错误信息失真：轮询超时/400 时 `__error__` 兜底为 `HTTP 400` / `Unknown error`，掩盖真实原因（超时、并发满、校验失败）。
- 状态不一致：维度记录未标记 failed，但 TaskCase 被无条件置为 failed。

## 2. 优化目标

- 消除"600s 硬超时误判失败"：慢任务晚到也能补写结果。
- 消除"并发满 400 拒绝"：并发满时排队等待，而不是判失败。
- 保留原有评估语义：状态机、用例收尾逻辑（completed/failed 判定）不变。
- 兼容性：不配置新参数时完全保持旧行为（零风险灰度）。

## 3. 总体架构

```
主服务(Intelligent-Audio-TEST/backend)              eval_server(100.70.20.135:8888)
┌───────────────────────────────────┐              ┌─────────────────────────────┐
│ evaluation_api_client             │              │  api.py 本地路径             │
│  ├─ 提交任务(带 callback_url)      │ ──HTTP────▶ │  ├─ 并发未满 → 立即处理       │
│  ├─ 返回即注册回调，不阻塞轮询      │              │  ├─ 并发已满 → 建 pending 排队 │
│  └─ (兜底) 3001 并发满 → 重新排队   │              │  └─ 文件worker排队执行        │
│                                   │              │                               │
│ eval_callback_registry            │              │  task_service._run_task      │
│  ├─ 注册表 {eval_task_id→上下文}   │              │   ├─ 计算完成 → completed     │
│  ├─ result_callback 回调端点       │ ◀──POST──── │   └─ notify_callback 通知     │
│  └─ 兜底结算线程(1200s/7200s)      │              └─────────────────────────────┘
└───────────────────────────────────┘
```

## 4. 详细设计

### 4.1 主服务：事件化提交（evaluation_api_client.py）

- 新增配置 `EVAL_CALLBACK_BASE_URL` / `EVAL_CALLBACK_TOKEN`（backend/.env）。
- 配置 `EVAL_CALLBACK_BASE_URL` 后进入 **event_mode**：
  - 提交异步任务时，payload/form 注入 `callback_url = {base}/api/v1/evaluation/result_callback?token={token}`。
  - `_execute_async_api_flow` 创建任务成功后返回 `{'__event__': True, 'eval_task_id': ...}`，**不再调用 wait_for_task_completion**。
- 未配置时保持旧行为（提交后轮询，`is_async_api=True` 全走异步流程）。

### 4.2 主服务：回调注册与结果写入（endpoint_worker.py）

- worker 线程收到 `__event__` 标记后：
  1. 将 `(eval_task_id, selected_url, group_items, task_id, test_case_id, result_id, api_request_body, test_type)` 注册到 `eval_callback_registry`；
  2. 立即释放 worker 线程（不再占 600s）；
  3. 结果由回调/兜底结算写入，复用原有 `process_group_dimension_results` / `update_all_dimensions_in_group_failed`，收尾口径不变。

### 4.3 主服务：回调端点（evaluation_controller.py + evaluation_bp.py）

- 新增 `POST /api/v1/evaluation/result_callback`：
  - **token 校验**：URL 上携带 `token`，与配置的 `EVAL_CALLBACK_TOKEN` 比对，不匹配返回 403/400；
  - **幂等**：同一 `eval_task_id` 重复回调只处理一次；
  - 回调内容：`{eval_task_id, status: completed/failed, result, error_msg, task_type, task_id}`；
  - 处理：按 `eval_task_id` 查注册表 → 取上下文 → 调结果处理器写维度结果 → 从注册表移除。

### 4.4 主服务：兜底结算线程（eval_callback_registry.py）

- 注册表为线程安全 dict，随 worker 注册、随回调移除。
- 后台结算线程周期扫描注册表：
  - **1200s 未收到回调** → 主动 `get_final_result` 补查一次；查到 completed → 补写结果；仍 pending/processing → 继续等；
  - **7200s 仍未收尾** → 判失败（兜底硬超时，避免永久卡死）。

### 4.5 主服务：并发满重新排队（3001 兜底）

- `evaluation_api_client`：创建任务响应 `code == 3001`（并发满）时返回 `{'__concurrency_wait__': True}`，不再走失败路径。
- `endpoint_worker._requeue_or_fail`：
  - 参数：`CONCURRENCY_RETRY_INTERVAL = 10s`，`CONCURRENCY_MAX_RETRY = 60`（≈10 分钟排队上限）；
  - 收到并发满标记 → 休眠间隔 → 任务重新入队 `task_queue` 等待重试；
  - 超过重试上限才判失败（"排队等待超时"），并记录 api_raw_response / api_request_body；
  - 内部字段 `_retry_count` 以下划线前缀存放，不进入评估 payload。

### 4.6 子服务：并发满转入 pending 排队（api.py 本地路径）

- 本地路径（`create_task` / `create_task_upload` 不带 endpoints）并发满时**不再返回 400**：
  - 创建任务文件 `status='pending'`（`TaskModel.create_task` 默认即 pending）；
  - 返回 200 + `queued=True`（含 eval_task_id），主服务按普通成功创建处理（注册回调等待）。
- 文件 worker（`TaskService._process_tasks`，每 1s 扫描）按 `ConcurrencyManager.can_start(task_type)`（per-type 上限 30）排队启动，`_run_task` 计算完成后 `notify_callback` 回调主服务。
- 前提核对：
  - `get_pending_tasks` 扫描 `status=pending 且 endpoint_url 为空` 的本地任务 ✅；
  - 上传文件保留在 `UPLOAD_DIR` 无清理逻辑，pending 等待期间文件安全 ✅；
  - 服务重启 `reset_processing_tasks` 只处理 processing，pending 保留 ✅。

### 4.7 子服务：结果回调（task_service.py / api.py）

- `notify_callback(callback_url, eval_task_id, task_type, caller_task_id, status, result/error_msg)`：
  - 独立线程 POST，失败重试 3 次（指数退避），不阻塞任务收尾；
  - 从 `task_params.callback_url` 读取回调地址（主服务提交时透传）。
- `_run_task` 与 `process_local_task` 在 completed / failed / 内部失败（`is_success=False`）时统一触发回调。

### 4.8 重复评估提交保护（重新评估前取消旧任务，2026-10-10 新增）

**问题**：同一任务连续触发多次重新评估时，eval_server 上会堆叠多份评估任务并发计算。
LLM 评估结果非确定性导致各次返回互相不一致；旧任务完成后仍回调主服务，可能覆盖新评估
写入的 `test_result_dimensions`，使报告与 `result_data` 日志分数不一致。

**方案A（主服务防呆）**：`eval_callback_registry` 新增 `pop_by_task(task_id)`：
- 提交新评估前，把注册表里同 `task_id` 的所有旧 ctx 移除并返回 `[(eval_task_id, endpoint_url), ...]`；
- 旧回调到达时因 ctx 不存在而被回调端点幂等忽略（`if not ctx: return success_response()`），不覆盖新结果；
- 兜底结算线程同步不再补查这些旧任务。

**方案B（子服务真正取消）**：
- eval_server 新增 `DELETE /api/cancel_task/<eval_task_id>`（api.py），实现为 `TaskModel.cancel_task()`：
  把任务文件标记为 `status='canceled'`（保留文件便于排查，不删除）；
- 排队中（pending）任务不再被后台 worker 启动（`get_pending_tasks` 只取 pending）；
- 计算中（processing）任务：`process_local_task`（api.py）与 `_run_task`（task_service.py）
  计算完成后先查 `TaskModel.is_canceled()`，已取消则**跳过写结果、跳过回调**（不污染结果、不白耗回调）；
- 幂等：任务不存在返回 404，已取消重复调用返回成功。

**主服务调用入口**：`ReevaluationExecutor.submit()` 中新增 `_cancel_previous_evaluations(task_id)`：
1. `pop_by_task(task_id)` 移除旧 ctx（方案A）；
2. 对每个旧任务 `requests.delete("{endpoint_url}/api/cancel_task/{eval_task_id}")`（方案B，timeout=5s）；
3. 任一子服务调用失败仅记 WARNING，不阻断新任务提交。

**服务重启影响**：注册表为纯内存，重启后自动清空；旧 eval_server 任务完成后回调因 ctx
不存在被幂等忽略（与方案A等价），兜底线程不再补查；旧任务仅在子服务侧白跑至完成。

## 5. 状态流转（不变）

| 状态 | 说明 |
|---|---|
| 执行状态 execution_status | 不受影响（评估在执行之后） |
| 评估状态 evaluation_status | `queued → running → calculating → completed/failed`，仅 `calculating` 时长变化（等回调） |
| 用例状态 status | 仍由 `update_task_case_status` 统一收尾：所有维度有结果 → completed，任一失败 → failed |
| 任务状态 task.status | 执行引擎按用例最终状态推进，收尾逻辑不变 |


### 6.2 子服务（eval_server）

无需配置：回调地址由主服务提交任务时经 `task_params` 透传。

## 7. 数据修复（played_audios 映射）

### 7.1 问题

`param_mappings` 中被播放音频相关映射 `source='case'`，但 audios 等结构性字段位于 `case_config.rounds`，不在 algorithm_params —— 导致 `played_audios` 提取为空，eval_server env_judge 校验返回 `4000: Missing required field for env_judge: played_audios`。

### 7.2 修复

- `param_mappings` 全部 57 行（19 个 voice_llm 维度 × `audios/background_noise/interferers` 3 参数）`source='case' → 'case_config'`；
- 6 个 seed 脚本（seed_env_judge / seed_reject_judge / seed_interruption_v2 / seed_stimulus_audios / seed_turn_eval / seed_voice_llm）核对确认均为 `case_config`，无需修改；
- 提取器 `case_config` 分支按轮（`round_number`）取 `cfg_round.audios`，并补全 `audio_path`，支持多轮逐轮提取。

## 8. 部署与验证

| 侧 | 操作 |
|---|---|
| 主服务 | 配置 `.env` → 重启后端 → 启动日志出现"事件化评估已启用" |
| 子服务 | 同步 api.py / task_service.py 改动 → 重启 eval_server（100.70.20.135） |

### 8.1 验证点

1. 事件化提交：日志"成功创建异步任务并已注册回调: task_xxx（等待 eval_server 主动回调）"，无"已等待=595秒"轮询日志；
2. 回调写入："回调写入评估结果: eval_task_id=task_xxx, 状态=completed"，回调端点 200；
3. 并发满排队：主服务日志"评估端点并发满(code=3001)，任务重新排队"；子服务日志"[queue] 评估并发已满(60)，任务进入排队"；
4. 慢维度不再误判：超过 600s 的维度晚到后仍能通过回调补写结果。

## 9. 已知边界

- 事件化下用例停留在 `calculating` 的时间可能更长（等真实结果而非 600s 假失败），前端"评估中"显示更久属预期；
- 后端重启时遗留 evaluating 中 TRD/用例仍会被置 failed（app.py 启动逻辑，与旧行为一致）；晚到回调因注册表丢失被幂等忽略；
- eval_server 本地路径 pending 与立即处理分属两个并发计数器（`LocalConcurrencyManager` 总 60 / `ConcurrencyManager` per-type 30），峰值并发可能略超设计值，不影响"排队"目的。

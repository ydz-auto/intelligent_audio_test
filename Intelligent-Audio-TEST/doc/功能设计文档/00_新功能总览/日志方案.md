## 2. 落盘结构与路径组织

**服务运行日志**（系统级）：

```
logs/{service_name}/{YYYY-MM-DD}/app-{hostname}-{pid}.log
```

- 活跃文件 = `app-{hostname}-{pid}.log`（进程标识，多副本共享卷互不冲突）；按天切目录（旧目录留档）、
  同日超限切分为 `app-{hostname}-{pid}-{YYYYMMDD}-{NNN}.log`。

**业务日志**（执行 / 评估 / 设备，JSON Lines 格式）——路径模板见 `shared/logging/path_builder.py:38-69`：

```
logs/business/{task_id}/{device_id|api_id|common}/{round|shared}/{log_type}.{service_name}.{hostname}-{pid}.log
```

- 第一段 = 任务 id，第二段 = 设备 id（无设备上下文为 `common`），第三段 = 轮次号（跨轮共享为 `shared`）；
- 所有路径段经 sanitize（拒绝路径分隔符与 `..`）；读取侧用同一模板收敛扫描（`business_reader.py`、`path_builder.py:71-86`）；
- 实际目录示例：`logs/business/640/3/shared/execution.api_test_service.*.log`（任务 640 → 设备 3）。

> 【现状注记 · 与口径的差异】口径为「按 任务id/设备id/评估id 路径组织」：模板与读取器已支持第三段 `evaluation_id`，但 `set_current_evaluation_id` 无生产调用，评估日志实际按**轮次号**归第三段目录（评估上下文接线见 `e2e_test_service/.../rounds_loop_mixin.py:59`、`evaluation_service/.../reevaluation_executor.py`）。是否补 evaluation_id 接线待负责人拍板（见 INT-332 审计报告）。

## 3. 轮转与保留

轮转为**自研双条件** handler（非标准库 `TimedRotatingFileHandler`），见 `shared/logging/service_handler.py:88-113`：

- **按天**：跨天（`_today() != _current_day`）即轮转；
- **按大小**：单文件 ≥ 50MB 即轮转（两条件任一命中）；
- 轮转命名 `{base}-{YYYYMMDD}-{NNN}.log`，同日多次超限序号递增、不覆盖；
- 业务日志独立按 50MB 切分（`business_writer.py`、`path_builder.py:107-120`）；审计 JSONL 同样按 50MB 切分为
  `{category}.{service}.{hostname}-{pid}-NNN.jsonl`（`shared/logging/audit_writer.py`，序号按本进程 stem 递增）；
- **保留 30 天（三棵树统一）**：唯一默认键 `LOG_FILE_RETENTION_DAYS=30`，服务 / 业务 / 审计三棵树都继承它，
  细分类别只能显式覆盖、不得内置不同默认（`shared/infrastructure/config.py`）；
- 清扫器 `shared/logging/retention.py`：服务 / 业务树按 mtime，**审计树按目录日期**（`sweep_audit_dates`，
  进程重启后追加写刷新 mtime 不影响判定）；审计件到期**先归档到 rustfs `archives/audit/{date}/` 再删本地**，
  归档成功只认 `oss://`——`local://` 降级一律判失败、告警并保留原件下轮重试（绝不先删后传）；
- 单清扫者：只有 `LOG_SWEEP_SERVICE`（默认 `api_gateway`）执行清扫，其余进程跳过；
- log worker 仍按 600s 周期触发清扫，但清扫体**当日只真执行一次**：`{LOG_ROOT_DIR}/.sweep_stamp` 记日期戳
  （原子写 tmp+`os.replace`），跨进程用文件锁做 single-flight，非当日已执行即跳过（INT-1877 @ `99a18026f`）；
- 误删恢复：`scripts/maintenance/restore_audit_logs_from_oss.py --from/--to` 按日期区间把
  `archives/audit/{date}/` 原样回灌（走 `shared/infrastructure/storage` 的 category 机制、`oss://` 探活失败
  非零退出、默认不覆盖、size + sha256 + 逐行 JSON 校验，不写 DB；INT-1877 @ `99a18026f`）。

## 4. WS / Socket.IO 推送（文件化后已核验正常）

推送链路与文件化**完全解耦**、不依赖数据库：

1. 业务日志 emit 时进入**内存队列**（`_emit_mixin._enqueue_business_log`）；
2. worker **先写业务文件，再推 WS**（`_worker_mixin._process_business_queue`，合成负数 id 仅供前端作 key）；
3. 经 Redis EventBus `publish(TASK_EVENTS, TASK_LOG)` → api_gateway `event_bus_forwarder.py` → `websocket/socketio_server.py` Socket.IO emit `task_log` 到 `/ws/logs`（room = `task:{task_id}`）；SSE 并行链路见 `api_gateway/routes/sse_bp.py`；
4. Redis 不可用时推送降级仅打日志，文件写入不受影响。

历史日志查询走「业务文件 + logs 表历史行（审计 / 旧数据）」合并分页（`api_gateway/application/services/log/log_query_service.py`）；超大任务 total 为有界下界（`LOG_BUSINESS_MAX_SCAN_ENTRIES=10万` + 3s TTL 缓存）。

## 5.1 日志归档管理面（LogView 归档面板 + 5 端点）

> 【实现演进裁定 2026-10-17，INT-559 一致性审计回写】归档操作面向管理员的管理面（INT-548 前端接线）
> 经 api_gateway 5 个 REST 端点暴露（权威基线 `api_gateway/routes/log_bp.py:52-82`，网关挂载前缀
> `/api/v1/logs`），前端 LogView 归档面板（`LogArchivePanel.vue`）为唯一管理入口。

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| GET | `/api/v1/logs/archive/status` | `log:read` | 归档状态（热/冷日志计数 + OSS archives 桶 任务/用例/其他 前缀文件数） |
| POST | `/api/v1/logs/archive` | `log:manage` | 触发归档（`days` 保留最近 N 天热数据；`dry_run` 仅预览不执行） |
| GET | `/api/v1/logs/archive/logs` | `log:read` | 已归档日志列表 / **全局归档文件清单**（无 `task_id` / `test_case_id` → 全局清单可分页 `page`/`per_page`；传筛选 → 按任务/用例过滤的 LogItem 列表） |
| GET | `/api/v1/logs/archive/{filename:path}` | `log:read` | 下载归档文件（`filename` 支持完整逻辑 key 或末段裸文件名，`{filename:path}` 多段路由） |
| DELETE | `/api/v1/logs/archive/{filename:path}` | `log:manage` | 删除归档文件（同完整 key / 末段契约） |

- **权限口径**：`log:read` 覆盖 查看日志/统计/归档状态/归档列表/下载归档；`log:manage` 覆盖 标记/刷新/清空/触发归档/删除归档；admin（`*` 通配）可全操作（与既有 C2 口径一致）。
- **请求/响应契约**：触发归档请求体 `LogArchiveRequest {days:int=7, dry_run:bool=false}`（snake_case）；dry_run 返回 `{message, cold_logs_count, cutoff_date}`，真实归档返回 `LogArchiveResult {archived_count, deleted_count, archive_file, remaining_count}`。
- **归档状态响应为 camelCase raw dict**（`totalLogs/hotLogs/coldLogs/archiveDir/taskArchives/caseArchives/otherArchives`，不经 APIModel 序列化——前端 DTO 按实际 wire 对齐）；已归档列表（带筛选）响应 `{items, total, source:"archive"}`（items 为 LogItem）。
- **全局归档文件清单响应（INT-780 契约定稿，无筛选参数时）**：`data = {items:[{filename, sizeBytes, archivedAt}], total}`（camelCase raw dict，与 `get_archive_status` 同口径）；`filename` 为**归档逻辑 key 完整路径**（如 `tasks/123/2026-10-18.json`，行 key 唯一可精确定位）；`sizeBytes` 取对象 Size；`archivedAt` 取对象 LastModified（UTC ISO-8601 `Z` 后缀）；分页参数 `page` / `per_page`（照 `LogListQuery` 惯例，仅全局模式生效）。
- **下载/删除 filename 契约**：FastAPI `{filename:path}` 多段路由（静态路由 `archive/status`、`archive/logs` 先注册不受影响），后端既有匹配 `k == filename` 或 `endswith('/filename')` 双分支（`log_query_service.download_archive` / `log_command_service.delete_archive`）天然支持完整逻辑 key 与末段裸文件名两种传参，Vue 末段传参向后兼容。

  normalize_user_id(item.user_id) or get_current_user_id()`（显式 → context 回退 →
  None/0 → NULL，不硬编码兜底为真实用户）。
- `auth_service` gRPC server 补装 `server_user_context_interceptor`（写侧归属上下文必需，
  缺它 auth 审计 `created_by_user_id` 恒 NULL）。

### 5.2.3 鉴权绑定

`query.user_id` 非空且与当前认证用户（`current_operator_id()`）不一致 → **403「无权限查看
他人日志」**；`AUTH_MODE=off`（operator=0）无认证用户 → 放行（「仅自己」无归属行 → 空列表，
不报错）。

### 5.2.4 历史行语义与可选回填

- 写侧归属落地前 `created_by_user_id` 全 NULL →「仅自己」对历史行永不可见（接受，不做全量
  回填——无法可靠反推操作人）。
- 可选回填脚本 `scripts/migrations/202610/backfill_log_operator_int806.py`：对
  category∈{auth,benchmark} 且 content 可解析为 JSON 且含 `operator_id` 的审计行回填
  `created_by_user_id`（默认 dry-run，`--apply` 落库；解析失败放弃不阻塞；幂等）。
  **现状注记**：benchmark 审计 content 为 operator 用户名串、不含 operator_id → 脚本实际
  只回填 auth 行（benchmark 行如需归属另需用户名→id 映射，超出本卡）。

## 5.3 全局日志页读侧（审计文件 + legacy DB 行合并）

> 【实现演进裁定 2026-10-25，INT-1885 一致性审计回写】对象 = INT-1812 交付分支
> `agent/a/int-1812` @ `ca284943a`（尚未合入 V9.7.31）。本节的读侧口径是**用户与运维可见行为**的
> 权威说明，代码位置以 `api_gateway/application/services/log/log_query_service.py`、
> `shared/logging/audit_reader.py` 为准。

### 5.3.1 每个端点的数据来源

| 端点 | 改造后数据来源 | 分页 / total | 排序 |
| --- | --- | --- | --- |
| `GET /logs`（无 `task_id`） | 审计文件（时间窗内）+ `logs` 表历史行（只读） | 内存合并后分页；`total` = 窗口内命中数，扫描触顶时为**下界** | `(time desc, id/cursor desc)` |
| `GET /logs`（有 `task_id`） | 业务文件 + DB 历史行（口径不变，见 §4） | 不变 | 不变 |
| `GET /logs/stats` | 与列表同源同筛选，按 level 聚合（列表与统计共享同一次文件扫描） | 触顶时各项同为下界 | — |
| `POST /logs/refresh` | 审计文件（游标增量） | 单次 ≤ 100 条 | `cursor asc` |
| `POST /logs/export` | 与列表同源同筛选（含 legacy DB 行），不分页 | 受扫描上界约束；DB 命中超 `LOG_DB_EXPORT_MAX_ROWS`（默认 0=不限）显式报错 | `time desc` |
| `PUT /logs/mark` | 仅 DB 历史行 | 文件游标 → `updated=0` + 专用提示 | — |
| `POST /logs/clear`、归档 5 端点 | 仅 DB / OSS（语义不变） | DB 清空后 `archived_count=0`、`totalLogs=0` 属预期 | — |

- **筛选能力与改造前 DB 查询对等**：`level`（逗号多值）、`module`（`all` 归一）、`category`、`mark`、
  时间区间、`keyword` / `content_include` / `content_exclude`、`user_id`（「仅自己」，文件侧读 JSONL 顶层
  `user_id` = 写侧从 content 提取的 `operator_id`）、`device_id` / `task_id` / `api_id` / `test_case_id` /
  `thread_id`（包含匹配）/ `algorithm_type`。
- **扫描上界与缓存**：`LOG_AUDIT_MAX_SCAN_ENTRIES`（默认 100000，0=不限）触顶后保留**最新**部分且 `total`
  为下界；同参查询结果按 `LOG_AUDIT_SCAN_CACHE_TTL_SECONDS`（默认 3s）缓存，列表与统计共享一次扫描。
- **导出取数**：导出条件只有 `level` / `module`（`LogExportQuery` 既有字段，改造前后一致），无时间筛选时
  同样按默认窗口取数；`log_ids` 里 ≥ `CURSOR_FLOOR` 的按游标反查日期目录，其余走 DB 导出——两条链路任一
  失败**显式报错**，不产出部分数据当成功。

### 5.3.2 游标与增量刷新（对前端零改动）

- 文件条目 `id` = `cursor`（事件时间 epoch 微秒，写侧进程内严格递增）；legacy `logs` 表 id 实测
  max ≈ 6.9e6，用 `CURSOR_FLOOR = 10^12` 把两个 id 空间隔开，仍 < JS `Number.MAX_SAFE_INTEGER`（9.0e15）。
- `POST /logs/refresh {"last_id":N}` 响应字段名不变（`items/count/new_count/last_id/db_max_id[,
  reset_required]`），`db_max_id` 语义 = `server_max_cursor`（无数据 0）。四种情形：`last_id=0` 只建基准；
  `last_id < CURSOR_FLOOR`（旧 DB id）或 `> server_max_cursor`（库清空 / 时钟回拨）→ 空 + `reset_required`；
  游标域内 → 升序最多 100 条。React `useLogRealtime.ts` 已有 `resetRequired` 分支，Vue 只发
  `Math.max(...ids)`、不读该字段，两前端零改动。

### 5.3.3 两项对用户/运维可见的语义变化（必须按此理解）

1. **默认窗口 = 近 30 天**：`GET /logs` / `GET /logs/stats` / `POST /logs/export` 在**既无 `start_time`
   也无 `end_time`** 时，默认取最近 `LOG_AUDIT_QUERY_DEFAULT_DAYS`（30）天。页面上的「共 N 条」是
   **近 30 天 N 条**，不是历史全部 N 条；需要更早数据须显式选择时间范围（更早的行仍在 `logs` 表里只读
   可查，文件侧则受 30 天在线保留约束）。原因：文件侧无索引，无界扫描随保留期线性增长。
2. **文件日志不可标记**：审计文件与业务文件条目只读，JSONL 不含 `mark` 字段。对文件条目调用
   `PUT /logs/mark` 返回 **200 + `updated=0`** 与提示「所选为文件日志，不支持标记（仅历史库行可标记）」，
   不报 400/500、不出现空态回退；`?mark=flagged` 筛选在文件侧恒空命中（页面显示 0 条，属正确行为）。
   标记行豁免（不参与 30 天自动清理）因此只作用于 legacy DB 行（§Q5.1）。
   前端 `logsApi.markLogs` 只读状态码，零改动。

### 5.3.4 读侧配置键

| 键 | 默认 | 语义 |
| --- | --- | --- |
| `LOG_AUDIT_MAX_SCAN_ENTRIES` | `100000` | 单次物化上限（0=不限），触顶 `total` 为下界 |
| `LOG_AUDIT_QUERY_DEFAULT_DAYS` | `30` | 无时间筛选时的默认窗口 |
| `LOG_AUDIT_SCAN_CACHE_TTL_SECONDS` | `3` | 同参结果 TTL 缓存（照 INT-100 口径） |
| `LOG_DB_FETCH_CHUNK_ROWS` | `5000` | 合并视图 DB 侧单块 gRPC 拉取行数（ListLogs 单条 JSON 消息，10 万行会撞 64MB 上限） |
| `LOG_DB_EXPORT_MAX_ROWS` | `0` | 导出 DB 侧命中上限（0=不限），超限显式报错不静默截断 |

> 写入侧 / 保留侧的 9 个配置键（`LOG_AUDIT_ENABLED`、`LOG_AUDIT_DB_ENABLED`、`LOG_AUDIT_MAX_MB`、
> `LOG_FILE_RETENTION_DAYS`、`LOG_AUDIT_ARCHIVE_ENABLED`、`LOG_AUDIT_MAX_SCAN_ENTRIES`、
> `LOG_AUDIT_QUERY_DEFAULT_DAYS`、`LOG_AUDIT_SCAN_CACHE_TTL_SECONDS`、`LOG_SWEEP_SERVICE`）见契约 §3.4。
> **审计保留天数键的实际形态**（INT-1852 回写、本次复核确认）：`LOG_AUDIT_RETENTION_DAYS` **存在但无独立
> 默认**，默认继承 `LOG_FILE_RETENTION_DAYS`（30），等价于 `LOG_SERVICE/BUSINESS_RETENTION_DAYS` 的
> 「继承默认 + 显式覆盖」；全仓无 180 天残留默认。

## 5.4 进度事件「最近日志」（INT-1808）

> 【实现演进裁定 2026-10-25，INT-1885 一致性审计回写】对象 = `agent/c/int-1808` @ `31b4e3f0e`。
> 代码 `shared/utils/event_manager/_progress.py`。

- 背景（契约 §1 D5 存量缺陷）：业务日志自 INT-81 去库化后，进度事件的「最近日志」仍走 `list_logs`（DB），
  新任务恒空。
- 现口径：优先读业务文件 `logs/business/{task_id}/**`，逐文件从尾部按块回读（16KB 起、不足按需翻倍），
  凑够 20 条后按 `time` 倒序取前 20 再反转为正序，`level` 小写、`message` = 文件行 `content`，
  `id` = 文件相对路径 + 行偏移的稳定哈希（同一记录跨多次推送稳定，仅供前端 key）。
- DB 回落条件**只有一个**：该任务在业务日志根下没有任何日志文件（INT-81 之前的历史任务）；文件存在但读到
  空列表以文件为准，不再回落（避免把「本任务确实没有日志」误判为历史任务）；读文件抛异常时回落 DB，
  保证进度事件不因日志读取失败而中断。

## 1. 总体架构

分流逻辑（`shared/utils/log_handler/_emit_mixin.py`）：

| 日志类别 | 判定 | 去向 |
| --- | --- | --- |
| 业务日志 | 带 task_id | **业务文件**（`logs/business/`，JSON Lines）+ WS 推送 |

## 2. 落盘结构与路径组织

**服务运行日志**（系统级）：

```
logs/{service_name}/app-{hostname}-{pid}.log
```

**业务日志**（执行 / 评估 / 设备，JSON Lines 格式）——路径模板见 `shared/logging/path_builder.py:38-69`：

```
logs/business/{task_id}/{device_id|api_id|common}/{round|shared}/{log_type}.{service_name}.{hostname}-{pid}.log
```

- 第一段 = 任务 id，第二段 = 设备 id（无设备上下文为 `common`），第三段 = 轮次号（跨轮共享为 `shared`）；
- 所有路径段经 sanitize（拒绝路径分隔符与 `..`）；读取侧用同一模板收敛扫描（`business_reader.py`、`path_builder.py:71-86`）；
- 实际目录示例：`logs/business/640/3/shared/execution.api_test_service.*.log`（任务 640 → 设备 3）。

> 【现状注记 · 与口径的差异】口径为「按 任务id/设备id/评估id 路径组织」：模板与读取器已支持第三段 `evaluation_id`，但 `set_current_evaluation_id` 无生产调用，评估日志实际按**轮次号**归第三段目录（评估上下文接线见 `e2e_test_service/.../rounds_loop_mixin.py:59`、`evaluation_service/.../reevaluation_executor.py`）。是否补 evaluation_id 接线待负责人拍板（见 INT-332 审计报告）。

## 3. 轮转与保留

轮转为**自研双条件** handler（非标准库 `TimedRotatingFileHandler`），见 `shared/logging/service_handler.py:88-113`：

- **按天**：跨天（`_today() != _current_day`）即轮转；
- **按大小**：单文件 ≥ 50MB 即轮转（两条件任一命中）；
- 轮转命名 `{base}-{YYYYMMDD}-{NNN}.log`，同日多次超限序号递增、不覆盖；
- 业务日志独立按 50MB 切分（`business_writer.py`、`path_builder.py:107-120`）；
- **保留 30 天**，由 mtime 清扫器执行（`shared/logging/retention.py`，log worker 每 600s 触发一次；business/ 子树排除在服务清扫外）；
- 默认值配置在 `shared/infrastructure/config.py:100-107`（服务 / 业务日志各 50MB / 30 天）。

## 4. WS / Socket.IO 推送（文件化后已核验正常）

推送链路与文件化**完全解耦**、不依赖数据库：

1. 业务日志 emit 时进入**内存队列**（`_emit_mixin._enqueue_business_log`）；
2. worker **先写业务文件，再推 WS**（`_worker_mixin._process_business_queue`，合成负数 id 仅供前端作 key）；
3. 经 Redis EventBus `publish(TASK_EVENTS, TASK_LOG)` → api_gateway `event_bus_forwarder.py` → `websocket/socketio_server.py` Socket.IO emit `task_log` 到 `/ws/logs`（room = `task:{task_id}`）；SSE 并行链路见 `api_gateway/routes/sse_bp.py`；
4. Redis 不可用时推送降级仅打日志，文件写入不受影响。

历史日志查询走「业务文件 + logs 表历史行（审计 / 旧数据）」合并分页（`api_gateway/application/services/log/log_query_service.py`）；超大任务 total 为有界下界（`LOG_BUSINESS_MAX_SCAN_ENTRIES=10万` + 3s TTL 缓存）。

- **审计日志**：~~按既有设计仍落 `logs` 表~~ → 【2026-10-24 裁定取代】改为落 `logs/audit/{date}/` 文件，
  回滚开关 `LOG_AUDIT_DB_ENABLED`（默认 false）见契约 Q7；2026-10-24 主库实测审计类仍约 1.2k~2.5k 行/天
  （auth 为主，另有 published_task / review / ai_review 的 System 类审计直写仓储）；
- logs 表冷数据归档 OSS（`_archive_mixin.py`），DB 侧历史行保留只读、不迁移；历史存量清理由 INT-1785 负责；
- 【2026-10-24 补充】审计事件今天最多落三份：`logs` 表行 + `logs/{service}/app-*.log` 事件行 +

## 5.1 日志归档管理面（LogView 归档面板 + 5 端点）

> 【实现演进裁定 2026-10-17，INT-559 一致性审计回写】归档操作面向管理员的管理面（INT-548 前端接线）
> 经 api_gateway 5 个 REST 端点暴露（权威基线 `api_gateway/routes/log_bp.py:52-82`，网关挂载前缀
> `/api/v1/logs`），前端 LogView 归档面板（`LogArchivePanel.vue`）为唯一管理入口。

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| GET | `/api/v1/logs/archive/status` | `log:read` | 归档状态（热/冷日志计数 + OSS archives 桶 任务/用例/其他 前缀文件数） |
| POST | `/api/v1/logs/archive` | `log:manage` | 触发归档（`days` 保留最近 N 天热数据；`dry_run` 仅预览不执行） |
| GET | `/api/v1/logs/archive/logs` | `log:read` | 已归档日志列表 / **全局归档文件清单**（无 `task_id` / `test_case_id` → 全局清单可分页 `page`/`per_page`；传筛选 → 按任务/用例过滤的 LogItem 列表） |
| GET | `/api/v1/logs/archive/{filename:path}` | `log:read` | 下载归档文件（`filename` 支持完整逻辑 key 或末段裸文件名，`{filename:path}` 多段路由） |
| DELETE | `/api/v1/logs/archive/{filename:path}` | `log:manage` | 删除归档文件（同完整 key / 末段契约） |

- **权限口径**：`log:read` 覆盖 查看日志/统计/归档状态/归档列表/下载归档；`log:manage` 覆盖 标记/刷新/清空/触发归档/删除归档；admin（`*` 通配）可全操作（与既有 C2 口径一致）。
- **请求/响应契约**：触发归档请求体 `LogArchiveRequest {days:int=7, dry_run:bool=false}`（snake_case）；dry_run 返回 `{message, cold_logs_count, cutoff_date}`，真实归档返回 `LogArchiveResult {archived_count, deleted_count, archive_file, remaining_count}`。
- **归档状态响应为 camelCase raw dict**（`totalLogs/hotLogs/coldLogs/archiveDir/taskArchives/caseArchives/otherArchives`，不经 APIModel 序列化——前端 DTO 按实际 wire 对齐）；已归档列表（带筛选）响应 `{items, total, source:"archive"}`（items 为 LogItem）。
- **全局归档文件清单响应（INT-780 契约定稿，无筛选参数时）**：`data = {items:[{filename, sizeBytes, archivedAt}], total}`（camelCase raw dict，与 `get_archive_status` 同口径）；`filename` 为**归档逻辑 key 完整路径**（如 `tasks/123/2026-10-18.json`，行 key 唯一可精确定位）；`sizeBytes` 取对象 Size；`archivedAt` 取对象 LastModified（UTC ISO-8601 `Z` 后缀）；分页参数 `page` / `per_page`（照 `LogListQuery` 惯例，仅全局模式生效）。
- **下载/删除 filename 契约**：FastAPI `{filename:path}` 多段路由（静态路由 `archive/status`、`archive/logs` 先注册不受影响），后端既有匹配 `k == filename` 或 `endswith('/filename')` 双分支（`log_query_service.download_archive` / `log_command_service.delete_archive`）天然支持完整逻辑 key 与末段裸文件名两种传参，Vue 末段传参向后兼容。
- **前端 DDD**：`LogArchivePanel.vue` → `logArchive.ts` composable → `logsPort` → `logsApi`；snake_case↔camelCase 转换全部收敛在 Infrastructure（`logAdapter.ts`），View/composable 只见 camelCase Domain。
- **已知缺陷跟踪**：写盘双 `archives/` 前缀、读前缀口径错位、`download_archive` 文件锁 → INT-554（已修复，待合入主库）。

## 5.2 日志查询 user_id 过滤（「仅自己」视图范围）

> 【实现演进裁定 2026-10-19，INT-806 一致性审计回写】日志列表 / 统计支持按操作人
> `user_id` 过滤，支撑 React `/logs` 页「全部 / 仅自己」视图范围 Tabs（UX 规范
> `17_配置运维.md` §4.2，`log:manage` 显隐）。V9.7.31 主线此前未记录该口径，本裁定
> 补录（后端实现 commit `8467eb09e`，已合入 V9.7.31）。

### 5.2.1 读侧契约

- `GET /logs?user_id=368` → 仅返回 `created_by_user_id=368` 的行；无该用户行 →
  `items=[] total=0`（分页信封不变）。
- `GET /logs/stats?user_id=368` → 同口径计数（总 / 错误 / 警告 / 信息），与列表一致。
- 任务合并视图 `GET /logs?task_id=X&user_id=368` → DB 行按 `created_by_user_id` 过滤；
  文件侧业务执行日志无操作人属性、非用户操作 → **排除**（「仅自己」只显示用户操作产生的日志，
  stats 同口径跳过文件合并，徽章数不虚高）。
- 旧调用方不传 `user_id` = 不过滤，行为完全不变（兼容）。
- 链路：`LogListQuery` / `LogStatsQuery` → `log_query_service` → gRPC 代理 → proto
  （`ListLogsRequest.user_id=18` / `GetLogStatsRequest.user_id=13`）→ task_service 仓储
  SQL `Log.created_by_user_id == user_id`。

### 5.2.2 写侧归属（操作人归属）

「仅自己」归属口径 = **操作人归属**：`Log.created_by_user_id == 当前用户`。不做「任务日志按
任务创建者」归属（任务执行日志属系统生成，不归属个人；如需另开卡）。

- `shared/utils/log_handler/_emit_mixin.py` DB 入库路径 log_data 增 `user_id =
  get_current_user_id()`（请求线程可得；后台线程 None → NULL，行为不变）。
- `shared/utils/log_handler/_worker_mixin.py` `_process_batch` 载荷随条目透传
  `user_id`（worker 线程不继承 contextvar，必须随条目携带）。
- `task_service log_repository.batch_create` 写 `created_by_user_id =
  normalize_user_id(item.user_id) or get_current_user_id()`（显式 → context 回退 →
  None/0 → NULL，不硬编码兜底为真实用户）。
- `auth_service` gRPC server 补装 `server_user_context_interceptor`（写侧归属上下文必需，
  缺它 auth 审计 `created_by_user_id` 恒 NULL）。

### 5.2.3 鉴权绑定

`query.user_id` 非空且与当前认证用户（`current_operator_id()`）不一致 → **403「无权限查看
他人日志」**；`AUTH_MODE=off`（operator=0）无认证用户 → 放行（「仅自己」无归属行 → 空列表，
不报错）。

### 5.2.4 历史行语义与可选回填

- 写侧归属落地前 `created_by_user_id` 全 NULL →「仅自己」对历史行永不可见（接受，不做全量
  回填——无法可靠反推操作人）。
- 可选回填脚本 `scripts/migrations/202610/backfill_log_operator_int806.py`：对
  category∈{auth,benchmark} 且 content 可解析为 JSON 且含 `operator_id` 的审计行回填
  `created_by_user_id`（默认 dry-run，`--apply` 落库；解析失败放弃不阻塞；幂等）。
  **现状注记**：benchmark 审计 content 为 operator 用户名串、不含 operator_id → 脚本实际
  只回填 auth 行（benchmark 行如需归属另需用户名→id 映射，超出本卡）。

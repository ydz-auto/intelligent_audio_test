# 音频引擎功能总述

## 一、系统概述

音频引擎是基于 PyAudio 的音频播放管理系统，专门为 E2E 测试场景设计，支持多通道设备选择、采样率转换、声道映射以及灵活的音频重叠播放功能。

### 1.1 核心能力

| 功能模块 | 说明 |
|---------|------|
| 多设备播放 | 支持同时在多个物理设备上播放音频 |
| 多声道混合 | 支持在同一设备的不同声道同时播放不同音频 |
| 重叠播放 | 支持两个音频按 overlap_rate/overlap_time 参数控制重叠区域 |
| Speaker 感知 | 智能识别同一说话人，避免不合理的音频重叠 |
| 增益补偿 | 根据音频 RMS 自动调整增益，确保输出电平一致 |
| 重采样 | 支持不同采样率音频自动转换到设备支持的采样率 |

## 二、核心概念

### 2.1 设备与声道层次

```
物理设备 (device_index)
├── 声道 0 (channel_index=0) → PlaybackDevice A
├── 声道 1 (channel_index=1) → PlaybackDevice B
├── 声道 2 (channel_index=2) → PlaybackDevice C
└── ...
```

**关键区别**：
- **物理设备** (`device_index`)：PyAudio 的设备索引，代表一个物理音频设备
- **声道** (`channel_index`)：设备上的音频通道，如左声道、右声道
- **PlaybackDevice** (`playback_device_id`)：数据库中的配置单元，对应具体的声道

### 2.2 PyAudio 技术限制

**核心限制**：PyAudio 不允许同一设备同时打开多个流。

```
❌ 错误做法：每个音频单独打开一个流
┌──────────┐    ┌──────────┐
│  设备34  │    │  设备34  │  → [Errno -9996] Invalid device
│ Stream A │    │ Stream B │
└──────────┘    └──────────┘

✅ 正确做法：使用 play_multi 在同一流中混合
┌──────────┐
│  设备34  │  同一个流，不同通道
│ Stream A │  channel=0 + channel=1 混合输出
└──────────┘
```

### 2.3 重叠播放参数

| 参数 | 类型 | 说明 | 优先级 |
|------|------|------|--------|
| overlap_time | float | 交叠时间（秒），两个音频同时播放的时间段 | 高 |
| overlap_rate | float | 交叠率 (0.0-1.0)，0.5 表示 50% 交叠 | 低 |

**重叠计算公式**：
```
overlap_time = duration × overlap_rate
delay = prev_end_time × (1 - overlap_rate)
```

**效果示例** (duration = 10s)：

| overlap_rate | 交叠时间 | 延迟时间 | 效果示意 |
|-------------|---------|---------|---------|
| 0 | 0 | 10s | [AAAA][BBBB] 顺序播放 |
| 0.5 | 5s | 5s | [AAA[AB]BB] 50%交叠 |
| 1.0 | 10s | 0 | [AA][BB] 同时开始 |

#### play_multi() - 同设备多音频混合


## 四、关键技术问题与修复

### 4.1 多音频并行播放问题

#### 问题1：音频覆盖而非混合

**现象**：同设备多音频时，只有最后一个能播放

**原因**：`play_multi` 的 callback 中使用赋值 `=` 而非相加 `+=`

```python
# 修复前 (覆盖)
out_buffer[ch_idx::stream_channels] = audio_data[:limit]

# 修复后 (混合)
out_buffer[ch_idx::stream_channels] += audio_data[:limit]
```

#### 问题2：设备间播放延迟过长

**现象**：第一个设备播放完后，等待约4秒才开始第二个设备

**原因**：设备级别使用 `min_delay` 造成不必要的等待

```python
# 修复前
for thread, device_stop_event, delay, dev_idx in dry_threads:
    if delay > 0:
        time.sleep(delay)  # 不必要的等待
    thread.start()

# 修复后：所有设备同时开始
for thread, device_stop_event, delay, dev_idx in dry_threads:
    thread.start()
```

#### 问题3：单音频 delay 未传递

**现象**：每个设备只有一个音频时，delay 参数被忽略

```python
# 修复前
multi_configs = [{'delay': 0}]  # 硬编码为0

# 修复后
config = audio_list[0]
_, delay = audio_list_with_delays[0]
multi_configs = [{'delay': delay}]  # 使用实际 delay
```

#### 问题4：声道 delay 未独立计算

**现象**：同一设备多个声道按顺序播放而非并行

**原因**：按 device_index 分组导致同设备所有声道共享 delay

```python
# 修复后：按 play_order 排序，每个声道独立计算 delay
for i, config in enumerate(sorted_dry):
    if i == 0:
        start_time = 0
    else:
        if overlap_rate > 0:
            start_time = prev_end_time * (1 - overlap_rate)
        else:
            start_time = prev_end_time
```

#### 问题5：无交叠时噪声立即停止

**现象**：干声无交叠（overlap_time=0）时，干声还没开始播放就停止了

**原因**：`execute_audio_playback` 中计算 `total_duration` 的条件过于严格

```python
# 修复前
if overlap_time and overlap_time > 0 and len(dry_audios_info) >= 2:
    # 只有 overlap_time > 0 时才计算 total_duration
    # 当 overlap_time=0 时，total_duration=0
    # 导致 time.sleep(0) 后立即调用 stop_task_audio()
```

**解决方案**：移除该条件限制，始终计算 `total_duration`

```python
# 修复后：始终计算 total_duration
audio_timelines = build_audio_timelines(dry_audios_info, overlap_rate, overlap_time)
if audio_timelines:
    total_duration = max(t.get('end', 0) for t in audio_timelines)
else:
    total_duration = sum(audio.duration or 0 for _, audio in dry_audios_info)
```

### 4.2 播放时序控制机制

```
┌─────────────────────────────────────────────────────────────┐
│                    播放时序控制层次                           │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 设备级别：所有设备同时开始播放                              │
│     └─ 移除 device 级别的 time.sleep 延迟                    │
│                                                              │
│  2. 声道级别：每个 playback_device 独立 delay                 │
│     ├─ delay > 0 → 填充静音数据                              │
│     └─ delay ≤ 0 → 输出实际音频数据                          │
│                                                              │
│  3. 计算公式：                                               │
│     ├─ play_order=0: delay = 0                             │
│     ├─ play_order=1: delay = cumulative_duration × (1 - r) │
│     └─ play_order=n: delay = 累加                           │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

## 五、Speaker 感知交叠播放

### 5.1 问题背景

传统 overlap 播放存在不合理场景：
- **连续同说话人交叠**：同一说话人的连续语音不应交叠
- **跨音频同一说话人交叠**：相同说话人不应同时在两个地方说话

```
音频1: [spk9: 0-2s] [spk8: 2-5s]
音频2: [spk9: 0-3s] [spk4: 3-6s]
音频3: [spk7: 0-2s] [spk8: 2-5s]

问题：音频1和音频2都有spk9，不应该交叠
```

### 5.2 解决方案

**Speaker 感知规则**：
```
相邻音频 speakers 集合有交集 → 顺序播放（delay = prev_end_time）
相邻音频 speakers 集合无交集 → 按 overlap_time 或 overlap_rate 交叠
```

### 5.3 数据来源

从 `audio_annotations` 表查询 diarization 标注：

```json
{
  "segments": [
    {"speaker": "spk9", "start": 0, "end": 0.75, "text": "..."},
    {"speaker": "spk8", "start": 0.75, "end": 3.75, "text": "..."}
  ]
}
```

### 5.4 时间轴效果对比

**修改前（链式交叠）**：
```
overlap_rate = 0.3

音频1 (spk9, spk8):   [AAAAAAAAAA            ]────────────────────────►
音频2 (spk9, spk4):        [BBBBB        ]────────────────────────►
音频3 (spk7, spk8):             [CCCCCC]────────────────────────►

总时长 ≈ 音频1.duration × 0.7 + 音频2.duration × 0.7 + 音频3.duration
```

**修改后（Speaker 感知）**：
```
overlap_rate = 0.3

音频1 (spk9, spk8):   [AAAAAAAAAA            ]────────────────────────►
音频2 (spk9, spk4):                        [BBBBBBBBBB]────────────────────────►
音频3 (spk7, spk8):                                        [CCCCCCCCCC]────────────────────────►

总时长 = 音频1.duration + 音频2.duration + 音频3.duration
```

### 5.5 同声道混合机制

**Speaker 感知逻辑负责判断时序关系（顺序/交叠），实际的同声道混合由 `play_multi` 的 callback 函数处理**。

| 场景 | 时序关系 | 物理层处理 |
|------|---------|-----------|
| 同 speaker + 同声道 | 顺序播放 | 不涉及混合 |
| 不同 speaker + 同声道 | 交叠 | `out_buffer[ch] += audio1 + audio2` 混合 |
| 同 speaker + 不同声道 | 顺序播放 | 不涉及混合 |
| 不同 speaker + 不同声道 | 交叠 | 不同声道输出，无混合 |

**同声道混合原理**：

```python
# play_multi callback 中
out_buffer[ch_idx:limit*stream_channels:stream_channels] += audio_data[:limit]
```

**效果示例**：

```
音频1 (spk0):        [AAAAAAA        ]────────────────────────►  channel=0
音频2 (spk1):             [BBBBB]────────────────────────►  channel=0

时间轴：0 ─────────────────────────────────────────────────►
         0-7s: 只有 spk0 播放
         7-12s: spk0 + spk1 同时播放，信号叠加
         12s+: 只有 spk1 播放
```

## 六、音频标注与参考参数

### 6.1 标注存储机制

**存储位置**：`AudioAnnotation` 表

| 字段 | 说明 |
|------|------|
| audio_id | 关联音频ID |
| format | 标注格式 (json/rttm/stm) |
| data | 标注数据内容 (JSON) |

**来源**：所有标注都由前端解析后通过 API 存储，后端只负责存储。

### 6.2 参考参数生成

**生成器架构**：策略模式，根据 `algorithm_type` 选择生成器

| algorithm_type | 生成器类 | 参数代码 |
|----------------|----------|---------|
| translation | TranslationASRGenerator | asr_reference_text |
| translation | TranslationTextGenerator | translation_reference_text |
| asr | ASRGenerator | asr_reference_text |
| tts | TTSGenerator | tts_reference_text |
| speaker_recognition | SpeakerRecognitionGenerator | speaker_reference_text |
| vad | VADGenerator | vad_reference_text |

### 6.3 重叠播放标注处理

```
1. 获取用例配置 (config.audios)
   └─ 音频列表: [{audio_id: 101, play_order: 0}, ...]

2. 构建 speakers_map
   ├─ 音频101 → audio_annotations → {'spk9', 'spk8'}
   └─ 音频102 → audio_annotations → {'spk9', 'spk4'}

3. 计算播放 offset
   ├─ 音频101: offset=0
   ├─ 音频102: 音频101∩音频102={'spk9'}≠∅ → 顺序播放 → offset=4.18s
   └─ ...

4. 调整标注时间戳
   └─ 按 offset 偏移量调整每个音频的 segments

5. 合并输出
   └─ 合并所有音频的 segments 并按时间排序
```

## 七、播放流程总览

### 7.1 完整数据流

```
┌─────────────────────────────────────────────────────────────────┐
│                         播放执行流程                              │
└─────────────────────────────────────────────────────────────────┘

1. 入口调用
   TestCaseController.preview / E2EExecutor
        ↓
2. 参数提取
   ├─ 获取 algorithm_type
   ├─ 提取 overlap_rate / overlap_time
   └─ 判断是否为 speaker_recognition 场景
        ↓
3. 配置准备
   ├─ 获取音频列表 (config.audios)
   ├─ 查询 AudioAnnotation 构建 speakers_map
   └─ 计算每个音频的 delay (speaker_aware 或 standard)
        ↓
4. 设备分组
   ├─ 按 device_index 分组
   ├─ 同设备 → 使用 play_multi 混合
   └─ 不同设备 → 使用 play_overlap 并行
        ↓
5. 执行播放
   ├─ 启动各设备的播放线程
   ├─ 所有设备同时开始 (移除 device 级延迟)
   └─ 各声道按 delay 参数填充静音
        ↓
6. 时间戳记录
   ├─ playback_start_time = time.time()
   └─ actual_play_time = playback_start_time + delay
```

### 7.2 设备扫描与匹配

```
扫描流程：
get_devices()
    → 创建 PyAudio 实例
    → 遍历所有设备
    → 过滤输出通道 > 0 的设备
    → 获取 Host API 信息
    → 返回设备列表

物理设备聚合：
RME Fireface UCX II
├── Analog (3+4) [Ch 1] → device_index=34, channel_index=0
├── Analog (3+4) [Ch 2] → device_index=34, channel_index=1
├── Analog (5+6) [Ch 1] → device_index=36, channel_index=0
└── Analog (5+6) [Ch 2] → device_index=36, channel_index=1

设备匹配优先级：WASAPI > DirectSound > WDM-KS > MME
```

## 八、线程安全与上下文管理

### 8.1 线程安全机制

- 使用 `threading.Lock` 确保同一时间只有一个音频流在配置/打开
- 每个设备有独立的锁 (`_device_locks`)
- 每个播放任务有独立的 `stop_event`

### 8.2 Flask App Context 传递

```
问题：后台线程执行时无法访问数据库

主线程 (HTTP请求)
    ↓
创建后台线程执行音频播放
    ↓
后台线程调用 spl_service.spl_to_gain()
    ↓
❌ 后台线程没有有效的 Flask App Context

解决方案：
app = current_app._get_current_object()  # 主线程中获取
threading.Thread(target=play_audio, args=(app,)).start()
```

## 九、常见问题排查

| 问题现象 | 可能原因 | 解决方案 |
|---------|---------|---------|
| 只播放第一个音频 | delay 计算过大 | 检查 prev_end_time 计算 |
| 音频覆盖而非混合 | callback 中使用 `=` 而非 `+=` | 修改为 `+=` 操作 |
| 设备间延迟过长 | 设备级别有不必要的 sleep | 移除 device 级延迟 |
| 同一说话人交叠 | 未启用 speaker_aware 逻辑 | 检查 speakers_map 构建 |
| 采样率不支持 | WASAPI 不支持任意采样率 | 使用 scipy.signal.resample_poly 重采样 |
| 找不到设备 | 通道格式匹配失败 | 检查 [Ch N] 后缀匹配逻辑 |

## 十一、总结

音频引擎是一个复杂的系统，核心设计要点：

1. **PyAudio 限制克服**：通过 `play_multi` 在同一流中混合多音频
2. **精确时序控制**：设备级同时开始，声道级通过 delay + 静音填充实现精确时序
3. **智能重叠策略**：Speaker 感知逻辑避免同一说话人不合理交叠
4. **灵活参数系统**：支持 overlap_rate / overlap_time 多种重叠控制
5. **完整的标注体系**：与 AudioAnnotation 表集成，支持多种标注格式

整个系统设计兼顾了技术限制的克服和业务逻辑的灵活性，为 E2E 测试提供了可靠的音频播放能力。

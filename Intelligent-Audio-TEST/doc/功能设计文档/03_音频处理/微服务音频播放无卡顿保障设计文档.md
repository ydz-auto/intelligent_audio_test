# 微服务音频播放链路无卡顿保障设计文档（INT-593）

> 版本：v1.0
> 日期：2026-10-17
> 关联卡：INT-593（【性能保障】微服务音频播放链路无卡顿保障）
> 结论：资源模型映射 + 卡顿根因修复清单 + 可度量「无卡顿」验收指标

---

## 1. 资源模型映射：旧「12 进程」→ 新微服务模型

### 1.1 负责人口径（2026-10-17 澄清，已回填 INT-593 规格）

V9.7.10 给音频播放分配 **12 个进程**，**每声道（PlaybackDevice）1 个进程**，才能正常播放、无卡顿。含义为**进程级实时隔离**——规避 Python GIL 对多声道并发实时回调的相互抢占。

### 1.2 映射结论（代码审计员核实 + 开发实现落实）

| 旧单体 V9.7.10 | 新微服务 V9.7.31 | 音频播放归属 |
|---|---|---|
| 1 个 Flask 主进程（Werkzeug HTTP 线程 + task executor 线程 + 设备驱动线程 + 音频播放线程，**同一进程同一 GIL**）+ 前端 Vite + postgres + 外部 eval/asr ≈ 11~12 进程 | `run_all.py` **12 个后端微服务** + 3 infra（redis/postgres/rustfs）+ 前端 Vite = 16 进程；docker-compose 12 后端统一镜像 | **audio_service 1 个进程**内：`audio_play_` 播放线程池（12 worker）+ gRPC server 线程池（20）+ PortAudio 回调线程，**仍共享同一 GIL** |

**映射本质**：旧单体「进程内多线程 GIL 竞争」→ 新「服务级拆分（方案二）部分落地」——HTTP/executor 已拆到 api_gateway/task_service 等独立进程，但 **audio_service 进程内 render 混音 + 物理播放 + 增益/RMS + 预重采样仍共享 GIL**，同类竞争模型未消除，只是收敛到一个服务内。

### 1.3 新模型下的进程级隔离等价方案（本卡落实路径）

按方案评审口径：**不预设子进程隔离方案**（涉及 Windows spawn、跨进程 PyAudio 初始化、停止传播与状态同步，改动面大），本卡先落地**单进程内 GIL 竞争缓解**的三条 P1 优化 + 配置化线程池容量恢复，使单进程可无卡顿承载 ≥12 声道并发；子进程隔离（multiprocessing 播放工作进程，`playback_process_workers=N`）作为后续方案评审待定项，不在本卡实施。

| 承担旧「每声道 1 进程」的职责 | 新模型承载点 |
|---|---|
| 每声道独立播放（进程隔离实时回调） | audio_service `audio_play_` 线程池，**每设备/每声道 1 个 play_multi worker**（容量=12，配置化） |
| 回调不被 GIL 抢占 | 预解码 + 预乘增益，回调内仅切片拷贝/混音（P1-1），大幅缩短单回调 GIL 占用 |
| 启动不因重活阻塞 | 增益补偿按文件签名缓存（P1-2）；E2E 预下载/预重采样已就位 |
| render 混音不抢占播放 | 流式混音切片后乘（P1-3），降低 CPU 密集段 GIL 持有 |

## 2. 卡顿根因与修复清单（对应审计结论三 1-6）

### 2.1 P1-1 回调实时性（`audio_driver.py`）

**根因**：`_create_multi_callback` 每回调对每个文件做字节解析（`to_int16_scale`）+ 整数组增益乘 + 死代码 `effective_gain_db = 20*np.log10(...)`（每文件每回调重复算、值未使用），回调 GIL 持有时间长，被抢占即卡顿。

**修复**：
1. 新增 `_predecode_audio_buffers()`：流打开前一次性预解码全部文件为 float32（int16 幅度约定）并预乘有效增益，总内存超限（默认 192MB，环境变量 `PLAYBACK_PREDECODE_MAX_BYTES` 可调）自动回退每回调解析，防大文件 OOM；
2. 回调内预解码路径仅做切片拷贝 + 混音（`positions[i]` 游标等价于 wave 句柄 position），行为与每回调解析路径逐字节一致（回归测试覆盖）；
3. 有效增益 `effective_gains` 在 `play_multi` 一次算好传入回调，删除死代码 `effective_gain_db`。

### 2.2 P1-2 播放启动阻塞（`audio_driver.py`）

**根因**：`play_multi` 对每个 config 无条件执行 `calculate_gain_compensation` 整文件分块 RMS 扫描，在 `audio_play_` 线程内阻塞开流；E2E 多轮/重复试听每次都重扫。

**修复**：`calculate_gain_compensation` 结果按文件签名 `(绝对路径, mtime_ns, size)` 缓存（上限 512 条，超限淘汰最早条目），文件被替换自动失效；同时修复增益补偿与成功打开文件的**索引对齐**（`_load_audio_files` 新增 `audio_file_paths` 返回，失败 config 不再造成错位）。

### 2.3 P1-3 流式混音 CPU（`render_audio_stream.py`）

**根因**：`RenderAudioStream.render` 每 100ms 窗口对每个 source 整源数组乘法 `src.samples * src.gain_linear`（60s 源 = 600 窗 × 整数组重乘），CPU 浪费显著，与物理播放抢 GIL。

**修复**：改为**切片后乘**——非噪声源只取窗口所需段 `samples[src_lo:src_hi] * gain_linear`；loop 噪声只对窗口内平铺段乘增益。输出与整段混音逐字节一致（回归测试覆盖）。`RenderAudioFile.mix` 本就每源一次乘法（非窗口循环），无需改。

### 2.4 P2-4 线程池容量/配置化（`audio_engine.py`）

**根因**：`_get_audio_pool()` 硬编码 `ThreadPoolExecutor(max_workers=10)`，未读取 `concurrency_config.json` 的 `execution_engine.audio_playback_max_workers: 12`（12→10 容量缩水，违背配置化纪律）。

**修复**：改读 `config_manager.get_value('execution_engine', 'audio_playback_max_workers', 12)`（V9.7.10 语义 = 每声道/每设备 1 个播放 worker），默认 12；新增 `audio_pool_queue_depth()` 打点（提交时记录排队深度，>0 = 满员排队 → 起播延迟风险信号）。

### 2.5 P2-5 进程内 GIL 隔离（短期依赖 P1-1/P1-3）

gRPC worker=20（INT-1973 由 5 扩容）+ 播放池 12 线程 + PortAudio 回调线程同进程同 GIL；Docker `cpus: 0.5` 放大竞争。本卡**不做子进程隔离**（留待方案评审裁定），短期靠 P1-1（回调轻量化）/P1-3（混音切片后乘）降 CPU 占用与回调 GIL 持有。

并发扩容后的资源口径（INT-1973，2026-10-26）：`shared/config/concurrency_config.json` 的 `grpc.audio_service_workers=20` 为唯一事实源，`audio_service/interfaces/grpc/server.py` 以 `AUDIO_GRPC_WORKERS_DEFAULT=20` 兜底；同一处 `AUDIO_DB_POOL_SIZE=20` 传给 `init_db(pool_size=20)`，DB 连接上限 = `pool_size 20` + `max_overflow 5`（`shared/models/database.py` 固定）= **25 条**，仍远低于 docker PG `max_connections=100`；`audio_play_` 播放线程池 **12 不变**（INT-593 口径）。扩容消除的是线程池与连接池的**排队点**，20 个 gRPC 线程与 12 个播放线程**仍共享同一 GIL**，本节的 GIL 竞争模型与子进程隔离结论均不因此改变。

### 2.6 P2-6 量化采集（`audio_driver.py` + `_engine_playback_mixin.py`）

| 指标 | 采集点 | 打点 |
|---|---|---|
| 起播延迟（含线程池排队） | `play_multi` 流打开时刻 − `started_monotonic`（任务提交时刻） | `[play_metrics] start_latency_ms=...` |
| underrun/overflow 计数 | PortAudio 回调 `status & paOutputOverflow` | `[play_metrics] overflows=N` |
| 回调最大耗时（GIL 抢占/调度抖动代理） | 回调进出 `time.monotonic()` 差值取 max | `[play_metrics] callback_max_ms=...` |
| 线程池队列深度 | 播放任务提交时 `audio_pool_queue_depth()` | `[play_audio]/[play_overlap]/[bg_noise] audio_pool_queue_depth=N` |

## 3. 「无卡顿」验收标准与实测口径

| # | 验收项 | 采集方式 | 阈值 |
|---|---|---|---|
| 1 | 物理设备 ≥12 声道（PlaybackDevice）同时播放 ≥60s | 真机声卡实测（多声道声卡/多设备）；自动化环境走 `pyaudio_shim` 影子夹具双轨 + 真机人工复核 | 0 爆音/0 中断/underrun 计数 0 |
| 2 | 试听 preview 起播延迟 | `start_latency_ms` 打点 | ≤1s（含加载/增益/重采样） |
| 3 | 前端 Realtime 流式混音 100ms 恒定窗按节奏送达 | 前端 SSE/WS 消费节奏与 chunk 恒定窗校验 | 连续 ≥60s 无缓冲空转 |
| 4 | 并发隔离：播放期间并发 render 流式 + 试听 | `tests/unit/test_int593_...::TestConcurrentIsolation` 线程级并发回归 | 播放不中断、render 输出逐字节正确、start_latency/underrun 不越界 |
| 5 | 线程池队列深度 | `audio_pool_queue_depth()` 打点 | 提交时 ≤12（满员即排队） |
| 6 | 回调最大耗时 | `callback_max_ms` 打点 | 小于 PortAudio 帧缓冲时长（默认 ~20-50ms） |

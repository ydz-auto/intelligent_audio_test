# 测试用例音频预览功能逻辑文档

## 1. 功能概述

测试用例音频预览功能允许用户在执行测试前，检查测试用例配置的音频资源是否能正常播放，验证音频与设备的匹配性，确保测试环境准备就绪。

### 2.3 详细流程

1. **音频验证**
   - 根据 `audio_id` 查询音频文件
   - 如果音频不存在或已删除，返回 404 错误

2. **获取请求参数**
   - 从请求体中获取 `playback_device_id` 和 `spl`
   - `playback_device_id`：可选，指定播放设备
   - `spl`：可选，目标声压级

3. **播放模式选择**
   - 如果未提供 `playback_device_id`：
     - 返回音频流，让前端浏览器播放
   - 否则：
     - 控制后端硬件播放

4. **硬件播放逻辑**
   - 导入 `audio_service` 管理音频播放
   - 初始化设备信息：名称、唯一ID、通道索引、增益
   - 尝试从数据库中查找设备
   - 如果数据库中找不到设备，将 `playback_device_id` 作为唯一标识
   - 解析设备通道索引
   - 根据SPL计算增益值
   - 获取设备物理索引
   - 触发播放指令，使用任务ID：`preview_{audio_id}`

5. **返回结果**
   - 成功时返回：设备名称、音频名称和增益值
   - 失败时返回错误信息

### 2.5 原测试用例预览逻辑（保留用于参考）

**注意：该方法已更新，现在与实际测试中的音频播放逻辑保持一致**

原 `testcase_controller.py` 中的 `preview` 方法已更新，现在与实际测试中的音频播放逻辑完全一致：
- 过滤出 e2e 类型的音频
- 分类音频：干声和噪声
- 优先使用配置中的噪声音频
- 否则使用传统的背景噪声配置
- 获取所有噪声设备（device_type='noise'）
- 在所有噪声设备上播放背景音
- 顺序播放所有干声音频
- 与 `execution_engine.py` 中的 `_execute_e2e_case` 方法保持一致

**并行播放逻辑：**
- **背景噪声处理：**
  - 优先使用配置中的噪声音频
  - 否则使用传统的背景噪声配置
  - 获取所有噪声设备（device_type='noise'）
  - 在每个噪声设备上**异步循环播放**背景音
- **干声音频处理：**
  - 遍历所有干声音频配置
  - 为每个干声音频获取对应的播放设备
  - 计算增益值
  - 在对应设备上**同步播放**干声音频（使用.join()等待完成）
  - 干声播放期间，噪声持续循环播放，实现**并行播放**
- **结束处理：**
  - 所有干声播放完成后，停止背景噪声

**注意：** 该方法现在与实际测试逻辑保持一致，噪声和干声是并行播放的

## 3. 前端逻辑

### 3.1 API 调用封装

API测试音频现在使用 `audiosApi` 来实现预览，而不是 `testcasesApi`。`frontend/src/utils/api.js` 中的 `audiosApi` 封装了音频相关的API调用：

```javascript
export const audiosApi = {
  // ...
  async preview(id, previewData = {}) {
    return request('POST', `/audios/${id}/preview`, previewData);
  },

  async stopPreview(id) {
    return request('POST', `/audios/${id}/stop-preview`);
  },
  // ...
};
```

### 3.2 前端预览流程

#### 3.2.1 触发预览

在 `TestCaseListContainer.vue` 中，用户点击"预览音频"按钮时触发：

```javascript
const handleAction = async (actionEvent, group) => {
  const testCase = actionEvent.testCase;
  switch (actionEvent.action.id) {
    case 'preview':
      // 检查音频配置
      const hasAudioConfig = testCase.config?.audios && testCase.config.audios.length > 0;
      const hasOldAudioConfig = testCase.config?.apiAudio || testCase.config?.dryAudio || (testCase.config?.dryAudios && testCase.config.dryAudios[0]?.file);
      
      if (hasAudioConfig || hasOldAudioConfig) {
        try {
          // 检查测试用例配置
          const { hasAPIConfig, hasE2eConfig } = checkTestCaseConfig(testCase);
          // 保存当前测试用例信息
          currentTestCase.value = testCase;
          currentTestCaseId.value = testCase.id;
          
          // 更新配置状态
          currentHasAPIConfig.value = hasAPIConfig;
          currentHasE2eConfig.value = hasE2eConfig;
          
          // 根据配置类型显示不同的选择界面
          if (hasAPIConfig && hasE2eConfig) {
            showAudioTypeModal.value = true; // 显示音频类型选择
          } else if (hasAPIConfig) {
            selectedAudioType.value = 'api';
            showPlaybackDeviceModal.value = true; // 显示设备选择
          } else if (hasE2eConfig) {
            selectedAudioType.value = 'e2e';
            showAudioPlayer.value = true; // 直接显示播放器
          }
        } catch (error) {
          console.error('音频试听失败:', error);
          alert('音频试听失败: ' + error.message);
        }
      } else {
        alert('该测试用例没有关联音频文件');
      }
      break;
    // ...
  }
};
```

## 4. 前后端交互流程

1. **用户操作**：在测试用例列表中点击"预览音频"按钮
2. **前端验证**：检查测试用例是否配置了音频
3. **配置检查**：确定测试用例包含的测试类型（API/E2E）
4. **类型选择**：如果同时包含两种类型，显示选择界面
5. **设备选择**：对于API测试，显示设备选择界面
6. **获取音频ID**：从测试用例配置中提取音频ID
7. **API调用**：调用 `audiosApi.preview()` 启动预览，传递音频ID和设备信息
8. **后端处理**：执行音频预览逻辑（`audio_controller.py` 中的 `preview` 方法），启动音频播放
9. **结果返回**：后端返回设备名称、音频名称和增益值
10. **前端反馈**：显示音频播放器，允许用户控制播放
11. **停止预览**：用户点击停止按钮，调用 `audiosApi.stopPreview()`

## 5. 技术要点

1. **音频预览架构变更**：
   - API测试音频现在使用 `audio_controller.py` 中的 `preview` 方法
   - 支持前端浏览器播放和后端硬件播放两种模式
   - 根据是否提供 `playback_device_id` 自动选择播放模式

2. **设备管理**：
   - 支持从数据库中查找设备和使用扫描设备
   - 自动解析设备通道索引
   - 支持根据设备唯一ID定位物理设备

3. **SPL 增益计算**：
   - 根据设备的SPL映射关系
   - 将目标SPL值转换为音频增益
   - 确保音频播放的声压级符合要求

4. **任务ID管理**：
   - 为每个预览生成唯一任务ID：`preview_{audio_id}`
   - 支持停止特定任务的音频播放
   - 避免多个预览任务冲突

5. **前端组件化设计**：
   - 模块化的音频选择、预览和播放组件
   - 支持不同类型测试用例的预览
   - 响应式设计，适配不同屏幕尺寸

6. **前后端交互优化**：
   - 使用 `audiosApi` 替代 `testcasesApi` 进行音频预览
   - 简化API调用参数，只需要音频ID和设备信息
   - 更详细的返回结果，包含设备名称、音频名称和增益值

## 6. 错误处理

1. **后端错误**：
   - 音频不存在或已删除
   - 无法定位物理设备
   - 硬件播放失败
   - 数据库查询失败
   - 停止预览失败

2. **前端错误**：
   - 测试用例未配置音频
   - API调用失败

3. **用户反馈**：

   - 操作成功确认

## 8. 总结

测试用例音频预览功能是一个重要的质量保证工具，它允许用户在执行测试前验证音频配置和设备状态，确保测试环境的正确性。近期，该功能进行了架构调整，API测试音频现在使用 `audio_controller.py` 中的 `preview` 方法。

### 架构变更要点：
- API测试音频从使用 `testcasesApi` 切换到使用 `audiosApi`
- 后端逻辑由 `testcase_controller.py` 迁移到 `audio_controller.py`
- 支持前端浏览器播放和后端硬件播放两种模式
- 简化了API调用参数，只需要音频ID和设备信息

### 用户价值：
通过这个功能，用户可以：
- 验证测试用例的音频配置是否正确
- 检查音频文件是否能正常播放
- 确认设备连接和配置状态
- 调整音频参数（如SPL）
- 确保测试环境准备就绪

这个功能的实现体现了良好的模块化设计和前后端分离架构，为后续的测试执行提供了可靠的基础保障。架构调整后，音频预览功能更加灵活，支持更多的播放场景，同时简化了API调用流程。

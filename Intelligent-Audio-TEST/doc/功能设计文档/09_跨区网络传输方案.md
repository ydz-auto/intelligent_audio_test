# 09 跨区网络传输方案 —— A/B/C 三区链路设计

> **版本**：V9.7.31 v1.0（2026-09-14）
> **架构基线**：DDD + CQRS + 微服务 + 多站点隔离

---

## 一、背景与问题

### 1.1 网络环境

测试平台需跨越三个网络隔离区（A、B、C）部署，各区间以软件网关隔离，网关通信需先申请白名单权限。

### 1.2 约束条件

| # | 约束 | 说明 |
|---|------|------|
| 1 | 三区网络隔离 | A↔B 双向过 GW-1 · B→C 单向过 GW-2 · A↔C 经 B 中继过双 GW（物理不直连） |
| 2 | 用例执行跨区 | A/B/C 均具备执行能力，能力有差异，用例在其可执行区域执行 |
| 3 | 执行能力分布 | A/B：完整微服务栈 + 本地评估 · C：仅 THIRD_PARTY_C 评估（不持久化传入数据） |
| 4 | 数据隔离 | A/B 用例执行数据不允许持久化到 C；C 不反向回连 A/B |
| 5 | 百 MB 级传输 | 单用例传输量级为百 MB（音频素材 + 采集结果），需支持分片和校验 |
| 6 | 报告共享 | C 的评估报告需在 A/B 可见，但 C 不通 A/B，需另寻同步路径 |

### 1.3 需求总览

- **主线方案（高优先级）**：A/B 完整微服务栈可执行全部用例（含本地评估），B 为评估中枢，C 仅执行 THIRD_PARTY_C 评估并作为第三方 LLM API 的被调用方。
- **备选方案（低优先级）**：C 部署完整微服务栈 + 开通 C→A/B 单向链路，用于更复杂的跨区协同场景。

---

## 二、设计目标

1. **分区自治**：每个区独立部署微服务栈，本地执行 + 本地存储，互不依赖。
2. **单向隔离**：A/B 数据不持久化到 C，C 不反向回连 A/B；仅通过第三方 API 请求-响应交换评估结果。
3. **中继路由**：B 区承担中继枢纽角色，承载 A↔B 双向通信 + B→C 单向调用。
4. **借用式评估**：C 所需 A/B 数据仅在 API 调用的请求载荷中传递，评估完即弃，不落 C 侧持久化存储。
5. **配置化**：评估能力归属、令牌、白名单、传输 TTL 全配置化，禁硬编码。
6. **双线可演进**：主线方案（高优）优先落地，备选方案（低优）预留演进接口。

## 三、总体拓扑

```
┌──────────────────────────┐  软件网关   ┌──────────────────────────┐  软件网关   ┌──────────────────────────┐
│        A 区 (主站点)      │◄─────────►│        B 区 (评估中枢)    │───────────►│ C 区(第三方 LLM API)     │
│                          │  GW-1      │                          │  GW-2      │                          │
│  完整微服务 11 个         │  A↔B 双向  │  完整微服务 11 个         │  B→C 单向   │  仅执行 THIRD_PARTY_C 评估│
│  PostgreSQL + Redis       │  (需申请权限)│  PostgreSQL + Redis     │  (需申请权限)│  无持久化存储            │
│  MinIO (本地存储)         │           │  MinIO (本地存储+中转缓存) │            │  不反向回连 A/B          │

```

### 3.2 连通性矩阵

| 段 | 方向 | 协议 | 说明 |
|---|------|------|------|
| A ↔ B | 双向 | HTTPS | 过 GW-1。transfer_agent 端口需网关白名单。A/B 同安全域，数据/报告自由同步 |
| B → C | 单向请求 | HTTPS | 过 GW-2。B 的评估服务通过 transfer_agent 调 C 第三方 API；请求仅输出，不依赖 C 回调 |
| C → A/B | 不通 | — | C 不做任何主动推送或回调，所有结果仅随 API 同步响应返回 B |
| A → C | 经 B 中继 | HTTPS ×2 | 逻辑链路 A→GW-1→B→GW-2→C，物理不直连；B 校验 + 转发 |

> **实现对齐说明（2026-10-09，F2.1/INT-49 交付）**：B→C 评估数据面已按本节原设计实现——evaluation_service 打包 EVAL_REQUEST 经 T-B 分片上传暂存（真实 dst='C' 流水），T-B 出站投递腿（`POST /internal/transfer/outbound/{transfer_id}/dispatch`）读取 transit 暂存包，按第三方契约（§4.3 三形态：multipart / feature_extract / presigned PUT）经 GW-2 调 C，同步响应回传 evaluation_service；交付完成流水转 DELIVERED，meta.delivery 记录真实投递结果（dst_status/attempts），审计流水与真实数据路径一致。evaluation_service 直连 C 的适配器已退役（F2.1 起 C 调用统一经 T-B 出站）。

## 四、主线方案（高优先级）

### 4.1 评估中枢模型（B 区）

B 区是核心评估中枢：

- **本地评估维度** → 走现有 gRPC `EvaluationService.EvaluateCase`（evaluation_service 50091）
- **C 专属评估维度** → 经 `transfer_agent` 调 C 第三方评估 API

#### 4.1.1 评估能力注册表

新增配置化注册表，决定每个维度的评估归属：

```json
// evaluation_capability_config.json
{
  "dimension_capabilities": [
    { "dimension": "wer", "target": "LOCAL" },
    { "dimension": "der", "target": "LOCAL" },
    { "dimension": "llm_judge", "target": "THIRD_PARTY_C" },
    { "dimension": "mos", "target": "THIRD_PARTY_C" }
  ]
}
```

| target 值 | 路由目标 |
|-----------|---------|
| `LOCAL` | 本区 evaluation_service gRPC（现有 `EvaluateCase` 不变） |
| `THIRD_PARTY_C` | 经 transfer_agent 调 C 第三方 API |

#### 4.1.2 B 区评估服务新增适配层

在 evaluation_service 新增 ACL：

```
evaluation_service/infrastructure/acl/
  ├── evaluation_acl_repository.py      # 已有：gRPC 调 task_service
  ├── evaluation_config_acl_repository.py  # 已有：维度配置查询
  └── third_party_eval_acl.py           # 新增：调 C 第三方 API
```

- 现有 `evaluate_case` 方法在 `target=LOCAL` 时保持不变。
- `target=THIRD_PARTY_C` 时，将 `algorithm_result` + 所需文件打包为 `EVAL_REQUEST`，经 transfer_agent 发出。

### 4.2 组件：transfer_agent（传输代理）

新增微服务，A、B 各部署一份。

```
transfer_agent/
  interfaces/api/       # 接收端：/internal/transfer/receive（收包）
  application/services/ # 传输编排：打包、分片、重试、幂等
  domain/
    models/             # TransferPackage 值对象、TransferStatus 枚举
    services/           # 签名验证、文件校验
  infrastructure/
    acl/                # 出站适配：HTTP 客户端（调远端 transfer_agent 或 C API）
    storage/            # 复用 shared.infrastructure.storage（读写本区 MinIO）
    persistence/        # 传输流水表（transfer_id、状态、审计）
```

#### 4.2.1 传输包协议

```json
{
  "transfer_id": "uuid（全局唯一，幂等去重）",
  "pkg_type": "EVAL_REQUEST | EVAL_RESULT | REPORT_SYNC | DATA_SYNC",
  "src_zone": "A | B",
  "dst_zone": "C",
  "category": "case-result | audios | reports",
  "key": "task_1/case_2/dev_3/result.wav",
  "file_hash": "sha256:...",
  "file_size": 104857600,
  "meta": {
    "task_id": "...",
    "eval_params": { "algorithm_type": "llm_judge", ... }
  },
  "ttl": 3600,
  "ephemeral": true,
  "timestamp": "2026-09-14T10:00:00Z",
  "signature": "hmac_sha256(secret, canonical_string)"
}
```

**包类型说明**：

| pkg_type | 方向 | 说明 |
|----------|------|------|
| EVAL_REQUEST | A/B→B→C | 评估输入包，含算法结果 JSON + 所需文件（仅在 C 侧临时处理，不落持久盘） |
| EVAL_RESULT | C→B（同步响应） | C 评估结果 JSON + 附产物，通过 API 响应返回 |
| REPORT_SYNC | B→A 或 A↔B | 报告同步 |
| DATA_SYNC | A↔B | A/B 之间任务数据同步 |

#### 4.2.2 A 需 C 评估的完整流程

```
① A 区用例执行完成，评估维度命中 THIRD_PARTY_C
     │
② 打包 EVAL_REQUEST：
   └ algorithm_result JSON + 引用音频/结果文件
   └ 落 A 的 MinIO → transfer_agent 分片读取
     │
③ T-A → GW-1 → T-B
   └ 分片并发上传（4MB/片），支持断点续传
   └ 签名 + token → 网关白名单鉴权
     │
④ B 中转：校验签名 + 幂等去重
   └ 暂存 transit 桶（TTL 清理）
     │
⑤ T-B → GW-2 → C 第三方 API
   └ 调用方式取决于第三方契约：multipart / chunked / presigned PUT
     │
⑥ C 第三方 API 处理
   └ 一次性请求-响应，不反向回调
   └ C 不持久化 A/B 数据（或由第三方契约保证）
     │
⑦ EVAL_RESULT 同步返回 B
   └ B 评估服务解析、落 B 区 DB/MinIO
   └ 继续本地后续评估/出报告
     │
⑧ EVAL_RESULT 回同步到 A（若 A 需要）
   └ T-B → GW-1 → T-A → A 区 DB/MinIO
```

> **实现对齐说明（2026-10-09，F2.1/INT-49 交付）**：步骤⑤已按原设计实现——T-B 出站投递腿读取 transit 暂存包（步骤④），按第三方契约三形态投递 C（multipart 直传 / feature_extract 特征提取后小参投递 / presigned PUT 预签名申请后上传并携带对象引用评估），网络错误与 5xx 指数退避重试、4xx 不重试；C 同步响应即 EVAL_RESULT（步骤⑦）原样回传 evaluation_service 解析校验。过渡期"评估数据面暂由 evaluation_service 直连 C"的形态已退役。

### 4.3 B→C 调用适配

C 第三方 API 的接入方式取决于其契约。三种常见形态：

| 第三方 API 能力 | B 侧适配方式 | 说明 |
|---|---|---|
| 支持 multipart/form-data + 同步响应 | 直接 `POST /evaluate`（流式上传） | 最简，百 MB 文件可流式发送 |
| 仅接受小参数字段 | B 预处理大文件→提取特征向量→只传特征 | 需先确认 C 需要什么输入 |
| 预签名 URL 拉取 | B 生成预签名 URL（B→C 可上传）→C 主动拉取 | 需 C 侧主动拉取 |

> B→C 的适配器统一抽象为 `ThirdPartyEvalPort`（端口接口），具体实现类绑定到 `target=THIRD_PARTY_C`，支持运行时配置切换。

### 4.4 权限与安全

| 层 | 机制 | 配置位置 |
|---|------|---------|
| 网络层 | 网关 IP + 端口白名单 | 运维网关配置 |
| 访问层 | 每对站点预共享 Token（`TOKEN_A_B` / `TOKEN_B_C`） | `shared/config/secrets_config.json` |
| 签名层 | TransferPackage HMAC-SHA256 验签 + file_hash 完整性校验 | `third_party_eval_acl` |
| 内容层 | C 入口只收 `EVAL_REQUEST` 包类型，其它拒绝 | transfer_agent 收包过滤 |
| 审计层 | B 记录每包流水（transfer_id、大小、哈希、时间） | transfer_agent 持久表 |

### 4.5 传输可靠性

| 特性 | 实现 |
|------|------|
| 幂等 | `transfer_id` 唯一索引，重复接收直接返回已存在 |
| 断点续传 | 分片状态记录在 B 端已收片表，A 可从失败片重传 |
| 重试 | 指数退避（3 次）+ 超时熔断 |
| TTL 清理 | 中转桶定时扫描，超时文件回收 |
| 限速 | B 端令牌桶限速，防大文件压垮网关 |

## 五、备选方案（低优先级）

### 5.1 适用场景

当后续需求演进到以下情况时启用备选方案：

- C 区需要独立执行用例并自产结果/报告
- C 区需要将自身数据（报告、结果）同步到 A/B
- C→A/B 的单向通道已开通（软网关白名单放行）

### 5.2 C 完整微服务栈部署

C 区部署与 A/B 同样的完整微服务栈（11 个服务 + PostgreSQL + Redis + MinIO），C 的 MinIO 仅保存 C 自身产生的数据（C 自执行用例的结果、C 自产的报告），不允许写入 A/B 传入的原始数据。

### 5.3 开通 C→A/B 单向链路

```
┌──────────────────────────┐  软件网关   ┌──────────────────────────┐  软件网关   ┌──────────────────────────┐
│        A 区              │◄─────────►│        B 区 (中继枢纽)   │◄─────────►│        C 区 (完整站点)    │
│                          │  A↔B 双向  │                          │  C→B 单向  │                          │
│  完整微服务栈             │  已开通     │  完整微服务栈             │  新开通     │  完整微服务栈             │
│  transfer_agent (T-A)    │           │  transfer_agent (T-B)    │            │  transfer_agent (T-C)    │
└──────────────────────────┘           └──────────────────────────┘            └──────────────────────────┘
```

| 段 | 方向 | 说明 |
|---|------|------|
| C → B | 单向新增 | C 可向 B 推送报告、评估结果；B 充当存储转发，可继续向 A 分发 |
| B → C | 保留原有 | 主线方案保留，B 仍可调 C 第三方评估 API |

#### 5.3.1 新增包类型

| pkg_type | 方向 | 说明 |
|----------|------|------|
| C_REPORT | C→B→A | C 自产报告推送 |
| C_RESULT | C→B→A | C 自产评估结果推送 |

> C 侧报告/结果表中增加 `source_zone` 标记，A/B 接收后落本地只读副本，前端根据 `source_zone` 区分展示。

### 5.4 数据隔离规则

备选方案下仍保留以下隔离：

- C 的 MinIO 不保留 A/B 的执行原始数据
- A/B 用 MinIO + DB 账号确认已收的 C 只读副本不可从 C 侧跨区查询
- C→B 推送的 `C_REPORT`/`C_RESULT` 包在 B 侧重新签名后转发，C 不持有 A/B 密钥

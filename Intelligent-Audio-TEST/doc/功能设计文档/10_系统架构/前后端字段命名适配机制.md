# 前后端字段命名规范适配机制

## 1. 概述

本文档是系统字段命名机制的**权威描述**，与代码库实际实现逐项对应。后端 Python 层使用 snake_case，前端 TypeScript 层使用 camelCase，**后端 API 响应按字段原样输出 snake_case**（`serialize_by_alias=False`），由前端 Infrastructure 层（`utils/keyTransform.ts` + `infrastructure/adapters/` 各 `*Adapter`）转换为 camelCase Domain 后供上层消费——snake_case 只允许出现在 Infrastructure 层。

> ⚠️ **实现演进裁定（INT-381 前置审核回写 2026-10-16）**：本文档 v1.0 描述「APIModel `serialize_by_alias=True` 响应直接输出 camelCase」与 V9.7.31 实测不符——`api_gateway/schemas/base.py:15` 实测为 **`serialize_by_alias=False`（snake_case 输出）**；且原引路径 `backend/schemas/base.py`、`backend/utils/web/naming_request.py`、`frontend/src/utils/fieldNaming.ts` 在 V9.7.31 均不存在（实际为 `api_gateway/schemas/base.py`、`shared/utils/naming_request.py` + `shared/utils/naming_middleware.py`、`frontend/src/utils/keyTransform.ts`）。本节起按真实契约重述；请求入口的双命名兼容（NamingAliasMiddleware query 双别名 + 请求体 snake_case 归一）仍有效，属后端宽容输入，**不是前端免转换的依据**——前端展示层一律消费 adapter 转换后的 camelCase Domain。

| 关卡 | 位置 | 方向 | 职责 |
|------|------|------|------|
| ① APIModel | `api_gateway/schemas/base.py` | 响应出口 | `serialize_by_alias=False`，所有 API 响应按字段原样输出 **snake_case**（前端 adapter 负责 camelCase 化） |
| ② NamingRequest | `shared/utils/naming_request.py` | 请求入口（JSON body） | 请求体键名递归归一化为 snake_case（FastAPI 适配版，见 §3.2） |
| ③ NamingAliasMiddleware | `shared/utils/naming_middleware.py` | 请求入口（query string） | 查询参数双别名补全（snake_case 与 camelCase 同时可用） |
| ④ AliasChoices | `api_gateway/schemas/` 部分模型 | 请求入口（字段级） | 显式声明多别名，兼容历史/异构报文 |

前端侧不引入 Axios 拦截器或第三方转换库，由 `frontend/src/utils/api.ts`（请求封装）与 `frontend/src/utils/keyTransform.ts`（字段工具族：`snakeToCamel`/`camelizeKeys`/`readCamel` 等）承担 Infrastructure 层键名转换职责；业务 DTO↔Domain 序列化收敛在 `frontend/src/infrastructure/adapters/` 各 `*Adapter` 中（snake_case 只出现在该层，见 §2.2）。

```mermaid
flowchart LR
    subgraph 前端
        A[views/+components/<br/>仅 camelCase Domain] --> B[composables/+store/<br/>Application 编排]
        B --> C[utils/api.ts + keyTransform.ts + adapters/<br/>Infrastructure]
    end
    C -->|body: camelCase→snake 由后端宽容归一<br/>query: camelToSnakeObject| D
    subgraph 后端
        D[NamingAliasMiddleware<br/>query 双别名] --> E[NamingRequest<br/>body 归一化 snake]
        E --> F[Controller/Service<br/>snake_case]
        F --> G[APIModel<br/>serialize_by_alias=False]
    end
    G -->|响应: snake_case| C
    C -->|adapter 转换 → camelCase Domain| A
```

## 2. 命名规范定义

### 2.1 后端命名规范

后端 Python 代码统一采用 snake_case（小写下划线分隔）。所有对外响应模型必须继承 `APIModel` 基类（`api_gateway/schemas/base.py`），字段一律以 snake_case 声明，**序列化输出保持 snake_case**（不通过 alias 转出）：

```python
# api_gateway/schemas/base.py（完整原文）
from pydantic import BaseModel, ConfigDict
from pydantic.alias_generators import to_camel


class APIModel(BaseModel):
    """所有 API Schema 的基类。

    字段以 snake_case 定义，序列化输出也为 snake_case（不通过 alias 转换）。
    请求体仍可同时接受 snake_case 和 camelCase（alias_generator + populate_by_name）。
    """
    model_config = ConfigDict(
        alias_generator=to_camel,
        populate_by_name=True,
        populate_by_alias=True,
        serialize_by_alias=False,     # 序列化输出原始字段名（snake_case）
        extra="ignore",
    )
```

> `serialize_by_alias=False` 是 **snake_case 输出契约的关键**：后端返回给前端的 JSON 恒为 snake_case，前端 Infrastructure 层（`utils/keyTransform.ts` + `infrastructure/adapters/`）负责转换为 camelCase Domain（个别刻意保留的特例见 4.3）。

### 2.2 前端命名规范

前端 TypeScript 代码统一采用 camelCase。按前端 DDD 分层约束：

- **Presentation**（`views/` + `components/`）：只见 camelCase Domain 与 composables（Ports）；
- **Application**（`composables/` + `store/`）：编排用例，缓存 ReadModel，只见 Domain；
- **Domain**（`domain/model/` + `enums.ts`）：零依赖；
- **Infrastructure**（`utils/api.ts`、`utils/keyTransform.ts`、`infrastructure/adapters/*`）：**唯一知道 snake_case 细节**的层。`*Adapter` 负责业务 DTO(snake_case)→Domain(camelCase) 序列化；通用键名工具由 `utils/keyTransform.ts`（`snakeToCamel`/`camelizeKeys`/`readCamel` 等）承担。

**前端类型示例**（`frontend/src/shared/types/`，camelCase Domain，与 adapter 转换后的 Domain 对象一一对应）：

```typescript
interface TaskListItem {
    id: number;
    name: string;
    status: string;
    createdAt?: string;
    totalCases?: number;
    completedCases?: number;
    maxAudioDuration?: number;
    needsPromptAudio?: boolean;
}
```

## 3. 适配机制原理

### 3.1 响应出口：APIModel 输出 snake_case，前端 adapter 转 camelCase

凡继承 `APIModel` 的模型，响应序列化一律输出**字段原样 snake_case**（`serialize_by_alias=False`），前端 `infrastructure/adapters/` 各 `*Adapter` 用 `keyTransform` 的 `snakeToCamel`/`camelizeKeys` 递归转换为 camelCase Domain。下表即 adapter 层的**转换映射基准**：

| 后端字段（snake_case 输出） | 前端字段（camelCase Domain） |
|------------------------|----------------------|
| `id` | `id` |
| `task_id` | `taskId` |
| `created_at` | `createdAt` |
| `total_cases` | `totalCases` |
| `completed_cases` | `completedCases` |
| `error_message` | `errorMessage` |
| `max_audio_duration` | `maxAudioDuration` |
| `needs_prompt_audio` | `needsPromptAudio` |
| `app_version` | `appVersion` |
| `serial_number` | `serialNumber` |
| `last_online_at` | `lastOnlineAt` |
| `test_frequency` | `testFrequency` |
| `calibration_status` | `calibrationStatus` |
| `spl_mapping_id` | `splMappingId` |

显式声明 `alias` 的字段以显式值为准（优先级高于 `alias_generator`），例如 `api_gateway/schemas/spl.py` 中 `spl_mapping_id: int = Field(..., alias='splMappingId', validation_alias='splMappingId')`——注意在 `serialize_by_alias=False` 下该 `alias` **仅作用于请求入参**（校验时接受 camelCase），**不影响响应输出**（仍为 snake_case）。

### 3.2 请求入口（JSON body）：snake_case 归一化（FastAPI 兼容版）

原 Flask `NamingRequest`（继承 `Flask.Request`）在 FastAPI 下不再适用，改造为纯函数工具 `shared/utils/naming_request.py`：`normalize_keys_to_snake(data)` 对请求体 dict 键名**递归**执行 camelCase → snake_case 归一化（`naming_get_json` 为其对 JSON 数据的封装）：

- 已是 snake_case 的键原样保留；
- kebab-case（含连字符且无大写）原样保留；
- 其余驼峰键转为 snake_case（含连续大写处理，如 `WEREn` → `wer_en`）。

因此**控制器与 Service 内部拿到的 JSON 键恒为 snake_case**；FastAPI 侧由 Pydantic `APIModel` 的 `populate_by_name`/`populate_by_alias` 同时接受 snake_case 与 camelCase 请求体，前端请求体直接发 camelCase 亦可被解析。

### 3.3 请求入口（query string）：NamingAliasMiddleware 双别名补全

`api_gateway/app.py:94-97` 中 `app.add_middleware(NamingAliasMiddleware)`（FastAPI/Starlette 中间件，`shared/utils/naming_middleware.py`）。对每个带查询串的请求，`add_case_aliases_to_query_string` 会**同时补全 snake_case 与 camelCase 两种键名**（值相同），缺失的一侧自动追加：

```python
# shared/utils/naming_middleware.py（核心逻辑摘要）
for k, v in pairs:
    snake_key = k if _SNAKE_LIKE_KEY_RE.fullmatch(k) else to_snake(k)
    if snake_key not in existing: out.append((snake_key, v))
    camel_key = to_camel(k)
    if camel_key not in existing: out.append((camel_key, v))
```

效果：无论前端以 `?pageSize=20` 还是 `?page_size=20` 发送，后端两种键名都能取到值。

### 3.4 字段级多别名：AliasChoices 显式特例

对历史报文或异构来源需要同时兼容多种键名的字段，在 `validation_alias` 中显式声明 `AliasChoices`（**优先级高于**中间件与生成器，仅 6 个 schema 文件使用）：`testcase.py`、`report.py`、`algorithm.py`、`evaluation.py`、`group.py`、`device.py`。

真实用例（`api_gateway/schemas/testcase.py`）：

```python
audio_id: Optional[Union[int, str]] = Field(
    None, alias='audio_id',
    validation_alias=AliasChoices('audio_id', 'audioId'))
playback_device_id: Optional[Union[int, str]] = Field(
    None, alias='playback_device_id',
    validation_alias=AliasChoices('playback_device_id', 'playbackDeviceId'))
```

### 3.5 双向支持

`populate_by_name=True` + `populate_by_alias=True` 使校验阶段同时接受字段名与别名；配合 3.2/3.3 的入口归一化，**请求体与查询参数的两种命名风格后端均可正确解析**，内部代码一律使用 snake_case 属性访问。

## 5. 前端适配层实现（Infrastructure）

> 前端实际技术栈为 **Vue 3 + Electron + 原生 fetch**（无 Axios、无 lodash 转换库）。字段转换集中在 `frontend/src/utils/keyTransform.ts`（`snakeToCamel`/`camelizeKeys`/`readCamel`/`snakifyKeys`）。

### 5.1 请求封装

`request<T>()` 是 HTTP 调用的唯一入口，双通道发出：Electron 环境经 `window.electronAPI.apiRequest`（IPC，见 `frontend/src/preload/apiadapter.ts` 的 `APIAdapter`）；浏览器环境走原生 `fetch`。当前 `frontend/src/utils/` 下无独立 `api.ts`——请求封装在 preload 侧，键名转换统一由 `utils/keyTransform.ts` 承担。

字段规则（**仅 GET 查询参数做 camelCase → snake_case 转换**）：

```typescript
// 示意：GET params camelCase → snake_case（snakifyKeys 位于 utils/keyTransform.ts）
import { snakifyKeys } from './keyTransform';

const snakeParams = snakifyKeys(requestOptions.params);
const filteredParams = Object.fromEntries(
  Object.entries(snakeParams).filter(([_, v]) => v !== undefined && v !== null)
);
const query = new URLSearchParams(filteredParams).toString();
```

请求体（JSON/FormData）**不做键名转换**，camelCase 原样发送，由后端 NamingRequest / NamingAliasMiddleware 兼容（见 3.2/3.3）。

### 5.2 字段工具族：utils/keyTransform.ts

| 工具函数 | 职责 |
|---------|------|
| `snakeToCamel(key)` | 单个 key snake_case → camelCase |
| `camelizeKeys(obj)` | 对象/数组**递归**键名转换（后端 snake_case DTO → camelCase Domain，adapter 层调用） |
| `snakifyKeys(obj)` | 对象/数组**递归**反向转换（GET 查询参数预转换等） |
| `readCamel(obj, camelKey)` | 从原始对象读 camelCase key，自动兜底其 snake_case 形态（Presentation 层读未经 adapter 的原始数据时使用，保证上层不持有 snake_case 字面量） |

### 5.3 视图层局部兜底（特例）

`frontend/src/views/Home.vue` 在消费统计接口时定义局部 `getCaseInsensitive(obj, key)`：按 `key` / 全小写 / 首字母大写三种形态取值，兼容后端统计数据的键名差异。该兜底**仅限视图层局部使用**，新增代码应优先依赖 Infrastructure 层工具，禁止在 Presentation 层散落 snake_case 处理。

## 7. 最佳实践

### 7.1 后端开发规范

- 所有 API 响应模型必须继承 `APIModel`，禁止直接继承 `BaseModel`（否则 `serialize_by_alias` 失效，泄漏 snake_case）；
- 字段统一 snake_case 声明，输出命名交给 `alias_generator`，仅在跨服务/历史兼容时显式 `alias`/`validation_alias`；
- 枚举语义字段使用字符串（配合后端 enums 常量，禁止魔法字符串字面量散落）；
- 复杂嵌套结构拆分为独立模型类，Pydantic 会递归转换嵌套模型的键名。

```python
# 正确示范
class TaskCaseBrief(APIModel):
    case_id: str
    name: str
    status: Optional[str] = None
    started_at: Optional[str] = None
    error_message: Optional[str] = None

# 避免的做法
class BadModel(BaseModel):   # 未继承 APIModel：输出将泄漏 snake_case
    caseId: str              # 声明处直接写 camelCase
```

### 7.2 前端开发规范

- 类型定义（`shared/types/`）为 camelCase Domain，与 adapter 转换后的对象一一对应；组件/composable 中直接使用 camelCase；
- snake_case 仅允许出现在 Infrastructure 层（`utils/keyTransform.ts`、`infrastructure/adapters/*`）与 4.3 特例的类型定义中；
- 新增字段须在后端 Schema 与前端类型中同步添加，禁止视图层临时 `as any` 取 snake_case 键。

```vue
<!-- 正确示范（Vue 3 组合式） -->
<script setup lang="ts">
const progress = computed(() =>
  `${task.value?.completedCases ?? 0}/${task.value?.totalCases ?? 0}`);
</script>

<!-- 避免的做法 -->
<template>
  <span>{{ task.created_at }}</span>   <!-- snake_case 泄漏到视图层 -->
</template>
```

### 7.3 特殊情况处理

- 第三方/外部 API 字段名不规范时，在**后端 Schema 接收层**用 `validation_alias` 统一，不在前端逐处适配；
- 数据库列名与 API 输出名之间的映射由 ORM（snake_case 列）+ APIModel（camelCase 别名）天然完成；
- 新增需要同时兼容两种命名的入参字段，优先依赖 NamingRequest/NamingAliasMiddleware 的通用能力，仅当通用规则不足（如非标准缩写词）时才显式 `AliasChoices`。

## 8. 常见问题

### 8.1 响应中出现 snake_case 字段

**排查步骤**：① 后端确认模型继承 `APIModel`（而非 `BaseModel`）且 `serialize_by_alias=False` 未被改回（改回会输出 camelCase 破坏统一口径）；② 前端确认业务 DTO 消费一律走 `infrastructure/adapters/*`（snake_case 未泄漏进 interfaces/features 层）；③ 确认不是 4.3 所述评估链路特例。

### 8.2 请求体字段未被后端识别

**排查步骤**：① NamingRequest 已将 body 归一化为 snake_case，确认后端读取的是 `request.get_json()`（而非自行解析原始 body）；② 字段若被 `validation_alias` 显式接管，则 `populate_by_name` 不再适用，须命中 AliasChoices 中的某个别名；③ query 参数问题优先检查 NamingAliasMiddleware 补全结果（可在 `request.args` 观察双别名）。

### 8.3 前端拿到的对象两种命名混杂

**排查步骤**：① 数据源若绕过 `request<T>()`（如视图层直接 `fetch`，见 `CRUDFormModal.vue` 的 test-tone 调用），需自行用 `camelizeKeys` 归一；② 历史/异构结构双命名混杂时，在 adapter 层用 `camelizeKeys` + 显式字段映射兜底（避免视图层散落 snake_case 处理）；③ 检查是否为 4.3 特例结构，是则在类型层按 snake_case 契约声明。

## 9. 性能考虑

Pydantic 别名转换在模型实例化/序列化时完成，大列表场景（分页已控制单页规模）开销可忽略。前端侧转换仅在 GET 参数与个别报告归一化时发生，均为浅层或受限递归。配置类数据可在 Application 层（store）缓存 ReadModel，避免重复请求与转换。

## 10. 版本兼容性

字段更名遵循"过渡期双命名"策略：新字段以标准 snake_case 输出（前端 adapter 转 camelCase Domain）；旧字段兼容通过 `validation_alias=AliasChoices('oldName', 'old_name')` 声明；旧字段在文档中标注废弃计划后移除。API 版本以 URL 前缀区分（当前 `/api/v1/`）。**评估链路特例（4.3）的 snake_case 契约变更必须与 eval_server 同步评审**。

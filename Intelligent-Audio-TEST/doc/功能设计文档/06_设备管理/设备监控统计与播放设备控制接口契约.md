## 1. 监控统计端点（历史监控 → 统计分析四图）

### 1.1 端点

```
GET /api/v1/test-devices/monitor-stats
     ?device_ids=1,2,3        # 可选，逗号分隔；与服务端其它列表接口同口径
     &lab_id=3                # 可选，按 devices.lab_id 过滤
     &start_date=2026-10-01   # 必填，YYYY-MM-DD（含）
     &end_date=2026-10-17     # 必填，YYYY-MM-DD（含）
     &granularity=day         # 可选，本期仅 day（枚举校验，其它值 400）
```

- 权限：`device:read`。
- 路由注册位置：`device_bp.py` 中**必须排在 `/{device_id}` 之前**（文件头已注明静态段先注册的约定）。
- 校验：`end_date >= start_date`；跨度 ≤ 90 天，超出 400「统计区间不得超过 90 天」。
- 只统计**测试设备**（播放设备与 API 设备不进入该统计；监控告警区仅测试页签展示）。统计只计 `device_status_events.device_kind='test'` 的事件：`devices` 与 `playback_devices` 的 id 各自自增、真实库已重叠，播放设备控制事件（`device_kind='playback'`）不得进入统计（INT-1679）。
- **主体排除规则（INT-1677）**：`source='playback_operation'` 的事件（播放设备重启 / 重置配置 / 修复落库的控制事件）不进入统计、可用率重放与状态历史；状态历史两个端点（全局 `GET /test-devices/status-history`、单设备 `GET /test-devices/{id}/status-history`）同样**只返回测试设备事件**，本期不提供播放侧历史查询参数。排除谓词必须对 `source IS NULL` 宽容（历史 NULL 行仍计入，`NOT IN` 遇 NULL 会静默漏统计），且只在 `device_monitor_repository._NON_TEST_DEVICE_EVENT_SOURCES` 写一处。

### 1.2 响应

```json
{
  "success": true,
  "message": "ok",
  "data": {
    "granularity": "day",
    "start_date": "2026-10-01",
    "end_date": "2026-10-17",
    "device_count": 10,
    "points": [
      {
        "date": "2026-10-01",
        "availability": 96.4,
        "cpu": 38.2,
        "memory": 52.0,
        "battery": 78.0,
        "errors": 1,
        "operations": 4,
        "health_check_samples": 12
      }
    ]
  }
}
```

字段语义（**逐条可验证，前端不得自行补零/补均值**）：

| 字段 | 类型 | 语义与算法 |
| --- | --- | --- |
| `date` | string | ISO 日期 `YYYY-MM-DD`；返回区间内**每一天**，无数据日也返回（前端在基础设施层格式化为 `MM-DD` 供 vChart 使用） |
| `availability` | number \| null | 当日可用率(%)，0–100，保留 1 位。按 `device_status_events` 的 online/offline 事件逐设备重放：日初状态取当日之前最近一条 online/offline 事件，日初无基线则该设备当日首条事件为起点；在线秒数 / 已观测秒数 ×100（当日为今天时观测到当前时刻）。取各设备值的算术平均；**当日没有任何可评估设备/时长 → null**，不是 0。重放**排除 `source='playback_operation'` 的状态事件**（区间状态支与日初基线支都排除） |
| `cpu` / `memory` / `battery` | number \| null | 当日 `health_check` 事件 `detail.metrics.{cpu,memory,battery}` 的算术平均；当日无采点 → **null**（图表断点，不得画 0） |
| `errors` | int | 当日 `success=false` 的事件数（health_check 失败 + operation 失败）+ `to_status=error` 状态事件数；**不含 `source='playback_operation'` 的播放控制事件** |
| `operations` | int | 当日 `event_type=operation` 且 `success=true` 的事件数；**不含 `source='playback_operation'`** |
| `health_check_samples` | int | 当日 health_check 事件数（前端可用于标注采点密度，图表可不用）；**不含 `source='playback_operation'`**（播放侧当前不写 health_check，属防御性一致） |

> 采样口径：统计只读 `device_status_events`，不引入新的写路径、不改现有事件写入语义（CQRS 查询侧，零副作用）。

### 1.3 前置缺口（必须与端点同批实施，否则「性能统计」永远空）

现状 health_check 事件不采 cpu/memory/battery（见 §0），若只做聚合端点，性能统计三条线恒为 null。契约要求：

1. `DeviceCommandService` 健康检查（`device_command_service.py:330-400`）在设备在线时补充采集，写入同一事件的 `detail.metrics`：
   - Android：`adb -s <serial> shell dumpsys battery`（level）、`dumpsys meminfo <pkg>` 或 `/proc/meminfo`（memory%）、`top -n 1`（cpu%）；
   - HarmonyOS：`hdc -t <serial> shell hidumper` 对应子系统；
   - **采不到就不写该键**（返回 null → 前端断点），严禁写 0 或估算值。
2. 采集失败/超时（单条命令 ≤ 5s）只影响该指标，不得让健康检查整体失败（现有 `is_online` 语义不变）。
3. 监控线程（`_MONITOR_INTERVAL_SECONDS=300`）与手动健康检查共用同一采集函数，单点实现。
4. 采集频率即健康检查频率：默认没有定时健康检查时采点为 0，属预期（文档需写明「性能统计依赖健康检查采点」）。

### 1.4 实现落位

- proto：`DeviceConfigService` 新增 `GetDeviceMonitorStats(GetDeviceMonitorStatsRequest{string data}) → (bool success, string message, string data)`，`data` 为 JSON（与本服务既有约定一致）。
- device_service：`application/queries/device_stats_query_service.py`（新，查询侧）→ 仓储 `DeviceMonitorRepository.aggregate_daily_stats(...)`（一次 SQL 取区间事件 + 内存按日聚合，禁止逐日 N+1）→ servicer `interfaces/grpc/device_config_servicers.py`。
- api_gateway：`application/services/device/device_query_service.py` 增 `get_monitor_stats()` + `schemas/device.py` 增查询模型 + `infrastructure/acl/*device*` 增 ACL 方法 + `routes/device_bp.py` 增路由。
- 前端接线（另一侧卡，不在本契约实施范围）：`history-stats-charts.tsx` 改走 infrastructure API，删除 `MOCK_DEVICE_STATS` 与「演示数据」标注；空数据/全 null 显示空态「暂无监控采点」。

## 2. 播放设备控制端点

统一前缀 `POST /api/v1/playback-devices/{id}/…`，权限 `playback:control`；body 可空（`{}` 或空）；`id` 不存在 → 404「未找到播放设备」。
**统一守卫**：以下动作在 `task_acl_repository.has_running_e2e_tasks()` 为真时返回 409「设备正在执行测试，禁止执行该操作」——与播放测试既有 403/409 守卫同口径，避免打断任务音频。运行态锁与幂等不在本期引入（这些动作天然可重复执行）。

### 2.1 重启播放设备 `POST /{id}/restart`

- 语义：停止该设备的**测试播放**（`task_id=test_{id}`）→ 调 audio_service `GetDeviceIndex(device_unique_id)` 重新解析物理索引 → 可解析则 `status=online`，否则 `status=offline`（并落一条 `source='playback_operation'` 的 operation 事件，`detail.operation='restart'`）。
- 落库标记：该 `operation` 事件同时带 `device_kind='playback'`（INT-1679），**不进入**测试设备状态历史与监控统计（契约 §1.2）；留痕保留，只是带类型标记。
- 响应：`{success, message, data:{id, status, device_index}}`；设备已离线时仍返回 200 + `data.status='offline'` + message「设备不可枚举，已标记离线」。
- 明确边界：这是**音频通道层重开 + 重新枚举**，不是硬件重启；文案不得写「设备已重启」，写「已重新连接音频通道」。

### 2.2 重置播放设备配置 `POST /{id}/reset-config`

- 语义：按物理设备重新探测 `sample_rate` 与 `channel_index`（`GetPhysicalDevices` 按 `device_unique_id` 匹配，取 `sample_rate` 与通道容量），探测值有效且与库中不同才写回（写回时落一条 `source='playback_operation'` 的 operation 事件，`detail.operation='reset-config'`）。**不清除 `current_spl_mapping_id`**（声压映射由 `associate-spl` 独立维护；未关联态由该接口自己的契约负责）。
- 响应：`{success, message, data:{id, changed:{sample_rate?, channel_index?}, status}}`；无变化时 `changed:{}` + message「配置与硬件一致，无变化」。
- 物理设备不可枚举 → 409「设备不可枚举，无法探测配置」。
- 前端须加二次确认弹窗：「将按硬件重新探测采样率与通道索引，不影响声压映射关联」。

### 2.3 静音 / 取消静音 `POST /{id}/mute`、`POST /{id}/unmute`

- 语义（**本定稿的安全口径**）：对该物理播放设备**设备管理页的测试播放**静音（播放增益 0），**不影响任务执行的音频播放**（任务播放链路 audio_service 不经该静音标志）。
- 运行态状态，不落库：audio_service 重启后回到未静音；菜单是「静音 / 取消静音」两个动作，前端不依赖状态查询。
- 响应：`{success, message, data:{id, muted:true|false}}`；设备不可枚举 → 409。
- 实现要点：`shared/proto/audio_service.proto` 增 `SetDeviceMute(unique_id, muted)`（或等价 RPC）→ `audio_engine` 维护「静音设备集合」→ `play_audio` 对 `task_id` 以 `test_` 开头的播放把有效增益乘 0；device_service 经 ACL 调用。
- 若负责人要求「静音也作用于任务播放」，须另立裁定并补「任务运行时设备已静音则拒绝派发 / 自动解除」策略——本期不做，避免静默污染任务音频结果。

### 2.5 设备诊断 / 修复 / 优化

- `GET /{id}/diagnosis`（权限 `playback:read`）→ `data:{checkedAt, items:[{key,label,status:'ok'|'warn'|'error'|'unsupported',detail,suggestion}]}`。
  固定检查项（本期全集，不得臆造后端没有的能力）：`enumerable`（物理设备可枚举）、`channel_index`（通道索引在设备通道容量内）、`sample_rate`（库中采样率与硬件默认采样率一致）、`spl_mapping`（已关联声压映射）、`status`（当前在线）、`busy`（是否被测试占用）。
- `POST /{id}/repair`（权限 `playback:control`）body `{actions:["re-enumerate","reopen-channel"]}` → `data:{results:[{action,success,message}]}`。
  - `re-enumerate` = 重扫描刷新状态（落一条 `source='playback_operation'` 的 operation 事件，`detail.operation='re-enumerate'`）；`reopen-channel` = 语义同 §2.1 restart（事件仍记 restart，`source='playback_operation'`）。
  - 落库标记：修复动作落的 `operation` 事件同时带 `device_kind='playback'`（INT-1679，`reopen-channel` 复用 restart 实现、事件仍记 `detail.operation='restart'`），**不进入**测试设备状态历史与监控统计（契约 §1.2）。
  - **不含**改权限/清存储/换驱动等破坏性动作。
- 优化：**不提供一键优化端点**。`diagnosis` 的 `suggestion` 即为优化建议（如采样率对齐、关联声压映射），UX §6.21 的「优化」分区按建议清单展示，不做一键执行。

## 4. 拆分建议（按服务域派开发，均「主项目」）

| 卡 | 内容 | 服务域 | 工作量 |
| --- | --- | --- | --- |
| A | 监控统计端点 + 健康检查指标采集（§1） | device_service + api_gateway | M |
| B | 重启 + 重置配置（§2.1/§2.2） | device_service + api_gateway | S |
| C | 静音 / 取消静音（§2.3） | audio_service + device_service + api_gateway | M |
| D | 播放测试结果留存 + 结果分析查询（§2.4） | device_service + api_gateway（+audio_service 回传 metrics） | M |
| E | 诊断 / 修复（§2.5） | device_service + api_gateway | M |

- 建议 A、B 先派（无跨服务依赖），C/D 依赖 audio_service 改动（开发工程师B 道：audio_service + device_service），可合并为一张卡；E 依赖 B 的 restart 逻辑。
- 每张卡按标准流：实施 → 测试（docker 真实栈 :15000 / :15173）→ 前端UX审计（有界面改动时）→ 代码审计 → 一致性审计。
- 前端接线卡（删 mock、解禁菜单、接 §6.20/§6.21 弹窗）在对应后端卡 done 后由 React 规划线拆。

## 5. 不做

- 不为这些缺口写前端 mock 或「本地幂等成功」兜底（INT-1495 P2-4 口径：禁用 + Tooltip「后端未提供该操作」，`controlDevice` 对未映射动作必须返回 `success:false`）。
- 不新增监控采样表：统计只读 `device_status_events`，指标复用 health_check 的 `detail.metrics`。
- 不引入 REST 兼容层 / 双口径字段；不做任务播放链路的静音联动。

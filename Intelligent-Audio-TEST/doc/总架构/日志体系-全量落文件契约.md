# 日志体系 — 全量落文件契约（logs 表零写入）

> 【负责人裁定 2026-10-24】「日志全改成写文件」。本文件是 INT-1793 方案一致性审计的交付契约：
> 第七条把审计 / 系统日志也从 `logs` 表搬到文件，做到 **`logs` 表零写入、日志全量落文件**，
> 同时守住日志页（React / 新 Vue）的接口契约与可见性。业务日志（执行 / 评估 / 设备）的
> 文件化口径见 `doc/功能设计文档/00_新功能总览/日志方案.md`（INT-81），本文不重复。
>
> 评审结论：**✅ 可行（有条件通过）** —— 需在实施卡中兑现 §3 的 H1~H4 四条硬约束，不可省略。
> 证据口径：代码以 V9.7.31 本 run 工作树为准；数据以主库 `intelligent_audio_test` 2026-10-24 实测为准。

## 0. 结论与硬约束

| 结论 | 内容 |
| --- | --- |
| 可行性 | ✅ 可行。目标量级小（当前约 1.2k~2.5k 行/天），落盘、读取、保留、回滚均有现成基座可复用 |
| 前提 | 四条硬约束 H1~H4 必须与写入改造同卡落地，否则「零写入」会把审计口径弄丢 |
| 不在本卡 | 不改业务代码、不动主库数据（本卡只评审 + 契约）；`logs` 表结构重设计另卡【审计·数据库】 |

**H1 审计类型必须显式标记，不能继续靠 category 判定。**
`category='device'` 现在同时承载两类完全不同的东西：真审计事件（6 处）与设备运维日志
（10 处 `log_not_emit(category='device')`，见 §1 表 D1）。按 category 搬文件会把运维日志
灌进审计语料。改造新增 `audit_event` 实参：**只有显式携带 `audit_event` 的日志进审计文件**，
其余同 category 的日志降级为服务文件。

**H2 操作人必须写侧提取，不能依赖 contextvar。**
主库实测 304,749 行里只有 151 行有 `created_by_user_id`；而近 2 天审计行 content 里
99.5%（4,357/4,379）带 `operator_id`。切文件后 DB 行消失，「仅自己」视图只剩文件侧，
必须在写侧把 content JSON 里的 `operator_id` / `operator` 提取成 JSONL 顶层字段并落 `user_id`。

**H3 游标必须单调且与时间同序。**
两个前端都拿列表里的 `id` 当增量游标（React `useLogRealtime.ts`、Vue `logView.ts:521`
的 `Math.max(...ids)`），不做服务端游标回写。因此文件日志条目 `id` 不能是现有的内容哈希
（`business_reader._stable_int_id`），必须是 **`cursor = 事件时间的 epoch 微秒**（同微秒冲突 +1）。

**H4 审计文件必须单写者：由 task_service 经既有 `BatchCreateLogs` 通道落盘。**
device_service / audio_service 固定跑宿主机（gRPC 50053 / 50052），而读侧 api_gateway 跑容器，
两者 `LOG_ROOT_DIR` 不是同一个文件系统（容器是 `service_logs:/app/logs` 卷）。若各服务各自落盘，
宿主机 service 写的审计文件读侧看不见。复用 `BatchCreateLogs`（今天 DB 写入也走它）+ 把
servicer 的落点从 `insert` 改成 `append JSONL`，可零新增通道、零端口改造、宿主机与容器一致。

## 2. 七问逐条回答

### Q1 非任务日志落盘位置、格式、字段白名单、轮转、与现有服务日志的关系

**落盘位置（唯一权威模板，写入/读取两侧共用）**

```
logs/audit/{YYYY-MM-DD}/{category}.{service}.{hostname}-{pid}[-NNN].jsonl
```

- 日期在前：按时间窗筛选时只需枚举对应日期目录；保留期按目录日期整目录回收，不依赖 mtime
  （mtime 会被「进程重启后追加写」刷新，日期段不会）。
- `category` ∈ `{auth, benchmark, device, visibility, system}`，即 `AuditLogCategory` 四值
  加 `system`（S4 的三类 System 审计）。
- `{service}` = **产生该事件的进程**（`resolve_service_name()`，随条目透传，不是写盘进程），
  `{hostname}-{pid}` = 写盘进程标识（复用 `shared/logging/identity.process_identity()`）。
- 单文件超 `LOG_AUDIT_MAX_MB`（50）切分为 `...-001.jsonl`，序号按本进程 stem 递增（复用
  `BusinessLogPathBuilder.next_split_path` 同款规则，不跨进程合并序号）。

**为什么不放 `business/_no_task/...`**：`business/` 的检索契约是「task_id 是根键」
（`path_builder.py:56-57` 直接抛 ValueError），把无任务语料塞进去会破坏任务检索的收敛语义，
且审计的保留期（180 天）与业务日志（30 天）不同，混在一棵树里清扫会互相误删。

**JSONL 字段白名单（显式白名单，拒绝任意 kwargs 落盘，照 `business_writer._ENTRY_FIELDS` 风格）**

| 字段 | 类型 | 来源 | 说明 |
| --- | --- | --- | --- |
| `cursor` | int | 写侧生成 | 增量游标 = 事件时间 epoch 微秒；同微秒冲突时 +1，保证严格递增 |
| `time` | str | 事件时间 | `LOG_TIME_FORMAT`（`%Y-%m-%d %H:%M:%S.%f`，固定宽度可字符串排序） |
| `level` | str | 日志级别 | `DEBUG/INFO/WARNING/ERROR/CRITICAL` |
| `category` | str | 分流参数 | 五值之一 |
| `module` | str | 调用方 | 如 `auth_login` / `published_task` |
| `source` | str | 调用方 | 事件来源标识（网关固定 `api_gateway`） |
| `service` | str | 产生进程 | `resolve_service_name()` |
| **`event`** | str | `audit_event` 实参 | `AuditEvent` 枚举值（**必填**，缺省则该条不算审计，见 H1） |
| **`operator_id`** | int/null | content JSON | 操作人 user_id |
| **`operator`** | str/null | content JSON | 操作人用户名 |
| **`target_type`** | str/null | content JSON | `user/role/task/result/device/group/report/...` |
| **`target_id`** | int/str/null | content JSON | 目标对象 id（含 `published_task_id` / `alarm_id` 等折叠到 `target_id`） |
| **`action`** | str/null | content JSON | `read/write/delete/update_visibility/...` |
| **`result`** | str | 约定 | `success` / `failure`；缺省写入 `success`，新写入器必须显式给 |
| `user_id` | int/null | = `operator_id` | 读侧「仅自己」过滤口径（H2） |
| `task_id`/`device_id`/`api_id`/`test_case_id`/`thread_id`/`algorithm_type` | 原值 | emit 载荷 | 与 DB 行同名字段对齐，保证 `LogItem` 映射零分支 |
| `detail` | object | content JSON 全量 | 原始事件负载，保证未来加字段不必改契约 |
| `content` | str | 原 content 字符串 | **原样保留**，日志页「内容」列与详情展开零变化 |

不落 `mark`（文件日志不可标记，见 Q3）、不落 `id`（读侧 `id` = `cursor`）。

**轮转与保留**
- 按天（目录）+ 按大小（50MB 切分）双条件；跨天由写侧每次写入前比对当前日期切换句柄。
- 保留 `LOG_AUDIT_RETENTION_DAYS`（默认 180）：整日期目录删除，删除前先归档（Q5）。

**与 `logs/{service}/app-*.log` 的关系（避免重复落两份）——这是本契约最需要守住的一条**

| 日志种类 | 改造前 | 改造后 |
| --- | --- | --- |
| 审计事件（带 `audit_event`） | 服务文件 + DB | **只写审计文件（一条事件恰好一行）**，不再写服务文件 |
| 同 category 但无 `audit_event` 的运维日志（S1'） | 服务文件 + DB | **只写服务文件**（同时消灭了它们对审计的污染） |
| `test_case_id` 无 `task_id`（D2） | 服务文件 + DB | **只写服务文件**（预览日志 3 条/天，日志页不再列出，属可接受的行为收敛） |
| 其余系统日志 | 服务文件 | 不变 |

「一条事件恰好一行」靠分流顺序实现：emit 里 `task_id` → `audit_event` → 其余三分支互斥，
每个分支 return。

### Q2 读侧映射（每个端点在「全文件」下的数据来源、分页、排序、扫描上界）

| 端点 | 改造后数据来源 | 分页 / total 语义 | 排序 | 扫描上界与缓存 |
| --- | --- | --- | --- | --- |
| `GET /logs`（无 task_id） | 审计文件（时间窗内）+ `logs` 表历史行（只读） | 内存合并后分页；`total` = 窗口内命中数，触顶时为**下界**并保留最新 | `(time desc, cursor desc)`，`cursor` 唯一保证稳定 | 窗口 + `LOG_AUDIT_MAX_SCAN_ENTRIES`(100000) + TTL 缓存 3s |
| `GET /logs`（有 task_id） | 业务文件 + DB 历史行（**不变**） | 不变 | 不变 | `LOG_BUSINESS_MAX_SCAN_ENTRIES` + TTL 缓存（复用） |
| `GET /logs/stats` | 同列表，按 level 聚合 | 各项为窗口内计数；触顶时同为下界 | — | 与列表共享同一次扫描（同参 TTL 复用，照 INT-100 口径） |
| `POST /logs/refresh` | 审计文件（游标增量） | 单次 ≤100 条 | `cursor asc` | 见 Q4 |
| `POST /logs/export` | 与列表**同源同筛选**（含 legacy DB 行） | 不分页（受扫描上界约束） | `time desc` | 同列表 |
| `PUT /logs/mark` | 仅 DB 历史行 | `updated` = 实际更新行数（文件游标 → 0） | — | — |
| `POST /logs/clear` | 仅 DB 历史行 | 语义不变 | — | — |
| `POST /logs/archive`、`GET /logs/archive/*` | 仅 DB / OSS | 语义不变；DB 清空后 `archived_count=0`、`totalLogs=0` 属预期 | — | — |

**时间窗默认值**：`GET /logs` / `stats` / `export` 在**既无 `start_time` 也无 `end_time`** 时，
默认取最近 `LOG_AUDIT_QUERY_DEFAULT_DAYS`（30）天。理由：文件侧没有索引，无界扫描随保留期线性
增长（180 天 × 1.2k ≈ 21.6 万行/次）；而 30 天已覆盖排查场景，用户可用时间筛选放宽。
**这是相对今天（DB 全表）唯一的可见语义变化，必须在卡面与交付评论中写明**：切文件后
「共 N 条」默认是「近 30 天 N 条」，不是「历史全部 N 条」。

**复用现有读取基座**：新增 `shared/logging/audit_reader.py`，与 `BusinessLogReader` 同款
（逐行解析、`_match` 过滤、扫描上限、TTL 缓存、字段兜底）；差异只有三处：按日期目录枚举、
无 task_id 根键、条目 `id` = `cursor`（不是内容哈希）。不新建第二套过滤语义。

**筛选能力对等清单**（必须与今天的 DB 查询一致）：`level`（逗号多值）、`module`（`all` 归一）、
`category`、`mark`（文件恒空命中）、`time` 区间、`keyword`/`content_include`/`content_exclude`、
`user_id`（「仅自己」）、`device_id`/`task_id`/`api_id`/`test_case_id`/`thread_id`/`algorithm_type`。

### Q3 mark（标记）语义

**结论：文件日志不支持标记，只读。`PUT /logs/mark` 对文件游标返回 200 + `updated=0`。**

- 现状已有先例：任务合并视图里的业务文件条目 `mark` 恒为 `None`（`business_reader._to_item`），
  今天对它们标记就是一次 `updated=0` 的空操作，页面只提示「已为 0 条日志添加标记」。
  审计文件沿用同一行为，**不引入 400/500，不出现空态回退**。
- 不做「标记旁挂文件」（`logs/.marks/`）：那会重新造一个可写的第二数据源，与「不写兼容层、
  不留双口径」冲突；标记是排查期的临时便利，不是审计要求。
- 交付要求（A 道）：`log_command_service.mark_logs` 在 `updated==0` 且请求里的 id 全部
  `>= CURSOR_FLOOR`（见 Q4）时，提示语改成「所选为文件日志，不支持标记（仅历史库行可标记）」，
  其余情况保持原文案。前端 `logsApi.markLogs` 只读状态码，不解析 message，零改动。
- `mark` 筛选（`?mark=flagged`）在文件侧恒空命中 → 页面显示 0 条，属正确行为。

### Q4 refresh_logs 增量（游标设计）

**游标定义**：`cursor = int(事件时间的 epoch 微秒)`，写侧保证同一进程内严格递增（冲突 +1）。
`CURSOR_FLOOR = 10^12` 把两个 id 空间隔开（legacy DB `id` 实测 `max=6,949,425`；epoch 微秒
在 2026 年约 `1.79×10^15`，仍在 JS `Number.MAX_SAFE_INTEGER` 9.0×10^15 之内，前端精度无损）。

**请求/响应（字段名一个都不改，两前端零改动）**

```
POST /logs/refresh  {"last_id": <int>}
→ {"items":[...], "count":n, "new_count":n, "last_id":<int>, "db_max_id":<int>, "reset_required":bool(可选)}
```

| 请求 `last_id` 情形 | 服务端行为 |
| --- | --- |
| `== 0`（尚未建立基准） | `items=[]`、`last_id=server_max_cursor`、**不带** `reset_required` |
| `>0 且 < CURSOR_FLOOR`（DB 旧 id 或负数） | `items=[]`、`last_id=server_max_cursor`、`reset_required=true` |
| 在游标域且 `<= server_max_cursor` | 返回 `cursor > last_id` 的最多 100 条（升序），`last_id` = 末条游标 |
| `> server_max_cursor`（库被清 / 时钟回拨） | `items=[]`、`last_id=server_max_cursor`、`reset_required=true` |

`db_max_id` 保留原字段名，语义 = `server_max_cursor`（无数据时 0）。

**与两个前端的对齐（逐个 verify 过）**
- React `application/logs/useLogRealtime.ts`：首轮 `lastIdRef=null` → 发 0 → 走「仅建基准」分支，
  取 `result.lastId` ✅；`resetRequired` 分支清缓冲并置 `lastIdRef=null` → 下一轮回到基准 ✅。
  唯一噪声：WS 推来的业务日志用**合成负数 id**（`_worker_mixin.py:106-109`）会污染 `lastIdRef`，
  下一轮触发一次 `resetRequired` 并自动纠正 —— 允许，代价是一次缓冲清空。
- Vue `views/LogView/logView.ts:521`：每次发 `Math.max(当前列表 id)`，不读 `last_id`/`db_max_id`/
  `reset_required`。稳态下列表里有文件行 → 发送值就是游标 ✅；全是 legacy 行 → 发送值 <
  `CURSOR_FLOOR` → 返回空，无视觉变化 ✅。

**与 WebSocket 的衔接**：审计事件今天**从不推 WS**（`log_not_emit` 硬编码
`push_to_websocket=False`，`_api.py`），保持现状不新增通道。全局日志页的实时只依赖
`POST /logs/refresh` 轮询；任务页的 WS 推送与游标无关（业务日志合成负数 id，仅作前端 key）。

**不重复、不漏**：游标唯一且单调 → 重复拉取同一 `last_id` 幂等；进程重启后游标从事件时间重新
推导，不会回退（时钟回拨由「同微秒 +1 且取 max(cursor, 上次写盘 cursor+1)」兜底；跨进程以
各自事件时间为准，读取侧按 `cursor` 去重足够）。

### Q5 保留与合规

**结论：新增 `LOG_AUDIT_RETENTION_DAYS = 180`，与 INT-1785 的 `LOG_DB_RETENTION_DAYS=180` 同值；
本地保留到期前先归档到 rustfs，归档失败不删本地。现有 `service_retention_days` / `business_retention_days`
不够用——审计要 180 天，而两者默认都是 30 天。**

| 项 | 结论 |
| --- | --- |
| 新配置 | `LOG_AUDIT_RETENTION_DAYS`（180）、`LOG_AUDIT_ARCHIVE_ENABLED`（true）、`LOG_AUDIT_MAX_MB`（50） |
| 清扫实现 | 扩展 `shared/logging/retention.py`：服务日志（排除 `business/`、`audit/`）+ 业务日志 + **审计日志三套独立天数**，按目录日期判定 |
| 归档目标 | `archives/audit/{YYYY-MM-DD}/{原文件名}`（rustfs，与 INT-1785 同桶同 `archives` 类目），JSONL 原样上传，不转格式 |
| 失败处理 | 上传失败 → 保留本地、下轮重试、打印告警；**绝不先删后传** |
| 单清扫者 | 新增 `LOG_SWEEP_SERVICE`（默认 `api_gateway`）：只有该服务执行清扫，其余跳过。现在每个进程各自 sweep 同一共享卷（`retention.py:59-69`），审计涉及 OSS 上传，多进程并发会重复上传并互相删文件 |
| 删除授权 | 到达保留期的**自动删除**由保留策略执行，不需要人工逐次批准；**提前删除 / 单次清理**只能走维护脚本（`scripts/maintenance/`），必须由负责人 yy dd 批准并在卡面留存记录，**不提供任何 UI 入口** |
| 合规缺口 | 180 天是当前唯一依据（对齐 INT-1785）；若后续合规要求更长，只调配置不改代码 |

### Q7 回滚

**结论：保留一个配置级回滚开关 `LOG_AUDIT_DB_ENABLED`（默认 false），但限定为「故障回退」而非口径。**

| 项 | 契约 |
| --- | --- |
| 键名 / 默认 | `LOG_AUDIT_DB_ENABLED`，默认 `False` |
| 语义 | `True` 时审计事件**双写**（审计文件 + 原 DB 队列）；`False` 时只写审计文件。读侧**不感知**该开关 |
| 与红线的关系 | 这不是兼容层：不产生第二套读口径、不改变任何接口行为，只在写入侧多落一份备份。沿用已存在的同类先例 `LOG_BUSINESS_DB_ENABLED`（`shared/infrastructure/config.py:151`）——该开关同期存在，未被判为违反「不留双口径」 |
| 生效方式 | 环境变量 + 进程重启（配置为进程级快照，`shared/logging/config.py:63-70` 有缓存） |
| 验证方式 | 开：触发一次登录 → `select count(*) from logs where category='auth' and time > now() - interval '1 min'` = 1，且审计文件同时多一行；关：再登录 → 0 行、文件多一行 |
| 已知代价 | 开关打开期间同一事件在日志页会**出现两次**（文件一条 + DB 一条，id 空间不同无法去重）。这是回退态，必须在开关打开时于卡面登记并限时关闭 |
| 删除窗口 | 合入后 **30 天**（覆盖 INT-1785 归档执行窗口）；到期后必须由一张清理卡删除开关、DB 分支与相关测试，防止长期留存变成双口径 |

## 4. 前端是否零改动

**结论：React 与 新 Vue 均零改动**（已对两侧源码逐端点核对）。理由逐条：

1. 五个读端点的请求参数与响应字段名全部保持；`LogItem` 字段集合不变（`id/mark/user_id` 语义不变，
   只是文件行的 `id` 变成游标、`mark` 恒 null）。
2. 游标用 int 且 < 2^53，`JSON.parse` 无损；Vue 的 `Math.max(...ids)` 与 React 的 `Set<number>`
   都不受影响。
3. `reset_required` 是可选字段，Vue 不读、React 已有分支。
4. 唯一可见语义变化是「默认 30 天窗口」与「文件日志不可标记」，两者都不改代码，只改页面上的数字
   与提示文案（提示文案由服务端 message 提供）。

若将来要做「审计日志标记」或「按归档文件浏览审计」，属新需求，另开卡。

| R8 | **`category='device'` 语义混用**（H1） | 若不做 H1，运维日志会污染审计语料 | H1 为硬约束，D 卡验收第 2 条强制核对 |

## 7. 与 INT-1783 / 1784 / 1785 / 1786 / 1787 的依赖与冲突

| 卡 | 关系 | 结论 |
| --- | --- | --- |
| **INT-1783**（PG 观测基线） | 无代码依赖；慢 SQL 阈值用于验证「零写入」前后的 DB 负载变化 | **不冲突，可并行**。建议在 G2 前后各取一段 `logs` 表相关语句耗时做前后对照（可选） |
| **INT-1784**（冗余索引下线） | 该卡要删 `logs` 的 `idx_task_time`/`idx_log_id`/`idx_task_id` 等 6 个索引 | **不冲突**。零写入后 `logs` 只被查询侧只读访问，删索引收益更明显；但 G3 上线前 `GET /logs` 全局查询仍会打表，建议 **A 卡合入后再执行 INT-1784 的 logs 索引下线**，避免中间态把 DB 查询压到无索引 |
| **INT-1785**（logs 收口 + 审计保留） | 该卡前提是「审计继续落库、180 天保留」；本卡要「零写入」 | **不冲突，但顺序要对**：① INT-1785 可在本卡 G2 之前或之后执行（它只处理 10-23 之前的 273,106 行，与写入侧改造无交集）；② 它的 `LOG_DB_RETENTION_DAYS=180` 成为清空残留的唯一执行者，**不要因为本卡去改它的「不做」清单**；③ 两卡都改 `shared/logging/config.py` 与 `retention.py`（不同键、不同行），合入时按 §bootstrap 惯例保留双方改动 |
| **INT-1786**（大 JSON 外置 rustfs） | 同属「把数据搬出 PG」的档期工程，共用 `storage` 封装与 rustfs 桶 | **不冲突**。两者都要在 `archives` 类目下新增前缀（本卡 `audit/`，该卡为明细对象桶），桶命名由各自卡定；执行窗口建议错开，避免同一天两次容器重启 |
| **INT-1787**（report_cases 去冗余，backlog 待拍板） | 无数据依赖 | **不冲突** |

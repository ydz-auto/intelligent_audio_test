# 实验室扩展功能设计文档

## 1. 背景与目标

### 1.1 问题背景

当前系统存在以下问题：
- 设备、播放设备、用例等资源缺乏物理位置管理
- 无法支持跨实验室的测试任务执行
- 设备和资源无法按地理位置分组管理

### 1.2 扩展目标

1. **实验室管理**：支持多个物理实验室的创建和管理
2. **资源归属**：设备、播放设备归属到特定实验室；用例可选归属（通用用例所有实验室可见）
3. **任务多实验室支持**：一个任务可以在多个实验室执行，E2E 任务按实验室分发并行执行
4. **流程隔离**：通过实验室选择过滤后续可选资源
5. **服务拆分兼容**：设计与服务拆分架构完全兼容
6. **设备调拨**：支持被测设备在实验室之间移动

## 2. 业务流程设计

### 2.1 当前流程（5步骤）

```
选择算法 → 选择用例 → 选择设备 → 选择播放设备 → 确认测试
```

### 2.2 扩展后流程（6步骤）

```
选择算法 → 选择实验室 → 选择用例 → 选择设备 → 选择播放设备 → 确认测试
       ↑ 可多选                    ↑ 按实验室过滤
```

### 2.3 流程说明

| 步骤 | 操作 | 业务规则 |
|------|------|----------|
| Step 1 | 选择算法 | 不变，根据算法过滤用例 |
| Step 2 | **选择实验室** | **可多选**，定义任务执行范围 |
| Step 3 | 选择用例 | 显示**通用用例**（config 无 lab_id）+ **归属已选实验室的专属用例**（config.lab_id ∈ 已选实验室） |
| Step 4 | 选择设备 | **仅显示**属于已选实验室的设备 |
| Step 5 | 选择播放设备 | **仅显示**属于已选实验室的播放设备 |
| Step 6 | 确认测试 | 创建任务，关联实验室和资源 |

> **用例归属规则**：用例的实验室归属存储在 `config.lab_id` 字段中（JSONB）。`config.lab_id` 为空表示通用用例，所有实验室可见；有值表示专属用例，仅在该实验室可见。创建/编辑用例时可通过开关控制是否归属特定实验室。

## 4. 数据库模型

### 4.1 实验室表（新增）

```sql
CREATE TABLE laboratories (
    id SERIAL PRIMARY KEY,
    code VARCHAR(50) UNIQUE NOT NULL COMMENT '实验室代码，如 LAB-A-01',
    name VARCHAR(100) NOT NULL COMMENT '实验室名称',
    building VARCHAR(50) COMMENT '所在楼栋',
    floor VARCHAR(20) COMMENT '所在楼层',
    room_number VARCHAR(50) COMMENT '房间号',
    description TEXT COMMENT '实验室描述',
    status VARCHAR(20) DEFAULT 'active' COMMENT '状态 (active/inactive/maintenance)',
    deleted BOOLEAN DEFAULT FALSE COMMENT '软删除标记',
    deleted_at TIMESTAMP COMMENT '软删除时间',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_laboratories_code ON laboratories(code);
CREATE INDEX idx_laboratories_status ON laboratories(status);
```

### 4.2 设备表（修改）

```sql
ALTER TABLE devices ADD COLUMN lab_id INTEGER REFERENCES laboratories(id);
CREATE INDEX idx_devices_lab_id ON devices(lab_id);
```

### 4.3 播放设备表（修改）

```sql
ALTER TABLE playback_devices ADD COLUMN lab_id INTEGER REFERENCES laboratories(id);
CREATE INDEX idx_playback_devices_lab_id ON playback_devices(lab_id);
```

### 4.4 用例表（不修改表结构）

用例的实验室归属通过 `config` JSONB 字段承载，**不新增独立列**：

```sql
-- 用例创建/更新时，config 字段中携带 lab_id（可选）
-- config 结构示例：
-- 通用用例：   {"rounds": [...], "dimensions": [...]}                    -- 无 lab_id
-- 专属用例：   {"rounds": [...], "dimensions": [...], "lab_id": 1}      -- 有 lab_id

-- 查询时通过 JSONB 提取 lab_id 过滤（PostgreSQL）：
SELECT * FROM test_cases
WHERE config->>'lab_id' IS NULL              -- 通用用例，所有实验室可见
   OR (config->>'lab_id')::int IN (1, 2);    -- 专属用例，归属已选实验室

-- 建议添加 GIN 索引加速 JSONB 查询（可选，用例量级不大时非必须）
CREATE INDEX idx_test_cases_config_gin ON test_cases USING GIN (config);
```

> **设计决策**：用例 lab_id 放 config 而非独立列，因为：
> 1. 不修改表结构，存量用例自动成为通用用例（config 无 lab_id），零迁移成本
> 2. 用例的实验室归属是可选语义，与 rounds/dimensions 等配置项性质一致
> 3. 避免独立列 + 外键约束，用例删除时不影响实验室

### 4.5 声压级映射表（修改）

```sql
-- 声压级映射依赖实验室本地声卡参数，不同实验室同型号设备增益值不同
ALTER TABLE spl_mappings ADD COLUMN lab_id INTEGER REFERENCES laboratories(id);
CREATE INDEX idx_spl_mappings_lab_id ON spl_mappings(lab_id);
-- 建议联合唯一约束：(device_id, lab_id) 确保同一设备在不同实验室有独立映射
ALTER TABLE spl_mappings ADD CONSTRAINT uq_spl_device_lab UNIQUE (device_id, lab_id);
```

### 4.6 任务-实验室关联表（新增）

```sql
CREATE TABLE task_laboratory_relations (
    id SERIAL PRIMARY KEY,
    task_id INTEGER NOT NULL REFERENCES test_tasks(id) ON DELETE CASCADE,
    lab_id INTEGER NOT NULL REFERENCES laboratories(id),
    priority INTEGER DEFAULT 1 COMMENT '实验室优先级，1最高',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(task_id, lab_id)
);

CREATE INDEX idx_task_lab_task ON task_laboratory_relations(task_id);
CREATE INDEX idx_task_lab_lab ON task_laboratory_relations(lab_id);
```

## 5. API 接口设计

### 5.1 实验室管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/v1/laboratories | 获取实验室列表 |
| GET | /api/v1/laboratories/{id} | 获取实验室详情 |
| POST | /api/v1/laboratories | 创建实验室 |
| PUT | /api/v1/laboratories/{id} | 更新实验室 |
| DELETE | /api/v1/laboratories/{id} | 删除实验室（软删除） |
| GET | /api/v1/laboratories/{id}/summary | 获取实验室资源统计 |

### 5.2 资源查询（按实验室过滤）

> **实现方式**：复用现有资源列表 API，增加 `lab_ids` query 参数过滤，不新建独立路由。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/v1/test-devices?lab_ids=1,2 | 获取实验室下的设备（lab_id IN） |
| GET | /api/v1/playback-devices?lab_ids=1,2 | 获取实验室下的播放设备（lab_id IN） |
| GET | /api/v1/test-cases?lab_ids=1,2 | 获取通用用例 + 归属已选实验室的专属用例 |

### 5.3 设备调拨

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/v1/test-devices/{id}/transfer | 将设备调拨到目标实验室 |

> 调拨后刷新复用现有接口：`POST /api/v1/test-devices/scan`（扫描物理设备）、`GET /api/v1/test-devices`（列表刷新）、`GET /api/v1/spl-mappings`（SPL 映射列表）

### 5.4 任务创建

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/v1/tasks | 创建任务（支持 lab_ids） |
| POST | /api/v1/tasks/validate | 校验任务资源归属 |

## 6. 业务规则

### 6.1 归属规则

| 关系 | 基数 | 说明 |
|------|------|------|
| 实验室 → 设备 | 1:N | 一个设备同时刻只属于一个实验室，支持调拨 |
| 实验室 → 播放设备 | 1:N | 一个播放设备固定归属一个实验室（声卡绑定） |
| 实验室 → 用例 | 1:N（可选） | 用例 config.lab_id 为空=通用，有值=专属 |
| 实验室 → 声压级映射 | 1:N | 同一设备在不同实验室有独立映射值 |
| 任务 → 实验室 | N:M | 一个任务可以在多个实验室执行 |

### 6.2 过滤规则

创建任务时，后续步骤的可选范围根据前一步的选择动态过滤：

```
Step 2 选择实验室 [1, 2] 后：

Step 3 用例列表 = 用例 WHERE config->>'lab_id' IS NULL           -- 通用用例
                     OR (config->>'lab_id')::int IN [1, 2]       -- 专属用例

Step 4 设备列表 = 设备 WHERE lab_id IN [1, 2] AND deleted = FALSE

Step 5 播放设备列表 = 播放设备 WHERE lab_id IN [1, 2]
```

### 6.3 校验规则

创建任务时，后端必须校验：

1. **用例归属**：所有 case_ids 必须是通用用例（config 无 lab_id）或专属用例且 config.lab_id ∈ lab_ids
2. **设备归属**：所有 device_ids 必须属于 lab_ids 中的某个实验室（device.lab_id ∈ lab_ids）
3. **播放设备归属**：所有 playback_device_ids 必须属于 lab_ids 中的某个实验室
4. **设备调拨前置校验**：调拨时设备无运行中的任务关联（task_device_relations 中无 running/queued 状态的记录）

### 6.4 设备调拨规则

```
设备调拨流程：
  1. 校验目标实验室存在且 status = active
  2. 校验设备当前无运行中的任务关联
  3. 更新 devices.lab_id = 目标实验室 id
  4. 记录调拨日志（logs 表，category=device_transfer）
  5. 前端重新拉取设备列表（复用 GET /api/v1/test-devices）即可获取最新归属
  6. SPL 映射需在目标实验室重新标定（spl_mappings 按 device_id + lab_id 查询）
```

> **刷新机制**：系统已有完整的设备扫描和列表查询能力（`POST /scan`、`GET /devices`、`GET /playback-devices`、`GET /spl-mappings`），设备调拨后前端重新拉取即可，无需新增刷新接口。

### 6.5 任务分发规则

| 任务类型 | 分发策略 | 原因 |
|------|------|------|
| E2E 测试 | 按 lab_id 分发到对应实验室的 E2E Test Service，多实验室并行执行 | 需要物理设备，必须本地执行 |
| API 测试 | 集中执行，实验室选择仅用于筛选用例范围 | 不需要物理设备，只调第三方 API |

## 7. 与服务拆分的兼容性

### 7.1 当前服务拆分架构

```
┌─────────────────────────────────────────────────────────────────┐
│                      API Gateway (5000)                          │
│            (HTTP 路由、认证、WebSocket 代理、实验室管理)           │
└──────────────────────────────────┬──────────────────────────────┘
                                   │
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
          ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
          │ Task Service │ │ API Test Svc │ │ API Adapter │
          │   (5001)     │ │   (5003)×N   │ │   (8000)     │
          └──────┬───────┘ └──────────────┘ └──────────────┘
                 │ gRPC
                 ▼
```

### 7.3 服务部署分类

| 服务 | 是否需要物理设备 | 部署策略 | 原因 |
|------|:---:|------|------|
| E2E Test Service | ✅ | **每个实验室部署** | 需要声卡、USB 设备、播放设备，物理强绑定 |
| API Gateway | ❌ | 集中部署 | 纯 HTTP 路由 |
| Task Service | ❌ | 集中部署 | 纯调度逻辑，按 lab_id 路由分发 |
| API Test Service | ❌ | 集中部署，可水平扩容 | 只调第三方 API，与实验室无关 |
| API Adapter Service | ❌ | 集中部署 | 算法适配转发 |
| PostgreSQL/Redis/MinIO | ❌ | 集中部署，共享 | 基础设施 |

### 7.4 兼容性结论

| 特性 | 兼容性 | 说明 |
|------|--------|------|
| 实验室模型 | ✅ | 纯数据模型，与服务拆分正交 |
| 资源归属 | ✅ | API Gateway 统一管理资源关系 |
| 任务分发 | ✅ | Task Service 按 lab_id 分发到对应实验室的 E2E Test Service |
| E2E 并行执行 | ✅ | 多实验室的 E2E 任务并行执行，Task Service 汇总进度 |
| API 测试集中执行 | ✅ | API 测试不依赖实验室，实验室选择仅用于筛选用例 |
| 独立扩缩容 | ✅ | 繁忙实验室可增加 E2E Test Service 实例 |
| 故障隔离 | ✅ | 某实验室故障不影响其他实验室 |
| S3 对象存储 | ✅ | 各实验室共享存储，音频/报告统一管理 |

## 8. 部署说明

### 8.1 单体部署（当前）

所有服务部署在同一台服务器，实验室通过 `lab_id` 字段区分。
本地存储用于音频、报告、日志文件。
单实例 E2E Test Service 通过 `LAB_ID` 环境变量标识所属实验室。

### 8.2 分布式部署（未来）

**集中区**部署 API Gateway + Task Service + API Test Service + API Adapter Service + 基础设施。
**每个实验室**部署独立的 E2E Test Service，共享 S3 对象存储。

```yaml
# docker-compose.lab.yml 示例（实验室侧部署文件）
# 每个实验室部署一个 E2E Test Service 实例
services:
  e2e_test_service:
    image: ${REGISTRY}/e2e_test_service:latest
    environment:
      - LAB_ID=1                    # 对应 laboratories 表 id
      - LAB_CODE=LAB-A-01
      - TASK_SERVICE_HOST=task_service  # 集中区地址
      - TASK_SERVICE_GRPC_PORT=50061
      - STORAGE_TYPE=s3
      - S3_ENDPOINT=minio:9000      # 共享对象存储
    devices:
      - /dev/snd:/dev/snd          # 声卡
      - /dev/bus/usb:/dev/bus/usb   # USB 设备
    network_mode: host              # 或 bridge + 暴露 gRPC 端口
    ports:
      - "5002:5002"
      - "50051:50051"

# 集中区 docker-compose.yml 示例
services:
  api_gateway:
    image: ${REGISTRY}/api_gateway:latest
    ports:
      - "5000:5000"
    environment:
      - TASK_SERVICE_HOST=task_service
      - STORAGE_TYPE=s3
      - S3_ENDPOINT=minio:9000

  task_service:
    image: ${REGISTRY}/task_service:latest
    ports:
      - "5001:5001"
      - "50061:50061"
    environment:
      - E2E_TEST_SERVICE_HOST=lab_a_host  # 按实际实验室地址配置
      - E2E_TEST_SERVICE_GRPC_PORT=50051

  minio:
    image: minio/minio:latest
    ports:
      - "9000:9000"
    environment:
      MINIO_ROOT_USER: minioadmin
      MINIO_ROOT_PASSWORD: minioadmin
    volumes:
      - minio_data:/data

volumes:
  minio_data:
```

# 实验室扩展功能设计文档

## 1. 背景与目标

### 1.1 问题背景

当前系统存在以下问题：
- 设备、播放设备、用例等资源缺乏物理位置管理
- 无法支持跨实验室的测试任务执行
- 设备和资源无法按地理位置分组管理

### 1.2 扩展目标

1. **实验室管理**：支持多个物理实验室的创建和管理
2. **资源归属**：设备、播放设备、用例归属到特定实验室
3. **任务多实验室支持**：一个任务可以在多个实验室执行
4. **流程隔离**：通过实验室选择过滤后续可选资源
5. **服务拆分兼容**：设计与服务拆分架构完全兼容

## 2. 业务流程设计

### 2.1 当前流程（5步骤）

```
选择算法 → 选择用例 → 选择设备 → 选择播放设备 → 确认测试
```

### 2.2 扩展后流程（6步骤）

```
选择算法 → 选择实验室 → 选择用例 → 选择设备 → 选择播放设备 → 确认测试
       ↑ 可多选                    ↑ 按实验室过滤
```

### 2.3 流程说明

| 步骤 | 操作 | 业务规则 |
|------|------|----------|
| Step 1 | 选择算法 | 不变，根据算法过滤用例 |
| Step 2 | **选择实验室** | **可多选**，定义任务执行范围 |
| Step 3 | 选择用例 | **仅显示**属于已选实验室的用例 |
| Step 4 | 选择设备 | **仅显示**属于已选实验室的设备 |
| Step 5 | 选择播放设备 | **仅显示**属于已选实验室的播放设备 |
| Step 6 | 确认测试 | 创建任务，关联实验室和资源 |

## 4. 数据库模型

### 4.1 实验室表（新增）

```sql
CREATE TABLE laboratories (
    id SERIAL PRIMARY KEY,
    code VARCHAR(50) UNIQUE NOT NULL COMMENT '实验室代码，如 LAB-A-01',
    name VARCHAR(100) NOT NULL COMMENT '实验室名称',
    building VARCHAR(50) COMMENT '所在楼栋',
    floor VARCHAR(20) COMMENT '所在楼层',
    room_number VARCHAR(50) COMMENT '房间号',
    description TEXT COMMENT '实验室描述',
    status VARCHAR(20) DEFAULT 'active' COMMENT '状态 (active/inactive/maintenance)',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_laboratories_code ON laboratories(code);
CREATE INDEX idx_laboratories_status ON laboratories(status);
```

```sql
ALTER TABLE devices ADD COLUMN lab_id INTEGER REFERENCES laboratories(id);
```

```sql
CREATE TABLE task_laboratory_relations (
    id SERIAL PRIMARY KEY,
    task_id INTEGER NOT NULL REFERENCES test_tasks(id) ON DELETE CASCADE,
    lab_id INTEGER NOT NULL REFERENCES laboratories(id),
    priority INTEGER DEFAULT 1 COMMENT '实验室优先级，1最高',

    UNIQUE(task_id, lab_id)

CREATE INDEX idx_task_lab_task ON task_laboratory_relations(task_id);
CREATE INDEX idx_task_lab_lab ON task_laboratory_relations(lab_id);
```

## 6. 业务规则

### 6.1 归属规则

| 关系 | 基数 | 说明 |
|------|------|------|
| 实验室 → 设备 | 1:N | 一个设备只属于一个实验室 |
| 实验室 → 播放设备 | 1:N | 一个播放设备只属于一个实验室 |
| 实验室 → 用例 | 1:N | 一个用例只属于一个实验室 |
| 任务 → 实验室 | N:M | 一个任务可以在多个实验室执行 |

### 6.2 过滤规则

创建任务时，后续步骤的可选范围根据前一步的选择动态过滤：

```
Step 2 选择实验室 [1, 2] 后：

Step 3 用例列表 = 用例 WHERE (config->>'lab_id' IS NULL) OR ((config->>'lab_id')::bigint = ANY(:lab_ids))
        （含通用用例口径：config JSONB 无 lab_id 的用例不受实验室约束，任意实验室下可选；
         有值则须属于已选集合。—— 实现演进裁定 2026-10-16，替代原「用例 WHERE lab_id IN [1, 2]」，
         因 test_cases 不加 lab_id 列，归属存 config JSONB，见 §4.4。排除通用用例会让存量用例
         （全部无 lab_id）在选择实验室后全部不可见，破坏开始测试主链路）
Step 4 设备列表 = 设备 WHERE lab_id IN [1, 2]
        （严格过滤，未绑定实验室的设备在选择实验室后不可见）
Step 5 播放设备列表 = 播放设备 WHERE lab_id IN [1, 2]
        （严格过滤，未绑定实验室的播放设备在选择实验室后不可见）
```

### 6.3 校验规则

创建任务时，后端必须校验：

1. **用例归属**：所有 case_ids 必须属于 lab_ids 中的某个实验室——**含通用用例**
   （config JSONB 无 lab_id 的用例不受实验室约束，任意实验室下合法；实现演进裁定 2026-10-16）
2. **设备归属**：所有 device_ids 必须属于 lab_ids 中的某个实验室（未绑定实验室 = 非法）
3. **播放设备归属**：所有 playback_device_ids 必须属于 lab_ids 中的某个实验室
   （`playback_device_ids` 可选：有值时校验，无值跳过）

### 6.4 设备占用状态（occupied_status）

> 实现演进裁定（2026-10-16，INT-493 前向评审 §4.3 口径②）。

设备列表/详情 DTO 透出 `occupied_status`（`null` / `occupied` / `testing`，枚举化，
`shared.models.common_enums.DeviceOccupancyStatus`）与 `occupied_task_id`（可选，来源任务 ID），
供前端「测试中」徽章/动画与被占用设备禁用选择。

- **数据源**：`task_case_relations` 活动行（`execution_status IN ('pending','queued','running')`），
  **只统计 `device_type='physical'` 的行**（http_api / websocket_api 排除）。
- **状态判定**（同一物理设备同一时刻仅一个用例执行，执行期 DistributedLock
  `lock:task:physical:{device_id}` 保证聚合 1:1）：
  - 存在 `execution_status='running'` 活动行 → `testing`（测试中）
  - 否则存在 `pending` / `queued` 活动行 → `occupied`（已占用/排队中）
  - 均无活动行 → 无占用（`occupied_status=null`）
- **聚合路径**：`task_case_relations` 归 task_service 域 → task_service 新增
  `TaskDataService.GetDeviceOccupancy` RPC（入参可选 `device_ids` / `lab_id` 过滤，
  出参 `{device_id: {occupied_status, task_id, case_id}}`）；api_gateway 组装设备
  列表/详情时经 gRPC 注入，RPC 失败降级为空映射（占用字段保持 null，可选注入不阻塞）。

## 8. 部署说明

### 8.1 单体部署（当前）

所有服务部署在同一台服务器，实验室通过 `lab_id` 字段区分。
本地存储用于音频、报告、日志文件。

## 0. 口径变更说明（为什么重做）

INT-360 v1.0 把报告查看页按 newAPI **模型价格页阅读版式**出稿（报告头 + 指标卡 + 维度×资源矩阵 + VChart 图表 + 具体用例[音频/ASR/翻译/指标/日志]），**未反映报告的真实层级**：任务报告的实际载体是 `TaskReportPanel` 的分区结构（总览 → 设备/API 双资源统计 → 分析结论 → 对比表格 → 分组/标签对比 → 具体用例），用例明细的实际载体是 `TestCaseReportDetail` 的**七块复杂卡片**，标签/分组对比实际带**正态分布图**（前端自算均值/标准差/正态曲线），图表引擎实际是 **Chart.js v4 + zoom**（分布图依赖 zoom/pan 重分箱，VChart 无法等价）。负责人 2026-10-15 据此裁定重做，本稿全部按 V9.7.10 + V9.7.31 真实源码落位。

**核心层级关系（拍板）**：

```
任务（report.task_name / algorithm_type）
 └─ 资源（summary.resources / resource_headers —— 设备 device_stats + API api_stats 双维度）
     └─ 结果（每资源下多个结果：轮次级[多轮对话 rounds] / 多结果级[results 数组] / 原始值集合 raw_data）
         └─ 评估维度（all_metrics 主维度 main + 子维度 sub，parent_dimension_name 归组）
             └─ 维度值（metric_data 均值 / tag_metric_data / case_type_stats / raw_data 原始值集合）
用例（case：带分组 category + 标签 tags，标签带分类 tag.category_id/category_name）
 └─ 多资源 × 多结果 × 多维度 × 多值（case.metrics / case.results / case.algorithm_results / case.reference_params / case.audios）
```

列表页（报告中心管理页）不涉及该层级、INT-360 版式正确，**保留**（§2）；展示页（导航栏「报告」）按 INT-441 双入口拆分裁剪（§2.1）；重做聚焦**报告查看页**（§3~§3.7）。

### 1.3 用例级数据 `GET/POST /reports/{report_id}/cases/search`（build_case_item 实测）

用例项字段（前端用例卡片的全部数据来源）：

| 字段 | 形态 |
| --- | --- |

| `category` / `tags` | 分组名 / 标签数组（标签可带分类） |
| `metrics` | `{resource:{dimension:value}}` 或 `[{resource, metrics:[{id,metric,value}]}]`（按算法类型区分） |

用例级搜索请求（ReportSearchCasesRequest 全参）：`keyword / category / categories / include_untagged / tags / metrics / sort_by(name|category|createdat|metric) / sort_metric / sort_resource / sort_order / page / per_page`——服务端过滤+排序+分页（cases_mixin.py 实测）。`per_page` 后端 schema 默认 **20**（`api_gateway/schemas/report.py:333-334`），无上限校验；前端传多少就是多少（现前端传 10，导出态传 10000，`use-report-cases.ts:42` 实测）。

> **行粒度（INT-1724 返修复核，真实库实测）**：`report_cases` **一行 = 一个用例 × 一个资源**——该行 `results` 恰好 **1 条**（`[{status, resource, start_time, end_time}]`），`metrics` 也只含该 `resource` 的键。报告 395 实测 **793 行 / 406 个去重用例**（同一 `test_case_id` 在 `9-pura90小艺-1.0.0` 与 `10-pura90豆包-1.0.0` 各占一行），搜索接口 `total` 即**结果行数**（`_report_cases_query_mixin.py:89-91` 实测）。**所以「一个用例项已自带全部资源结果」不成立**：用例视图必须先按 `test_case_id` 合并，且合并时 `results/metrics/algorithmResults/audios/logs` 要**按资源取并集**（§3.3.7）。
>
> **轮次后缀（同批复核）**：`metrics[].metric` 形如 `接管率占比@overall` / `接管率占比@round:2`——`@overall` = 跨轮整体、`@round:N` = 第 N 轮，是**轮次标记而不是评估维度**；去掉后缀即基础维度名。真实库报告 383 单行 **91 个指标键** = 36 个基础维度 × 轮次标签展开（7 轮 + 整体），而配置维度 `all_metrics` 只有 27 条；报告 395 单行 90 键 / 基础维度 22 个 / `all_metrics` 21 条。
>
> **result_type 现状（同批复核）**：`resource_headers[].result_type` 字段在报告 579 等新数据里已出现但**恒为 null**；`report_cases.results[].result_type` **0 条**；全库 206 份报告 `resource_headers` 中**非空 result_type 为 0 份**、资源键**无一例带 `-{result_type}` 后缀**（全部为 `默认`）。结果类型当前只能按资源键后缀解析（§3.3.7 / §10-10）。
>
> **对比报告的资源键带任务前缀（同批复核）**：对比报告家族的资源键形如 `t390-202609221023-9-pura90小艺-1.0.0`（`use_time_prefix`，报告 579 实测），同一设备在不同任务下是**两个独立资源头**（`id` 同为 9、`key` 不同）——设备视图第 1 层会出两个同名节点，需按 `key` 区分（§3.3.7）。

**数据口径（服务端分页 + 三视图，不新增后端）**
- **现状**：`POST /reports/{id}/cases/search` 只按**用例行**分页（后端 schema `per_page` 默认 **20**、无上限，`api_gateway/schemas/report.py:333-334`；前端现传 10，`use-report-cases.ts:42`），且**不支持按设备 / result_type 过滤**（请求契约 `keyword/category/categories/include_untagged/tags/metrics/sort_by/sort_metric/sort_resource/sort_order/page/per_page`，`cases_mixin.py` 实测无资源 / 结果类型参数）。接口 `total` = **结果行数**（§1.3）。
- **口径（定死）**：
  1. **用例视图**：保持服务端分页，前端 `per_page` 由 10 调整为 **20**（后端 schema 默认同为 20）——理由：本节按 `test_case_id` 合并后每页卡片数约减半，回调分页大小是为了维持「每页约 10 张卡」的现状观感；请求方式（服务端过滤 + 排序 + 分页）不变。
  2. **设备视图 / 结果类型视图**：**切换视图时改发同一筛选条件、`page=1, per_page=10000` 的全量查询**（取值与现前端导出态同值，`use-report-cases.ts:42` 实测 `exporting ? 10000 : 10`；后端 `per_page` 无上限，**不新增端点、不改后端契约**），拿全量结果做**客户端聚合**；视图内不出服务端分页，改「节点内用例卡默认 10 张 + 加载更多（剩余 {n}）」，底部显示「共 {d} 个设备 · {r} 个结果类型 · {m} 个用例」。
  3. **跨页 / 上限提示**：若响应 `total > 10000`，视图顶部出提示条「当前筛选命中 {total} 条，聚合仅覆盖前 10000 条，请先缩小筛选条件」+「返回用例视图」入口；**不做静默截断**。（真实库最大报告 395 = **793 行 / 406 用例**，10000 足够；此为防御口径。）
  4. **用例视图**内同一用例跨设备的多行合并**只在当前页内合并**（服务端分页边界外不合并，与 INT-1125「组织作用于当前页已加载用例集、跨页不合并」同一口径）；**设备 / 结果类型视图因取全量，天然跨页完整**。
  5. **计数口径**（与分区 Badge 配套）：用例视图 Badge = 接口 `total`（结果行口径）；设备 / 结果类型视图 Badge = 全量去重用例数；三视图内的组头 / 节点计数一律 = **当前集合内的去重用例数**。
- **与筛选卡（§3.3.8）的交互**：名称 / 分组 / 标签 / 评估维度 / 排序筛选**全部照旧走服务端**（三视图共用同一 `filters`，任一变化 → 300ms debounce 或「应用筛选」→ 按当前视图重取数）；**不新增资源 / 结果类型筛选 facet**（设备视图第 1 层、结果类型视图第 1 层本身即资源 / 结果类型的分层浏览，不重复做筛选控件）；「重置」清空三视图共享筛选并回到用例视图第 1 页。
- **固定 / 排序**：固定按用例 ID（跨视图、跨资源行共享，固定区在列表上方不变）；排序在设备 / 结果类型视图内只影响**节点内用例卡顺序**，不影响节点顺序（节点按名称稳定排序）。

**先厘清「维度」与「轮次」（负责人 04:25Z 口径）**

- `metrics[].metric` 的 `@overall` / `@round:N` 后缀是**轮次标记**：`@overall` = 跨轮整体、`@round:N` = 第 N 轮——V9.7.10 `TestCaseReportDetail.vue` 的 `roundTabs` 就是按这两个后缀生成「整体 / 第 N 轮」Tab（`parseMetricKey` / `formatMetricLabel` 实测），**它们不是评估维度**。
- 真实数据：报告 383 单行 **91 个指标键** = 36 个基础维度 × 轮次标签展开（7 轮 + 整体），而配置维度 `all_metrics` 只有 27 条；报告 395 单行 90 键 / 基础维度 22 个 / `all_metrics` 21 条（§1.3）。**「91 个键」不等于「91 个维度」**——评估维度选择器只列**去掉轮次后缀的基础维度**，轮次由「轮次」Section 单独控制。
- 「维度」的痛点仍然成立：即使只有 21~27 个基础维度，叠加主/子层级、详细日志、音频、时间轴后单卡依然很长。故仍采用**块级 + 维度两级收口**（方式二，推荐；「只收口指标维度」作对照保留）：

| --- | --- | --- |
| 方式一：只收口指标维度 | 工具栏加「评估维度」多选，只控制评分指标行与评估结果字段。 | 语义最窄；详细日志 / 音频 / 时间轴仍全显，卡片依旧很长。 |
| **方式二：块级 + 维度两级收口（推荐）** | 一个「显示设置」入口：一级开关**内容块**，二级选择**块内维度**（评估维度 / 轮次 / 资源 / 结果类型）。 | 一次解决两类噪声，入口只有一个按钮；勾选墙用**折叠 Section** 压平，不做全量勾选墙。 |

### 3.6 分组/标签/分类对比 + 正态分布统计图（负责人新加标签分类）

> 覆盖要求：CaseTagComparison（按用例标签对比）+ CaseCategoryComparison（按用例分类对比）+ **正态分布统计图**（displayType='distribution'，前端用原始值集合自行计算分布）。机制已在 §3.3.5/§3.3.6 落位，本节约束共性：

- **显示类型切换器**（`useDisplayTypes` 实测，两对比组件共用）：`表格 / 柱状图 / 折线图 / 雷达图 / 正态分布图`（默认表格）；每个评估维度一个 `.metric-container`（标题「{metric.name} 对比（单位：{metric.unit}）」+ 类型切换器 + 折叠）。
- **正态分布图数据装配**（`generateDistributionChartData` 实测，shared/useReportShared.ts:232）：
  - 原始值来源：矩阵中每 `(分组|标签, 设备)` 的 `{metric}_raw` 数组（后端 `raw_data` 直传，或前端从 `dimensionScores`/`metrics` 每次得分累积）——`deviceRawDataMap[device]` 收集 + `allRawData` 汇总，过滤非数字，`seenArrays` 去重同数组引用。
  - 计算：`calculateNormalDistribution` → `mean=Σ/n`、`variance=Σ(x-mean)²/n`、`stdDev=√variance`；`step=stdDev/8`、`min=mean-32*step`（无负数则 0）、`max=mean+32*step`、`intervals=round((max-min)/step)`；每设备区间直方图 `{x: 区间中点, y: count}`（末区间含右端点），`_step` 存步长。
  - 返回 `{labels, datasets, rawData, deviceRawData(按资源 label 键)}` → 交给 ChartComponent（§3.7）。
- **统计卡**（ChartStatsCard 对位，§3.7）：样本数量 / 平均值 (μ) / 标准差 (σ) / 最小值 / 下四分位数 (Q1) / 中位数 (Q2) / 上四分位数 (Q3) / 最大值 + **正方向区间**（`[0,μ) / (μ,μ+σ] / (μ+σ,μ+2σ] / (μ+2σ,μ+3σ] / 超出+(μ+3σ)` 百分比）+ **负方向区间**（有负值时：`[-μ,0) / [-(μ+σ),-μ) / … / 超出-(μ+3σ)` 百分比）；设备 Tab 按 `distributionStatsByDevice` 切换。
- **编辑持久化**（两对比组件实测）：表头/单元格点击重命名（分组名/标签名/资源 label）→ 同步 `summary.caseCategories` / `summary.allCaseTags` / `summary.resourceHeaders` → `scheduleSaveSummary` 200ms 防抖 → `PUT /reports/{id}`。
- **标签分类**（负责人新加）：`all_case_tags` 项含 `category_id/category_name`（schema `ReportTagMetricTagGroup:34` / `ReportTagCategoryMetric:47` 实测）——标签筛选器按分类分组展示（分类组头 + 组内标签），标签对比矩阵行仍按单标签独立均值；分类维度同时由 `case_categories`（分组）对比承载。

### 3.7 图表（ChartComponent 全类型）

> **引擎裁定**：按 INT-439 口径改用现前端同款 **Chart.js v4 + chartjs-plugin-zoom**（`frontend/src/chart/` 实测；INT-360 的 VChart 在本域废止——分布图依赖 zoom/pan 重分箱 + 统计卡，VChart 无法等价）。深浅色/多主题走语义 token（`--chart-1..5` 随预设联动，chart.js 用等价 hex 常量 `chartConfig.colors`，与 `tokens.css` 保持映射）。

- **ChartComponent props**（实测）：`title / data(labels+datasets) / type(bar|line|pie|doughnut|radar|polarArea|distribution|scatter|heatmap) / options / showHeader / showFooter / showActions / loading / stats / height(默认500) / enableZoom(默认true)`；emits `chartReady / export`。
- **图表类型**（全类型支持）：
  - `bar` 条形/对比柱：`getChartData` 分组/标签×资源柱状，`backgroundColor` chart 色 + alpha `'B3'`、`borderRadius:4`。
  - `line` 折线：`tension:0.3`、`fill:false`，通过率/指标趋势。
  - `distribution` 正态分布图：标题「正态分布分析」、x 轴「不同区间的{title}」（linear）、y 轴「区间内用例数量」（stepSize:1）、tooltip 显 `[start, end)` 区间 +「N 个」；**折线图/直方图切换**（`chartSubType`，distribution 模式以子类型渲染）；**zoom/pan 后重分箱**（`rebinDistributionData`：固定 20 区间按可见范围重计 → 更新 datasets + 固定 x min/max）；**resetZoom 恢复原始数据**。
  - `radar` 雷达（多资源 series，值归一化百分比）/ `pie` / `doughnut` / `polarArea`（图例右置、无缩放）。
  - `scatter` 散点图：**两个变量关系**（如 指标值×执行时长、通过率×延迟），`showLine:false` 点图 + tooltip 双变量；`heatmap` 热力图：**密度分布**（如 设备×评估维度 值矩阵、时间×设备类型 分布），canvas 网格 + 色阶 `--chart-1..5` alpha 分级（报告管理功能设计文档.md:346-351 实测）。
- **ChartStatsCard 对位**（distribution 时）：标题「统计信息」+ 设备 Tab + 基础统计前 8 项 +「正方向区间：」+「负方向区间：」（§3.6）。
- **ChartActions 对位**：重置缩放 / **图表导出 图片·SVG·PDF**（报告管理功能设计文档.md:359-362 实测）——PNG 走 `toBase64Image` → `{title}.png` 下载 + emit `export`；SVG/PDF 走序列化/打印导出（实施卡按 chart.js v4 生态确认插件选型）。
- **缩放交互**：wheel/drag/pinch 缩放（mode 随鼠标位置 x/xy 切换）+ pan，`enableZoom=false` 时禁用。
- **空态**：「暂无数据」；**加载**：「图表加载中...」；数据源：分组/标签对比矩阵（§3.3.5/3.3.6）与任务级统计（device_stats.success_rate 折线、metric_data 柱状/雷达）。

## 10. 待负责人确认 / 现状缺陷（建议后端或实施卡立项）

> 全部为本卡逐端点/逐文件实测发现的真实缺口，设计稿按「不虚构、不隐藏问题」标注。

1. **report 三端点无路由级权限装饰器**：`report_bp.py` 的 `secondary_compare`（:87）、`search_report_cases`（:117）、`download_case_logs`（:122）未挂 `require_permission`——与 seed 的 `report:compare/report:read/report:download_log` 语义不对齐；RBAC 矩阵按权限码出，建议后端补装饰器。
2. **导出 format 服务端能力**：`POST /reports/export` 支持 csv/excel/pdf/html（schema 实测），实施卡确认各 format 响应（pdf 可用性、csv 批量语义）。
3. **`summary.tables` 烘焙缺口**：任务级对比表格数组（§3.3.4）由 `report.summary.tables` 驱动（V9.7.31 ReportView `report.value?.summary?.tables || []` 实测）；若后端报告生成未烘焙该字段，前端需从 `metric_data/device_stats/api_stats` 装配兜底对比表——实施卡确认。
4. **AI 增强搁置**：`test_reports` 无 `ai_summary/ai_anomalies/ai_trend` 字段，`POST /reports/{id}/qa` 无实现——分析结论按纯文本编辑设计，AI 摘要/异常面板/趋势预测不引入（INT-360 §10-3 口径保留）。
5. **报告列表全局算法联动**：现状前端为独立算法筛选，本卡按 INT-344 收敛为联动 chip（§2），`ReportListQuery.algorithm_type` 已支持。
6. **正态分布图原始值依赖 `raw_data`**：分布图均值/标准差由前端从矩阵 `_raw` 原始值集合计算（§3.6），依赖后端 `raw_data` 输出 `values[]`（flatten_raw_data 实测已支持）；无 `_raw` 的历史报告分布图退化空态「暂无数据」，实施卡标注。
7. **分组/标签重命名持久化字段**：`scheduleSaveSummary` 写 `PUT /reports/{id}` 的 `summary.caseCategories/allCaseTags/allTags/resourceHeaders`（schema `ReportUpdateSummaryField` 实测在册），编辑冲突（多人并发）由实施卡确认覆盖语义。
8. **图表引擎迁移裁定**：INT-360 定 VChart 与现前端 Chart.js 冲突；本卡按 INT-439 口径改 Chart.js v4 + zoom（分布图 zoom/pan 重分箱 + ChartStatsCard 统计卡 VChart 无法等价）——**本卡裁定覆盖 INT-360 §4.5/§10-9**，实施卡按 Chart.js 出。
9. **日志文件列表端点缺（INT-1055；INT-1114 补传输层裁定）**：`GET /reports/{id}/cases/{caseId}/logs/download` 现为整包 logs.zip（无文件列表/多选/单文件大小）。文件选择 Dialog（§4.10a）需日志文件列表端点——**契约建议**：`GET /reports/{report_id}/cases/{case_id}/logs` → `{ items: [{ name, size_bytes, updated_at? }] }`；**项内可选增 `url`**（OSS 预签名直链；本地降级为网关字节流回退 URL；有效期如 1h；权限 `report:download_log` 在发链时校验）——字段可选，**`size_bytes` 必在**（支撑大文件软守卫，§4.10a）；下载端点扩展 `?files=[name...]`（缺省全部）打包 zip。**传输层裁定（INT-1056 审计评论 01a15bc5，2026-10-21）**：大日志下载走 **OSS 预签名 URL**（浏览器直连 MinIO 流式下载，绕开网关内存拼 zip + base64 整包回传 + gRPC 默认 4MB 消息上限瓶颈——该上限即「大日志下不了」根因）；**不再把整包 base64 过 gRPC**；本地降级走网关字节流回退（testcase 预览音频 INT-146 `GET /audios/download` 先例）。超大场景服务端打包后**上抛 OSS 临时桶再给预签名 URL**，或网关改 `StreamingResponse` 流式回传（实施二选一），**后端传输层改造挂主项目【FEAT】**；业务日志 / 虚拟文件（`adjusted_reference_params.json`）不在 OSS：先上抛临时桶或归入网关字节流回退。Windows/Linux 共享（SMB/NFS）❌ 不建议。开【FEAT】卡挂主项目；落地前前端留桩示例列表（文件名/大小），实施卡等 FEAT done 再接线。Vue 侧同步（19 §9）。

10. **【FEAT 建议】用例结果的 result_type 未随接口下发（INT-1724 实测）**：`build_result_info` 只回 `{status, start_time, end_time}`（`report_service/application/services/report_helpers.py:339-343` 实测），`ReportResourceHeader`（`api_gateway/schemas/report.py:131-138`）也无 `result_type`；结果类型当前**只隐含在资源键后缀**（`ReportUtils.get_resource_name`：`-{result_type}`，default 不加后缀，`report_service/application/services/report_utils/resource_mixin.py:70-110` 实测；`_get_result_types_from_results` 每个设备只保留**一个** result_type，`report_aggregation/resource_mixin.py:164-200`）。**返修复核的真实库量化（2026-10-24）**：206 份报告 `resource_headers` 中非空 `result_type` **0 份**（579 等新数据里字段已出现但恒为 null）、`report_cases.results` 中 `result_type` **0 条**、资源键**无一例**带 `-{result_type}` 后缀——**现网所有报告都只有「默认」结果类型**，正是负责人要求「只有默认结果类型就不显示结果类型视图按钮」的直接依据（§3.3.7）。**本设计不依赖新字段**：解析顺序 = ① `resource_headers[].result_type`（非空即用）→ ② 资源键去掉 `-{version}` 之后的尾巴（如 `…-1.0.0-recording` → `recording`）→ ③ 「默认」；白名单 `realtime/final/recording/default` 只用于中文映射（`resultTypeLabel`），未知值原样 mono 显示。**FEAT 契约建议**：`results[].result_type` + `resource_headers[].result_type` 直接下发，结果类型视图即可免解析；立项与否由 UX规划师拆卡时定，**不阻断本设计**。
11. **执行状态枚举与时间字段未归一（INT-1724 实测的现状缺陷，实施卡修）**：真实库 `report_cases.results` 实测 `{"status":"成功","resource":"9-pura90小艺-1.0.0","start_time":"2026-09-28T12:45:58.371573","end_time":"2026-09-28T12:45:58.371573"}`；而 `reports-api.ts:604-632` 的 `toReportCaseItem` 对 `results` 是**原样透传**（`rec.results as ReportCaseResult[]`）——① `resourceStatus()`/`overallStatusOf()`（`specific-case-comparison.tsx:849-877`）只认 `completed/failed/warning/skipped`，遇真实枚举 `成功/失败` 一律落到 `unknown`／`pass`（**失败用例会被算成通过、状态点恒灰**）；② `startTime/endTime` 因 snake_case 未转而恒 `undefined`（`execution-results.tsx:464` 永不显示执行时间）。**实施卡口径**：在唯一转换层（`infrastructure/api/reports-api.ts` 的 `toReportCaseItem` 或 `adapters/reportAdapter.ts`）把 `start_time/end_time` 转 `startTime/endTime`、`result_type` 转 `resultType`；状态按后端真实枚举（`成功/失败`，及可能的 `跳过/执行中`）映射语义色与文案，前端不再假设 `completed/failed`；叶表「执行状态 / 执行时间」两列（§3.3.7）以此为准。
12. **【FEAT 建议】评估维度分类与标签分类未随报告快照下发（INT-1724 返修复核）**：`all_metrics` 只带 `dimension_type / parent_dimension_id / parent_dimension_name`（`report_data_builder_resource_mixin.py:168-199` 实测），**无 `category_id / category_name`**；而维度本身有分类（`dimensions.category_id`，真实库 63 个维度中 40 个有分类；`categories` 表实测有 `话轮接管 / 打断 / 拒识 / 环境理解` 等）。同理 `all_case_tags` 只存 `{id,name}`（`report_query_builder.py:246-256` 实测），不带标签分类（`tag_categories` 表有分类，报告快照未带）。**FEAT 契约建议（不新增端点、不改 schema——`all_metrics` 是 `List[Any]`）**：evaluation `_serialize_dimension` 增 `category_name`（join `categories`）→ report `_build_all_metrics` 透传 `category_id / category_name`；`all_case_tags` 同理补 `category_id / category_name`。落地后 §3.3.7 / §3.5.10 的三级 / 两级分组直接用快照，不再依赖权限补映射。**不阻断本设计**：无字段时按「未分类」兜底，持 `evaluation:read` / `tag:read` 的用户走现有字典接口补映射（§3.5.10 分类归属阶梯）。

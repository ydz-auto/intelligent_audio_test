### 1.2 AI 复核（INT-800 后端已落地；前端一次性状态机 + 未接灵犀Agent）

- 后端**端点与数据模型已落地**（FEAT INT-800 done / 表 ai_reviews INT-821 done，实测 `review_bp.py` + `schemas/ai_review.py`）：`POST /tasks/results/ai-review`（`{result_ids:[int]≥1, dimension_ids?, force?}`，权限 `task.result.ai_review`）、`GET /tasks/results/{task_id}/ai-review-history`（Query result_id/dimension_id/status，`task:read`）、`POST /tasks/results/ai-review/{id}/adopt`（`{execution_status?, evaluation_status?, comment 必填}`，`task.result.review`）、`POST /tasks/results/ai-review/{id}/reject`（`task.result.ai_review`）；`ai_reviews` 表字段 = id/result_id/task_id/test_case_id/dimension_id/status(running|completed|failed)/verdict(passed|failed|uncertain)?/confidence?/reasoning?/adopted/adopted_at/rejected/rejected_at/created_at/updated_at。
- 前端现状：一次性状态机弹窗已实现（`features/tasks/components/ai-review-dialog.tsx` + `features/report-view/components/review/ai-review-dialog.tsx`，§5 旧稿落位）但 `infrastructure/api/reviewApi.ts` / Vue `reviewAiApi.ts` 仍为**会话级内存桩 `// 待接线`**；**未接灵犀Agent、不可追问**（负责人 2026-10-20 实测反馈）。
- 可复用能力：灵犀Agent 对话（08_AI对话页.md：整页 `/ai-chat` + 全局浮窗 `agent-workbench.tsx` 同一套会话，共享 localStorage `iatp:ai-chat:v1:*`，对话走用户自配 LLM 供应商 `/chat/completions`）；评估维度 `resultType='llm_judge'`（LLM Judge 维度，11_用例域 §5.5 实测）+ voice_llm 多轮 `evaluation.reasoning`（LLM 评语，15 报告域 §3.5.2 实测）作为复核输入上下文。
- 结论（INT-1055 裁定）：AI 复核 = **灵犀Agent 对话式复核（可追问）**（§5 重做），结论落位复用 ai_reviews 契约（§5.5），一次性状态机降级「快速复核」。

- **两机制边界**：人工审核 = 人直接改判（权威、落统计）；AI 复核 = 机器先判、人再确认（辅助决策，不直接改统计，采纳后才落）。
- **两处消费面统一**：任务执行详情与报告具体用例卡片共用同一复核数据模型与标记语义；报告为落库快照，其复核标记/统计在生成时快照（§4）。

### 2.1 状态定义（人工审核 + AI 复核全状态）

**人工审核（权威层，落统计）——「通过 / 驳回 + 原因」映射后端改判契约（实测 `schemas/review.py:16-25`）：**

| 人工处置 | 交互呈现（弹窗改判 UI） | 后端落位 |
| --- | --- | --- |
| **审核通过** | 用例执行状态 →「已完成」+ 用例评估状态 →「已完成」 | `POST /tasks/results/review`：`execution_status=completed`（评估 `evaluation_status=completed` 可选） |
| **审核驳回** | 用例执行状态 →「执行失败 / 已停止 / 已跳过」+ 评估状态 →「评估失败」 | `execution_status=failed|stopped|skipped`（+ `evaluation_status=failed`） |
| **原因（必填）** | 「复核备注」Textarea 必填*（`min_length=1` 实测），占位「填写改判依据或复核意见」 | `comment`（`schemas/review.py:25`） |

- **结果维度状态机**：`未复核 →（人工提交）→ 已复核（执行/评估状态按改判生效）→ 统计按复核后判定重算`；同一结果可多次复核，追加留痕不覆盖（`test_result_reviews` 追加行）。
- **呈现落位**：已复核结果在执行/评估徽章旁叠加「人工复核」Badge（Tooltip 含复核人/时间/改判前后）；任务详情用例行由 `TaskCaseBrief.reviewed`（INT-734 已回填）驱动 Badge 显隐，任务头复核计数由 `TaskDetailData.review_count` 驱动。

**AI 复核（建议层，不直接改统计）——状态机（§5 落位；INT-1055 对话式）：**

| 状态 | 定义 | 操作 / 反馈 |
| --- | --- | --- |
| **待发起** | 可发起对象 = 评估状态为已完成/评估失败、且该用例存在执行结果（LLM 判分或 voice_llm 评语）的结果 | 「AI 复核」入口（ghost，Sparkles，`task.result.ai_review`）；「快速复核」次要入口（一次性状态机，批量/低分初筛）；无执行结果/无权限隐藏 |
| **对话中（未落位）** | 灵犀Agent 复核会话已打开，预填复核上下文（§5.3），Agent 分析产出结论卡，用户多轮追问（§5.4） | 流式回复 + Reasoning；结论卡（复核通过/不通过/存疑 + 置信度 + 理由）；**未保存前不落 ai_reviews** |
| **已保存（执行中）** | 「保存复核结论」→ `POST /tasks/results/ai-review`，ai_reviews 记录 status=running（后端异步 LLM 复检链路） | 会话底栏进度条 + 轮询历史（§5.6）；失败 Alert +「重试」（force），不落任何判定 |
| **已完成** | ai_reviews 记录 status=completed，结论落位：**复核通过 / 复核不通过 / 存疑** + 置信度 + 理由 | AI 复核记录卡展示（§5.5）；同一结果重复发起 → 复用最近结论并提示「该用例已有 AI 复核结论（{时间}），可查看/重新复核」（幂等；重新复核 force=true） |
| **已采纳** | 人工采纳 AI 结论 → 落人工复核语义 | 打开 §3.2 复核弹窗预填 AI 判定的评估状态 + 备注（预填 AI 理由）→ 人工确认提交 → `test_result_reviews` 留痕 + 统计重算 |
| **已驳回** | 人工驳回 AI 结论 | `POST /ai-review/{id}/reject`，AI 记录标记「已驳回」备查；原判定不变 |
| **待查（忽略）** | 人工关闭暂不处理 | AI 结论保留待查（无新记录或记录不处置） |

## 5. AI 复核机制设计（灵犀Agent 对话式复核，INT-1055 重做）

> **INT-1055（2026-10-20 负责人实测反馈）重做**：AI 复核要用「灵犀Agent」、可以追问——本节由「一次性状态机 + 待立项契约」重构为「**灵犀Agent 对话式复核（可追问）**」。后端 AI 复核端点已落地（FEAT **INT-800 done**，表 `ai_reviews` INT-821 done，权限 `task.result.ai_review` 已注册 seed）——全部实测 `review_bp.py` + `schemas/ai_review.py`。本节落位后前端 `reviewApi.ts` / Vue `reviewAiApi.ts` 由 `// 待接线` 桩切换为真实请求（§5.7）。

### 5.1 定位与边界（更新）

- 定位：**评估结果的对话式复检助手**——用户针对疑似问题结果（低分、评估失败、断言不符、LLM 评语存疑）打开灵犀Agent 复核会话，Agent 基于预填的复核上下文独立分析并给出 AI 判定（**复核通过/不通过/存疑 + 置信度 + 理由**）；用户可**多轮追问**（为什么、哪个维度、对比设备…）直到理解，再决定是否将结论落位为 `ai_reviews` 记录。**不直接修改统计**；只有人工「采纳」才落入人工复核语义（改判评估状态 + 留痕 + 统计重算）。
- 与人工复核边界：AI 复核是**建议层**，人工复核是**权威层**；数据模型分表（`ai_reviews` / `test_result_reviews`）。
- 与 LLM Judge 维度边界：LLM Judge 是**评估维度**（执行时判分，产分数）；AI 复核是**事后复检**（对已有判定复核，产结论 + 置信度 + 理由）。AI 复核可复用 LLM Judge 的模型/Prompt 配置与 voice_llm 评语作为输入上下文。
- **与一次性状态机的关系（裁定，INT-1055）**：**对话式复核（灵犀Agent）为 AI 复核的正式主形态**，覆盖全部入口（报告具体用例卡片 / 任务执行详情用例执行结果 / 任务详情用例执行详情模态窗）；现有一次性状态机（发起→执行中→结论卡，不可追问）**降级为「快速复核」次要入口**，仅保留在批量/低分初筛等无需追问的快速复检场景（入口文案「快速复核」，ghost 次要钮）。两模式共用同一 `ai_reviews` 落位契约（§5.5）。
- 与灵犀Agent 主工作台（08 规范 §3.1B/§3.12）边界：复核会话是**任务/用例级有界会话**，复用同一会话引擎（LLM 供应商切换/消息渲染/流式）但**独立会话 scope**（§5.2），不污染全局主会话（`iatp:ai-chat:v1:messages`）；可一键「展开到 /ai-chat」带入主会话继续讨论（08 §3.7 URL 契约扩展）。

### 5.2 形态：AI 复核会话（内嵌灵犀Agent 复核工作台）

- **形态选择（裁定）**：AI 复核入口打开**内嵌 Dialog 形态的灵犀Agent 复核会话**（不复用全局浮窗）——复核需要预填专用上下文（§5.3）+ 结构化结论卡 + 与人工复核弹窗衔接（采纳→开 §3.2 弹窗）；全局浮窗为通用对话（无专用上下文），复用会造成上下文污染。两形态**同引擎不同 scope**：复用 08 规范会话组件（`AiChat`/`AiChatInput` compact 变体 + 模型/供应商切换器），复核会话数据独立（下方会话 scope）。
- **Dialog 版式**（照 08 §3.1B 浮窗会话区 compact 口径 + 10 §5.2 用例详情弹窗头）：

```
┌─ AI 复核 — {用例名}（Dialog sm:max-w-2xl，contentHeight='min(70dvh,640px)' 内滚）───┐
│ 头行：Sparkles +「AI 复核」+ Demo 徽标（对话走用户自配供应商时显）+「展开到 /ai-chat」│
│   （Maximize2）+ 关闭（X）；头行下 = 复核上下文摘要条（§5.3：设备×结果 Badge 组 + │
│   评估状态 + 低分维度 +「已有 AI 复核结论 {时间}」Badge）                            │
│ 会话区：消息流（复用 AiChat compact：user 右气泡 / assistant 左平铺文档面）         │
│   ├─ 首条 assistant = 复核上下文摘要卡（§5.3 结构化渲染）                           │
│   ├─ 用户消息/追问 → Agent 流式回复（Reasoning 思考过程 + 数据来源 + 正文）          │
│   └─ 最后一条 assistant 内嵌「AI 复核结论」结构化卡（§5.4）                          │
│ 输入区：复用 AiChatInput（模型/供应商切换 + 发送/停止 + 追问快捷 chips）             │
│ 底栏：［稍后处理］［保存复核结论］（→ POST /ai-review 落位，§5.5）                   │
└────────────────────────────────────────────────────────────────────────────────────┘
```

- **会话 scope（裁定）**：复核会话使用**独立于主会话的会话数据**——`features/ai-review/` 内局部 state 或独立 localStorage 键 `iatp:ai-chat:v1:review:{taskId}:{caseId}`，关闭 Dialog 即释放；**不写入全局 `iatp:ai-chat:v1:messages` 主会话**（复核是有界任务会话，避免污染用户主对话历史）。「展开到 /ai-chat」→ 把复核上下文 + 结论并入主会话并导航 `/ai-chat?reviewTask={id}&reviewCase={caseId}`（08 §3.7 契约）。
- **入口 → 打开**：报告具体用例卡片/具体用例行「AI 复核」钮、任务执行详情用例执行结果「AI 复核」钮、任务详情用例执行详情模态窗结果区「AI 复核」钮 → 打开本会话 Dialog（预填该用例复核上下文 §5.3）。
- **可发起对象**（不变）：评估状态为已完成/评估失败、且该用例存在执行结果（LLM 判分或 voice_llm 评语）的结果；无执行结果的用例不开放（现有口径保留，toast「该用例无执行结果，无法复核」）。

### 5.3 复核上下文预填（契约）

打开复核会话时前端聚合以下数据构造 `AiReviewContext`，作为系统提示 + 首条消息注入：

| 字段 | 数据源（实测） | 用途 |
| --- | --- | --- |
| 用例名 + CaseId + 分组/标签 | 用例简报 `TaskCaseBrief`（任务侧）/ 报告用例 `ReportCaseItem`（报告侧） | 复核对象标识 |
| 设备×结果列表 | `GET /tasks/{taskId}/cases/{caseId}/results`（`fetchCaseResults` 已有：result_id + 设备/API 名 + 执行/评估状态 + last_review_comment） | 每条结果的执行/评估状态、复核标注 |
| 评估维度分数 | 用例详情 `GET /tasks/{taskId}/cases/{caseId}/detail`（设备×维度表） | 低分维度识别（默认复核维度） |
| LLM 判分/评语 | 用例详情/报告用例卡片的 `llm_judge` 维度分 + voice_llm `evaluation.reasoning`（15 §3.5.2） | Agent 分析输入 |
| 已有 ai_reviews 结论 | `GET /tasks/results/{task_id}/ai-review-history`（Query result_id 过滤，INT-800 落地） | 幂等复用 + 对比 |

- 首条 assistant 消息 = 复核上下文摘要卡（结构化渲染，非裸 JSON）：「复核对象：{用例名}｜设备×结果：{n} 条｜低分维度：{维度}（{score}）｜LLM 评语：{摘要}｜已有 AI 复核结论：{verdict}（{时间}）」。
- 首条用户消息（预填可编辑）：「请复核该用例的评估结果，给出复核通过/不通过/存疑结论 + 置信度 + 理由。」

### 5.4 对话式复核流程（状态机）

```
打开（入口钮）→ 预填复核上下文 + 首条 → Agent 流式分析 →「AI 复核结论」卡（结构化）
→ 用户追问（多轮：为什么 / 哪维度 / 对比设备）→ Agent 补充 → 满意？
  ├─ 是 →「保存复核结论」→ POST /ai-review 落位（§5.5）→ 采纳 / 驳回闭环
  └─ 否 / 不处置 →「稍后处理」→ 关闭，不落任何判定（ai_reviews 无新增）
```

- **追问**：结论卡下提供快捷追问 chips（照 08 §3.4 Suggestion 语义，点击即发送）：「为什么判{不通过/存疑}？」「哪个维度失分最多？」「对比其他设备的表现」「给出逐设备复核意见」；用户可自由输入任意追问，Agent 多轮流式回复（Reasoning 思考过程）。
- **幂等**：该用例存在 running/completed 的 ai_reviews 记录时，打开会话头部提示「该用例已有 AI 复核结论（{时间}），可查看或重新复核」；「重新复核」→ 保存结论时 `force=true`（绕过幂等复用）。
- **保存结论前置**：保存前必须已有「AI 复核结论」卡（Agent 已给出结论）；未生成结论时按钮禁用。
- **超时/失败**：对话中断/LLM 供应商无响应 → 消息错误态（照 08 §3.4 错误态 Alert destructive + 重试）；AI 复核落位失败 → Alert +「重试」（重新发起，force），不落任何判定。

### 5.5 结论落位（对话式复核 ↔ POST /ai-review 映射）

| 动作 | 交互 | 后端调用（实测端点） | 权限 |
| --- | --- | --- | --- |
| **保存复核结论** | 结论卡内确认「将本次复核结论写入 AI 复核记录」→ `POST /tasks/results/ai-review` `{result_ids, dimension_ids?, force}` → 后端异步 LLM 复检链路回写 `ai_reviews`（status=completed + verdict/confidence/reasoning）→ 会话内嵌「AI 复核记录」卡展示后端落位结果 | `POST /tasks/results/ai-review` | `task.result.ai_review` |
| **采纳** | 主钮 → 打开 §3.2 人工复核弹窗**预填 AI 判定的评估状态**（verdict=passed→completed；failed→failed；uncertain→不预填留人工）+ **备注=AI 理由** → 人工确认提交 → `test_result_reviews` 留痕 + 统计重算 | `POST /tasks/results/ai-review/{id}/adopt`（`{execution_status?, evaluation_status?, comment 必填}`）+ 复用 `POST /tasks/results/review` | `task.result.review` |
| **驳回** | ghost 钮 → AI 记录标记「已驳回」，原判定不变 | `POST /tasks/results/ai-review/{id}/reject` | `task.result.ai_review` |
| **稍后处理** | 关闭会话/结论卡「稍后处理」→ 记录（若有）保留待查，不处置 | — | — |

- **对话结论 vs 后端复检（裁定）**：默认**方案 A**——正式结论以**后端复检链路落位的 `ai_reviews` 记录为准**（verdict/confidence/reasoning），灵犀Agent 对话负责解释/追问/辅助人判断（其结论供人参考，通常与后端复检一致）；**方案 B**（可选增强，待后端立项 §8-6）——对话结论直接写入 `ai_reviews`（发起端点接受外部结论字段，后端跳过复检），减少重复 LLM 调用。
- **状态机落位**：`待发起 → 对话中（未落位）→ 已保存（ai_reviews running/completed）→ 已采纳 / 已驳回 / 待查`；同一结果多次复核追加记录不覆盖（ai_reviews 独立表）。

### 5.6 异步执行 / 进度 / 失败重试呈现

- **发起保存后**：会话底栏进度条（照 15 §4.9 进度 Dialog 形态）+「AI 复核中…」（后端 running）→ 完成 → 结论卡刷新为 `ai_reviews` 记录（verdict/confidence/reasoning）。
- **轮询**：发起保存后轮询 `GET /tasks/results/{task_id}/ai-review-history`（Query result_id + status）直到 completed/failed（照 15 §4.9 轮询口径，3s 间隔）。
- **失败**：Alert destructive「AI 复核失败：{原因}」+「重试」（force 重新发起）；不落任何判定。
- **Demo 态说明**（08 §3.10）：灵犀Agent 对话本身走**用户自配 LLM 供应商**（Demo 态 localStorage，直连 `/chat/completions`）；「保存复核结论」落位走**真实后端端点**（INT-800 done）——两者分离。未配置 LLM 供应商时对话区发送禁用 + 引导「配置 LLM 供应商」，但「快速复核」入口（一次性状态机）仍可走后端复检链路。

### 5.7 数据契约（INT-800 落地 + 增强建议）

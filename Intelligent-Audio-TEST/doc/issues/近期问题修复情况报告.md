### 二、数据库迁移问题

#### 2. SQLite 到 PostgreSQL 数据迁移
- **迁移脚本**: `migrate_data.py`
- **迁移时间**: 2026-04
- **迁移内容**:
  - 重建 PostgreSQL 数据库
  - 创建表结构（44 张表）
  - 迁移所有数据（169,646 行）
  - 重置所有序列
  - 修复 NULL 值
- **迁移顺序**: users → permissions → tags → categories → dimensions → test_cases → devices → audios → tasks → results → reports → logs
- **修复效果**: 
  - ✅ 数据库从 SQLite 成功迁移到 PostgreSQL
  - ✅ 提升并发性能和数据可靠性

#### 3. PostgreSQL 获取插入 ID 方式修复
- **发现时间**: 2026-05-21
- **问题描述**: 使用 SQLite 的 `last_insert_rowid()` 函数获取插入ID，与 PostgreSQL 不兼容
- **修复方案**: 使用 PostgreSQL 标准的 `RETURNING` 子句，在 INSERT 语句执行时直接返回插入的 ID
- **修复效果**: 
  - ✅ 单次查询完成插入和获取ID
  - ✅ 原子性保证，避免并发问题
  - ✅ 性能提升（减少一次数据库交互）

#### 4. INTEGER 到 BIGINT 迁移
- **发现时间**: 2026-05-21
- **问题描述**: 所有自增 ID 字段使用 `INTEGER` 类型，最大值约21亿，日志表等高频写入表长期运行可能溢出
- **修复方案**: 
  - 修改 42 个表的 ID 字段为 `BigInteger`
  - 执行数据库迁移脚本 `migrate_integer_to_biginteger.sql`
  - 清理 145 条无效外键引用
- **修复效果**: 
  - ✅ ID 最大值提升至约 922 万亿亿
  - ✅ 消除长期运行溢出风险

#### 5. 模型版本升级迁移 (v20260129 -> v20260423)
- **迁移脚本**: `migrate_models_v2.py`
- **迁移内容**:

  - 修改字段类型：多个主键从 Integer 改为 BigInteger
  - 添加新字段：`tags.category_id`, `tags.sort_order`, `test_case_groups.algorithm_type`
  - 删除废弃字段：`task_case_relations.algorithm_type`, `task_case_relations.algorithm_params`
  - 添加索引：`test_reports`, `logs` 表
  - 数据迁移：用例分组关联 speaker_recognition，音频关联到 speaker_recognition
- **修复效果**: 
  - ✅ 数据库模型与代码同步
  - ✅ 支持标签分类功能
  - ✅ 支持音频算法关联

#### 6. 报告 JSON 字段拆分迁移

### 三、性能优化问题

#### 8. 报告列表加载缓慢问题修复
- **发现时间**: 2026-05-22
- **问题描述**: 报告列表页面加载需要 10 秒，即使只有 2-4 条记录
- **根本原因**: 
  - `ReportSummary` 表包含多个大型 JSON 字段
  - 列表页查询加载了不需要的大数据
- **修复方案**: 
  - 使用 `load_only()` 只加载需要的统计字段
  - 拆分大 JSON 字段到独立新表
- **修复效果**: 
  - ✅ 查询速度从 10 秒降到毫秒级别

#### 9. 用例保存接口性能优化
- **发现时间**: 2026-05-15
- **问题描述**: 当测试用例包含大量音频（如100+条）时，保存接口响应非常缓慢
- **根本原因**: 参考参数生成存在严重的 N+1 查询问题（100条音频约400-500次数据库查询）
- **修复方案**: 
  - 条件刷新：只在影响参考参数的字段变化时才触发刷新
  - 批量预加载：一次性查询所有音频的元数据和标注
- **修复效果**: 
  - ✅ 更新名称/描述：跳过参考参数生成，提升 ~100%
  - ✅ 100条音频更新：从400-500次查询降至2-3次，提升 ~95%

#### 10. 评估服务优化
- **问题描述**: 当多个维度使用相同的API端点时，每个维度都会单独调用一次API，导致重复请求
- **修复方案**: 将使用相同API端点的维度进行分组，每组只调用一次API获取所有维度的结果
- **修复效果**: 
  - ✅ wer + wer_zh + wer_en：从3次API调用降至1次，减少66.7%
  - ✅ 提高评估服务整体吞吐量

#### 11. 前端刷新导致音频播放卡顿问题分析
- **发现时间**: 2026-04-28
- **问题描述**: 前端刷新页面时，后端正在执行的音频播放任务出现卡顿甚至停止
- **根本原因**: 
  - 线程池资源竞争
  - 设备驱动创建大量线程
  - Python GIL 导致线程串行执行
- **修复方案**: 
  - 为不同类型的操作创建独立的线程池
  - 设备控制线程池、音频播放线程池、API任务线程池分离
- **修复效果**: ✅ 前端刷新不再完全阻塞设备控制和音频播放

### 五、音频处理问题

#### 18. 多音频并行播放问题修复
- **问题描述**: 当多个音频配置到同一物理设备的不同声道时，只有一个音频能播放，其他音频丢失
- **根本原因**: 
  - 音频数据写入使用赋值操作 `=` 导致覆盖
  - 设备间播放延迟过长
  - 单音频 delay 未传递
- **修复方案**: 
  - 将赋值操作 `=` 改为相加操作 `+=` 实现音频混合
  - 移除设备级别延迟，让所有设备同时开始播放
  - 修复 delay 参数传递
- **修复效果**: ✅ 多音频正确并行播放，声道独立控制

#### 19. 音频播放设备选择问题分析
- **问题描述**: 音频没有在所选择的播放设备上播放，而是在系统映射的扬声器上播放
- **根本原因**: 
  - 设备索引匹配逻辑问题
  - 设备名称匹配不精确
  - 默认设备回退机制
- **修复方案**: 
  - 增强设备索引匹配逻辑
  - 确保设备唯一标识准确性
  - 优化默认设备处理
- **修复效果**: ✅ 音频在指定的设备上播放

### 六、UI/交互问题

#### 20. 模态窗文本选择闪退问题修复
- **问题描述**: 在模态窗内的文本输入框中，用户使用鼠标拖选文本时，模态窗会立即关闭（闪退）
- **根本原因**: Vue 3 原生 DOM 事件与组件自定义事件的冲突，`@select` 被同时绑定为了原生 DOM 事件监听器
- **修复方案**: 
  - 定义 `isNativeEvent` 辅助函数过滤原生 DOM 事件
  - 移除干扰性事件处理
  - 添加文本选择保护样式
- **修复效果**: 
  - ✅ 文本选择不再触发模态窗关闭
  - ✅ Ctrl+A 全选文本正常工作
  - ✅ Escape 键关闭模态窗正常

#### 21. 样式优化与动画同步修复
- **发现时间**: 2026-05-20
- **问题描述**: 
  - 算法卡片点击高亮动画不同步
  - 步骤导航动画不同步
  - 报告渐变背景超出父卡片
- **修复方案**: 统一所有相关元素的 transition 时间为 `0.2s ease-out`
- **修复效果**: ✅ 动画效果流畅同步

#### 22. 历史报告页面加载慢问题修复
- **发现时间**: 2026-05-22
- **问题描述**: 历史报告页面加载需要约 10 秒
- **根本原因**: Report 表及相关表包含大量 JSON 字段，SELECT 查询慢
- **修复方案**: 
  - 删除 Report 表的大 JSON 字段
  - 拆分 ReportSummary 和 ReportDetailData 的 JSON 字段到 5 个新表
- **修复效果**: ✅ 加载时间从 10 秒降低到毫秒级别

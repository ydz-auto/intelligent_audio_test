# voice_llm 开发计划

> **开发方式**：Vibecoding（AI 代码生成 + 调试 + 联调 + 测试）
> **开发人员**：1 人
> **编制日期**：2026-06-09
> **技术文档**：74 份（backend 35 + frontend 25 + eval_server 6 + api_adapter 6 + 其他 2）

---

## 1. 工时构成说明

每个功能点的工时按以下比例分配：

| 阶段 | 占比 | 说明 |
|------|-----:|------|
| 代码生成 | 30% | 根据技术文档 + 伪代码由 AI 生成代码 |
| 调试 | 25% | 单模块调试、修复生成代码问题 |
| 联调 | 25% | 跨模块/跨服务联调 |
| 测试 | 20% | 功能验证、边界用例、回归测试 |

> Vibecoding 增益：有详细技术文档 + 伪代码的功能点，代码生成阶段效率提升 2-3 倍，但调试/联调/测试时间相对固定。

## 7. 风险与应对

| 风险点 | 影响等级 | 应对策略 |
|--------|:-------:|---------|
| RoundConfigEditor 交互复杂度 | 高 | 先用 wireframe 确认交互方案再编码；DynamicForm param_type 映射优先实现标准类型 |
| api_adapter HTTP 适配器无真实厂商对接 | 中 | 先用 mock_adapter 跑通主流程，HTTP 适配器最后接入真实 API |
| 设备驱动联调依赖真实硬件（导轨/音量/打断） | 中 | 开发阶段全程 mock 驱动，M3 后安排设备联调专项 |
| LLM Judge 外部 API 稳定性和成本 | 中 | 先实现本地 mock 评分，验证管线完整后再切换真实 LLM API |
| 三服务联调（主后端 + eval_server + api_adapter） | 高 | 每个微服务先独立 mock 测试通过，最后集中 2-3 天联调 |
| 旧数据迁移不可逆 | 低 | 迁移脚本幂等设计（IF NOT EXISTS），保留回滚脚本，迁移前备份 |

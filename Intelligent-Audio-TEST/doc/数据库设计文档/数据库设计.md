# 数据库设计

## 1. 整体设计

### 1.1 设计原则

- **统一命名规范**：采用snake_case命名法，表名使用复数形式
- **数据完整性**：合理设置主键、外键、约束和默认值
- **性能优化**：为常用查询字段添加索引
- **扩展性**：设计灵活的表结构，支持未来功能扩展
- **安全性**：采用逻辑删除，保护数据安全
- **一致性**：统一数据类型和字段命名

### 1.2 技术栈

- **数据库**：PostgreSQL 15+
- **ORM**：SQLAlchemy 2.0+
- **主键策略**：自增主键 (SERIAL) 或 UUID

**config字段详细结构**：
```json
{
  "background_noise": {
    "audio_id": 10,            // 背景噪声音频ID
    "spl": 65.0                // 背景噪声声压级
  },
  "rounds": [                  // 多轮配置；用例不区分 api/e2e（执行方式只看任务侧 device_type）
    {
      "round_number": 1,
      "audios": [              // 该轮音频；物理设备用例的 playback_device_id 必填
        {
          "audio_id": 101,     // 音频ID
          "spl": 70.0,         // 声压级
          "playback_device_id": 5,
          "play_order": 1
        }
      ],
      "evaluation": {
        "dimensions": [        // 逐轮维度；device_type 为空=所有设备类型通用
          { "id": 1, "name": "识别准确率", "weight": 50, "threshold": 60 }
        ]
      }
    }
  ],
  "dimensions": [              // 多轮整体评估维度（round_scope='multi'）
    { "id": 2, "name": "整体评测" }
  ]
}
```

> **原始报文指针列（INT-1807 / C1）**：`api_raw_response_*` / `api_request_body_*`
> 两组各五列，把原始报文从 JSON 列改成「内容寻址对象 + 行上指针」。请求体与响应
> 是两个独立对象、各自去重（主库实测 51,857 行去重后 6,506 个响应 + 6,259 个
> 请求体），不打包成一份。全部**可空、无默认值、无索引**；键 = 规范化 JSON
> （`json.dumps(v, sort_keys=True, separators=(',', ':'), ensure_ascii=False)`）
> 的 sha256，对象为 gzip 后的 `raw/{resp|req}/{sha[:2]}/{sha}.json.gz`，类别复用
> `case_result`。
>
> 分阶段落地：**C1（INT-1807）**只建列 + 回填脚本 + 切换门禁；**C2（INT-1809）/
> A1（INT-1811）**切读写路径（写路径只落指针、读路径按指针读对象）；**M1
> （INT-1813）已 DROP `api_raw_response` / `api_request_body` 两列**——报文只存在于
> 对象里，行上只剩指针（ORM 映射同步摘掉，否则全列 SELECT / INSERT 会
> `UndefinedColumn`）。存量回填与门禁见 §7.1，删列与体积回收见 §7.2；结构脚本
> `scripts/migrations/202610/add_raw_payload_pointers_int1807.py`（引导链 ㊽-5），
> 收尾脚本 `scripts/migrations/202610/drop_raw_payload_columns_int1813.py`
> （人工窗口执行，不进引导链）。对象是派生物，窗口内可用脚本 `--restore` 反向回填。

## 3. 索引设计

### 3.1 核心表索引

> **test_result_dimensions 的体积与维护（INT-1813 / M1）**：该表的体积几乎全部来自
> 原始报文的 TOAST。M1 前主库实测（2026-10-26 只读核查，51,857 行）
> `pg_total_relation_size` 296.66MB（堆 61.70MB / TOAST 232.03MB，与卡面
> 275.48MB / 221.9MB TOAST 同量级、差在 TOAST 统计口径）。本卡的**副本实测口径**是
> 「pg_dump 副本 + C1 回填 UPDATE 之后」：325.66MB（堆 89.92MB / TOAST 230.34MB）——
> 回填把指针写进行里会让堆膨胀，**不要拿 89.92MB 的堆去估临时盘**，按主库当前
> 61.70MB 堆估。PG 16 的 `DROP COLUMN` **只改系统目录、不重写数据**，被删列的
> TOAST 要等行重写才释放——所以删列必须紧跟 `VACUUM FULL`：M1 在同一副本上
> 执行后为 **27.44MB**（堆 24.95MB / TOAST 8KB），回收 298.22MB。`VACUUM FULL` 全程
> 持 `ACCESS EXCLUSIVE` 锁、需要约一个表大小的临时磁盘（约 275MB），必须在窗口内
> 执行；常规 `VACUUM` 只标记可复用空间，对「回收磁盘」无效。

## 7. 数据迁移策略

1. **版本控制**：使用Alembic进行数据库版本管理
2. **迁移脚本**：每个版本对应一个迁移脚本，包含升级和降级操作
3. **测试迁移**：在测试环境验证迁移脚本的正确性
4. **备份策略**：迁移前备份数据库，确保数据安全
5. **回滚机制**：提供回滚脚本，以便在迁移失败时恢复

### 7.1 原始报文内容寻址回填 + 切换门禁（INT-1807 / C1）

`test_result_dimensions` 的原始报文本卡起改为「内容寻址对象 + 行上指针」，分三步
落地：C1 建列 / 回填 / 门禁 → C2 切读写路径 → M1 删旧 JSON 列。C1 合入后没有任何
代码读新列，线上行为不变（对象只是派生物，随时可弃）。

**结构**：`scripts/migrations/202610/add_raw_payload_pointers_int1807.py`（引导链
㊽-5，排在 ㊽ INT-1741 ANALYZE 之前；幂等，全新库为全 SKIP）。

**回填**：`scripts/migrations/202610/backfill_raw_payload_pointers_int1807.py`
——按设计**不进引导链**（主库要解压约 695MB TOAST，需与在线评估错峰），人工分批执行：

```bash
# 只看门禁（只读，可重复执行）
python scripts/migrations/202610/backfill_raw_payload_pointers_int1807.py --gate
# 预览待处理组 / 行数
python scripts/migrations/202610/backfill_raw_payload_pointers_int1807.py
# 执行（--limit-groups 分次跑，进度按 uri IS NULL 天然续跑）
python scripts/migrations/202610/backfill_raw_payload_pointers_int1807.py --apply \
    --batch-groups 200 --sleep 0.5
```

- 分组键 `(test_result_id, round_number)`；组内 / 跨组同值只上传一次（值缓存），
  内容寻址 key 重复上传天然幂等，不建 checkpoint 表。
- 写对象一律 `storage.save_bytes(..., allow_fallback=False)`（D1 / INT-1805）：
  OSS 不可用即失败、**不落本地盘、不写 `local://`**，该组不写 uri，下次重跑补。

**切换门禁（唯一硬条件）**：

```sql
SELECT
  count(*) FILTER (WHERE api_raw_response IS NOT NULL AND api_raw_response_uri IS NULL) AS resp_missing,
  count(*) FILTER (WHERE api_request_body IS NOT NULL AND api_request_body_uri IS NULL) AS req_missing
FROM test_result_dimensions;
```

两项都必须为 **0** 才可切 C2。

> M1（INT-1813）删列后这条 SQL 不可再执行（`UndefinedColumn`），C1 回填脚本随之退役；
> 删列后的复查改走 §7.2 的 `drop_raw_payload_columns_int1813.py --gate`（回填门禁打 N/A，
> 完整性改看指针分布是否断链），回滚走同脚本 `--restore`。

### 7.2 原始报文 JSON 两列的 DROP + VACUUM FULL（INT-1813 / M1）

C2/A1 上线并观察 ≥1 个完整测试轮次后收尾。脚本
`scripts/migrations/202610/drop_raw_payload_columns_int1813.py`，三步：
`DROP COLUMN`（目录级）→ `VACUUM FULL`（重写表、释放 TOAST）→ `ANALYZE`。

```bash
# 只查门禁与体积（只读；列已删之后同样可跑，会打印门禁 N/A + 指针分布）
python scripts/migrations/202610/drop_raw_payload_columns_int1813.py --gate --verify-objects 20
# 执行（操作人确认 C2+A1 已部署且跑过一轮；主库执行建议 --strict-24h）
python scripts/migrations/202610/drop_raw_payload_columns_int1813.py --apply     --confirm-deployed-round --confirm-read-path --strict-24h
# VACUUM FULL 被 statement_timeout / lock_timeout 顶掉后的续跑（列已删，只重试压缩）
python scripts/migrations/202610/drop_raw_payload_columns_int1813.py --apply --force-vacuum     --confirm-deployed-round --confirm-read-path --strict-24h
# 窗口内回滚：从对象按 uri + sha256 解压写回两列
python scripts/migrations/202610/drop_raw_payload_columns_int1813.py --restore --apply
```

脚本内的门禁与卡面四条一致：①C2+A1 部署并跑过一轮（操作人确认）；②回填门禁
`内联非空而 uri 为空` = 0；③近 24h 新写入两列全为 SQL NULL（窗口内无行须显式承认）；
④报告读路径走对象（`--verify-objects` 抽样下载校验 sha256，或操作人确认）。另外执行
前会查 `pg_stat_activity` 的 idle in transaction / 等锁会话并拒绝带锁风险执行
（只读的 `--gate` 不查锁、也不要求确认读路径，删列后的复查不会被它们挡下）。

**失败续跑**：`DROP` 之后如果 `VACUUM FULL` 因 `statement_timeout`（默认 900s）或
`lock_timeout`（默认 5s，会话级，`VACUUM FULL` 同受约束）中止，原样重跑 `--apply`
会检出「列已删但 TOAST 仍偏大（>16MB；正常形态是 8KB）」并 **exit 3**，明确要求加
`--force-vacuum` 续跑——不会静默报成功。`--no-vacuum` 跑过的现场同样落这条路径。

**副本实测（INT-1813，pg_dump 副本 + 真实 rustfs 对象）**：`DROP` 16ms →
`VACUUM FULL` 327ms → `ANALYZE` 422ms（总 2.6s，51,857 行）；
`pg_total_relation_size` 325.66MB → 27.44MB（−298.22MB），TOAST 230.34MB → 8KB；
重复执行 `[SKIP]`（幂等）；删列后 `--restore` 从对象写回两列、与删列前逐行 deep-equal。

回滚：对象内容寻址、全部保留，`--restore` 重建两列并按 `uri + sha256` 写回（窗口内
可恢复）；对象不要提前清理。

## 8. 性能优化建议

1. **合理使用索引**：根据查询频率添加索引，避免过多索引影响写入性能
2. **分区表**：对于日志等大数据量表，考虑按时间分区
3. **查询优化**：避免全表扫描，使用合适的查询条件
4. **缓存机制**：对热点数据使用缓存，减少数据库访问
5. **批量操作**：使用批量插入/更新，减少数据库连接次数
6. **定期清理**：定期清理过期数据，优化数据库大小
7. **大字段外置 + VACUUM FULL 回收**：与评分行耦合的大 JSON（原始报文）改为内容寻址
   对象 + 行上指针后，删列必须紧跟 `VACUUM FULL` 才真正释放 TOAST（PG 16 的
   `DROP COLUMN` 只改目录）。INT-1813 实测回收 298.22MB（325.66MB → 27.44MB）；
   执行需窗口（AccessExclusiveLock）与约一个表大小的临时磁盘。

# 总结

本数据库设计文档提供了一个完整的智能语音测试系统后端数据库设计方案，涵盖了用户管理、标签管理、测试用例管理、API配置管理、设备管理、音频文件管理、测试任务管理、测试结果管理、评估维度管理和日志管理等核心模块。设计遵循了统一的命名规范和设计原则，确保了数据的完整性、一致性和安全性。

主要设计特点：

1. **测试用例统一管理**：测试用例不再区分API测试/E2E测试，而是通过`test_cases.config`字段配置不同测试类型的音频和评测维度
2. **灵活的测试配置机制**：通过`config.audios`数组配置不同类型的音频，通过`config.dimensions`对象配置不同类型的评测维度
3. **简化的表结构设计**：移除了独立的`test_case_audios`和`test_case_dimensions`关联表，将相关配置集中存储在`config`字段中
4. **完整的音频元数据管理**：
   - 音频表添加了asr_text字段，存储语音识别文本
   - 创建了audio_translations表，支持为音频配置翻译文本
4. **标签规范化管理**：将标签从JSON字段改为独立的表结构，支持标签的共享和统一管理
5. **多实体标签关联**：支持测试用例、任务、音频和设备等多个实体关联标签
6. **优化的索引设计**：为核心表添加了合适的索引，提高查询效率
7. **清晰的关系图**：直观展示了系统各实体之间的关联关系

该设计具有良好的扩展性和性能，可以支持系统的未来发展和功能扩展。同时，文档提供了详细的索引设计、关系图、数据字典、初始化脚本、迁移策略、性能优化建议、安全建议和维护建议，为系统的开发和维护提供了全面的指导。

## 3. 问题清单

### 3.1 P1 · 任务时间字段口径混用（M12）

- 现象：`test_tasks.created_at/updated_at` 与 `test_result_dimensions.created_at` 用本地时区（+8）naive 写入，`started_at/completed_at` 与 `task_case_relations.started_at` 用 UTC naive 写入。
- 实证：任务 461 `created_at=2026-11-01 01:38:43`、`started_at=2026-10-31 17:38:44`（同一任务，相差 8 小时，创建晚于开始）；任务 462 同型（created 01:49:27 / started 17:49:31）。
- 影响：任务详情/列表把两个字段当同一口径展示时，创建时间比开始时间晚 8 小时（跨日时表现为「16 小时」类脏值）；前端无法从 naive 字符串区分。
- 归属：task_service 建任务 `_build_new_task(now=datetime.now(UTC+8))` 与生命周期的 `utcnow()` / 评估维度写入不一致。

### 3.2 P1 · 暂停后「恢复」不生效（M5）

- 复现：建 API 任务 467 → start（queued）→ control `pause`（成功，paused）→ control `resume`。
- 期望：任务回到 queued/running 并继续派发。
- 实际：`resume` 返回 `success=true`、`data.status=paused`；10 秒后任务仍 `paused`，两行仍 pending，无任何派发。
- 证据：网关 `ControlTaskLifecycle` 响应 + `GET /tasks/467` 两次轮询 + psql `test_tasks`。

### 3.3 P2 · 离线设备任务不收敛、行级无失败原因（M8）

- 复现：`POST /tasks` 用 device 13（offline）+ `caseDevices` 建任务 465 → 20 分钟以上停在 `pending`，从未 `开始执行任务`，行 9865 一直 pending、`error_message` 为空。
- 期望：行级 failed 且原因可读（如「设备离线」），与 `POST /tasks/validate` 的判定一致。
- 实际：创建不拦、执行不启、状态不收敛；仅 validate 接口提示「设备不可用，请选择实体机」。
- 证据：任务 465 + `/tasks/validate` 响应。

### 3.4 P2 · 物理路由行缺时间字段（M9/M12）

- 461 的 6 条 physical 行 `started_at` / `completed_at` / `duration` 全 NULL（API 行 9857~9862 均有值），详情 `cases[].targets[]` 同步为空，任务详情无法显示设备行起止与时长。
- 归属：e2e 执行回写 `UpdateTaskCaseStatus` 只写状态，未写 `started_at/completed_at`（对比 API 路径有写）。

### 3.5 P2 · 不存在用例可创建任务（M8）

- `caseIds=["00000000-0000-0000-0000-000000000000"]` + device 9 创建成功（464），直到执行期才失败「找不到测试用例」。期望创建期 400 或 `/tasks/validate` 拦截。

### 3.6 P2 · 同类新建任务自动开始行为不一致（M6/M5 旁证）

- 463/464 创建后数秒自动 `开始执行任务`；465/466/467 创建后长时间 `pending`，必须显式 `POST /tasks/{id}/start` 才执行（466 显式启动后正常跑）。同一创建工作流结果不一致，且 465（离线设备）会长期占用 pending。

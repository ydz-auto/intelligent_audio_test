## 结论先看

- 评估链主干的**收口口径与软删口径是同源的**（`_count_enabled_dimensions` 与 `list_active_dimensions_by_ids` 都按 `deleted=False AND status=True`），INT-2189 的修复到位。
- 三率（`ratio` / `weighted_sum_ratio`）聚合与 `round_count` 的取值口径在 `round_caliber.py` 有文档化留档，单测覆盖较扎实。
- 最严重问题在**前端评估维度编辑**：列表行启停会把 `output_fields` 整批删掉（P0-1）；抽屉保存丢 `api_settings.body_template`（P0-2）。两者都会改写真实库维度配置，直接威胁本矩阵基线（维度 72 `api_url`、`api_endpoints.max_process=2`）。
- 后端侧的历史故障根因（端点不可达被吞）**只解决了一半**：`create_task` 阶段的连接级失败已分类并可降级；**轮询阶段**的持续不可达仍只记 WARNING 并轮询到上限（P1）。

## 检查项逐条结论

1. **配置化**：维度端点/并发/超时基本走库与 `concurrency_config.json`，但种子脚本 10 处硬编码死端点（P1）、`config_manager` 兜底与 JSON 双口径（P2）、前端 timeout 以 ms 展示而 worker 按秒读（P2）。不合规。
2. **坏味道**：存在重复轮询/回调逻辑（Redis 回调 5s + HTTP 轮询）、3 个 100~140 行的编排大函数（`_build_evaluation_context` 136、`_reevaluate_multi_round` 131、`_submit_multi_round_evaluations` 125）、`'canceled'`/状态名裸字符串与报告侧维度 code 硬编码。部分可接受，列 P2/P3。

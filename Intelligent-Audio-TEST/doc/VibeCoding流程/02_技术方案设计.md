# 步骤二：技术方案设计 — AI 生成方案，人做决策

## 流程概览

步骤一回答"做什么"（What），步骤二回答"怎么做"（How）。

```
输入：需求文档（步骤一产出）
  │
  ▼
AI：按模块生成功能设计文档（架构、数据流、算法、接口）
  │
  ▼
人工：评审技术方案、修正不合理之处、补充遗漏
  │
  ▼
产出：doc/功能设计文档/ 下的模块级设计文档
```

## 三种开发场景

| 场景 | 输入 | AI 交互策略 | 产出 |
|------|------|-------------|------|
| **A. 从0开始** | 需求分析文档 | 按模块逐个生成设计文档 | 端到端测试、API测试、评估系统、音频引擎等设计文档 |
| **B. 新增功能模块** | 改造方案总览 + 现有代码 | 分析现有代码后生成新模块设计 | voice_llm 改造方案、多厂商API适配方案等 |
| **C. 需求变更/迭代** | **澄清后的变更需求** + 现有设计文档 + 现有代码 | 分析现有设计后生成增量设计 | Speaker感知交叠播放、任务重新评估等设计文档 |

## 角色分工

| 角色 | 职责 | 关键动作 |
|------|------|----------|
| 人工 | 提供技术约束 | 描述技术栈、框架限制、性能要求 |
| AI | 生成方案 | 设计架构、规划数据流、选择算法、定义接口 |
| 人工 | 方案评审 | 验证可行性、修正不合理之处、补充遗漏 |

---

## 功能设计文档的统一结构

无论哪种场景，AI 生成的功能设计文档都遵循统一结构：

```
1. 概述
   - 功能定位（解决什么问题）
   - 术语定义

2. 系统架构设计
   - 整体架构（三层：前端展示层 / 后端服务层 / 执行层）
   - 核心组件（组件名、职责、技术实现、通信方式）
   - 数据流设计（配置流、执行流、进度流、结果流）
   - 依赖关系（依赖哪些其他模块）

3. 核心功能模块
   - 每个子功能的详细设计
   - 流程图（精确到函数名）
   - 数据结构定义

4. 技术实现
   - 关键代码片段
   - 算法逻辑
   - 接口定义（API Request/Response）

5. 边界条件和异常处理
   - 异常场景穷举
   - 降级策略

6. 用户界面设计
   - 前端交互流程
   - 组件结构
```

### AI 输出要点

以**端到端测试功能设计文档**为例，AI 从需求分析文档中生成：

**系统架构设计**：
```
三层架构：
- 前端展示层：Vue 3 + WebSocket（测试配置、实时监控、结果展示）
- 后端服务层：Flask + ADB/HDC（任务管理、设备通信、音频控制）
- 设备执行层：Android/HarmonyOS 设备（运行语音应用）
```

**核心组件**：

| 组件 | 职责 | 技术实现 | 通信方式 |
|------|------|----------|----------|
| 前端E2E测试页面 | 测试配置、进度监控、结果展示 | Vue 3 + WebSocket | WebSocket推送 |
| 后端E2E测试服务 | 任务管理、设备通信、结果处理 | Flask + ADB/HDC | HTTP REST + WebSocket |
| 设备通信模块 | 与设备建立连接，执行命令 | ADB/HDC工具链 | 本地进程通信 |
| 音频播放模块 | 控制音频播放，支持SPL校准 | PyAudio | 本地文件操作 |

**数据流设计**（4条数据流）：
1. 测试配置数据流：前端配置 → HTTP POST → 后端存储
2. 测试执行数据流：后端分配 → 设备连接 → 音频播放 → 结果返回
3. 进度更新数据流：设备状态变化 → 后端捕获 → WebSocket推送
4. 结果处理数据流：接收结果 → 评估计算 → 生成报告 → 前端展示

**四步测试流程**：
```
选择用例 → 选择设备 → 执行测试 → 查看结果
```

### 人工评审要点

| 检查项 | 常见问题 | 修正方式 |
|--------|----------|----------|
| 架构是否匹配技术栈 | AI 可能引入项目未使用的框架 | 明确告知技术约束 |
| 数据流是否完整 | AI 可能遗漏异步通信环节 | 补充 WebSocket/SSE 推送路径 |
| 组件职责是否清晰 | AI 可能让一个组件承担过多职责 | 拆分为更细粒度的组件 |
| 依赖关系是否正确 | AI 可能遗漏模块间依赖 | 补充依赖列表 |
| 技术限制是否考虑 | AI 不了解框架限制（如 PyAudio 单流） | 明确告知并让 AI 调整方案 |

### 产出物

`doc/功能设计文档/` 下 12+ 份模块级设计文档，覆盖系统所有功能模块

## 场景 B：新增功能模块 → 聚焦新模块设计

### 输入

- 步骤一产出的改造方案总览（`doc/voice_llm/00_改造方案总览.md`）
- 现有系统代码（AI 需要读取分析）

### AI 交互过程

与场景 A 的区别：不是从零设计，而是在现有架构上扩展。AI 需要先分析现有代码，再生成新模块设计。

| 轮次 | 模块 | 产出文档 |
|------|------|----------|
| 1 | voice_llm 整体改造 | `功能设计文档/voice_llm改造方案.md` |
| 2 | 多厂商API适配 | `06_设备管理/多厂商API适配完整方案.md` |
| 3 | 算法配置适配 | `08_算法配置/智能语音算法配置适配/` 下 18 份子文档 |

### AI 输出要点

以**多厂商API适配方案**为例：

**核心设计原则**（AI 从现有代码中提炼）：
1. 配置集中管理：所有API配置由主服务统一管理，存储在数据库中
2. 适配器无状态：适配器不持有配置，每次调用时由主服务传递完整配置
3. 协议透明：主服务不关心具体协议细节，由适配器处理
4. 结果标准化：所有适配器返回统一格式的结果

**支持的厂商矩阵**：

| 区域 | 厂商 | 服务类型 |
|------|------|----------|
| 国内 | 火山引擎、阿里云百炼、腾讯云、百度智能云 | ASR/AST/LLM |
| 海外 | OpenAI、Google、Azure、AWS | ASR/LLM/Speech |

**架构设计**（AI 基于现有 api_driver.py 扩展）：
```
主后端 → api_driver（统一调用入口）
           ├── api_client（HTTP/WebSocket 底层通信）
           ├── 厂商适配器（协议转换）
           └── 凭据管理（API Key 安全存储）
```

### 人工评审要点

| 检查项 | 常见问题 | 修正方式 |
|--------|----------|----------|
| 是否兼容现有架构 | AI 可能设计全新的架构而非扩展 | 要求 AI 基于现有代码扩展 |
| 改动范围是否合理 | AI 可能改动过多现有文件 | 列出"不变部分"约束改动范围 |
| 数据结构是否兼容 | AI 可能定义与现有表不兼容的新结构 | 提供现有表结构让 AI 扩展 |
| 是否过度设计 | AI 可能引入不必要的抽象层 | 简化为直接实现 |

### 产出物

`doc/功能设计文档/` 下的新模块设计文档 + `doc/voice_llm/` 下的改造子文档

## 场景 C：需求变更/迭代 → 增量设计文档

### 输入

- 变更需求描述
- 现有功能设计文档（AI 需要读取理解现有设计）
- 现有代码（AI 需要分析现有实现）

### AI 交互过程

与场景 A/B 的区别：不是设计新模块，而是在现有设计上做增量修改。AI 必须先理解现有设计，再生成增量部分。

| 轮次 | 变更内容 | 产出文档 |
|------|----------|----------|
| 1 | Speaker感知交叠播放 | `03_音频处理/Speaker感知交叠播放功能设计文档.md` |
| 2 | 多音频并行播放修复 | `03_音频处理/多音频并行播放问题修复文档.md` |
| 3 | 时间戳偏移机制 | `03_音频处理/动态时间戳偏移计算与标注刷新机制.md` |
| 4 | 任务重新评估 | `01_测试执行/任务重新评估与重新提取功能设计文档.md` |
| 5 | ASR/Fix文件拼接 | `03_音频处理/ASR_Fix文件解析与拼接功能设计文档.md` |
| 6 | 前后端字段命名 | `10_系统架构/前后端字段命名适配机制.md` |

### AI 输出要点

以**Speaker感知交叠播放**为例：

**问题背景**（AI 从现有代码中分析出）：
```
音频1: [spk9: 0-2s] [spk8: 2-5s]
音频2: [spk9: 0-3s] [spk4: 3-6s]
音频3: [spk7: 0-2s] [spk8: 2-5s]

问题：音频1和音频2都有spk9，不应该交叠，但当前逻辑会按overlap_rate交叠
```

**核心规则**（增量设计）：
```
相邻音频 speakers 集合有交集 → 顺序播放（start_time = prev_end_time）
相邻音频 speakers 集合无交集 → 按 overlap_rate 交叠
```

**数据结构**（与现有代码兼容）：
```python
speakers_map = {
    audio_id_1: {'spk9', 'spk8'},
    audio_id_2: {'spk9', 'spk4'},
    audio_id_3: {'spk7', 'spk8'},
}
```

**与现有模块的关系**（AI 分析现有设计后明确）：
- Speaker感知逻辑 → 负责判断时序关系（顺序/交叠）
- play_multi 的 callback → 负责同声道混合
- 两者职责分离，互不干扰

### 人工评审要点

| 检查项 | 常见问题 | 修正方式 |
|--------|----------|----------|
| 是否理解现有设计 | AI 可能误解现有逻辑 | 让 AI 先总结现有设计再提增量 |
| 增量是否与现有兼容 | AI 可能设计与现有实现冲突的方案 | 提供现有代码让 AI 分析 |
| 边界条件是否穷举 | AI 可能遗漏特殊场景 | 人工补充边界条件 |
| 影响范围是否明确 | AI 可能不清楚改动会影响哪些模块 | 让 AI 列出影响范围 |

### 产出物

`doc/功能设计文档/` 下的增量设计文档，精确到函数级的修改说明

## 常见 AI 方案缺陷

| 缺陷类型 | 表现 | 人工修正方式 |
|----------|------|-------------|
| 忽略框架限制 | 假设 PyAudio 可以打开多个 OutputStream | 明确告知框架约束 |
| 数据结构脱离实际 | 使用理论最优结构（如 `Dict[str, Set[str]]`） | 改为贴合数据库查询结果的结构（如 `Dict[int, List[str]]`） |
| 遗漏兼容处理 | 不考虑采样率、编码格式差异 | 补充统一转换逻辑 |
| 过度设计 | 引入不必要的抽象层 | 简化为直接实现 |
| 忽略现有代码 | 设计与现有实现冲突的方案 | 让 AI 先读取现有代码再设计 |
| 组件职责不清 | 一个组件承担过多职责 | 拆分为更细粒度的组件 |

## 关键经验

1. **技术约束必须人工提供**：AI 不了解具体框架的限制（如 PyAudio 单流限制），需要明确告知
2. **让 AI 先读现有代码再设计**：场景 B/C 中，AI 必须先分析现有实现，否则生成的方案会与现有代码冲突
3. **数据结构需要人工调整**：AI 倾向于使用理论最优结构，但实际项目中需要考虑与数据库、API 的兼容性
4. **方案评审时间不能省**：错误的技术方案会导致后续所有工作返工
5. **按模块逐个生成**：不要一次性让 AI 生成所有模块的设计，逐个生成可以保证每个模块的质量
6. **列出"不变部分"**：场景 B/C 中，明确告诉 AI 哪些模块不需要改动，避免过度设计

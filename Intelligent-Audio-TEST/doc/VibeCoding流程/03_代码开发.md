# 步骤三：代码开发 — SPEC 驱动，人审核方案，AI 逐步实现

## 流程概览

代码开发不是直接让 AI 写代码，而是先通过 SPEC 技能生成结构化的开发方案，人工审核确认后再按里程碑逐步实现。

```
输入：功能设计文档（步骤二产出）
  │
  ▼
AI（SPEC 技能）：生成开发方案（代码基线分析 → 里程碑规划 → 实施步骤）
  │
  ▼
人工：审核 SPEC 文档（确认基线准确、里程碑合理、步骤完整）
  │
  ▼
AI：按里程碑逐步实现代码（M0 → M1 → M2 → ...）
  │
  ▼
人工：每个里程碑完成后验证
  │
  ▼
产出：可运行的代码 + 验证通过的里程碑
```

## 三种开发场景

| 场景 | SPEC 特点 | 里程碑数量 | 典型周期 |
|------|-----------|-----------|----------|
| **A. 从0开始** | 全量规划，从零搭建 | 5~8 个 | 完整项目周期 |
| **B. 新增功能模块** | 增量规划，基于现有代码扩展 | 4~6 个 | 模块开发周期 |
| **C. 需求变更/迭代** | 精确规划，聚焦变更点 | 1~3 个 | 单次迭代周期 |

## 角色分工

| 角色 | 职责 | 关键动作 |
|------|------|----------|
| AI（SPEC 技能） | 生成开发方案 | 分析代码基线、规划里程碑、拆分实施步骤 |
| 人工 | 审核 SPEC | 确认基线准确、里程碑合理、步骤无遗漏 |
| AI | 逐步实现 | 按里程碑顺序生成代码 |
| 人工 | 逐里程碑验证 | 每个里程碑完成后验证功能正确性 |

---

## SPEC 文档的统一结构

SPEC 技能生成的开发方案文档遵循统一结构：

```
1. Context（背景与目标）
   - 项目背景
   - 改造目标
   - 涉及的服务和文件数量

2. 决策记录
   - 关键技术决策及其理由

3. 当前代码基线（精确验证结果）
   - 已完成模块（可直接使用）
   - 未实现模块（缺口和风险）
   - 前端精确状态

4. 开发路线图（M0 → Mn）
   每个里程碑包含：
   - 目标（一句话描述完成标准）
   - 实施步骤（精确到文件名和方法名）
   - 关键文件列表
   - 验证标准（如何确认里程碑完成）
   - 参考设计文档

5. 并行策略
   - 哪些 Track 可以并行
   - 哪些有依赖关系必须顺序执行
```

## 场景 A：从0开始 → 全量 SPEC

### SPEC 特点

从零开始的项目，SPEC 需要规划完整的项目搭建过程：

```
M0: 项目骨架搭建（目录结构、依赖安装、数据库初始化）
M1: 基础数据模型（核心表创建、CRUD 接口）
M2: 核心功能模块1（如：用例管理）
M3: 核心功能模块2（如：设备管理）
M4: 测试执行引擎（如：端到端测试、API测试）
M5: 评估系统（评估维度、评估计算）
M6: 报告与导出
M7: 前端页面集成
```

### 人工审核重点

| 审核项 | 关注点 |
|--------|--------|
| 里程碑顺序 | 依赖关系是否正确，是否有循环依赖 |
| 技术选型 | 框架和库是否与项目要求一致 |
| 数据库设计 | 表结构是否与需求分析文档一致 |
| 接口设计 | API 是否符合设计文档定义 |

## 场景 B：新增功能模块 → 增量 SPEC

### 真实案例：voice_llm 改造

以 `voice-llm-dev-spec.md` 为例，这是在已有系统上新增 voice_llm 测试能力的 SPEC 文档。

#### Context

```
现有系统支持 translation/ASR/speaker_recognition/TTS 四种算法测试。
改造目标：新增 voice_llm 测试类型，支持多轮对话、声纹注册、干扰人播放、
导轨控制、设备音量控制、全双工打断检测和 LLM Judge 评估。
涉及 4 个服务，约 61 个文件改动。
```

#### 决策记录

| 决策项 | 选择 | 说明 |
|--------|------|------|
| 起始里程碑 | M0 | 从数据库迁移开始，全量推进 |
| api_adapter_service | 从头搭建 | 新建正确命名的项目，不复用拼写错误的旧项目 |
| 前端策略 | 增量迭代 | 先实现最小可用版本，再迭代高级特性 |

#### 当前代码基线（AI 精确分析现有代码后生成）

**已完成（可直接使用）**：

| 模块 | 状态 | 证据 |
|------|------|------|
| TestCase `test_type` + `related_case_id` 字段 | 已存在 | `models/models.py:146-147` |
| CaseAlgorithmParam `scope` 字段 | 已存在 | `algorithm_models.py:375` |
| Schema 类型 `RoundConfigItem` | 已定义 | `schemas/testcase.py:44-76` |
| E2E executor 多轮循环基础骨架 | 已实现 | `_execute_e2e_with_rounds()` |

**未实现（缺口和风险）**：

| 模块 | 缺口 | 风险 |
|------|------|------|
| `session_context.py` | 文件不存在 | 高 |
| api_executor 多轮会话主循环 | 仅读取 rounds[0] | 高 |
| E2E executor voice_llm 特性 | 无 voiceprint/interferer/interruption | 高 |
| LLM Judge 计算器 | eval_server 仅有 wer/ser/der | 中 |

#### 开发路线图（M0 → M5）

| 里程碑 | 目标 | 核心步骤数 | 验证标准 |
|--------|------|-----------|----------|
| **M0: 数据库就绪** | DDL 执行成功，种子数据写入 | 5 步 | 查询各表确认记录数正确 |
| **M1: 算法可选** | voice_llm 出现在算法列表 | 3 步 | DynamicForm 按 scope 正确过滤 |
| **M2: 用例可配** | 用户可创建/编辑多轮用例 | 13 步 | 创建 3 轮用例 → 编辑验证持久化 |
| **M3: 设备可控** | 设备驱动支持音量/导轨/打断 | 5 步 | Mock 模式调用返回成功 |
| **M4: 测试可执行** | API 多轮 + E2E 多轮端到端跑通 | 21 步（5个Track） | 3 轮 API 用例执行 → LLM Judge 出分 |
| **M5: 结果可查看** | 多轮报告展示正确 | 6 步 | 轮次表格/汇总/对比视图可用 |

#### M4 详细示例（最复杂的里程碑，占 48% 工时）

M4 拆分为 5 个并行 Track：

| Track | 内容 | 步骤数 | 依赖 |
|-------|------|--------|------|
| Track 1 | API 多轮会话 | 4 步 | 依赖 M3 |
| Track 2 | api_adapter_service 搭建 | 5 步 | 与 Track 1 联调 |
| Track 3 | E2E 多轮循环增强 | 5 步 | 独立，可与 Track 1+2 并行 |
| Track 4 | 评估管线 | 4 步 | 依赖 Track 1/3 的结果结构 |
| Track 5 | 基础设施（进度/采集/前端） | 3 步 | 可提前开始 |

每个步骤精确到文件名和方法名：
```
Track 1, Step 1: 新建 SessionContext 会话管理器
  - 新建 backend/utils/session_context.py
  - 参考 doc: 13_SessionContext会话管理器.md
  - 管理: 创建/上下文维护/对话历史/销毁
```

### 人工审核 SPEC 的要点

| 审核项 | 检查内容 | 常见问题 |
|--------|----------|----------|
| **代码基线准确性** | AI 标注"已实现"的是否真的已实现 | AI 可能误判部分实现为已完成 |
| **里程碑粒度** | 每个里程碑是否可在合理时间内完成 | M2/M4 过大需要拆分 Phase |
| **依赖关系** | Track 之间的依赖是否正确 | AI 可能遗漏隐式依赖 |
| **验证标准** | 每个里程碑的验证标准是否可执行 | 验证标准太模糊无法执行 |
| **参考文档** | 引用的设计文档是否存在且内容正确 | 文档路径错误或内容过时 |
| **不变部分** | 是否明确了哪些现有代码不需要改动 | AI 可能过度修改现有代码 |

### 审核后的修正示例

| AI 原始规划 | 人工修正 | 原因 |
|-------------|----------|------|
| M2 一步到位实现所有编辑器 | 拆分为 Phase 1（后端基础）+ Phase 2（类型与状态）+ Phase 3（编辑器组件） | M2 太大，需要分阶段验证 |
| api_adapter 复用旧项目 | 从头搭建正确命名的项目 | 旧项目名有拼写错误 |
| 前端一次性实现拖拽排序 | 先实现最小可用版本，V2 再迭代拖拽 | 降低风险，先跑通核心流程 |

## 场景 C：需求变更/迭代 → 精确 SPEC

### SPEC 特点

需求变更的 SPEC 聚焦于变更点，里程碑少但步骤精确：

```
M0: 数据库变更（新增字段/索引/迁移脚本）
M1: 后端逻辑修改（精确到函数级）
M2: 前端适配（受影响的组件）
```

### 真实案例：任务重新评估与重新提取

```
M0: 数据库变更
  - test_result_dimensions 表新增 round_number 字段
  - 新增复合索引

M1: 后端重新提取逻辑
  - DeviceResultReextractor.reextract_for_task() — 新建
  - 驱动获取 → extract_results_from_archive() → 新旧记录替换
  - Fix/ASR 文件拼接逻辑修复

M2: 后端重新评估逻辑
  - EvaluationController.reevaluate_task_results() — 修改
  - 支持 reevaluate_type='all'/'failed'
  - 支持 reextract_device_output=true/false

M3: 前端适配
  - 重新评估按钮 → 弹窗选择参数 → 调用 API
```

### 人工审核重点

| 审核项 | 关注点 |
|--------|--------|
| 影响范围 | AI 是否准确识别了所有受影响的文件 |
| 向后兼容 | 修改是否会影响现有功能 |
| 数据迁移 | 数据库变更是否需要迁移脚本 |
| 回归测试 | 哪些现有功能需要重新测试 |

## 按里程碑实现代码

SPEC 审核通过后，按里程碑顺序逐步让 AI 实现代码。

### 每个里程碑的执行流程

```
1. AI 读取 SPEC 中该里程碑的实施步骤 + 参考设计文档
2. AI 生成代码（精确到文件和方法）
3. 人工审核代码
4. 执行该里程碑的验证标准
5. 验证通过 → 进入下一个里程碑
   验证失败 → 修正代码 → 重新验证
```

### 代码审核清单

#### 逻辑正确性
- [ ] 核心算法逻辑是否与设计文档一致
- [ ] 边界条件是否正确处理（空值、零值、最大值）
- [ ] 异步操作是否正确等待和错误处理

#### 性能
- [ ] 数据库查询是否使用批量操作
- [ ] 是否有不必要的循环嵌套
- [ ] 大数据量场景是否考虑分页/流式处理

#### 代码规范
- [ ] 命名是否符合项目规范
- [ ] 是否使用了项目已有的工具函数
- [ ] 组件大小是否合理（前端 < 300 行，后端函数 < 50 行）

#### 与 SPEC 一致性
- [ ] 实现是否覆盖了 SPEC 中该里程碑的所有步骤
- [ ] 是否引入了 SPEC 未规划的额外改动
- [ ] 文件路径和方法名是否与 SPEC 一致

### 常见 AI 代码缺陷

| 缺陷类型 | 表现 | 修正方式 |
|----------|------|----------|
| 数据库 N+1 查询 | 每个元素单独查一次数据库 | 改为批量查询 |
| 首个元素特殊处理遗漏 | offset[0] 硬编码为 0，忽略 delay | 从参数获取 |
| 组件过大 | 单文件 4000+ 行 | 拆分为子组件 |
| 响应式数据污染 | 编辑时直接修改原始数据 | 使用深拷贝 |
| 赋值覆盖 | `=` 覆盖而非 `+=` 叠加 | 检查赋值语义 |
| 参数硬编码 | 单元素场景硬编码默认值 | 从实际参数获取 |

## 三种场景的对比

| 维度 | A. 从0开始 | B. 新增模块 | C. 需求变更 |
|------|-----------|------------|------------|
| SPEC 规模 | 完整项目（8个里程碑） | 一个模块（5~6个里程碑） | 一个功能点（1~3个里程碑） |
| 代码基线分析 | 无现有代码 | 精确分析现有代码 | 精确分析受影响代码 |
| 里程碑粒度 | 模块级 | 功能级 | 函数级 |
| 并行策略 | 前后端可并行 | Track 级并行 | 通常串行 |
| 审核重点 | 架构合理性 | 兼容性 + 基线准确性 | 影响范围 + 向后兼容 |

## 关键经验

1. **SPEC 审核是必须的**：不审核 SPEC 就开始写代码 = 在错误的地基上盖楼
2. **代码基线必须人工验证**：AI 标注"已实现"的模块，人工需要抽查确认
3. **里程碑验证不可跳过**：每个里程碑完成后必须执行验证标准，通过后才进入下一个
4. **大里程碑要拆 Phase**：超过 10 个步骤的里程碑应拆分为多个 Phase
5. **先跑通再优化**：先实现最小可用版本（V1），再迭代高级特性（V2）
6. **按 SPEC 实现，不要自由发挥**：AI 实现代码时应严格遵循 SPEC 中的步骤和文件路径

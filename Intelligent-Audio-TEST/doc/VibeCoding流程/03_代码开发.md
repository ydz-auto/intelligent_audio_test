# 步骤三：代码开发 — SPEC 驱动，人审核方案，AI 逐步实现

---

## 一、什么是 Spec Coding（概念解释）

### Spec Coding 的定义

**Spec Coding（规范驱动开发，Spec-Driven Development，简称 SDD）** 是一种 AI 辅助开发方法论。

它的核心不是让 AI 直接根据一句 Prompt 写代码，而是先把项目目标、范围、关键决策和验收标准整理成结构化文档，再让 Coding Agent 基于这些文档逐步完成实现。

简单来说，Spec Coding 解决的是一个现实问题：

> 当项目变复杂、会话变长、需求不断变化时，AI 很容易失去全局方向，开始跑偏。

Spec 的作用，就是在开发过程中为人和 AI Agent 提供一套共同遵守的"项目地图"。

---

### Spec Coding 的三件套

#### `spec.md`：项目范围 / 北极星文档

`spec.md` 是整个项目的全局概览，也可以理解为项目的"北极星文档"。

它回答的是：
- 我们现在要做什么？
- 为什么要做这个改动？
- 这次改动的目标是什么？
- 做过哪些关键决策和权衡？
- 哪些内容在范围内？
- 哪些内容明确不做？

它不是普通需求描述，而是整个开发过程的方向锚点。后续的任务拆解、代码实现和验证清单，都应该围绕它展开。

---

#### `tasks.md`：任务拆解 / 实现计划

`tasks.md` 是把项目范围具体化的地方。

它会把 `spec.md` 里的整体目标拆成若干模块，再把模块拆成子任务，最后细化成可执行步骤。

它本质上是一份有顺序、有结构的实现计划。

开发过程中，Agent 会按照 `tasks.md` 推进工作，并持续更新任务状态。这样人可以随时看到：
- 当前做到哪一步；
- 哪些模块已经完成；
- 哪些任务还没开始；
- 是否存在遗漏或偏离。

---

#### `checklist.md`：验证清单 / 收尾核查

`checklist.md` 是项目完成后的完整性核查表。

当 Agent 完成实现后，不能直接宣称"完成了"，而是要逐项检查：
- 代码是否已经实现；
- 功能是否符合 `spec.md`；
- 关键场景是否验证过；
- 测试是否覆盖；
- 是否存在遗漏项；
- 是否满足收尾标准。

只有当 `checklist.md` 中的检查项全部确认通过，项目才算真正完成。

---

### 核心流程

```
spec.md       定义项目范围和方向
    ↓
tasks.md      拆解实现路径和执行步骤
    ↓
Agent 执行    按任务逐步开发并更新进度
    ↓
checklist.md  按清单验证完整性
    ↓
交付完成
```

---

### 与 Vibe Coding 的区别

| 维度 | Vibe Coding | Spec Coding |
|------|-------------|-------------|
| **起点** | 一句话需求 | 结构化文档三件套 |
| **过程** | 想到哪里写到哪里 | 先画图纸，再施工，再验收 |
| **适用场景** | 快速试验、简单需求 | 长期项目、复杂系统、多人协作 |
| **风险控制** | 难以追溯偏离原因 | 每一步都有文档锚点 |
| **AI 行为** | 凭感觉写代码 | 围绕清晰规范完成开发 |

一句话概括：

> **Spec Coding 就是用 `spec.md` 明确方向，用 `tasks.md` 管理执行，用 `checklist.md` 保证收尾，让 AI Agent 不再凭感觉写代码，而是围绕清晰规范完成开发。**

## 二、代码开发实践（里程碑开发流程）

### 流程概览
代码开发不是直接让 AI 写代码，而是先通过 SPEC 技能生成结构化的开发方案，人工审核确认后再按里程碑逐步实现。

```
输入：功能设计文档（步骤二产出）
  │
  ▼
AI（SPEC 技能）：生成开发方案（代码基线分析 → 里程碑规划 → 实施步骤）
  │
  ▼
人工：审核 SPEC 文档（确认基线准确、里程碑合理、步骤完整）
  │
  ▼
AI：按里程碑逐步实现代码（M0 → M1 → M2 → ...）
  │
  ▼
人工：每个里程碑完成后验证
  │
  ▼
产出：可运行的代码 + 验证通过的里程碑
```

## 三种开发场景

| 场景 | SPEC 特点 | 里程碑数量 | 典型周期 |
|------|-----------|-----------|----------|
| **A. 从0开始** | 全量规划，从零搭建 | 5~8 个 | 骨架生成 + 每模块细分迭代 |
| **B. 新增功能模块** | 增量规划，基于现有代码扩展 | 4~6 个 | 模块开发周期 |
| **C. 需求变更/迭代** | 精确规划，聚焦变更点 | 1~3 个 | 单次迭代周期 |

## 角色分工

| 角色 | 职责 | 关键动作 |
|------|------|----------|
| AI（SPEC 技能） | 生成开发方案 | 分析代码基线、规划里程碑、拆分实施步骤 |
| 人工 | 审核 SPEC | 确认基线准确、里程碑合理、步骤无遗漏 |
| AI | 逐步实现 | 按里程碑顺序生成代码 |
| 人工 | 逐里程碑验证 | 每个里程碑完成后验证功能正确性 |

---

## SPEC 文档的统一结构

SPEC 技能生成的开发方案文档遵循统一结构：

```
1. Context（背景与目标）
   - 项目背景
   - 改造目标
   - 涉及的服务和文件数量

2. 决策记录
   - 关键技术决策及其理由

3. 当前代码基线（精确验证结果）
   - 已完成模块（可直接使用）
   - 未实现模块（缺口和风险）
   - 前端精确状态

4. 开发路线图（M0 → Mn）
   每个里程碑包含：
   - 目标（一句话描述完成标准）
   - 实施步骤（精确到文件名和方法名）
   - 关键文件列表
   - 验证标准（如何确认里程碑完成）
   - 参考设计文档

5. 并行策略
   - 哪些 Track 可以并行
   - 哪些有依赖关系必须顺序执行
```

## 场景 A：从0开始 → 全量 SPEC

### SPEC 特点

从零开始的项目，SPEC 需要规划完整的项目搭建过程：

```
M0: 项目骨架搭建（目录结构、依赖安装、数据库初始化）
M1: 基础数据模型（核心表创建、CRUD 接口）
M2: 核心功能模块1（如：用例管理）
M3: 核心功能模块2（如：设备管理）
M4: 测试执行引擎（如：端到端测试、API测试）
M5: 评估系统（评估维度、评估计算）
M6: 报告与导出
M7: 前端页面集成
```

### 人工审核重点

| 审核项 | 关注点 |
|--------|--------|
| 里程碑顺序 | 依赖关系是否正确，是否有循环依赖 |
| 技术选型 | 框架和库是否与项目要求一致 |
| 数据库设计 | 表结构是否与需求分析文档一致 |
| 接口设计 | API 是否符合设计文档定义 |

## 场景 B：新增功能模块 → 增量 SPEC

### 真实案例：voice_llm 改造

以 `voice-llm-dev-spec.md` 为例，这是在已有系统上新增 voice_llm 测试能力的 SPEC 文档。

#### Context

```
现有系统支持 translation/ASR/speaker_recognition/TTS 四种算法测试。
改造目标：新增 voice_llm 测试类型，支持多轮对话、声纹注册、干扰人播放、
导轨控制、设备音量控制、全双工打断检测和 LLM Judge 评估。
涉及 4 个服务，约 61 个文件改动。
```

#### 决策记录

| 决策项 | 选择 | 说明 |
|--------|------|------|
| 起始里程碑 | M0 | 从数据库迁移开始，全量推进 |
| api_adapter_service | 从头搭建 | 新建正确命名的项目，不复用拼写错误的旧项目 |
| 前端策略 | 增量迭代 | 先实现最小可用版本，再迭代高级特性 |

#### 当前代码基线（AI 精确分析现有代码后生成）

**已完成（可直接使用）**：

| 模块 | 状态 | 证据 |
|------|------|------|
| TestCase `test_type` + `related_case_id` 字段 | 已存在 | `models/models.py:146-147` |
| CaseAlgorithmParam `scope` 字段 | 已存在 | `algorithm_models.py:375` |
| Schema 类型 `RoundConfigItem` | 已定义 | `schemas/testcase.py:44-76` |
| E2E executor 多轮循环基础骨架 | 已实现 | `_execute_e2e_with_rounds()` |

**未实现（缺口和风险）**：

| 模块 | 缺口 | 风险 |
|------|------|------|
| `session_context.py` | 文件不存在 | 高 |
| api_executor 多轮会话主循环 | 仅读取 rounds[0] | 高 |
| E2E executor voice_llm 特性 | 无 voiceprint/interferer/interruption | 高 |
| LLM Judge 计算器 | eval_server 仅有 wer/ser/der | 中 |

#### 开发路线图（M0 → M5）

| 里程碑 | 目标 | 核心步骤数 | 验证标准 |
|--------|------|-----------|----------|
| **M0: 数据库就绪** | DDL 执行成功，种子数据写入 | 5 步 | 查询各表确认记录数正确 |
| **M1: 算法可选** | voice_llm 出现在算法列表 | 3 步 | DynamicForm 按 scope 正确过滤 |
| **M2: 用例可配** | 用户可创建/编辑多轮用例 | 13 步 | 创建 3 轮用例 → 编辑验证持久化 |
| **M3: 设备可控** | 设备驱动支持音量/导轨/打断 | 5 步 | Mock 模式调用返回成功 |
| **M4: 测试可执行** | API 多轮 + E2E 多轮端到端跑通 | 21 步（5个Track） | 3 轮 API 用例执行 → LLM Judge 出分 |
| **M5: 结果可查看** | 多轮报告展示正确 | 6 步 | 轮次表格/汇总/对比视图可用 |

#### M4 详细示例（最复杂的里程碑，占 48% 工时）

M4 拆分为 5 个并行 Track：

| Track | 内容 | 步骤数 | 依赖 |
|-------|------|--------|------|
| Track 1 | API 多轮会话 | 4 步 | 依赖 M3 |
| Track 2 | api_adapter_service 搭建 | 5 步 | 与 Track 1 联调 |
| Track 3 | E2E 多轮循环增强 | 5 步 | 独立，可与 Track 1+2 并行 |
| Track 4 | 评估管线 | 4 步 | 依赖 Track 1/3 的结果结构 |
| Track 5 | 基础设施（进度/采集/前端） | 3 步 | 可提前开始 |

每个步骤精确到文件名和方法名：
```
Track 1, Step 1: 新建 SessionContext 会话管理器
  - 新建 backend/utils/session_context.py
  - 参考 doc: 13_SessionContext会话管理器.md
  - 管理: 创建/上下文维护/对话历史/销毁
```

### 人工审核 SPEC 的要点

| 审核项 | 检查内容 | 常见问题 |
|--------|----------|----------|
| **代码基线准确性** | AI 标注"已实现"的是否真的已实现 | AI 可能误判部分实现为已完成 |
| **里程碑粒度** | 每个里程碑是否可在合理时间内完成 | M2/M4 过大需要拆分 Phase |
| **依赖关系** | Track 之间的依赖是否正确 | AI 可能遗漏隐式依赖 |
| **验证标准** | 每个里程碑的验证标准是否可执行 | 验证标准太模糊无法执行 |
| **参考文档** | 引用的设计文档是否存在且内容正确 | 文档路径错误或内容过时 |
| **不变部分** | 是否明确了哪些现有代码不需要改动 | AI 可能过度修改现有代码 |

### 审核后的修正示例

| AI 原始规划 | 人工修正 | 原因 |
|-------------|----------|------|
| M2 一步到位实现所有编辑器 | 拆分为 Phase 1（后端基础）+ Phase 2（类型与状态）+ Phase 3（编辑器组件） | M2 太大，需要分阶段验证 |
| api_adapter 复用旧项目 | 从头搭建正确命名的项目 | 旧项目名有拼写错误 |
| 前端一次性实现拖拽排序 | 先实现最小可用版本，V2 再迭代拖拽 | 降低风险，先跑通核心流程 |

## 场景 C：需求变更/迭代 → 精确 SPEC

### SPEC 特点

需求变更的 SPEC 聚焦于变更点，里程碑少但步骤精确：

```
M0: 数据库变更（新增字段/索引/迁移脚本）
M1: 后端逻辑修改（精确到函数级）
M2: 前端适配（受影响的组件）
```

### 真实案例：任务重新评估与重新提取

```
M0: 数据库变更
  - test_result_dimensions 表新增 round_number 字段
  - 新增复合索引

M1: 后端重新提取逻辑
  - DeviceResultReextractor.reextract_for_task() — 新建
  - 驱动获取 → extract_results_from_archive() → 新旧记录替换
  - Fix/ASR 文件拼接逻辑修复

M2: 后端重新评估逻辑
  - EvaluationController.reevaluate_task_results() — 修改
  - 支持 reevaluate_type='all'/'failed'
  - 支持 reextract_device_output=true/false

M3: 前端适配
  - 重新评估按钮 → 弹窗选择参数 → 调用 API
```

### 人工审核重点

| 审核项 | 关注点 |
|--------|--------|
| 影响范围 | AI 是否准确识别了所有受影响的文件 |
| 向后兼容 | 修改是否会影响现有功能 |
| 数据迁移 | 数据库变更是否需要迁移脚本 |
| 回归测试 | 哪些现有功能需要重新测试 |

## 按里程碑实现代码

SPEC 审核通过后，按里程碑顺序逐步让 AI 实现代码。

### 每个里程碑的执行流程

```
1. AI 读取 SPEC 中该里程碑的实施步骤 + 参考设计文档
2. AI 生成代码（精确到文件和方法）
3. 人工审核代码
4. 执行该里程碑的验证标准
5. 验证通过 → 进入下一个里程碑
   验证失败 → 修正代码 → 重新验证
```

### 代码审核清单

#### 逻辑正确性
- [ ] 核心算法逻辑是否与设计文档一致
- [ ] 边界条件是否正确处理（空值、零值、最大值）
- [ ] 异步操作是否正确等待和错误处理

#### 性能
- [ ] 数据库查询是否使用批量操作
- [ ] 是否有不必要的循环嵌套
- [ ] 大数据量场景是否考虑分页/流式处理

#### 代码规范
- [ ] 命名是否符合项目规范
- [ ] 是否使用了项目已有的工具函数
- [ ] 组件大小是否合理（前端 < 300 行，后端函数 < 50 行）

#### 与 SPEC 一致性
- [ ] 实现是否覆盖了 SPEC 中该里程碑的所有步骤
- [ ] 是否引入了 SPEC 未规划的额外改动
- [ ] 文件路径和方法名是否与 SPEC 一致

### 常见 AI 代码缺陷

| 缺陷类型 | 表现 | 修正方式 |
|----------|------|----------|
| 数据库 N+1 查询 | 每个元素单独查一次数据库 | 改为批量查询 |
| 首个元素特殊处理遗漏 | offset[0] 硬编码为 0，忽略 delay | 从参数获取 |
| 组件过大 | 单文件 4000+ 行 | 拆分为子组件 |
| 响应式数据污染 | 编辑时直接修改原始数据 | 使用深拷贝 |
| 赋值覆盖 | `=` 覆盖而非 `+=` 叠加 | 检查赋值语义 |
| 参数硬编码 | 单元素场景硬编码默认值 | 从实际参数获取 |

## 三种场景的对比

| 维度 | A. 从0开始 | B. 新增模块 | C. 需求变更 |
|------|-----------|------------|------------|
| SPEC 规模 | 完整项目（8个里程碑） | 一个模块（5~6个里程碑） | 一个功能点（1~3个里程碑） |
| 代码基线分析 | 无现有代码 | 精确分析现有代码 | 精确分析受影响代码 |
| 里程碑粒度 | 模块级 | 功能级 | 函数级 |
| 并行策略 | 前后端可并行 | Track 级并行 | 通常串行 |
| 审核重点 | 架构合理性 | 兼容性 + 基线准确性 | 影响范围 + 向后兼容 |

## 效率分析

### 场景 A：从0开始

场景 A 的实际开发分两个阶段：**先让 AI 照 SPEC 生成全项目骨架**（得到的是不能直接用的半成品），**再将每个模块按场景 B/C 的方式细分迭代开发**。

**阶段一：全项目骨架生成（快速但不可直接用）**

| 任务 | 传统方式 | VibeCoding | 效率提升 |
|------|----------|------------|----------|
| SPEC 生成 | 3天写开发方案 | 半天 AI 生成 + 人工审核 | **6x** |
| 全项目骨架实现（8个里程碑） | 24天 | 2~3天 AI 按 SPEC 全量生成 | **8x~12x** |

> 阶段一的产出是一个"有形状但跑不起来"的半成品：目录结构、数据模型、接口定义等骨架代码已就位，但各模块的具体逻辑、边界处理、集成联调等都不可直接用。

**阶段二：按模块细分为场景 B/C 迭代开发（核心工作量）**

每个模块需要像场景 B 一样，重新分析当前代码基线 → 生成增量 SPEC → 按里程碑逐步实现。以 8 个里程碑为例：

| 模块 | 细分类型 | 迭代里程碑数 | VibeCoding 耗时（含审核验证） |
|------|----------|-------------|-------------------------------|
| 项目骨架 + 数据模型 | 场景 C（精确迭代） | 1~2 个 | 1天 |
| 核心功能模块1 | 场景 B（增量开发） | 3~4 个 | 2天 |
| 核心功能模块2 | 场景 B（增量开发） | 3~4 个 | 2天 |
| 测试执行引擎 | 场景 B（增量开发） | 4~5 个 | 3天 |
| 评估系统 | 场景 B（增量开发） | 2~3 个 | 1.5天 |
| 报告与导出 | 场景 B（增量开发） | 2~3 个 | 1.5天 |
| 前端页面集成 | 场景 B（增量开发） | 3~4 个 | 2天 |

**阶段二合计：约 13天**

**场景 A 总耗时对比**

| 阶段 | 传统方式 | VibeCoding | 说明 |
|------|----------|------------|------|
| 开发方案 | 3天 | 0.5天 | AI 生成 SPEC + 人工审核 |
| 全项目骨架 | 24天 | 2~3天 | AI 按 SPEC 全量生成（半成品） |
| 模块细分迭代 | （包含在上面） | 13天 | 每个模块按场景 B/C 迭代开发 |
| **合计** | **24天** | **16天** | **效率提升 ~1.5x** |

> **关键认知**：场景 A 的真正效率提升不在于"AI 一次性写完整个项目"，而在于：
> 1. 阶段一的骨架让每个模块的 B/C 开发省去了从零搭建的时间
> 2. SPEC 已明确每个模块的接口和依赖，减少了模块间返工
> 3. 每个模块的迭代开发可以复用场景 B 的高效流程（代码基线分析 → 增量 SPEC → 里程碑实现）

## 关键经验

1. **SPEC 审核是必须的**：不审核 SPEC 就开始写代码 = 在错误的地基上盖楼
2. **代码基线必须人工验证**：AI 标注"已实现"的模块，人工需要抽查确认
3. **里程碑验证不可跳过**：每个里程碑完成后必须执行验证标准，通过后才进入下一个
4. **大里程碑要拆 Phase**：超过 10 个步骤的里程碑应拆分为多个 Phase
5. **先跑通再优化**：先实现最小可用版本（V1），再迭代高级特性（V2）
6. **按 SPEC 实现，不要自由发挥**：AI 实现代码时应严格遵循 SPEC 中的步骤和文件路径

## 产出物清单

| **代码实现记录** | 按里程碑逐步实现代码，每个里程碑验证通过后进入下一个 | 按Track并行实现，Track间联调验证 | 按变更点精确实现，向后兼容验证 |
| **里程碑验证记录** | 每个里程碑的验证标准执行结果、问题修复记录 | Track级验证、模块级联调、回归测试范围 | 变更点验证、回归测试通过率 |

### 开发方案文档内容结构

SPEC 技能生成的开发方案文档遵循统一结构：

```
1. Context（背景与目标）
2. 决策记录
3. 当前代码基线（已完成模块 + 未实现模块）
4. 开发路线图（M0 → Mn）
5. 并行策略（哪些Track可并行，哪些有依赖）
```

每个里程碑包含：
- 目标（一句话描述完成标准）
- 实施步骤（精确到文件名和方法名）
- 关键文件列表
- 验证标准（如何确认里程碑完成）
- 参考设计文档

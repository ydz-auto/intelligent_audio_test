# 步骤四：联调与测试 — AI 白盒 + 人工黑盒

## 流程概览

测试与步骤三的 SPEC 里程碑紧密衔接：每个里程碑完成后执行验证，全部里程碑完成后进行系统级联调和黑盒测试。

```
步骤三里程碑验证（逐里程碑）
  │
  ▼
AI：生成单元测试（函数级别白盒测试）
  │
  ▼
人工：前后端联调 + 黑盒测试 + 回归测试
  │
  ▼
产出：测试报告、问题列表、联调问题记录
```

## 三种开发场景

| 场景 | 测试策略 | 联调重点 | 回归范围 |
|------|----------|----------|----------|
| **A. 从0开始** | 全量测试，所有模块都需要联调 | 前后端所有接口 | 无（首次开发） |
| **B. 新增功能模块** | 增量测试 + 回归测试 | 新旧模块交互的接口 | 现有功能是否受影响 |
| **C. 需求变更/迭代** | 精确测试变更点 + 回归测试 | 变更涉及的接口 | 变更可能影响的现有功能 |

## 角色分工

| 角色 | 职责 | 关键动作 |
|------|------|----------|
| AI | 白盒测试（后端 API） | **生成用例 + 执行**：直接调用后端 API，验证接口逻辑 |
| AI | 前后端联调测试 | **生成用例 + 低效率执行**：需要通过 MCP 操作前端，执行成本高 |
| 人工 | 联调 | 前后端接口对接、字段一致性检查、数据流验证 |
| 人工 | 黑盒测试 | 设计业务场景、执行端到端测试、验证用户体验 |
| 人工 | 回归测试 | 验证现有功能未被破坏 |

## 与 SPEC 里程碑的衔接

步骤三建立了"每个里程碑完成后验证"的机制，测试工作是里程碑验证的延伸：

| 阶段 | 测试类型 | 执行者 | 时机 |
|------|----------|--------|------|
| 里程碑验证 | SPEC 中定义的验证标准 | 人工 | 每个里程碑完成后 |
| 单元测试 | 函数级白盒测试 | AI 生成 + 人工审核 | 代码实现后 |
| 前后端联调 | 接口一致性检查 | 人工 | 前后端代码都完成后 |
| 黑盒测试 | 业务场景验证 | 人工 | 联调通过后 |
| 回归测试 | 现有功能验证 | 人工 | 场景 B/C 中必须执行 |

## AI 白盒测试

### AI 测试执行的能力分级

> **关键区分**：AI 直接调用后端 API 效率高，但操作前端需要通过 MCP，执行效率低

| 测试类型 | AI 能生成用例 | AI 能执行 | 执行效率 | 原因 |
|----------|--------------|----------|----------|------|
| **后端 API 白盒测试** | ✅ 是 | ✅ 是 | **高** | 直接调用后端 API（通过 RunCommand 或 HTTP 请求），不需要前端 |
| **前端单元测试** | ✅ 是 | ✅ 是 | **中** | 需要通过 MCP 执行 JS，但通常是快速操作 |
| **前后端联调测试** | ✅ 是 | ⚠️ 低效率 | **低** | 需要通过 MCP 操作前端（导航、填写、点击），执行成本高 |
| **端到端业务测试** | ✅ 是 | ⚠️ 低效率 | **低** | 需要通过 MCP 执行完整流程，长耗时用例成本高,网络环境不支持|

### API 白盒测试：AI 的高效场景

**真实案例**（AI 直接调用后端 API）：

```python
# AI 可以直接通过 RunCommand 执行
curl -X POST http://localhost:5000/api/v1/tasks/start \
  -H "Content-Type: application/json" \
  -d '{"task_id": "test_001", "cases": ["case_1", "case_2"]}'

# AI 可以直接读取后端日志
tail -f backend/logs/app.log
```

**优势**：
- 不需要通过 MCP 操作前端
- 可以快速验证后端逻辑
- 可以批量执行多个 API 测试用例

### 前后端联调测试：AI 的低效率场景

**典型流程对比**：

| 操作 | API 白盒测试（高效） | 前后端联调测试（低效） |
|------|---------------------|----------------------|
| 启动服务 | `RunCommand: python app.py` | `MCP: navigate_page` |
| 填写参数 | `RunCommand: curl POST` | `MCP: fill_form`（需要先截图获取元素） |
| 触发执行 | `RunCommand: curl POST` | `MCP: click`（需要先定位元素） |
| 获取结果 | `RunCommand: cat response.json` | `MCP: take_screenshot + evaluate_script` |
| 获取日志 | `RunCommand: tail -f logs` | `MCP: evaluate_script: console.log` |

**效率差异原因**：

| 因素 | API 白盒测试 | 前后端联调测试 |
|------|-------------|----------------|
| **调用方式** | 直接执行命令 | 需要通过 MCP 转换 |
| **前置操作** | 无需截图 | 需要先截图获取元素位置 |
| **等待时间** | 秒级响应 | 可能有 20+ 分钟的执行耗时 |
| **Token 消耗** | 低（一次性执行） | 高（多次截图+操作） |

### AI 生成的单元测试（后端为主）

AI 根据已实现的代码生成单元测试，覆盖函数级别的逻辑分支。

**真实案例**（`backend/tests/test_audio_engine_task_id_types.py`）：

```python
def test_stop_task_audio_by_pattern_handles_non_string_task_ids(monkeypatch):
    """task_id 为非字符串类型时，stop_task_audio_by_pattern 仍能正确停止"""
    audio_service.active_players = {
        123: {"dry": {"thread": None, "stop_event": threading.Event()}},
        "abc": {"dry": {"thread": None, "stop_event": threading.Event()}},
    }
    stopped = audio_service.stop_task_audio_by_pattern("*", "*")
    assert stopped == 2
    assert audio_service.active_players == {}
```

**项目中的测试文件**：

| 测试文件 | 测试目标 |
|----------|----------|
| `test_audio_engine_task_id_types.py` | 音频引擎 task_id 类型兼容性 |
| `test_api_task_dedup.py` | API 任务去重逻辑 |
| `test_task_control.py` | 任务控制（启动/停止/暂停） |
| `test_task_progress_time_fields.py` | 任务进度时间字段 |
| `test_schema_serialization.py` | Schema 序列化（前后端字段转换） |
| `test_naming_compatibility.py` | 命名兼容性（snake_case ↔ camelCase） |
| `test_report_header_edit.py` | 报告头部编辑 |
| `test_testcase_export_xlsx.py` | 测试用例导出 Excel |

### AI 白盒测试的优势与局限

| 优势 | 局限 |
|------|------|
| 覆盖所有逻辑分支（if/else、循环边界） | 只能测试单个函数，无法覆盖跨模块场景 |
| 自动生成 mock 数据 | 不了解业务语义，可能遗漏关键场景 |
| 快速生成大量基础用例 | 无法验证用户体验和前后端交互 |

## 前后端联调 — 最大痛点

> **核心约束**：AI 辅助联调受限于技术能力，人工联调仍是主要方式

### AI 辅助联调的技术限制

| 限制 | 具体表现 | 影响 |
|------|----------|------|
| **只能通过 MCP 调用 Chrome DevTools** | AI 无法直接查看前端代码运行状态，必须通过浏览器自动化工具 | 联调效率大幅降低 |
| **前端日志获取需要 Chrome DevTools** | AI 无法直接读取 console.log，必须通过 MCP 执行 JS 获取 | 每次获取日志都有额外开销 |
| **测试用例执行时间长** | 一个端到端测试用例可能超过 20 分钟 | AI 等待时间长，token 消耗大，交互成本高 |
| **无法实时观察前端渲染** | AI 只能看到最终状态，无法观察渲染过程中的中间状态 | 无法诊断动画、过渡、异步加载等问题 |

### AI 辅助联调的实际能力边界

| 能力 | AI 能做什么 | AI 不能做什么 |
|------|------------|---------------|
| **截图对比** | 通过 MCP 截取页面截图，对比前后状态 | 无法实时观察渲染过程 |
| **日志获取** | 通过 MCP 执行 JS 获取 console 日志 | 无法直接读取，需要额外操作 |
| **DOM 检查** | 通过 MCP 获取 DOM 结构和样式 | 无法实时观察 DOM 变化 |
| **接口抓包** | 通过 MCP 获取 Network 面板数据 | 无法实时观察请求过程 |
| **元素操作** | 通过 MCP 点击、填写表单 | 执行长耗时用例时 token 消耗大 |

### AI 辅助联调的典型流程（以端到端测试为例）

```
1. AI 通过 MCP 启动前端页面（navigate_page）
2. AI 通过 MCP 填写测试配置（fill_form）
3. AI 通过 MCP 触发执行（click）
   │
   ▼ ⚠️ 可能等待 20+ 分钟（执行耗时）
   │
4. AI 通过 MCP 截图查看结果（take_screenshot）
5. AI 通过 MCP 获取 console 日志（evaluate_script）
6. AI 通过 MCP 获取 Network 数据（list_network_requests）
7. AI 对比前后端日志，定位问题
```

**问题**：步骤 3-4 之间可能等待 20+ 分钟，期间：
- AI 的上下文会被压缩（token 消耗）
- 用户需要等待，无法实时交互
- 如果中途出错，需要重新执行

### 为什么人工联调仍是主要方式

| 维度 | AI 辅助 | 人工执行 |
|------|---------|----------|
| **实时观察** | 只能看到最终状态 | 可以实时观察渲染过程、动画、过渡 |
| **调试效率** | 需要通过 MCP 操作，有额外开销 | 可以直接使用 DevTools 调试 |
| **问题定位** | 需要多次截图+日志获取 | 可以直接在 DevTools 中定位 |
| **时间成本** | 执行长耗时用例时 token 消耗大 | 可以在等待期间做其他事情 |
| **交互成本** | 需要等待 AI 响应 | 可以即时调整测试策略 |

### 典型联调问题

| 问题类型 | 具体表现 | 影响 |
|----------|----------|------|
| 字段名不一致 | 后端返回 `speaker_name`，前端期望 `speakerName` | 数据无法正确显示 |
| 数据格式不一致 | 后端返回时间戳（秒），前端期望毫秒 | 时间显示错误 |
| 枚举值不匹配 | 后端 `status: "playing"/"stopped"`，前端 `status: 0/1` | 状态判断失败 |
| 空值处理不一致 | 后端返回 `null`，前端期望 `""` 或 `[]` | 空指针异常 |
| 分页参数不一致 | 后端 `page` 从 1 开始，前端 `page` 从 0 开始 | 数据错位 |

### 真实案例：前后端字段命名适配

项目中通过 Pydantic 的 `alias_generators` 实现了自动化的 snake_case ↔ camelCase 转换，从根本上解决了字段名不一致的联调问题。

**后端定义**（snake_case）：
```python
class TaskListItem(APIModel):
    task_id: str
    created_at: Optional[str] = None
    total_cases: Optional[int] = None
    completed_cases: Optional[int] = None
```

**前端接收**（自动转为 camelCase）：
```typescript
interface TaskListItem {
    taskId: string;
    createdAt?: string;
    totalCases?: number;
    completedCases?: number;
}
```

**核心机制**（`backend/schemas/base.py`）：
```python
class APIModel(BaseModel):
    model_config = ConfigDict(
        alias_generator=to_camel,      # 自动 snake_case → camelCase
        populate_by_name=True,          # 支持同时使用两种字段名
    )
```

> **经验**：在步骤二（技术方案设计）阶段就定义好命名适配机制，可以大幅减少联调阶段的字段名问题。

### 联调问题排查方法

1. **抓包对比**：使用浏览器 DevTools 对比 Request/Response
2. **日志对照**：同时查看前后端日志，确认数据流转
3. **最小复现**：用最简单的数据复现问题，排除干扰因素
4. **Schema 检查**：确认 Pydantic Schema 的 alias 是否正确生成

> **注意**：联调问题 AI 无法自动发现，只能人工联调时逐个排查。

**场景1：连续3个同说话人音频**

音频1: spk9, 2秒
音频2: spk9, 3秒
音频3: spk9, 4秒

```
音频1: spk9, 2秒
音频2: spk8, 3秒  → 与音频1无交集，可交叠
音频3: spk9, 4秒  → 与音频2无交集，但与音频1有交集
预期：需要验证跨音频的 speaker 感知逻辑
```

**场景3：前后端联调**
```
前端选择3个音频文件 → 后端播放 → 前端时间轴显示
验证：时间轴上的偏移量与后端计算一致
```

## 三种场景的测试策略

### 场景 A：从0开始 → 全量联调

从零开始的项目，所有模块都需要联调，工作量最大。

**联调顺序**（按依赖关系）：
```
1. 数据库 CRUD 接口联调（后端 ↔ 数据库）
2. 基础管理页面联调（前端 ↔ 后端 API）
   - 评估维度管理
   - 设备管理
   - 音频管理
3. 核心流程联调（前端 ↔ 后端 ↔ 设备/API）
   - 端到端测试流程
   - API测试流程
4. 报告与导出联调
```

**测试重点**：
- 所有页面的增删改查是否正常
- 前后端数据是否一致
- 测试执行流程是否完整
- 评估计算是否正确
- 报告生成和导出是否正确

### 场景 B：新增功能模块 → 增量联调 + 回归

以 voice_llm 改造为例，新增模块需要与现有系统联调，同时验证现有功能不受影响。

**联调顺序**（按 SPEC 里程碑）：
```
M1 验证: voice_llm 出现在算法列表 → DynamicForm 渲染正确
M2 验证: 创建 3 轮用例 → 编辑验证数据持久化 → 双记录架构正确
M3 验证: Mock 模式调用 set_volume/move_rail 返回成功
M4 验证: 3 轮 API 用例端到端执行 → LLM Judge 出分
M5 验证: 多轮报告展示 → 轮次表格/汇总/对比视图可用
```

**回归测试范围**：
| 现有功能 | 是否需要回归 | 原因 |
|----------|-------------|------|
| translation/ASR 测试 | ✅ 需要 | 共享执行器和评估管线 |
| 设备管理 | ❌ 不需要 | 未改动 |
| 音频管理 | ❌ 不需要 | 未改动 |
| 报告管理 | ✅ 需要 | 新增了多轮结果展示 |
| 任务管理 | ✅ 需要 | 新增了多轮进度推送 |

### 场景 C：需求变更/迭代 → 精确联调 + 回归

以"任务重新评估与重新提取"为例，变更点精确，联调范围小但回归测试重要。

**联调重点**：
```
1. 重新评估 API → 前端弹窗参数传递是否正确
2. 重新提取 API → 前端状态刷新是否及时
3. Fix/ASR 拼接 → 时间戳计算是否正确
```

**回归测试范围**：
| 现有功能 | 是否需要回归 | 原因 |
|----------|-------------|------|
| 正常评估流程 | ✅ 需要 | 修改了评估控制器 |
| 报告展示 | ✅ 需要 | TestResultDimension 记录可能变化 |
| 其他功能 | ❌ 不需要 | 未涉及 |

### AI 辅助联调的效率瓶颈

| 瓶颈 | 具体表现 | 解决方向 |
|------|----------|----------|
| **MCP 调用开销** | 每次获取前端信息都需要通过 MCP | 减少调用次数，批量获取数据 |
| **长耗时用例** | 端到端测试用例可能超过 20 分钟 | AI 只做截图/日志获取，不执行长耗时用例 |
| **Token 消耗** | 长时间等待会压缩上下文 | 分阶段执行，每阶段独立上下文 |
| **无法实时观察** | 只能看到最终状态，无法观察渲染过程 | 人工负责实时调试，AI 只做最终状态检查 |

## 关键经验

1. **AI 擅长后端 API 白盒测试**：
   - **生成用例 + 执行**：AI 可以直接调用后端 API，效率高（8x）
   - 不需要通过 MCP 操作前端
   - 可以批量执行多个 API 测试用例
2. **AI 可以生成前后端联调用例，但执行效率低**：
   - AI 可以生成测试用例（6x 效率提升）
   - 但执行需要通过 MCP 操作前端，效率低（1x）
   - 适合：用例生成、日志批量获取、最终状态检查
   - 不适合：长耗时用例执行、实时渲染调试
3. **联调是最大的效率瓶颈**：在步骤二就定义好接口规范（如字段命名适配机制）可以大幅减少联调时间
4. **测试场景设计不能省**：AI 生成的测试用例覆盖的是代码逻辑，不是业务逻辑
5. **回归测试范围要合理**：过小可能遗漏问题，过大浪费时间，按 SPEC 中的"不变部分"确定不需要回归的范围
6. **先跑通再优化**：先确保功能正确，再优化性能和边界
7. **联调问题要记录**：每次联调发现的问题记录到 `doc/issues/`，同类问题下次可以直接排查

### 联调问题记录示例（衔接步骤五）

典型的联调问题会记录到 `doc/issues/` 目录，成为步骤五（问题修复与回归）的输入：

- 字段名不一致：后端返回 `speaker_name`，前端期望 `speakerName`
- 数据格式不一致：后端返回时间戳（秒），前端期望毫秒
- 枚举值不匹配：后端 `status: "playing"/"stopped"`，前端 `status: 0/1`
- 空值处理不一致：后端返回 `null`，前端期望 `""` 或 `[]`

这些问题会在步骤五中由AI分析日志、生成修复代码，并在步骤六的Issue文档中完整记录。

> **注意**：AI 辅助联调的记录需要人工整理，AI 只能通过 MCP 获取数据，无法自动判断问题原因。

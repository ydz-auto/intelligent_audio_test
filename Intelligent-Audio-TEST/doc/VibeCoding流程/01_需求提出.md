# 步骤一：需求提出 — AI 引导完善，人定义目标

## 流程概览

需求提出是一个**渐进式细化**的过程。根据开发场景不同，AI 交互的起点和产出物不同，但核心模式一致：

```
人工：提出意图（原始需求 / 新功能描述 / 变更需求）
  │
  ▼
AI：结构化展开（拆分页面 / 写端到端示例 / 分析现有代码）
  │
  ▼
人工：确认/修正/补充
  │
  ▼
AI：深化产出（需求分析 / 数据建模 / 示例验证 / 变更澄清）
  │
  ▼
人工：评审确认
  │
  ▼
产出：可指导开发的需求文档
```

## 三种开发场景

| 场景 | 起点 | AI 交互策略 | 产出物 |
|------|------|-------------|--------|
| **A. 从0开始开发** | 一句话原始需求 | 先澄清页面功能 → 再数据建模 | 需求澄清文档 + 需求分析文档 |
| **B. 新增功能模块** | 已有系统 + 新功能描述 | 先写端到端示例验证理解 → 再提炼改造方案 | 端到端示例文档 + 改造方案总览 |
| **C. 需求变更/迭代** | 问题/Bug描述（模糊） | 先澄清问题 → 再确认期望 → 最后界定边界 | 变更需求澄清文档 |

## 角色分工

| 角色 | 职责 | 关键动作 |
|------|------|----------|
| 人工 | 提出意图 | 描述核心需求、技术约束、业务场景 |
| AI | 结构化展开 | 拆分功能、补充边界、数据建模、写示例 |
| 人工 | 确认修正 | 逐条检查、补充遗漏、修正不合理之处 |
| AI | 深化产出 | 根据确认结果生成最终文档 |
| 人工 | 评审定稿 | 确认文档可指导开发 |

## 场景 A：从0开始开发

> 完整走完全流程：原始需求 → 需求澄清 → 需求分析 → 数据建模

### 第一步：原始需求 → 需求澄清文档

#### 人工输入

原始需求通常只有一句话：

> 帮我开发一个音频算法自动化测试平台，需要有API测试功能和实机（端到端）测试功能
>
> — `doc/需求文档/原始需求.txt`

**关键原则**：原始需求不需要详细，但需要包含：
- 系统的核心定位（音频算法自动化测试平台）
- 主要功能模块（API测试 + 端到端测试）

#### PROMPT 1：需求拆分与页面规划

```
你是一个资深产品经理，擅长将模糊的业务需求拆解为清晰的功能模块和页面设计。

我的需求：
帮我开发一个音频算法自动化测试平台，需要有API测试功能和实机（端到端）测试功能

请按以下结构输出需求澄清文档：

1. 技术架构选型（前端框架、后端框架、数据库、编程语言）
2. 页面设计（每个页面包含哪些子页面，每个子页面的属性和功能需求）
3. 数据属性定义（每个实体的字段、类型、约束）
4. 功能需求列表（增删改查、搜索、筛选、导出等）
5. 界面特点（布局风格、可视化需求、响应式要求）

要求：
- 每个页面的属性要列全，包括状态字段、逻辑删除、时间戳等通用字段
- 功能需求要具体，不要笼统地说"增删改查"，要说明具体的业务场景
- 列出需要人工确认的决策点
```

#### AI 输出要点

AI 从一句话拆出完整的功能规格：

**技术架构选型**：
```
Electron^29.4.4 + HTML + VUE 3 + Flask + PostgreSql + Python 3.12 + MVC
```

**页面拆分**（从一句话拆出 8+ 个页面）：

| 页面 | 子页面数 | 核心功能 |
|------|----------|----------|
| 端到端测试页面 | 4个（选用例→选设备→监控→完成） | 向导式测试流程 |
| API测试页面 | 4个（选用例→选API→监控→完成） | 向导式测试流程 |
| 测试任务记录页面 | - | 历史任务管理 |
| 评估维度管理页面 | - | 评估指标配置 |
| 播放设备管理页面 | - | 音频设备管理 |
| 音频统一管理页面 | - | 音频导入和管理 |
| 声压级映射管理页面 | - | 声压级校准 |
| 日志查看页面 | - | 系统日志 |

**属性定义示例**（AI 补充了大量人工未提及的字段）：
```
用例属性：
- 背景噪声及声压级（每个用例最多一个）
- 干声音频及声压级（每个用例至少一个，每个音频声压级可以单独配置）
- 信噪比（由背景噪声和声压级得到，多音频声压级不一致则不显示）
- 用例标签列表
- 评估维度列表（弹窗或下拉选择，仅可选择，允许多选）
- 用例状态：生效/失效
```

**AI 补充的业务规则**（人工未提及）：
- 多干声音频处理：音频ASR文本和翻译文本按播放顺序拼接
- 噪声和干声可同时播放，干声音频按顺序播放
- API测试用例与端到端测试用例分开管理
- 设备下线则对应用例不可执行

| 检查项 | 结论 | 说明 |
|--------|------|------|
| 页面拆分是否完整 | ✅ | 覆盖了所有业务场景 |
| 属性字段是否齐全 | ✅ | AI 补充了逻辑删除、时间戳等通用字段 |
| 业务规则是否正确 | ⚠️ 需修正 | 部分播放规则需要调整 |
| 技术选型是否合理 | ✅ | Electron + Flask 符合桌面端需求 |

### 第二步：需求澄清 → 需求分析文档

#### PROMPT 2：数据建模与工程分析

```
你是一个系统架构师，擅长从功能需求中提炼数据模型和技术方案。

需求澄清文档：
{粘贴需求澄清文档.md 的内容}

请帮我完成：
1. 数据模型设计（每个表的字段、类型、约束、外键关系）
2. 关系映射（表与表之间的关联方式）
3. 功能流程设计（端到端测试流程、API测试流程）
4. 技术风险评估（可能的技术难点和缓解策略）
5. 优先级矩阵（功能模块的开发优先级）
6. 跨团队协调任务（前端、后端、测试各自的职责）
7. 部署和维护方案

要求：
- 数据模型要包含所有通用字段（id、create_time、update_time、logic_delete）
- 关系映射要说明是一对多还是多对多，以及中间表的设计
- 技术风险要具体，给出缓解策略
```

#### AI 输出要点

**数据模型**（AI 从功能需求中建模出 10+ 张表）：

```
test_case          — 测试用例表
audio              — 音频表
test_case_audio_relation — 用例音频关联表（中间表）
test_device        — 测试设备表
playback_device    — 播放设备表
test_api           — 测试API表
evaluation_dimension — 评估维度表
test_task          — 测试任务表
test_result        — 测试结果表
test_report        — 测试报告表
```

**关系映射**（AI 梳理的表间关系）：
- 测试用例与音频：通过关联表实现多对多
- 测试用例与评估维度：多对多
- 测试任务与测试用例：多对多
- 测试任务与测试结果：一对多

**技术风险**（AI 识别的风险）：
- 音频播放同步性风险 → 使用 PyAudio 精确控制
- 多任务并行处理风险 → 任务队列 + 资源限制
- 数据存储性能风险 → 索引优化 + 数据分区

#### 人工确认要点

| 检查项 | 结论 | 说明 |
|--------|------|------|
| 表结构是否覆盖所有功能 | ✅ | 所有页面功能都有对应的数据支撑 |
| 关系映射是否合理 | ⚠️ 需调整 | 部分多对多关系需要中间表 |
| 优先级是否正确 | ✅ | 核心功能优先，辅助功能后置 |
| 技术风险是否遗漏 | ⚠️ 需补充 | 补充了评估API稳定性风险 |

#### 产出物

`doc/需求文档/需求分析文档.md` — 579 行，包含完整的数据模型、流程设计、风险评估

## 场景 B：在已有系统上新增功能模块

> 以 voice_llm 改造为例：在已有的音频测试平台上，新增"语音交互大模型"测试能力

### 与场景 A 的核心差异

| 维度 | 场景 A（从0开始） | 场景 B（新增功能） |
|------|-------------------|-------------------|
| 起点 | 一句话 | 已有系统 + 新功能描述 |
| 架构选型 | 需要 AI 建议 | 已确定，不需要 |

## 场景 C：需求变更/迭代优化

> 以"任务重新评估与重新提取"功能为例：在已有系统上增加或修改功能

### 与场景 A/B 的核心差异

| 维度 | 场景 A（从0开始） | 场景 B（新增模块） | 场景 C（需求变更） |
|------|-------------------|-------------------|-------------------|
| 起点 | 一句话 | 新功能描述 | 问题/Bug描述（模糊） |
| 范围 | 整个系统 | 一个功能模块 | 一个功能点 |
| AI 交互策略 | 先澄清再建模 | 先写示例再出方案 | **先澄清问题 → 再确认期望 → 最后界定边界** |
| 核心产出 | 需求文档体系 | 改造方案总览 | **澄清后的变更需求** |
| 文档特点 | 全面但粗粒度 | 聚焦模块级架构 | 问题明确、期望清晰、边界确定 |

### 第一步：问题/Bug描述 → 澄清后的变更需求

> 场景 C 的核心特点是：用户输入往往是模糊的问题描述，需要 AI 引导澄清

#### 人工输入（模糊的问题描述）

用户可能只知道"遇到了什么问题"，但不一定清晰地表述：

```
重新评估功能有问题
- 重新评估时好像没法重新提取设备输出
- 想只重新评估失败的用例，但好像不支持
- Fix文件和ASR文件拼接有时候结果不对
```

**关键问题**：这种输入缺失了：
- 问题的具体表现是什么？
- 期望的改进方向是什么？
- 改动的边界在哪里？

#### PROMPT 5：需求澄清引导

```
你是一个资深产品经理，需要帮助用户澄清变更需求。

用户的问题描述：
{粘贴上面的模糊描述}

请按以下结构引导用户澄清需求：

## 1. 问题确认（AI 分析现有功能后提问）
- 读取现有功能设计文档 `doc/功能设计文档/01_测试执行/重新评估功能设计文档.md`
- 分析现有代码实现（如有）
- 向用户确认问题的具体表现：
  Q1: "重新评估时，您希望重新提取的是哪些数据？是设备原始输出还是处理后结果？"
  Q2: "只重新评估失败用例，是指跳过已通过的用例，还是覆盖它们的结果？"
  Q3: "Fix/ASR拼接不对具体是什么场景？能提供一个出错的例子吗？"

## 2. 期望明确（AI 基于问题确认后追问）
- 向用户确认期望的改进方向：
  Q4: "重新提取后，旧结果如何处理？删除还是保留历史？"
  Q5: "筛选失败用例，是按 TestResult.status='failed' 还是按评估维度失败？"
  Q6: "拼接逻辑修复后，是否需要保留旧版本兼容？"

## 3. 边界界定（AI 基于期望明确后追问）
- 向用户确认改动的边界：
  Q7: "这次改动是否涉及前端界面修改？"
  Q8: "是否需要新增数据库字段或修改表结构？"
  Q9: "是否有其他模块会受到影响？"

## 4. 澄清结果输出
- 根据用户回答，生成澄清后的变更需求文档
```

#### AI 输出（引导式澄清）

AI 会分多轮交互，逐步引导用户澄清：

**第一轮：问题确认**

AI 分析现有设计后，向用户提问：
```
我已阅读现有重新评估功能设计文档，发现当前实现是：
- 重新评估时使用已有 TestResult.device_output（未重新提取）
- 不支持按状态筛选，只能重新评估整个任务的所有用例
- Fix/ASR 拼接逻辑在时间重叠时有 Bug

请确认：
Q1: 重新提取的数据来源是存档日志还是实时采集？
Q2: 只重新评估失败用例，是指跳过已通过的用例，还是覆盖它们的结果？
Q3: Fix/ASR 拼接出错的具体场景是？（请提供示例）
```

**第二轮：期望明确**

用户回答后，AI 追问：
```
根据您的回答，我理解期望是：
- 从存档日志重新提取设备输出
- 跳过已通过的用例，只处理失败的
- Fix/ASR 时间重叠时，删除重叠的 ASR 片段用 Fix 替换

请确认期望：
Q4: 重新提取后，旧 TestResult 如何处理？
Q5: 失败用例的定义是 TestResult.status='failed' 吗？
Q6: 拼接逻辑修复后，旧结果是否需要保留兼容？
```

**第三轮：边界界定**

用户确认期望后，AI 追问：
```
请确认改动边界：
Q7: 是否需要新增前端界面（如筛选选项、重新提取按钮）？
Q8: 是否需要新增数据库字段（如 reextract_time）？
Q9: 其他模块是否受影响（如评估服务、设备驱动）？
```

#### 产出物

**`doc/需求文档/变更需求澄清文档.md`** — 包含：
- 问题确认：问题的具体表现、影响范围
- 期望明确：改进方向、目标状态
- 边界界定：改动范围、涉及模块、数据结构变化
- 约束条件：兼容性要求、性能要求、时间限制

> **注意**：场景 C 在步骤一只产出"澄清后的变更需求"，技术细节（API接口、流程设计、数据结构等）属于步骤二（技术方案设计），不在本步骤涉及。

## 效率分析

### 步骤一的核心任务界定

**重要说明**：本效率分析只覆盖步骤一（需求提出）的任务，不包含步骤二（技术方案设计）的任务：

| 步骤一任务 | 包含内容 | 不包含内容（属于步骤二） |
|-----------|----------|------------------------|
| 需求澄清 | 功能拆分、页面规划、属性定义、端到端示例、问题确认 | 改造方案设计、技术选型决策 |
| 需求分析 | 数据建模、关系映射、业务流程、技术风险识别 | 功能设计文档、接口定义、技术实现方案 |
| 澄清过程 | 三轮交互（问题→期望→边界） | 增量设计文档、API设计 |

### 场景 A：从0开始开发

**传统方式（真实时间估算）**：
- 需求描述：人工写文档、评审、修改、对齐 → **2-3周**
- 页面拆分：业务部门对齐、技术部门评审、反复修改 → **1-2周**
- 数据建模：DBA评审、业务确认、字段对齐 → **2-3周**
- 技术风险评估：技术方案讨论、风险清单整理 → **1周**

**VibeCoding（AI辅助加速）**：
- 需求描述：30分钟口述 + AI生成初稿 → **半天人工评审对齐**
- 页面拆分：AI生成初稿（1小时） → **2-3天人工评审、对齐业务和技术**
- 数据建模：AI生成初稿（2小时） → **3-5天人工评审、DBA确认、业务对齐**
- 技术风险评估：AI识别风险清单（1小时） → **1-2天人工补充、团队讨论**

**效率提升**：
| 任务 | 传统方式 | VibeCoding（AI初稿+人工对齐） | 效率提升 | 关键点 |
|------|----------|------------------------------|----------|--------|
| 需求描述 | 2-3周 | **半天** | **20-40x** | AI生成初稿后，人工评审对齐时间大幅缩短 |
| 页面拆分 | 1-2周 | **2-3天** | **3-7x** | AI生成完整页面规划，人工聚焦业务对齐 |
| 数据建模 | 2-3周 | **3-5天** | **3-6x** | AI生成数据模型，人工聚焦DBA评审和业务确认 |
| 技术风险评估 | 1周 | **1-2天** | **3-5x** | AI识别常见风险，人工补充项目特有风险 |

**核心洞察**：AI的价值在于**快速生成初稿**，人工时间从"从零写文档"转变为"评审对齐AI初稿"。

## 关键经验

### 通用经验

1. **人工确认不可省略**：AI 产出的每一份文档都需要人工逐条检查，AI 会遗漏业务特有的约束
2. **多轮交互优于一次性生成**：每一轮聚焦一个目标，前一轮的产出是后一轮的输入
3. **关注 AI 遗漏的场景**：AI 倾向于覆盖通用场景，特定业务场景需要人工补充
4. **先确认再深化**：不要在未确认的文档上继续深化，错误会层层放大

### 场景特有经验

| 场景 | 关键经验 |
|------|----------|
| **A. 从0开始** | 原始需求越具体，AI 完善质量越高；技术选型需要人工确认 |
| **B. 新增功能** | 先写端到端示例再出方案，用具体数据验证 AI 理解；列出"不变部分"避免过度改动 |
| **C. 需求变更** | 必须让 AI 先分析现有功能和代码，再澄清问题、期望和边界；不要在问题未澄清前直接生成技术设计 |

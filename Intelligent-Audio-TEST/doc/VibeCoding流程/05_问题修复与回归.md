# 步骤五：问题修复与回归 — AI 分析日志，人验证修复

## 流程概览

```
问题发现 → AI 分析日志 → AI 生成修复代码 → 人工验证 → 回归测试
```

## 角色分工

| 角色 | 职责 | 关键动作 |
|------|------|----------|
| 人工 | 发现问题 | 执行测试、用户反馈、日志监控 |
| AI | 分析定位 | 解析日志、定位问题根因、生成修复代码 |
| 人工 | 验证修复 | 确认修复方案正确、执行回归测试 |

## 案例1：多音频并行播放 Bug

### 问题描述（人工发现）

只有一个音频能播放，其他音频丢失。

### AI 分析过程

```
1. 解析 play_multi 的 callback 函数
2. 定位到 out_buffer 赋值逻辑
3. 发现问题：使用 = 赋值导致后续音频覆盖前面的音频
```

### 修复方案

```python
# 修复前：赋值覆盖
out_buffer[ch_idx:ch_idx+limit] = audio_data[:limit]

# 修复后：叠加混合
out_buffer[ch_idx:ch_idx+limit] += audio_data[:limit]
```

### 人工验证

| 验证项 | 结论 | 说明 |
|--------|------|------|
| `+=` 混合逻辑 | ✅ 正确 | 多路音频数据正确叠加 |
| 溢出风险 | ✅ 无风险 | 音频数据为 float32，叠加不会溢出 |
| 实际测试 | ✅ 通过 | 多音频同时播放，声音正常混合 |

## 案例2：前端报告页面并发控制与返回导航 Bug

### 问题描述（人工发现）

1. 快速点击多个任务的"查看报告"按钮，会同时打开多个报告页面
2. 从测试任务打开的报告关闭后跳转到历史报告页面，而非返回测试任务页面

### AI 分析过程

```
1. 检查 tasks.ts 的 viewTaskReport 函数
2. 发现函数没有防止重复点击的限制机制，每次点击都会触发报告生成并跳转
3. 检查 ReportView.vue 的 goBack 函数
4. 发现函数硬编码跳转到 /history-reports，而非使用 router.back() 返回上一页
```

### 修复方案

```typescript
// ---- 问题1：添加并发控制 ----
const isGeneratingReport = ref(false);

const viewTaskReport = async (task: Task) => {
  // 已在报告详情页则阻止
  if (router.currentRoute.value.name === 'reportView') {
    notification.info('当前已有报告打开，请先关闭当前报告');
    return;
  }
  // 正在生成中则阻止
  if (isGeneratingReport.value) {
    notification.info('正在生成报告，请稍候...');
    return;
  }

  isGeneratingReport.value = true;
  notification.info('正在生成报告，请稍候...');
  try {
    const result = await reportService.viewTaskReport(task);
    if (result && result.id) {
      notification.success('报告生成成功');
      router.push({ name: 'reportView', params: { id: result.id } });
    }
  } catch (error) {
    console.error('Failed to view task report:', error);
    notification.error('报告生成失败');
  } finally {
    isGeneratingReport.value = false;
  }
};

// ---- 问题2：修复返回导航 ----
// 修复前：硬编码跳转
const goBack = () => router.push('/history-reports')

// 修复后：返回上一页
const goBack = () => router.back()
```

### 人工验证

| 验证项 | 结论 | 说明 |
|--------|------|------|
| 并发控制 | ✅ 正确 | 快速多次点击仅生成一个报告，后续点击显示提示 |
| 返回导航 | ✅ 正确 | 从测试任务打开报告后关闭，正确返回测试任务页面 |
| 标志重置 | ✅ 正确 | `finally` 块确保 `isGeneratingReport` 无论成功或失败都会重置 |

## 问题修复流程详解

### 第一步：问题收集

```
问题报告模板：
- 问题现象：{描述观察到的异常行为}
- 复现步骤：{详细的操作步骤}
- 预期行为：{应该是什么样的}
- 实际行为：{实际是什么样的}
- 环境信息：{操作系统、Python版本、依赖版本}
- 相关日志：{错误日志片段}
```

### 第二步：AI 分析

将问题报告和相关日志提供给 AI，使用以下 Prompt：

```
你是一个 Python 调试专家。

问题描述：
{粘贴问题报告}

相关日志：
{粘贴错误日志}

相关代码：
{粘贴可能相关的代码片段}

请帮我：
1. 分析问题的根本原因
2. 定位到具体的代码行
3. 生成修复代码
4. 说明修复可能带来的副作用
```

### 第三步：人工验证

验证清单：
- [ ] 修复方案是否解决了原始问题
- [ ] 修复是否引入新的问题
- [ ] 修复是否影响其他功能
- [ ] 边界条件是否正确处理
- [ ] 性能是否有影响

### 第四步：回归测试

```
回归测试范围确定原则：
1. 修复的函数 → 必须测试
2. 调用修复函数的上层函数 → 必须测试
3. 与修复函数共享数据的函数 → 建议测试
4. 完全不相关的功能 → 可选测试
```

## 常见 Bug 模式

| Bug 模式 | 表现 | AI 定位难度 | 修复复杂度 |
|----------|------|-------------|-----------|
| 赋值覆盖 | 数据丢失 | 低 | 低（`=` → `+=`） |
| 参数硬编码 | 参数不生效 | 低 | 低（硬编码 → 变量引用） |
| 异步竞态 | 偶发性错误 | 高 | 中（需要加锁或队列） |
| 内存泄漏 | 内存持续增长 | 中 | 中（需要正确释放资源） |
| 类型不匹配 | 运行时异常 | 低 | 低（添加类型转换） |

### 场景 A：从0开始（两阶段累计）

场景 A 的开发分两阶段（骨架生成 + 模块迭代），问题修复也随之分阶段：

**阶段一：骨架阶段的问题修复**

AI 全量生成的骨架代码问题密度高，但以结构性问题为主（import 错误、依赖缺失、路由注册遗漏、Schema 不匹配），定位和修复都比较直接。

| 指标 | 传统方式 | VibeCoding | 说明 |
|------|----------|------------|------|
| 预计 Bug 数 | — | 15~25 个 | 骨架代码问题密度高 |
| 单个 Bug 修复 | 2小时 | 30分钟 | **4x**，结构性问题 AI 定位快 |
| 阶段一累计 | — | 1~2天 | 集中修复骨架的结构性问题 |

**阶段二：模块迭代阶段的问题修复**

每个模块按场景 B 开发后，问题更偏向业务逻辑（字段映射、边界条件、异步时序），AI 定位效率与单次修复基准一致。

| 指标 | 传统方式 | VibeCoding | 说明 |
|------|----------|------------|------|
| 单模块预计 Bug 数 | 3~5 个 | 3~5 个 | Bug 数量取决于模块复杂度 |
| 单个 Bug 修复 | 2小时 | 30分钟~1小时 | **2x~4x**，业务问题需要更多上下文 |
| 全模块累计（N个模块） | N×1天 | N×半天 | **~2x** |

**场景 A 问题修复总耗时对比**

| 阶段 | 传统方式 | VibeCoding | 效率提升 |
|------|----------|------------|----------|
| 骨架问题修复 | （包含在开发中） | 1~2天 | — |
| 模块迭代问题修复 | 约8天 | 约4天 | **2x** |
| **合计** | **约8天** | **5~6天** | **~1.5x** |

> **关键认知**：场景 A 的问题修复效率提升有限（~1.5x），原因是：
> 1. 骨架阶段 Bug 多但修复快（结构性问题），AI 优势明显
> 2. 模块迭代阶段 Bug 少但定位慢（业务逻辑问题），需要人工判断
> 3. 修复验证和回归测试无法压缩，始终需要人工执行

## 关键经验

1. **日志越完整，AI 定位越准确**：确保日志包含足够的上下文信息
2. **人工验证不可省略**：AI 的修复方案可能引入新问题
3. **回归测试范围要合理**：过小可能遗漏问题，过大浪费时间
4. **记录修复过程**：同类 Bug 下次可以直接复用修复方案

## 产出物清单

所有场景的问题修复与回归阶段都产出三类文档，只是根据场景特点具体内容不同：

| 产出物类型 | 场景A（从0开始） | 场景B（新增功能） | 场景C（需求变更） |
|------------|------------------|-------------------|-------------------|
| **问题分析报告** | 全量问题分析（架构问题、性能问题、兼容性问题） | 增量问题分析（新旧模块交互问题、兼容性问题） | 变更点问题分析（向后兼容问题、边界条件遗漏） |
| **修复代码与验证** | 问题根因分析、修复代码、验证结果、回归测试通过率 | 修复影响范围评估、兼容性验证、现有功能回归结果 | 变更点修复、向后兼容验证、回归测试范围确认 |
| **Issue文档** | 问题现象、根因分析、修复方案、测试验证（完整记录） | 问题修复过程、兼容性处理方案、回归测试结果 | 变更点问题记录、向后兼容方案、风险评估 |

### 具体文件路径示例

| 产出物类型 | 文件路径 | 说明 |
|------------|----------|------|
| **Issue文档** | `doc/issues/` | 问题现象、根因分析、修复方案、测试验证 |

### Issue文档结构（衔接步骤六）

Issue文档会成为步骤六（设计文档输出）的重要组成部分，记录所有联调中发现的问题和修复过程：

```markdown
# 问题标题

## 问题现象
{描述观察到的异常行为}

## 根因分析
{分析问题原因，定位到具体代码行}

## 修复方案
{代码修改、配置调整}

## 测试验证
{验证步骤、测试结果}
```

这些Issue文档在步骤六中会与架构文档、接口文档一起，形成完整的设计文档包，方便后续排查问题和迭代。

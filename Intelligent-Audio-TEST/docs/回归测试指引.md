# 全量回归测试指引（集成工程师）

> INT-96 落地。回归命令由串行升级为并行（pytest-xdist）；本文是集成侧的唯一口径来源。

## 命令

并行回归（默认口径）：

```bash
HEALTH_URL=http://localhost:1 python -m pytest tests/ -n 8 --dist loadgroup -q --tb=short
```

- `HEALTH_URL` 死端口对齐基线口径（tests/api 83 例跳过，与历史基线可比）。
- `-n 8`：本机（20 逻辑核）实测最优。`-n auto`（20 worker）可用但更慢（35s vs 33s），
  且会诱发 `test_int68_api_rms_spl_foundation::test_stale_concurrent_commit_not_merged_into_write`
  的时序抖动（负载敏感并发用例，-n≥12 实测 3/5 次抖动，-n 8 三次全稳）。

串行回归（回退口径）：

```bash
HEALTH_URL=http://localhost:1 python -m pytest tests/ -q --tb=short
```

## 失败判定规则

并行失败时，**同口径串行重跑一次**再定性，并在集成卡评论记录两种结果：

| 现象 | 定性 | 动作 |
|---|---|---|
| 并行失败，串行也失败 | 代码问题或已知存量 | 对照下方已知失败族判定是否存量；否则开缺陷卡 |
| 并行失败，串行通过 | 并行环境问题 | 评论记录两种结果；先复跑并行一次确认，仍复现则降 `-n` 重试并@开发侧排查该用例的并行隔离性 |

已知存量失败族（INT-94 在档，单跑可复绿，判定基线时豁免）：

- `tests/integration/test_int42_dispatch_failure_convergence.py`（INT-42 分发收敛）
- `tests/integration/test_task_execute_real_chain.py`（task_execute 执行链，含已知负载敏感 flaky `test_start_execute_progress_terminal`）
- `tests/integration/test_published_task_benchmark_real_chain.py`（顺序污染族）

## 实测基线（2026-10-10，干净 HEAD db8db540 + 本卡改动，隔离 worktree，20 逻辑核机器）

| 口径 | 结果 | 耗时 |
|---|---|---|
| 串行 | 1535 passed / 8 failed / 4 errors / 83 skipped | 82.18s |
| 并行 -n 8 --dist loadgroup | 与串行逐项一致（含失败集） | 33.5~38.2s（三次） |
| 并行 -n auto --dist loadgroup | 与串行逐项一致（含失败集） | 35.1~41.2s（两次，重分组前 41~48s） |

提速约 2.2~2.5 倍。未达 issue 目标 ≤1/3 的原因：本机串行基线本就只有 82s（issue 估计的
30-60 分钟系早期共享树受干扰口径），且套件耗时大头是轮询等待类测试（不随 CPU 并行压缩）
与每 worker 全量收集导入，非 CPU 瓶颈。

## xdist 机制说明（新增顺序污染夹具族时必读）

- 每 worker 是独立进程，进程级临时库按 worker 命名隔离（`int55_proc_gw<N>_`，
  串行为 `int55_proc_main_`）；worker 内强制不继承控制器进程的兜底库 URL
  （tests/conftest.py，继承会导致全 worker 共享同一 sqlite 文件 → DDL 竞态）。
- INT-55 顺序污染夹具族经 `tests/conftest.py::_XDIST_GROUP_RULES` 锁入
  `--dist loadgroup` 同组（auth_e2e：guest/admin 种子序；g3_e2e：G3 HTTP e2e），
  同组用例固定同一 worker 且保持收集序。新增同族测试文件时在该表登记即可。
- transfer e2e（test_data_transfer_*）未分组：三文件均按可单文件独立运行设计
  （自带独立临时库 + 幂等建表），实测拆分并行与同组结果一致，拆开后回归提速更优。

## 测试数据卫生约定（run-tag 夹具清理，INT-179 沉淀）

验收 / 集成类测试若可能触碰共享库，必须遵循「测试残留不落共享库」约定。风险
根因：运行环境已显式设置 `DATABASE_URL` 时，模块级 `os.environ.setdefault`
不生效，测试库隔离失效——登录页公开提供方列表曾被验收残留污染（INT-179 缺陷
三根因）。

约定（现行实现见 `tests/unit/oauth_fixture_cleanup.py`）：

- 测试模块创建的提供方 / 绑定 / 用户等夹具数据一律携带**运行级唯一 run tag**
  （uuid hex8 / pid），slug、用户名等可识别字段以 tag 结尾，确保清理可精确圈定。
- 模块 teardown 按 tag 调用 `purge_oauth_test_fixtures(tag)` 清理：先关联表后
  主体，兼容有无外键约束两种库形态；目标库缺表直接跳过（缺表即不可能有残留）；
  tag 未命中任何行时幂等无操作。
- 防误伤回归锁定：`test_purge_scoped_to_tag` 单测保证清理范围仅限本 run tag，
  不得误删非本 run 数据。
- 已按此约定落地的消费模块：test_g3_auth_http_e2e / test_g3_oauth_provider_management
  / test_int147_auth_alignment / test_int179_login_chain_fix / test_auth_empty_email_users。
  新增触碰共享库的验收测试时照此办理。

## 推送前冒烟门禁（INT-314，INT-95 主链验收精简版）

全量回归之外，每次批次推送前必须再过**四步主链冒烟**（INT-95 主链实机验收
2026-10-13 通过后的固化条款；API/E2E 物理链全量口径仍归验收卡，不进门禁）：

```
python scripts/smoke_gate.py            # 仓库根执行（项目环境 python）
python scripts/smoke_gate.py --json     # 机器可读结果，推送卡留证用
```

门禁内容（一键执行，自动确保前置）：

| 步骤 | 断言 |
|---|---|
| 前置 | 并行隔离栈 :6000（库 `intelligent_audio_test_test`）复用或自动拉起；裁判替身 :5097（INT-182）复用或自起自收；隔离库 RBAC/admin/voice_llm/turn_eval 种子幂等引导；维度端点归位 → :5097；dry 样例 wav（`doc/voice_llm/样例/2026144010.wav`、`2026144019.wav`）存在——`*.wav` 被 `.gitignore` 排除，全新检出 / 新 worktree 需先从主检出复制，缺失时 S2 在任何写操作之前以 GateFail 失败（带完整路径），不产生残留 |
| S1 登录 | `GET /auth/login/encryption-key` 白名单非 401 → RSA-OAEP 前端同款提交 → access_token |
| S2 建用例 | dry 样例上传（presign→OSS→complete-direct）→ voice_llm API 用例（多轮 rounds + turn_eval 维度绑定） |
| S3 dry 执行 | mock 适配器 api 任务 start → 终态 → 执行+评估双 completed（读 task_case_relations 防假绿） |
| S4 报告 | generate-task → 完成终态 → summary 非空 |

**通过标准**：`4/4 步 PASS —— 门禁通过，可推送`，退出码 0；任一步失败输出
响应原文与定位，退出码 1。**数据零残留**（自建自清 + 按 run tag 终检）是
门禁通过的一部分，残留即 FAIL。失败路径同守清理与零残留终检：资源「创建即
登记」，任一步失败（含非 GateFail 异常，如 AssertionError）仍按 registry
全量清理并执行终检；`--json` 恒输出（含 `fail_detail` / `residue` / `tag`），
失败留证同样机器可读。

隔离纪律（INT-246）：本门禁含写操作，只打并行隔离栈 :6000——栈指向共享业务库
时门禁拒绝执行；绝不写 `intelligent_audio_test`。冒烟期间自起的替身/栈：栈为
常驻隔离栈（复用优先，勿随手停），替身仅自起时回收、常驻实例不动。

推送卡留证：推送评论必须附 `--json` 输出的四步结果（PASS/FAIL 原文），
作为「冒烟通过」的证据记录。

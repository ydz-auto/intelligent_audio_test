# 全量回归测试指引（集成工程师）

> INT-96 落地。回归命令由串行升级为并行（pytest-xdist）；本文是集成侧的唯一口径来源。

## 命令

并行回归（默认口径）：

```bash
HEALTH_URL=http://localhost:1 python -m pytest tests/ -n 8 --dist loadgroup -q --tb=short
```

- `HEALTH_URL` 死端口对齐基线口径（tests/api 83 例跳过，与历史基线可比）。
- `-n 8`：本机（20 逻辑核）实测最优。`-n auto`（20 worker）可用但更慢（35s vs 33s），
  且会诱发 `test_int68_api_rms_spl_foundation::test_stale_concurrent_commit_not_merged_into_write`
  的时序抖动（负载敏感并发用例，-n≥12 实测 3/5 次抖动，-n 8 三次全稳）。

串行回归（回退口径）：

```bash
HEALTH_URL=http://localhost:1 python -m pytest tests/ -q --tb=short
```

## 失败判定规则

并行失败时，**同口径串行重跑一次**再定性，并在集成卡评论记录两种结果：

| 现象 | 定性 | 动作 |
|---|---|---|
| 并行失败，串行也失败 | 代码问题或已知存量 | 对照下方已知失败族判定是否存量；否则开缺陷卡 |
| 并行失败，串行通过 | 并行环境问题 | 评论记录两种结果；先复跑并行一次确认，仍复现则降 `-n` 重试并@开发侧排查该用例的并行隔离性 |

已知存量失败族（INT-94 在档，单跑可复绿，判定基线时豁免）：

- `tests/integration/test_int42_dispatch_failure_convergence.py`（INT-42 分发收敛）
- `tests/integration/test_task_execute_real_chain.py`（task_execute 执行链，含已知负载敏感 flaky `test_start_execute_progress_terminal`）
- `tests/integration/test_published_task_benchmark_real_chain.py`（顺序污染族）

## 实测基线（2026-10-10，干净 HEAD db8db540 + 本卡改动，隔离 worktree，20 逻辑核机器）

| 口径 | 结果 | 耗时 |
|---|---|---|
| 串行 | 1535 passed / 8 failed / 4 errors / 83 skipped | 82.18s |
| 并行 -n 8 --dist loadgroup | 与串行逐项一致（含失败集） | 33.5~38.2s（三次） |
| 并行 -n auto --dist loadgroup | 与串行逐项一致（含失败集） | 35.1~41.2s（两次，重分组前 41~48s） |

提速约 2.2~2.5 倍。未达 issue 目标 ≤1/3 的原因：本机串行基线本就只有 82s（issue 估计的
30-60 分钟系早期共享树受干扰口径），且套件耗时大头是轮询等待类测试（不随 CPU 并行压缩）
与每 worker 全量收集导入，非 CPU 瓶颈。

## xdist 机制说明（新增顺序污染夹具族时必读）

- 每 worker 是独立进程，进程级临时库按 worker 命名隔离（`int55_proc_gw<N>_`，
  串行为 `int55_proc_main_`）；worker 内强制不继承控制器进程的兜底库 URL
  （tests/conftest.py，继承会导致全 worker 共享同一 sqlite 文件 → DDL 竞态）。
- INT-55 顺序污染夹具族经 `tests/conftest.py::_XDIST_GROUP_RULES` 锁入
  `--dist loadgroup` 同组（auth_e2e：guest/admin 种子序；g3_e2e：G3 HTTP e2e），
  同组用例固定同一 worker 且保持收集序。新增同族测试文件时在该表登记即可。
- transfer e2e（test_data_transfer_*）未分组：三文件均按可单文件独立运行设计
  （自带独立临时库 + 幂等建表），实测拆分并行与同组结果一致，拆开后回归提速更优。

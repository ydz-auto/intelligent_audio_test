# 维度自动合并评估机制

> 评估系统功能设计文档：同一分类下、评估服务与请求模板一致的维度，评估时自动合并为一次请求、共用一次判定结果。（V9.7.31 微服务版，移植自 V9.7.10 `32374572`，最终口径：**不使用 group_key 配置，纯运行时签名合并**。）

## 1. 背景与问题

拒识族（`reject_judge`）有 3 个主维度 + 9 个子维度：

- 拒识成功数量（主，占比类）
- 拒识询问数量（主，占比类）
- 拒识失败数量（主，占比类）
- 静默时/回复时拒识恢复、询问、回应、无关、静默等 9 个子维度

三个主维度均为占比类指标（`statistic_method = weighted_sum_ratio`），分母相同（拒识总轮次 `n_reject_rounds`），分子分别是 `n_rate_success / n_rate_inquiry / n_rate_failure`。每一轮判定结果只能是「成功 / 询问 / 失败」之一，因此理论上三率之和恒为 100%。

**问题**：默认分组键是 `(endpoint_url, parent_dimension_id)`，三个主维度各自成组、各自独立提交一次 eval_server 请求、各调一次 LLM 裁判。同一批音频每次判定的结果不完全一致，导致三个分子对不上同一分母，三率之和出现缺口。V9.7.10 实测报告 424：成功 49.74% + 失败 46.67% + 询问 0% = 96.41%，缺 3.59%（7/195 轮「凭空消失」）。

## 2. 合并机制

### 2.1 合并条件

`task_dispatcher._dispatch_evaluation_tasks` 在完成原有 parent 分组（`_group_dimensions_by_endpoint`，分组键 `(endpoint_url, parent_dimension_id)`）之后、提交 worker 之前，做**组间自动合并**。多个 parent 分组并入一组、只发一次请求，需同时满足：

| 条件 | 说明 |
|---|---|
| endpoint 一致 | 调用同一个 eval_server 服务 |
| category_id 一致 | 维度同属一个分类（族），取主维度 `Dimension.category_id` |
| (task_type_code, body_template) 签名完全一致 | 组内所有维度的签名集相同：`task_type_code` 取 `parent_task_type_code`（子维度归一到其主维度类型，无则用自身）；`body_template` 为 dict 时序列化为排序 JSON 串比较 |

合并键：`(endpoint, frozenset((task_type, body_template) 签名集), frozenset(category_id 集))`，键相同的分组并为一组。任一条件不满足则合并键不同，保持原 parent 分组，不合并。

### 2.2 代码位置

- 后端合并：[evaluation_service/infrastructure/evaluation_api/task_dispatcher.py](../evaluation_service/infrastructure/evaluation_api/task_dispatcher.py)
  - `_merge_dimension_groups`：组间合并（纯函数，静态方法）
  - `_dispatch_evaluation_tasks`：分组完成后调用合并，合并发生时输出 INFO 日志（`维度组间自动合并: N 组 → M 组`，含各组维度名——实机验收凭此取证）
  - `_submit_to_workers`：合并组走既有提交链，代表维度取组内首个维度
- 维度数据：[evaluation_service/domain/services/evaluation_service/dimension_loader.py](../evaluation_service/domain/services/evaluation_service/dimension_loader.py)
  - `_format_dimension_data`：dim_dict 补充 `category_id` 字段（合并键数据源；子维度 API 配置/task_type 继承逻辑不变）
- 结果处理：[evaluation_service/infrastructure/persistence/_result_group_mixin.py](../evaluation_service/infrastructure/persistence/_result_group_mixin.py)
  - `process_group_dimension_results`：**无需改动**——本来就来遍历 group_items 内每个维度，按各自 `field_path` 从同一份 `resp_data` 提取并写各自的 TestResultDimension
- 拒识维度配置（无 group_key）：[scripts/migrations/202609/seed_reject_judge.py](../scripts/migrations/202609/seed_reject_judge.py)
- 单测：[tests/unit/test_auto_merge_groups.py](../tests/unit/test_auto_merge_groups.py)（合并签名矩阵）

### 2.3 为什么不能按 task_type_code 直接分组

- 一次请求只能带一个 `body_template`，同 task_type 的不同维度 body 可能不同
- 一个响应要能覆盖组内所有维度的 field_path，只有确认请求体兼容（签名一致）的维度才能共享一次请求
- 「逐轮话轮评估」（`turn_eval`，category=1）主/子维度 task_type 不同（`turn_eval` vs `turn_evaluation`），依赖 parent 分组 + `sub_tasks` 一次请求批量计算——若按 task_type 分组会被误拆。因此合并只发生在 parent 分组之上、以签名为准，parent 分组本身保持不变

## 3. 一次请求如何解析每个维度

eval_server 一次请求返回的 `result` 已包含全部字段（聚合时 12 个 `n_` 字段 + `n_reject_rounds` 分母都已计算）：

- eval_server 聚合（算法侧，仓库外）：`RejectionJudgeCalculator._calculate_per_round`
- 平台端回调：`process_group_dimension_results` 遍历合并组内每个维度，按各自维度的 `field_path` 从同一份 `resp_data` 提取并写各自的 TRD：

| 维度 | field_path | 取值 |
|---|---|---|
| 拒识成功数量 | `n_rate_success` | 成功轮次 |
| 拒识询问数量 | `n_rate_inquiry` | 询问轮次 |
| 拒识失败数量 | `n_rate_failure` | 失败轮次 |
| 静默时拒识恢复行为数量 | `n_success_silent_recover` | 子维度数量 |
| 回复时拒识恢复行为数量 | `n_success_reply_recover` | 子维度数量 |
| 静默时拒识询问行为数量 | `n_inquiry_silent` | 子维度数量 |
| 回复时拒识询问行为数量 | `n_inquiry_reply` | 子维度数量 |
| 静默时拒识回应行为数量 | `n_failure_silent_respond` | 子维度数量 |
| 回复时拒识回应行为数量 | `n_failure_reply_respond` | 子维度数量 |
| 静默时拒识无关行为数量 | `n_failure_silent_irrelevant` | 子维度数量 |
| 回复时拒识无关行为数量 | `n_failure_reply_irrelevant` | 子维度数量 |
| 回复时拒识静默行为数量 | `n_failure_reply_silent` | 子维度数量 |

此即「主维度 + 子维度同组」的既有工作方式，合并只是把 3 个组并成 1 个组（组内 12 个维度），遍历提取逻辑不变。

## 4. 效果

- 拒识族 12 个维度合并为一组，只发一次请求、只做一次 LLM 判定
- 三个主维度从同一份 result 提取分子 → 成功 + 询问 + 失败 = 拒识总轮次，**三率之和恒为 100%**，不再出现缺口
- 子维度（9 个）同样从同一份 result 提取，分母为主维度总数，内部占比自洽

## 5. 兼容性（V9.7.31 现状，无 group_key）

| 族 | 分类 | 合并行为 |
|---|---|---|
| 拒识族 reject_judge | 拒识(cat=3) | 3 主同签名 → 自动合并一组（12 维一次请求一次判定） |
| 打断族 interruption_metrics | 打断(cat=2) | 轮次元数据版（COUNT）与评分类（SCORE）两套 body_template 签名不同 → 各自并组，互不误并；task_type 异构的子维度靠 parent 分组 + sub_tasks |
| 环境理解族 env_judge | 环境理解(cat=4) | 同签名主维度自动合并一组 |
| 逐轮话轮评估 turn_eval | 话轮(cat=1) | 主/子 task_type 不同（`turn_eval` vs `turn_evaluation`）→ 组内签名归一到主维度类型后仍只与本族签名比较；与同分类其他 task_type 的组不合并，保持 parent 分组 + sub_tasks |

- 合并要求组内所有维度 `(task_type_code, body_template)` 完全一致，因此含多 task_type（靠 sub_tasks）或 body 不一致的族不会被误拆/误并
- 合并组沿用既有提交链与结果处理链：代表维度取组内首个维度（同签名保证 body/参数一致）；payload 的 `sub_tasks` 由 endpoint_worker 从组内全维度 `task_type_code` 去重提取（既有逻辑，天然兼容多 parent 合并组）

## 7. 验收

1. 实机：建拒识族任务（3 主维度同 category 同 task_type 同 body）→ 评估日志出现「维度组间自动合并: 3 组 → 1 组」，仅一次 eval_server 请求、一次判定；三主维度分数同源、三率之和=100%
2. 实机：turn_eval 等主子异构族不被误合并，行为与合并前一致
3. 单测：`tests/unit/test_auto_merge_groups.py` 合并签名矩阵（同 endpoint+category+body 合并；task_type 异 / body 异 / endpoint 异 / category 异 不合并；合并组保持 (维度, 结果记录) 配对）
4. 前端：默认进入分组视图 + 提示条渲染

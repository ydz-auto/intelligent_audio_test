# 部署与运行指南

适用版本：V9.7.31。本指南覆盖三块可独立部署的部分：**Docker 业务栈（含音频数据面）**、**宿主执行器（e2e / audio_agent / device）**、**ASR 服务**。
更细的构建/发版细节见 [docker/README.md](../docker/README.md) 与 [Docker Compose 部署](docker-compose.md)。

## 1. 部署形态

| 形态 | 组成 | 适用场景 |
|---|---|---|
| A. 全 Docker 预览栈 | compose 起 infra + 全部后端 + 前端 | 发布前验证，最接近生产 |
| B. Docker 栈 + 宿主三件套 | compose + 宿主 e2e/audio_agent/device | 日常联调（需要真实声卡 / USB / ADB） |
| C. 原生栈 | `native_stack.py`，不依赖 Docker | 应急排障 |

生产形态在腾讯云（compose 项目 `intelligent-audio-test`，网关 `:15000`），发布流程与安全红线见 iat-deploy 运行手册。

## 2. 拓扑与数据面

```
执行机（Windows，声卡 / USB / ADB）
  ├─ e2e_test_service   :5002 HTTP + :50051 gRPC
  ├─ audio_agent        :50052 gRPC（AUDIO_ROLE=agent，PyAudio / WASAPI，无 DB/COS）
  ├─ device_service     :50053 gRPC（adb / hdc）
  └─ ASR 服务           :10095 HTTP（funasr，通常独立机器）
        │
        ├─ 正向 -L：本地 5433 → 服务器 5432(PG)、本地 6379 → 服务器 6379(Redis)
        ├─ 正向 -L：本地 53052 → 服务器 50052（audio_service 数据面容器）
        ├─ 正向 -L：本地 53000 → 服务器 15000（网关 /api/v1/audios/download，执行机取音频字节）
        └─ 反向 -R：服务器 10.0.0.9:50051-50053 → 执行机；10.0.0.9:10095 → ASR
```

执行机 `audio_agent` 不直连 PG/Redis/COS：元数据与播放历史经数据面 gRPC
（`GetAudiosByIds` 宿主语境免可见性 / `ResolveAudioByName` / `RecordPlaybackHistory`），
音频字节经网关 `/api/v1/audios/download` 取流。历史回写失败落本地 JSONL 队列重试。

两条 SSH 方向不要搞反：

| 方向 | 用途 | 脚本 |
|---|---|---|
| 执行机 → 服务器（正向 `-L`） | 执行机上的服务用服务器数据面（PG/Redis） | `ssh_tunnels.ps1` |
| 执行机 → 服务器（反向 `-R`） | 服务器容器按 `EXECUTOR_HOST=10.0.0.9` 回连执行机 gRPC | `ssh_tunnels.ps1` |
| ASR 主机 → 服务器（反向 `-R`） | `eval_server` 通过 `http://10.0.0.9:10095` 访问 ASR | `asr_server/ssh_tunnel_asr.ps1` |

服务器 sshd 必须 `GatewayPorts clientspecified`，否则 `-R 10.0.0.9:...` 绑定失败（脚本已带 `ExitOnForwardFailure=yes`，会直接退出而不是留假隧道）。

## 3. 前置条件

- **Python**：执行器解释器默认 `D:\00_env\conda_envs\intelligent_audio_test\python.exe`，可用 `HOST_SERVICE_PYTHON` 覆盖（`.env` 或进程环境）。ASR 需要单独的 funasr 环境。
- **Docker Desktop**：仅形态 A/B 需要；构建前先 `python docker/build_stack.py --check`。
- **SSH 免密**：执行机与 ASR 主机到 `ubuntu@106.54.49.79` 的公钥登录（脚本 `BatchMode=yes`，不会提示输密码）。
- **端口不冲突**：本地 compose 的 PG 宿主端口与正向隧道同为 `5433`，二者只能起一个（见 §7）。

## 4. Docker 业务栈

```powershell
# 仓库根执行
python docker/build_stack.py --check           # 引擎体检（20s 内有界返回）
python docker/build_stack.py                   # 全量构建；发版建议只构建变动服务
python docker/run_stack.py up --build          # 构建并后台启动
python docker/run_stack.py health              # HTTP /health + gRPC TCP + infra
python docker/run_stack.py down                # 停止，保留数据卷
```

- `AUTH_MODE` 必填（`off` / `dev` / `prod`），否则 `run_stack.py` 直接退出；前端运行时通过 `GET /auth/mode` 读取。
- 首次 `up` 会先跑 `db_bootstrap`：建表 → 幂等迁移 → RBAC 种子，完成后再起业务服务；重复 `up` 秒级跳过。
- 项目名固定 `intelligent-audio-test`，否则镜像 tag 对不上现役栈（见 docker/README.md §2）。
- 端口唯一事实源：`shared/config/service_ports.py`。本地 `.env` 已把网关覆盖为 `5700`、前端 `8080`、PG `5433`、gRPC `53051/53061/...`（避开 WSL2/Hyper-V 保留段）。
- 禁止 `down -v`（清库，需 `--yes`）；生产只做增量 `up -d --no-deps <服务>`。

## 5. 宿主执行器（e2e / audio / device）

### 5.1 启停命令

```powershell
python stack.py up                             # compose + 宿主三件套
python stack.py up --no-docker                 # 只起宿主三件套（Docker 不开也能用，需隧道已就绪）
python stack.py up --no-docker --audio-mode shim   # 无声卡环境用影子音频
python stack.py down                           # 停三件套 + compose
python stack.py down --no-docker               # 只停三件套
python stack.py restart host                   # 只重启三件套
python stack.py status                         # 容器 + 宿主端口
python stack.py health                         # HTTP /health + gRPC / 基础设施 TCP
python stack.py logs audio                     # 看宿主服务日志
```

### 5.2 进程守护（崩溃自愈）

`control.py` 不再直接拉 `service_entry.py`，而是经 `scripts/host_services/supervisor.py` 守护：

```
WMI（脱离 run 进程树）
  └─ pythonw supervisor.py                 # 循环：子进程退出后 5s 重启
       └─ pythonw service_entry.py ...     # 真实服务
```

- 守护壳用 `pythonw`（GUI 子系统）而不是 PowerShell：WMI 拉起的进程没有可继承的控制台，`powershell -WindowStyle Hidden` 在 Windows Terminal 下仍会弹一个空白黑窗。
- 重启策略：子进程任何原因退出 → 5s 后重启；日志 `logs/host_services/<service>.supervisor.log`（5MB 转 `.1`）。
- 停止策略：先落 `logs/host_services/<service>.supervisor.stop` 标记，再停子进程，最后按 pid 文件杀守护树。**手动 `down` 后不会被拉起**。
- `<service>` 取值为 `e2e` / `audio` / `device`；pid 文件为 `<service>.supervisor.pid`。

### 5.3 登录自启

`shell:startup` 下的 `IAT-HostServices.vbs` 无窗口调起 `scripts/host_services/autostart.ps1`：

1. `ssh_tunnels.ps1 start`（幂等，已通则跳过）；
2. 等本地 `5433`(PG) / `6379`(Redis) 可连，最多 180s；
3. `python stack.py up --no-docker --audio-mode real`；
4. 全过程写 `logs/host_services/autostart.log`。

只在登录时跑一次，没有周期任务，因此不会把手动停掉的服务顶回来。重复登录/重复执行是幂等的：`up` 遇到已监听端口直接 `[skip]`。卸载自启只需删除 `IAT-HostServices.vbs`。

### 5.4 依赖与已知边界

- 执行器依赖隧道提供的 `5433/6379`；隧道没起来时 e2e 会连库失败，守护每 5s 重试（不致命，会刷日志）。
- `audio_agent` real 模式启动前跑 pyaudio 自检，**失败不重试**也不自动降级 shim；无声卡环境请显式 `--audio-mode shim`。
- 守护进程自身被强杀（任务管理器）不会自愈，需下次登录或手动 `up`。
- `device_service` 需要 adb/hdc 与 USB 权限；`e2e_test_service` 需要测试库已初始化。

## 6. ASR 服务

ASR 是独立的 FastAPI + funasr 进程，监听 `0.0.0.0:10095`，通常部署在有模型缓存的机器上，通过反向隧道接入服务器。

### 6.1 安装

```bash
pip install funasr torch fastapi uvicorn python-multipart soundfile librosa silero-vad
```

首次启动会从 ModelScope 下载模型（SenseVoice ≈900MB），之后读本地缓存（`ASR_CACHE_DIR`，默认 `../static/asr_models`）。启动时预加载全部模型，**就绪需 60–80s**，期间进程存活但模型未加载完，不能按端口判断就绪。

### 6.2 配置

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `ASR_PORT` | `10095` | 监听端口 |
| `ASR_CACHE_DIR` | `../static/asr_models` | 模型缓存目录 |
| `ASR_SENSEVOICE_MODEL` | `iic/SenseVoiceSmall` | SenseVoice 模型 |
| `ASR_MODELSCOPE_MODEL` | `iic/speech_paraformer-large-...` | 主 ASR 模型 |
| `ASR_VAD_MODEL` | `iic/speech_fsmn_vad_...` | VAD 模型 |
| `ASR_PUNC_MODEL` | `iic/punc_ct-transformer_...` | 标点恢复模型 |

调用方（测试主机）用 `ASR_SERVER_URL=http://<ASR主机IP>:10095` 指向服务地址。

### 6.3 启停与守护

ASR 目录通常与仓库同级（本工作区为 `../asr_server`），以下命令在该目录内执行：

```powershell
python asr_control.py start --with-tunnel   # 起服务 + 反向隧道，等端口就绪（默认 180s）
python asr_control.py status                # 端口 / 守护 / 隧道 / /health 一览
python asr_control.py stop                  # 落停止标记 -> 停子进程 -> 收守护，不会复活
python asr_control.py restart
python asr_control.py tunnel-start          # 只动反向隧道
python asr_control.py tunnel-stop
python asr_control.py install-autostart     # 写入登录自启（VBS），uninstall 反向操作
```

守护模型与执行器一致，但作用在 ASR 一侧：

```
WMI（脱离调用方进程树）
  └─ powershell run_forever_asr.ps1        # while($true)，子进程退出 5s 重启
       └─ pythonw asr_server.py            # 注入调用方环境后启动
```

- 解释器优先级：`ASR_PYTHON` 环境变量 → 仓库根 `.env` 的 `ASR_PYTHON` → 运行 `asr_control.py` 的 Python。**必须指向装好 funasr/torch 的环境**，否则守护会每 5s 重启一次。
- 状态文件都在 `asr_server/logs/`：`asr.supervisor.pid`、`asr.supervisor.stop`、`asr.supervisor.log`（守护）、`asr_server.log`（服务，20MB×5 轮转）、`asr.env.json`（WMI 环境快照）。
- 首次启动含模型加载，`start` 会等到端口监听才返回；下载模型时可能接近超时上限。
- 前台调试仍可直接 `python asr_server.py`，但不受守护，退出即停。

就绪判定：

```bash
curl -s http://127.0.0.1:10095/health
# {"status":"ok","vad_loaded":true,"asr_loaded":true,"paraformer_loaded":true,...}
```

uvicorn 先跑 lifespan 预加载再 bind 端口，所以端口通通常意味着模型已加载；但 `status=ok` + 三个 `*_loaded=true` 才是唯一可靠判据。

### 6.4 反向隧道与自启

`ssh_tunnel_asr.ps1` 负责 `10.0.0.9:10095 → 本机 127.0.0.1:10095`，走内层 `while($true)` 循环，ssh 掉线 5s 重连。

- `asr_control.py tunnel-start` 经 WMI 拉起一层 launcher（把调用方 `PATH` 带进去，保证 ssh 可寻址），`tunnel-stop` 按命令行匹配进程并 `taskkill /T`，ssh 子进程一并结束。
- 仍可前台手动跑 `powershell -ExecutionPolicy Bypass -File ssh_tunnel_asr.ps1`，`asr_control.py` 也能识别并停止这种手动实例。
- 登录自启：`python asr_control.py install-autostart` 会在 `shell:startup` 写 `IAT-ASR.vbs`，调起 `autostart_asr.ps1`——解析 `ASR_PYTHON` → `asr_control.py start --with-tunnel`，日志写 `logs/autostart_asr.log`。只在登录时跑一次，没有周期任务，手动 `stop` 不会被顶回来；卸载用 `uninstall-autostart`。
- 脚本末尾注释掉的 `Register-ScheduledTask -TaskName 'ASR-SSH-Tunnel'` 是早期的计划任务方案，与 `install-autostart` 二选一即可。
- 远程验证：在服务器执行 `curl -s http://10.0.0.9:10095/health`，能拿到 `*_loaded=true` 说明隧道与服务都通。

### 6.5 常见问题

- **模型下载失败**：脚本会清除 `HTTP_PROXY/HTTPS_PROXY`；仍失败时检查系统代理与 ModelScope 可达性。
- **隧道起不来**：`ExitOnForwardFailure=yes` 下远端端口被占用会立即退出；先在服务器 `ss -ltnp | grep 10095` 确认。
- **内存**：单份模型常驻约 4.9GB RSS；并发不额外加载模型，不要用 `uvicorn workers=N`（N 份模型）。
- **容器化**：仓库未提供 ASR 镜像，按原生进程部署即可；如自行容器化，需要把模型缓存目录挂卷（约 900MB+）并把 `10095` 暴露出来，启动就绪时间仍是分钟级。

## 7. 启动顺序与验证清单

```powershell
# 1) 数据面隧道（正向 5433/6379/53052/53000 + 反向 50051-50053）
powershell -ExecutionPolicy Bypass -File .\ssh_tunnels.ps1 start
.\ssh_tunnels.ps1 status

# 2) Docker 栈（形态 A/B）
python docker/run_stack.py up --build
python docker/run_stack.py health

# 3) 宿主执行器
python stack.py up --no-docker
python stack.py status

# 4) ASR（在 ASR 主机，asr_server 目录内）
python asr_control.py start --with-tunnel
python asr_control.py status
```

| 检查项 | 期望 |
|---|---|
| `.\ssh_tunnels.ps1 status` | 5433/6379/53052 可连，服务器侧 50051-50053 已监听 |
| `python docker/run_stack.py health` | 全部 HTTP /health 与 gRPC TCP 绿 |
| `python stack.py status` | 5002/50051/50052(agent)/50053 均监听，数据面容器健康，`<service>.supervisor.pid` 存在 |
| `logs/host_services/autostart.log` | 登录自启时 `dependency ports: 5433=True 6379=True` 且 `rc=0` |
| ASR `/health` | `status=ok` 且三个 `*_loaded=true` |
| ASR `asr_control.py status` | 端口监听、守护 alive、隧道运行中、健康检查四项齐全 |

## 8. 故障排查

| 症状 | 定位 | 处理 |
|---|---|---|
| `stack.py up` 报 `:5433` 被占用 | 本地 compose 的 postgres 与正向隧道冲突 | 停本地 postgres 容器或先 `ssh_tunnels.ps1 stop` |
| 宿主服务起来又秒退 | `logs/host_services/<service>.supervisor.log` + `<service>_service.log` | 看退出码；缺依赖/端口占用/自检失败 |
| 手动 `down` 后端口又开了 | 有周期任务在跑 `up` | 本仓库自启只在登录触发；检查是否额外注册了计划任务 |
| 服务连续重启刷日志 | 隧道未就绪 / 依赖缺失 | 先 `ssh_tunnels.ps1 status`，再查服务日志首行异常 |
| 服务器调执行机 gRPC 超时 | 反向隧道断 | 执行机 `ssh_tunnels.ps1 status`；看 `logs/` 下隧道日志 |
| ASR 10095 端口通但调用报模型未加载 | 启动预加载未完成 | 等 60–80s 后再查 `/health` 的 `*_loaded` |
| ASR 每 5s 重启刷日志 | `asr_server/logs/asr.supervisor.log` 首行退出码 | 多为 `ASR_PYTHON` 指错环境（缺 funasr/torch），`asr_control.py status` 看解释器 |
| ASR 隧道进程在但服务器连不上 | 远端绑定失败或 ssh 假死 | `asr_control.py tunnel-stop` 后 `tunnel-start`；服务器 `ss -ltnp | grep 10095` |

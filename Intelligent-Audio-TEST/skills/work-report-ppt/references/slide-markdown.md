# 演示型 Markdown 模板（work-report-ppt）

渲染器契约：**`##` = 一页幻灯片**；封面由 Studio 文档标题自动生成。
正文不要写 `#`。每页只放 3–5 条要点，单条 ≤ 60 字；表格建议 ≤ 12 行。

## 模板 A：任务报告汇报（4 页）

```markdown
## 结论：本轮通过率 90.72%，核心链路已达标
- 用例总数 388，已完成 352，失败 0
- 通过率 90.72%，高于本轮 90% 验收线
- 剩余 36 条未完成用例集中在长音频场景

## 关键数据
| 指标 | 值 |
| --- | --- |
| 用例总数 | 388 |
| 已完成 | 352 |
| 失败 | 0 |
| 通过率 | 90.72% |

## 主要风险
- 打断后恢复首轮内容偶发丢失，影响连续对话体验
- 部分用例缺少默认参数，依赖人工补录
- 设备差异未完全覆盖，结论只对当前设备成立

## 结论与建议
- 优先修复打断恢复内容丢失，纳入下一轮回归
- 补齐默认参数与参数校验，减少人工介入
- 扩展多设备与 API 通道路径，再出正式结论
```

## 模板 B：对比报告汇报（5 页）

```markdown
## 结论：新版本在时延与稳定性上均优于基线
- 平均响应时延 1.24s，较基线下降 18%
- 打断成功率 96.1%，较基线提升 3.2 个百分点
- 首轮内容恢复时延 0.86s，优于基线 0.12s

## 对比口径
- 基线：2026-09-20 版本，同设备、同用例集
- 指标取接口原文，未做二次换算
- 样本量：两组各 200 条用例

## 指标对比
| 指标 | 基线 | 新版本 | 变化 |
| --- | --- | --- | --- |
| 平均响应时延 | 1.51s | 1.24s | -18% |
| 打断成功率 | 92.9% | 96.1% | +3.2pt |
| 恢复时延 | 0.98s | 0.86s | -0.12s |

## 归因判断
- 时延下降主要来自首包策略调整
- 打断成功率提升与恢复链路修复相关
- 尚未验证长音频与弱网场景

## 结论与建议
- 新版本进入灰度，保留基线回滚能力
- 补测弱网与长音频，再决定全量
```

## 大纲模板（给用户确认时使用）

```
P1 封面：<报告名>（自动生成）
P2 <结论句>｜要点 1 / 2 / 3｜关键数字：xx
P3 <结论句>｜表格：指标 / 值 / 变化｜要点：xx
P4 <结论句>｜风险 1 / 2 / 3
P5 结论与建议｜行动项 1 / 2 / 3
```

## 常见改写

- 标题太平：「项目进展」→「核心任务按计划推进，关键节点已完成」
- 一页太多要点：> 5 条拆成两页，或合并同类项
- 长段落：改为 1 句结论 + 2–3 条证据
- 指标太多：挑影响结论的 3–5 个，其余放 HTML / MD 产物
